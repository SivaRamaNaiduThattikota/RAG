Database decision

Oracle is your primary path.

PostgreSQL with pgvector was originally named because it is open source, lightweight, and common in RAG tutorials. It was a convenient default—not a technical requirement and not a claim that it is better for your situation.

PRIMARY · USE THIS

Oracle AI Database

Best fit because you already use Oracle. EvidenceForge will store business rows, metadata, permissions, and embeddings together using Oracle's native VECTOR type and vector-search SQL.

  • Reuse your Oracle SQL knowledge
  • Combine relational filters and vector similarity in SQL
  • Use Oracle Text plus vector search for a hybrid retrieval path
  • Connect from Python with the oracledb driver
OPTIONAL · PORTABILITY LAB

PostgreSQL + pgvector

Useful later to compare ecosystems, deployment trade-offs, indexing syntax, and retrieval behavior. You do not need it to start or complete the primary project.

  • Open-source local experimentation
  • Large tutorial and framework ecosystem
  • Simple Docker-based lab environment
  • Good second implementation for portability testing
See the exact Oracle implementation plan
  1. Start: use your existing Oracle environment if it exposes AI Vector Search; otherwise use Oracle AI Database Free for a local learning environment.
  2. Model: create document, version, chunk, permission, citation, evaluation, and feedback tables. Store each chunk embedding in a VECTOR column.
  3. Retrieve: perform vector similarity with Oracle SQL, then add ordinary relational predicates for tenant, role, freshness, document status, and sensitivity.
  4. Improve: compare exact and approximate search, add a vector index, then test Oracle Text plus vector retrieval for hybrid search.
  5. Keep portable: place Oracle-specific SQL inside an OracleRetrievalStore. A later PgvectorRetrievalStore can implement the same application interface without rewriting the whole RAG pipeline.

Important: confirm the exact Oracle version and enabled features in your workplace before choosing SQL syntax. The course will explain both the database-independent retrieval idea and the Oracle implementation.

Where Oracle, LangChain, LangGraph, and the other tools fit
Oracle AI DatabaseThe durable knowledge and retrieval layer: document metadata, permissions, chunks, vectors, relational filters, similarity search, and hybrid text-plus-vector retrieval.
LangChainThe component and integration layer: loaders, splitters, model adapters, embedding adapters, vector-store integrations, retrievers, tools, runnables, and conventional RAG composition.
LangGraphThe stateful orchestration runtime: explicit nodes and transitions, conditional routing, bounded loops, persistence, recovery, streaming, and human review for corrective or agentic RAG.
LangSmithAn optional observability and evaluation platform for traces, datasets, experiments, debugging, regression analysis, and production monitoring. The underlying evaluation concepts remain framework-independent.
LlamaIndex / HaystackAlternative RAG frameworks studied for architectural comparison and portability; learning them prevents LangChain-specific assumptions from becoming mistaken for RAG fundamentals.
Microsoft GraphRAGAn advanced indexing and query implementation for entities, relationships, communities, and local/global/DRIFT search in ResearchGraph Studio. It is not a replacement for every RAG pipeline.
MCPAn interoperability protocol for exposing external resources and tools to AI applications. It can connect knowledge systems, but it is not itself a retriever or database.
FastAPI / RedisApplication infrastructure: FastAPI exposes service endpoints; Redis is optional for suitable cache, rate-limit, or transient-state workloads. Neither defines the RAG architecture.

The key mental model: RAG is the architecture. Databases, frameworks, runtimes, evaluation platforms, and protocols implement different layers of that architecture; they are important, but they are not interchangeable.

PROJECT 01 · PRODUCTION LEVEL

EvidenceForge

A secure, multi-tenant enterprise knowledge platform that answers policy and operational questions with permission-aware evidence and claim-level citations.

BUSINESS SCENARIO

The production release additionally requires advanced retrieval, context engineering, evaluation, operations, security, privacy, and governance.

Programming foundation

Basic Python; functions, classes and modules; lists, dictionaries and JSON; file handling; exceptions; virtual environments; basic asynchronous programming; HTTP and REST APIs; SQL; Git; and basic automated testing. We will refresh these skills when the project increment needs them.

Purpose and why it was chosen

EvidenceForge is a secure, multi-tenant enterprise knowledge assistant for company policies, finance documents, operational manuals, security procedures, and HR guidance. The user does not merely ask a question: the system must establish identity, determine the tenant and permissions, retrieve only authorized evidence, construct a grounded answer, attach verifiable citations, and refuse when the evidence is missing or unsafe.

Most beginner projects stop at PDF → vector database → LLM → answer. That is a useful learning prototype, but it does not prove that the system remains correct when documents change, users have different permissions, retrieval is imperfect, a source contains malicious instructions, or a dependency fails. EvidenceForge was selected because it forces the prototype to become an operable business system.

The production problems you must solve

Each item is a separate engineering problem with its own tests and failure evidence:

Changing knowledgeIncremental ingestion, document identity, versions, updates, deletions, freshness, and index synchronization.
Identity and isolationUser authentication, tenant isolation, role and document-level authorization, and security trimming before LLM context construction.
Retrieval qualityDense and sparse candidates, hybrid retrieval, metadata filtering, reranking, context construction, and separate diagnosis of retrieval versus generation failures.
Grounded answersClaim-level citations, citation verification, conflict handling, calibrated abstention, and refusal when evidence is insufficient.
Adversarial safetyIndirect prompt injection, poisoned documents, malicious metadata, source trust, secret handling, and automated authorization-leakage tests.

What completing EvidenceForge proves

Completion means you can present evidence—not merely claim—that you can:

  • Convert business requirements and data-access rules into a defensible system architecture.
  • Build and explain an end-to-end RAG pipeline from source synchronization through cited generation.
  • Protect confidential information across ingestion, indexes, caches, prompts, logs, and answers.
  • Diagnose ingestion, retrieval, reranking, context, and generation failures separately.
  • Evaluate quality before deployment with datasets, metrics, error analysis, and regression gates.
  • Operate a changing document corpus with versioning, incremental updates, deletions, and rollback.
  • Design for dependency failures, monitoring, recovery, cost, latency, and production SLOs.
  • Defend production RAG decisions in system-design and engineering interviews.

This is the primary employment-ready project because it demonstrates the discipline required to operate RAG, not just assemble a demo.

PROJECT 02 · ADVANCED / PORTFOLIO

ResearchGraph Studio

A multimodal research-intelligence workspace that compares papers, reports, tables, and diagrams using vector retrieval, a knowledge graph, and bounded agentic investigation.

P2RESEARCH-GRADE
Papers + media→Layout parsing→Text/table/image units→Vectors + graph→Query router→Local/global search→Agent synthesis→Claim map
RESEARCH SCENARIO

Move from “find similar passages” to “understand the whole evidence landscape.”

A researcher asks entity-specific questions, compares numerical findings across tables, discovers relationships, identifies disagreements, and requests corpus-wide themes with traceable evidence.

WHY THIS IS THE BEST SECOND PROJECT
  • Exercises layout-aware and multimodal document understanding
  • Combines sparse, dense, table and graph retrieval
  • Uses entities, relationships, claims and community summaries
  • Routes between basic, local, global and exploratory retrieval
  • Requires multi-hop and cross-document reasoning
  • Tests agent planning without allowing an unbounded loop
  • Produces a visual evidence graph rather than only chat output
  • Demands evaluation of retrieval, claims, citations and trajectories
CORE USER FLOWS
  1. Ingest a collection of research PDFs and supplementary media.
  2. Explore entities, claims, relationships and source passages.
  3. Ask a local question about one entity or finding.
  4. Ask a global question about themes across the corpus.
  5. Compare claims and measurements across multiple sources.
  6. Audit the agent’s plan, retrieved evidence and final synthesis.
REQUIRED EVIDENCE
  • Modality-aware ingestion and retrieval tests
  • Vector-only versus graph-assisted ablation study
  • Local/global routing evaluation
  • Claim-support and citation-entailment report
  • Agent trajectory, budget and stopping-condition tests
  • Interactive graph and source-linked comparison view

Course readiness

Complete the baseline RAG sequence first, then query transformation, advanced retrieval, fusion and reranking, structured-data and knowledge-graph RAG, multimodal RAG, adaptive and agentic RAG, and evaluation. Its baseline starts only after EvidenceForge's first working version.

Purpose and why it was chosen

ResearchGraph Studio is a multimodal research-intelligence system for papers, reports, tables, charts, and diagrams. It must answer focused questions about one finding as well as corpus-wide questions about themes, relationships, supporting evidence, and disagreement across sources.

Ordinary vector retrieval is strong when the desired evidence resembles the query, but whole-corpus aggregation and relationship-heavy questions may require representations beyond independent chunks. The project therefore compares a strong vector baseline with entity, relationship, claim, community, table, and image evidence. It uses query classification to choose basic, local, global, multimodal, or multi-hop retrieval instead of routing every question through the most complex path.

GraphRAG is studied through entity and relationship extraction, claims, community detection, community summaries, local search, global map-reduce search, and DRIFT-style exploration. Because graph indexing can consume substantial model resources, the first experiments use a deliberately small corpus and measured budgets.

What completing ResearchGraph Studio proves

Completion means you can demonstrate that you can:

  • Process complex PDFs while preserving text, layout, table, image, and source-location evidence.
  • Build and connect vector, entity, relationship, claim, and community representations.
  • Perform focused local retrieval and corpus-wide global retrieval.
  • Classify questions and route them to retrieval strategies supported by measured evidence.
  • Implement multi-hop retrieval and cross-document claim comparison.
  • Build bounded agent workflows with explicit state, tool budgets, stopping conditions, and recovery.
  • Evaluate retrieval, citations, multimodal evidence, routing decisions, and agent trajectories.
  • Create an inspectable evidence graph and claim map rather than hiding reasoning behind chat output.

This is the advanced architecture and research portfolio project. Its success criterion is justified complexity: graph or agent stages must measurably help the questions for which they were introduced.

Build sequence and definition of done
  1. Corpus contract: define supported documents, modalities, questions, permissions, and evaluation cases.
  2. Vector baseline: build the strongest reasonable non-graph system first and record quality, latency, and cost.
  3. Graph memory: extract entities, relationships, claims, and communities with provenance back to source units.
  4. Routed retrieval: classify local/global/comparison questions and test vector, graph, and blended strategies.
  5. Bounded agent: expose retrieval tools, explicit state, budgets, stopping conditions, and a complete trace.
  6. Ablation report: identify which question groups genuinely improve, regress, or cost too much when graph and agent stages are added.
  7. Portfolio release: ship the visual claim map, source audit view, evaluation report, architecture decisions, and recorded demonstration.

Done means justified complexity: the evidence shows where GraphRAG or an agent improves outcomes and where the simpler EvidenceForge-style pipeline should remain the preferred design.
