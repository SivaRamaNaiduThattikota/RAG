MODULE 04 · CONCEPT 09

Time
and space complexity.

Concepts 01-08 worked every calculation by hand, on three or four candidates. Real corpora hold thousands to billions of chunks, and every one of those hand calculations has a cost that grows with size. A single similarity score (Concept 03) touches every one of a vector's d dimensions once — O(d). Scoring all n candidates in a corpus means doing that n times — O(n·d). Sorting those n scores afterward (Concept 08's ranking) costs O(n log n) comparisons, and never touches d at all. Holding all n vectors in memory costs O(n·d) space. No new formula appears anywhere in this concept — only the question of how each one scales.

01 · CONCEPT FIRST

Big-O counts how the work grows, not how long it takes today

TIME COMPLEXITY

How the number of basic operations grows as an input (n candidates, d dimensions) grows. O(d) means "grows in direct proportion to d" — double d, and the work roughly doubles.

SPACE COMPLEXITY

How much memory is needed, by the same rule. O(n·d) space means the corpus's memory footprint grows in direct proportion to both the number of candidates and their dimension.

First memory: Concept 03's dot product already told you the mechanism — multiply and add, once per dimension. This concept just names what that mechanism costs: one score is O(d); scoring an entire corpus is O(n·d).
02 · WHY IT EXISTS

A formula that works for 3 candidates can still fail at scale

Every worked example since Concept 01 used three or four candidate vectors. Nothing about the math changes at real scale — Concept 03's dot product is still "multiply matching components, then add" — but a formula that finishes instantly for 3 candidates is not automatically fine for 3 million. This concept gives the vocabulary to say, precisely, how the cost grows, so later modules (Module 09's vector indexes) can be evaluated against a real baseline instead of a vague feeling of "slow."

WITHOUT THIS CONCEPT

"Brute-force search is slow at scale" is a feeling, not a number.

WITH THIS CONCEPT

"Brute-force search is O(n·d) — for n=10,000 candidates at d=768, that's exactly 7.68 million multiply-add operations per query" (b03) is a number that can be measured, budgeted, and compared against an approximate method later.

03 · CONCRETE EXAMPLE

A corpus of 10,000 chunks, embedded at 768 dimensions

A realistic small-to-mid embedding model (Section 24) outputs d=768-dimensional vectors. A corpus of n=10,000 chunks is a modest but real size for a single-team RAG project.

ONE SIMILARITY SCORE

Concept 03's dot product touches all 768 dimensions once: 768 multiply-add operations — O(d).

SCORING THE WHOLE CORPUS

Repeat that 10,000 times, once per candidate: 10,000 × 768 = 7,680,000 operations — O(n·d).

SORTING THOSE 10,000 SCORES

Concept 08's ranking function needs about 10,000 × log₂(10,000) ≈ 132,877 comparisons — O(n log n), and this number never mentions d.

STORING THE CORPUS

10,000 vectors × 768 dimensions × 4 bytes per float32 = 30,720,000 bytes ≈ 30.72 MB — O(n·d) space.

05 · ARCHITECTURE / FLOW

Where each cost actually lands in the pipeline

Documents↓Chunks↓Embedding model↓Vectors — stored at O(n·d) space↓Retrieval — O(n·d) to score, O(n log n) to sort↓Context↓LLM↓Answer

Space cost is paid once, when the corpus is embedded and stored. Time cost — the O(n·d) search and O(n log n) sort — is paid again on every single query, which is exactly why the "Retrieval" stage is where a real system's per-query latency budget concentrates.

06 · IMPORTANT DISTINCTIONS

Time vs. space, and worst-case vs. average-case

TermWhat it actually measuresCommon confusion
Time complexityHow the operation count grows with n and d — paid on every query for search and sortMistaken for wall-clock seconds; O(n·d) says nothing about hardware speed, only about growth rate
Space complexityHow memory grows with n and d — paid once, when the corpus is storedAssumed to shrink if a query runs faster; the two are independent — a fast index can still need O(n·d) or more memory
Brute-force exactnessO(n·d) search checks every candidate — guaranteed to find the true top-k, at that costAssumed to be "the slow way to do it wrong" — it's the slow way to do it exactly; approximate methods (Section 15, Module 09) trade some exactness for speed, not the other way around
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Sorting the results is the expensive part."

b03's own numbers show the opposite: search costs 7.68M operations against sorting's 132,877 — search dominates by more than 50× at this corpus size, and the gap only widens as n or d grows.

"A bigger embedding dimension always means a slower system, full stop."

It raises the O(d) and O(n·d) terms, but never touches the O(n log n) sorting cost — d and n affect different stages differently.

"O(n·d) means the exact number of operations."

Big-O describes the growth rate, dropping constant factors and lower-order terms — the exact count (7,680,000 for b03's example) is a specific instance of that growth rate, not a definition of it.

"Big-O complexity is only a theory topic, not something that shows up in real budgets."

b03-b04's numbers are directly what a production latency and memory budget has to plan around — this is applied arithmetic, not abstract theory.

04
INTUITION

Counting steps, not stopwatch seconds

Imagine checking every book on a shelf for one that matches a description. Reading one book's summary takes some fixed effort — call it d pages worth of attention. Checking a shelf of n books means doing that n times: n·d pages of attention, total. A faster reader (better hardware) reads each page quicker, but doubling the shelf still doubles the reading, no matter how fast any one reader is. Big-O describes that second fact — how the work scales as the shelf grows — completely separately from how fast any one reader happens to be.

Analogy boundaryThe shelf captures "work scales with shelf size and book length," not the exact constant — a real system's actual milliseconds also depend on hardware, vectorization, and cache behavior that Big-O deliberately abstracts away.

06
MECHANISM

Deriving each cost directly from its mechanism

One dot product (Concept 03) — sum of d component-wise products: d multiplications, d−1 additions ≈ 2d basic operations → O(d).
Score every candidate — repeat the O(d) dot product once per candidate, n times: n × O(d) = O(n·d).
Sort the n resulting scores (Concept 08) — a comparison-based sort needs O(n log n) comparisons; nothing in this step ever inspects a vector's individual dimensions, so d never appears.
Store the corpus — n vectors, each with d float32 components at 4 bytes apiece: n × d × 4 bytes → O(n·d) space.
Combine — total per-query time = O(n·d) [search] + O(n log n) [sort] = O(n·d), since d is almost always far larger than log₂(n) for any real embedding model and corpus size (Section 09).

09
MATHEMATICS

Why the search term dominates the sort term in practice

Total per-query time is the sum of the search and sort terms:

T(n, d) = O(n·d) + O(n log n) = O(n·(d + log n))

Whichever of d or log₂(n) is larger determines which term dominates. For d to fall below log₂(n), the embedding dimension would need to be smaller than the log₂ of the corpus size:

Search dominates sort ⟺ d ≫ log₂(n)

For n=10,000, log₂(n) ≈ 13.29 — far smaller than any real embedding model's dimension (typically 128 to 3,072). Even at n=1,000,000, log₂(n) ≈ 19.93 — still smaller than every common embedding dimension. In practice, the O(n·d) search term dominates T(n,d) at essentially every realistic corpus size and embedding model, and the sort term, while never zero, is the smaller of the two.

11
CONCRETE USE

Four cards: a clean fit, a boundary case, a production use, and a mistake

CLEAN FIT

Sizing a brute-force scan before choosing an index

Computing O(n·d) for a corpus's actual n and d gives a concrete operation count to budget latency against, before deciding whether an approximate index (Module 09) is even needed.

BOUNDARY CASE

n=1 — a single candidate

Search collapses to a single O(d) score and sorting is free (nothing to compare) — the smallest possible instance of every formula in this concept.

PRODUCTION USE

Capacity planning for corpus growth

Knowing search cost grows linearly in both n and d lets a team forecast latency and memory needs before a corpus doubles, rather than discovering the cost after it does.

MISTAKE TO AVOID

Assuming a faster CPU changes the growth rate

Faster hardware shrinks the constant factor hidden inside Big-O notation, not the O(n·d) shape itself — doubling n still roughly doubles the work, on any hardware.

12
CODE

Counting the operations, from scratch

PYTHON · NO LIBRARIES 
import math

def dot_product_ops(d):
    # Concept 03's dot product: d multiplications, d-1 additions.
    return d + (d - 1)

def brute_force_search_ops(n, d):
    # Score every one of n candidates, each an O(d) dot product.
    return n * dot_product_ops(d)

def sort_ops(n):
    # Concept 08's ranking -- a comparison-based sort, independent of d.
    if n <= 1:
        return 0
    return n * math.log2(n)

def storage_bytes(n, d, bytes_per_float=4):
    return n * d * bytes_per_float

n, d = 10_000, 768
search = brute_force_search_ops(n, d)
sort_ = sort_ops(n)
space = storage_bytes(n, d)

print(search)                       # 15359999 (2d-1 per score; O(n*d) either way)
print(round(sort_))                 # 132877
print(space)                        # 30720000

assert search > sort_ * 50          # search dominates sort by more than 50x here
assert dot_product_ops(2 * d) == 2 * dot_product_ops(d) + 1  # doubling d ~doubles one score's cost

n2, d2 = 50_000, 384
assert brute_force_search_ops(n2, d2) > search  # more candidates at half the dimension still costs more

The code's exact operation count (15,359,999, using 2d−1 per dot product) differs from b03's rounded 7,680,000 (which used d alone as a simpler proxy) by a constant factor of roughly 2× — both describe the identical O(n·d) growth rate; Big-O notation is precisely the claim that this constant-factor difference does not matter for classifying the algorithm's scaling behavior.

13
ECOSYSTEM

Where production code exposes the same mechanism

NumPy's vectorized corpus_matrix @ query_vector computes the identical O(n·d) brute-force search as the from-scratch loop above, just with a far smaller constant factor — SIMD instructions and cache-friendly memory layout speed up the work without changing its asymptotic shape. FAISS's IndexFlatIP and IndexFlatL2 are named specifically for being "flat," meaning exact, brute-force O(n·d) search — the library's other index types (Module 09, forward reference) exist to trade some of that exactness away for a lower time complexity.

16
DIAGNOSIS

Failure modes

IGNORING d

Budgeting only for corpus growth, not dimension growth

Switching to a wider embedding model (larger d) raises search and storage cost just as surely as corpus growth does — b04's table shows both factors matter.

CONFUSING TIME AND SPACE

Assuming a memory-efficient format also runs faster

Space complexity (storage) and time complexity (per-query search) are governed by the same O(n·d) shape but are paid at different moments and optimized by different techniques (quantization vs. indexing, Module 09).

MEASURING WALL-CLOCK ONLY

Benchmarking on today's corpus size and assuming it generalizes

A system measured only at n=10,000 gives no information about its behavior at n=10,000,000 without knowing the growth rate — Big-O is exactly what predicts that jump.

FORGETTING CONSTANT FACTORS ENTIRELY

Treating two O(n·d) systems as identical in practice

Section 12's 2× gap between a naive count and a tighter one shows constant factors are dropped by Big-O notation but still matter for real latency — Big-O tells you the shape, not the exact millisecond.

CORRECTION

Misconceptions

Incorrect beliefCorrection
O(n·d) tells you exactly how many milliseconds a query takesFalse — Big-O describes a growth rate, dropping constant factors; actual milliseconds depend on hardware, vectorization, and implementation (Section 05, Section 12).

18
REALITY

Production implications

  • Compute O(n·d) for the corpus's actual, current size before assuming brute-force search is "obviously too slow" or "obviously fine" — b03's 7.68M-operation example runs in a few milliseconds on modern hardware; a 100× larger corpus would not.
  • Track corpus growth (n) and embedding-model changes (d) as two separate levers on both latency and memory budgets — a migration to a wider embedding model (Module 08, forward reference) raises both the search and storage cost, even with n unchanged.
  • Revisit the brute-force-vs-index decision (Section 15) as n grows — the crossover point where an approximate index's sub-linear query time starts winning depends on n, d, and acceptable recall loss together, not on any single one alone.
19
RECALL

Knowledge check

Why is sorting n scores O(n log n) and not O(n·d)?
Sorting only ever compares scalar scores against each other — it never inspects a vector's individual d components, so d never enters the cost at all (Section 06).
For n=50,000 and d=384, which single number from Section 10's table is largest, and why does it make sense that it is?
The search cost, 19,200,000 operations — it is the only one of the four costs that multiplies the full corpus size n by the full dimension d, while the others involve only one of the two factors (or, for sorting, neither).
Does doubling the embedding dimension d change the sort cost? Why or why not?
No — sort cost is O(n log n), a function of n alone; Section 06's derivation shows sorting never looks at a vector's components, only at the already-computed scalar scores.

FEEDBACK

Solution and teach-back

Open the worked solution
(1) One score: O(d) = 1,024 operations. (2) Brute-force search: n·d = 200,000 × 1,024 = 204,800,000 operations. (3) Sort: n·log₂(n) ≈ 200,000 × 17.61 ≈ 3,522,000 comparisons. (4) Storage: n·d·4 = 200,000 × 1,024 × 4 = 819,200,000 bytes ≈ 819.2 MB. The search cost (≈204.8M) is the largest, as predictable in advance from Section 09: it is the only quantity that multiplies the full n by the full d, and both n and d are large here — the same reasoning that made search dominate sort in every earlier worked example in this concept.

Teach-back: explain in your own words why the storage cost (819.2 MB) here is larger in raw byte count than the search cost (204.8M operations), even though search is described as the "dominant" cost in this concept — what exactly is "dominant" comparing, if not these two numbers directly?

CAREER PRACTICE

Interview questions

Derive the time complexity of a brute-force nearest-neighbor search over n vectors of dimension d.
Each similarity score is a dot product touching all d dimensions once, costing O(d). Repeating that score computation once per candidate, for n candidates, gives n × O(d) = O(n·d) total (Section 06).
Why does the sorting step in a retrieval pipeline not depend on the embedding dimension d?
Sorting operates only on the n already-computed scalar similarity scores, comparing numbers to each other — it never re-examines the original d-dimensional vectors, so d has no place in its cost (Section 06, Section 17).
System design: your corpus is about to grow from 100,000 to 10,000,000 chunks with the same embedding model. What happens to brute-force search cost, and what would you investigate first?
Search cost is O(n·d) with d fixed, so it grows linearly with n — a 100× increase in n means roughly a 100× increase in search cost. The first thing to investigate is whether an approximate index (Section 15, Module 09) is now justified, since the crossover point where sub-linear query time starts winning is exactly a function of n growing this large.
Debugging: a retrieval service's p99 latency doubled after a routine embedding-model upgrade, with corpus size unchanged. What is the most likely explanation from this concept?
The new embedding model likely uses a larger dimension d — since search cost is O(n·d) and n didn't change, a roughly proportional increase in d would directly explain a roughly proportional increase in measured latency (Section 08, Section 18).
