MODULE 03 · CONCEPT 08

RAG versus fine-tuning,
search and tool use.

Concept 07 ruled out one alternative to RAG — long-context prompting — on size, cost, and quality grounds. This concept draws boundary lines against three completely different techniques RAG gets confused with for a different reason: each one solves a genuinely different problem, not a worse version of the same one. Fine-tuning bakes a skill into weights. Search alone hands back documents with no generation step. Tool use takes a real external action. RAG does none of those three things — it retrieves, then generates.

01 · CONCEPT FIRST

Three techniques, three different jobs

FINE-TUNING

Trains a stable skill, style, or format into the model's own weights — Concept 05's parametric memory — once, up front. Right for something the model should always do a certain way, not a fact to look up per query.

SEARCH / IR ALONE

Returns a ranked list of documents for a human to read themselves. No generation step at all — Concept 01's two-box definition requires generation; search alone stops one box short.

TOOL USE / AGENTIC

Takes a real external action — sends an email, books something, executes code — rather than producing an answer. Concept 01's b06 named this boundary; the mechanics of deciding to act are Module 23's job.

RAG, FOR CONTRAST

Retrieves current, specific, non-parametric evidence at query time, then generates an answer conditioned on it — Concept 01's two boxes, unchanged.

First memory: ask what the request actually needs — a trained habit, raw documents, a real action, or a generated answer grounded in fresh evidence — before reaching for RAG by default.
02 · WHY IT EXISTS

RAG is not the only tool on the bench

Concept 01 through 07 built a strong case for RAG. That case can quietly turn into treating RAG as the default answer to every problem — which is exactly backwards. Each of these three techniques solves a problem RAG solves badly or not at all: fine-tuning for a skill that should always apply, search alone for someone who wants the raw sources rather than a synthesized answer, tool use for a request that needs a real effect in the world, not text.

RAG AS DEFAULT

Treats every information need the same way — retrieve, then generate — even when nothing needs retrieving or nothing needs generating.

RAG AS ONE OF FOUR

Asks what the request actually needs first, then picks fine-tuning, search, tool use, or RAG accordingly — this concept's actual job.

03 · CONCRETE EXAMPLE

Four Oracle RAG requests, four different right tools

"Always reply in Oracle's formal internal voice, in every response" — a stable style, not a fact. Fine-tuning. "List every policy PDF that mentions 'expense report' so I can read them myself" — no answer wanted, just documents. Search alone. "Email my manager my current PTO balance, and cc me on it" — a real action, not text back. Tool use. "How many employees currently work in the Vienna office?" — current, specific, and would go stale in the weights. RAG.

STYLE, NOT A FACT

WANTS RAW DOCUMENTS

NEEDS A REAL ACTION

Tool use actually sends the email — no answer text substitutes for the action itself.

CURRENT AND SPECIFIC

RAG retrieves the live headcount figure and generates the answer from it.

04 · TECHNICAL MECHANISM

What each technique actually changes

FINE-TUNING

Changes the weights

A training run updates parametric memory (Concept 05) once — no retrieval or ranking step exists in its path at all.

SEARCH ALONE

Stops before generation

Ranks and returns documents — the exact same retrieval step RAG uses, minus the generation step that would make it RAG.

TOOL USE

Executes, doesn't answer

Invokes an external action and returns its result or confirmation — not a generated answer grounded in retrieved text.

RAG

Retrieves, then generates

Both boxes from Concept 01, every time — the one combination none of the other three techniques perform.

06 · IMPORTANT DISTINCTIONS

Where beginners flatten four techniques into one

ThisIs notBecause
Fine-tuningRAG with the facts memorized instead of retrievedFine-tuning has no retrieval step at all — the knowledge lives in weights, Concept 05's parametric memory, not in a searchable corpus
Search aloneRAG without the "smart" partSearch alone is what a requester actually wanted when they want raw sources, not a synthesized answer — it isn't an inferior RAG, it's the correct tool for that request
Tool useA more advanced form of RAGTool use produces a real external effect; RAG only ever produces a generated answer, however well-grounded
RAGThe universal default for any information needIt specifically fits current, specific, non-parametric information needing an answer — the other three techniques exist because that isn't every request
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"RAG can replace fine-tuning for anything."

A stable style or skill that should always apply doesn't need looking up per query — that's fine-tuning's job, not RAG's.

"If retrieval already happened, might as well generate an answer too."

Not if the requester explicitly wanted the raw documents — generating unasked-for prose isn't a free upgrade, it's answering the wrong request.

"An agent that retrieves and then acts is just RAG with extra steps."

The action is the point, not the generated text around it — that makes it tool use, with RAG possibly feeding it evidence, not RAG itself.

"Fine-tuning and RAG are mutually exclusive choices."

Not addressed by this concept — they can combine in practice; this concept only draws the boundary between what each one is for.

DEPENDENCIES

04
INTUITION

Four different requests to four different specialists

A stable habit gets trained through repeated practice, not looked up each time — that's fine-tuning. Wanting the raw source material yourself means asking a librarian for the shelf, not a summary — that's search alone. Needing something actually done means hiring someone to do it, not describing how it could be done — that's tool use. Needing a specific, current answer grounded in real evidence means asking someone to check a source and then tell you — that's RAG.

Analogy boundaryThese four "specialists" don't coordinate or negotiate the way people might. In a real system, a single request is routed programmatically by criteria like Section 06's cascade — there's no judgment call happening the way choosing between human specialists would involve one.
05
PRECISION

Formal definitions

TechniqueDefinitionBoundary
Fine-tuningA training run that updates a model's parametric memory (Concept 05) to reliably produce a target skill, style, or formatNo retrieval step; the target behavior must be stable enough to be worth training in once
Search / information retrieval aloneRanking and returning documents relevant to a query, with no generation stepDistinguished from RAG solely by the absence of Concept 01's generation box — the retrieval mechanism itself can be identical
Tool use / agentic actionInvoking a real external action (send, book, execute, modify) in response to a requestProduces an effect in the world, not a generated answer — the mechanics of the decision to act belong to Module 23
RAGRetrieval (Concept 01, Concept 06) followed by generation conditioned on the retrieved evidenceRequires both boxes; missing either one makes it a different technique, not a weaker RAG
06
MECHANISM

A four-question decision cascade

Q1 — Does this go beyond a well-trained base model's own fluent ability? If no, stop: no technique here is needed at all (Concept 05's parametric memory already covers it).
Q2 — Does fulfilling it require a real external action, not just an answer? If yes, stop: tool use.
Q3 — Does the requester want raw source material to read themselves, with no generated answer at all? If yes, stop: search alone.
Q4 — Does the needed knowledge change over time, or is it specific information better looked up than memorized? If yes: RAG. If no (a stable skill or style instead): fine-tuning.

Section 14's lab runs exactly this cascade, live, against six example requests — including one that never leaves Q1 at all.

08
ARCHITECTURE

Where each technique sits relative to the nine-box RAG skeleton

Documents↓Parsing↓Chunking↓Embedding model↓Vectors / index↓Retrieval↓Context↓LLM↓Answer

Search alone keeps everything up through "Retrieval" and stops — no Context, LLM, or Answer box. Tool use replaces "Answer" with an external action, bypassing the question of retrieved evidence entirely for many requests. Fine-tuning touches none of these nine boxes at all — its training run happens completely outside this per-query skeleton. RAG is the only technique that uses every box exactly as drawn.

09
MATHEMATICS

A light update-cost contrast, not a new derivation

This concept stays at the boundary-drawing level, but one comparison is worth making precise: how often does each technique's "update" happen? Fine-tuning's update cost is a full training run, paid once per skill change — Concept 05's parametric write cost, applied here to a skill rather than a single fact. RAG's "update" is a corpus edit — Concept 05's non-parametric write cost — paid per fact change, independent of how many queries follow. Neither number is re-derived; both are Concept 05's existing update-cost distinction, applied to a new comparison: a skill worth training in once, versus a fact worth looking up on demand.

11
CONCRETE USE

Four cards: a clean fit, a boundary case, a counterexample, and a mistake

CLEAN FIT

A support bot that must always speak in a fixed tone

A stable style is exactly fine-tuning's job — retrieving "how to sound formal" on every reply would be the wrong tool entirely.

BOUNDARY CASE

A request that could go either way — "summarize these three documents"

If the documents are handed over directly, this may not even need retrieval — but generation is explicitly wanted, so it isn't search alone either; it resolves as a narrow RAG-like case with a pre-selected context.

COUNTEREXAMPLE

"Just fine-tune the model on our policy PDFs"

Policies change; fine-tuning's update cost is a full retraining run per change — Section 09's contrast — making it the wrong tool for frequently-changing information regardless of how well it might work once.

MISTAKE TO AVOID

Adding a generation step nobody asked for

A user who explicitly wants source documents to read themselves is better served by search alone — generating a summary answers a question they didn't ask.

CODE

The four-question cascade, from scratch

PYTHON · ROUTE A REQUEST TO ONE OF FOUR TECHNIQUES 
def route_request(beyond_base, needs_action, wants_raw_docs, needs_fresh_lookup):
    if not beyond_base:
        return "already_parametric"   # Concept 05's parametric memory already covers this
    if needs_action:
        return "tool_use"             # Module 23 -- a real external effect, not an answer
    if wants_raw_docs:
        return "search_alone"         # retrieval without Concept 01's generation step
    return "rag" if needs_fresh_lookup else "fine_tuning"


# The six s10 requests, as boolean facts about each one
requests = [
    dict(beyond_base=False, needs_action=None, wants_raw_docs=None, needs_fresh_lookup=None),          # grammar
    dict(beyond_base=True,  needs_action=True,  wants_raw_docs=None,  needs_fresh_lookup=None),         # email
    dict(beyond_base=True,  needs_action=False, wants_raw_docs=True,  needs_fresh_lookup=None),         # pdfs
    dict(beyond_base=True,  needs_action=False, wants_raw_docs=False, needs_fresh_lookup=False),        # tone
    dict(beyond_base=True,  needs_action=False, wants_raw_docs=False, needs_fresh_lookup=True),         # threshold
    dict(beyond_base=True,  needs_action=False, wants_raw_docs=False, needs_fresh_lookup=True),         # headcount
]

for req in requests:
    print(route_request(**req))
# already_parametric
# tool_use
# search_alone
# fine_tuning
# rag
# rag

assert route_request(True, False, False, True) == "rag"
assert route_request(True, False, False, False) == "fine_tuning"
13
ECOSYSTEM

Where this comparison has actually been studied

Ovadia, Menachem, Ariel & Nadler (2023) directly compare knowledge injection via fine-tuning against retrieval-augmented generation and find RAG more effective for injecting new or frequently-changing factual knowledge, while fine-tuning better suits stable behavioral adaptation — the exact split this concept draws. Balaguer, Benara, Cunha et al. (2024) run a real-world case study across an agricultural domain, comparing RAG and fine-tuning pipelines end to end on cost and accuracy trade-offs, reinforcing that the right choice depends on how often the underlying knowledge changes. Yao, Zhao, Yu et al. (2022), ReAct, is the founding reference for this concept's tool-use boundary: interleaving reasoning with real actions, the pattern this concept names but explicitly defers to Module 23.

16
DIAGNOSIS

Failure modes

RAG-BY-DEFAULT

Reaching for retrieval-then-generate on every request

Misses cases better served by a trained habit, raw documents, or a real action.

FINE-TUNING A MOVING TARGET

Training in a fact that changes frequently

Pays a full retraining cost repeatedly for information Concept 05's non-parametric memory would update in one edit.

UNWANTED SYNTHESIS

Generating an answer when raw documents were requested

Search alone was the correct tool; adding generation answers a question nobody asked.

ANSWER INSTEAD OF ACTION

Describing what should happen instead of doing it

A tool-use request needs the action executed, not narrated.

CORRECTION

Misconceptions

Incorrect beliefCorrection
Fine-tuning and RAG solve the same problem, fine-tuning just does it worseFine-tuning has no retrieval step at all — it's suited to stable skills, not lookups, per Section 09's update-cost contrast.
Search alone is RAG missing its best featureSearch alone is the right tool when raw documents are what's actually wanted — generation would be unwanted synthesis, not a missing feature.
Tool use is just RAG with an API call at the endThe action is the deliverable; RAG's deliverable is always a generated, evidence-grounded answer, never an external effect.
18
REALITY

Production implications, at introductory depth

  • Route requests through something like Section 06's cascade before defaulting every information need to a RAG pipeline.
  • Track how often a piece of knowledge changes before choosing fine-tuning over RAG for it — Section 09's update-cost contrast is the deciding factor.
  • Log which technique handled each request type, so a misrouted request (e.g. RAG-by-default on a tool-use need) is discoverable, not silent.
  • None of this rules out combining techniques (e.g. a fine-tuned model used as RAG's generator) — named, not designed, here.
19
RECALL

Knowledge check

Why isn't fine-tuning just "RAG with memorized facts"?
Fine-tuning has no retrieval step at all — the information lives in parametric memory (Concept 05), updated only by a full training run, not by an edit to a searchable corpus.
What's the deciding factor between RAG and fine-tuning for a given piece of knowledge?
How often it changes — Section 09's update-cost contrast: a stable skill favors fine-tuning's one-time training cost; frequently-changing information favors RAG's per-edit corpus update.
Why does search alone stop short of being RAG?
It never performs Concept 01's generation step — it returns ranked documents and stops, by design, for requesters who want the sources themselves.

CAREER PRACTICE

Interview questions

A stakeholder wants to fine-tune a model on documents that change weekly. What do you recommend instead, and why?
RAG — Section 09's update-cost contrast means weekly-changing knowledge would require a full retraining run every week under fine-tuning, versus a simple corpus edit under RAG's non-parametric memory (Concept 05).
How do you decide between search alone and RAG for a document-heavy feature request?
Ask whether the user wants a synthesized answer or the source documents themselves — if it's the latter, search alone is correct and adding generation would be unwanted synthesis.
Design question: sketch a request router for a system that must support all four techniques.
A four-question cascade like Section 06's: does it exceed base ability, does it need a real action, does it want raw documents, does the knowledge change over time — routing to already-parametric, tool use, search alone, or RAG/fine-tuning in that order.
