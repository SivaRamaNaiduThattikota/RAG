MODULE 09 · CONCEPT 09

One machine isn't enough.
Split it, copy it, live with the gap.

Concepts 01-08 all quietly assumed one machine held the whole index. Real corpora outgrow one machine's storage, and one machine is a single point of failure. Qdrant's own documentation names the two real fixes -- sharding (split the corpus across machines) and replication (copy the same shard onto more than one machine) -- plus the cost neither one erases: a write lands on one replica before the others, and a client reading the wrong one can see stale data. A verified 12-chunk, 3-shard worked example traces exactly when that fan-out gets the right answer, when it gets lucky, and when it silently misses.

01 · CONCEPT FIRST

Sharding, replication, consistency -- three precise words

SHARDING

Split the corpus across machines, by some fixed rule -- so no single machine has to hold all of it.

REPLICATION

Copy the same shard onto more than one machine -- so no single machine failing takes that shard down with it.

First memory: per Qdrant's own documentation, "writes execute in parallel on all active replicas of a shard," but "Qdrant prioritizes availability and throughput, so concurrent updates to the same document can leave replicas temporarily inconsistent" -- eventual consistency, by default, not a bug.
02 · WHY IT EXISTS

Concepts 01-08 silently assumed one machine, forever

Exact search, HNSW, IVF, PQ/SQ, metadata filtering, tombstones -- every one of them was reasoned about as if the whole index lived on one machine's own disk and memory. Two real limits break that assumption: a corpus can grow past what one machine can store (sharding answers this), and one machine is a single point of failure and a read-throughput ceiling (replication answers this). They are two separate levers, not one.

03 · CONCRETE EXAMPLE

12 chunks, 3 shards, and a fan-out that can miss

A toy corpus of 12 chunks, 2D coordinates (same illustrative convention as Concepts 03-04's own toy corpus). Each doc id is hashed and assigned to one of 3 shards -- Qdrant's own docs name "a consistent hashing algorithm" for this; the toy example below stands in with a simple hash mod 3. The split lands unevenly: Shard 0 gets 3 docs, Shard 1 gets 5, Shard 2 gets 4. Hash-based sharding does not guarantee equal shard sizes.

Query Q=(2,1) is sent to every shard -- never just some, unlike Concept 04's own nprobe<nlist, which deliberately skips clusters. The full brute-force ranking (Concept 01's own exact search) says the true top-4 nearest to Q are doc-01, doc-02, doc-03, doc-12. Each shard searches only its own members and forwards its own local top-(local_k) back to a coordinator, which merges everything and re-sorts:

local_kCandidates fanned backMerged resultMatches ground truth?
1 (too small)3doc-01, doc-02, doc-03NO -- doc-12 never sent
3 (below k=4)9doc-01, doc-02, doc-03, doc-12Yes -- but only by luck
4 (= k, the safe rule)11doc-01, doc-02, doc-03, doc-12Yes -- guaranteed

At local_k=1, doc-12 -- the true 4th-nearest point, sitting inside Shard 1 -- is never surfaced, because Shard 1 only forwarded its own single best result. At local_k=3 the merge happens to be correct, because doc-12 happened to land inside Shard 1's own top-3 anyway -- a lucky case, not a rule. The safe rule: set local_k=k on every shard. No single shard can ever hold more than k of the true global top-k results, since there are only k slots to begin with -- so local_k=k is guaranteed correct for any query, on any shard split.

04 · TECHNICAL MECHANISM

Hash to assign, fan out to search, ack-count to write

Sharding. Qdrant's own documentation: "points are assigned to shards using a consistent hashing algorithm," and "a search request sent to any single node automatically fans out to the rest of the cluster to gather the full result" through Raft consensus. Replication. Qdrant's own docs: "Writes execute in parallel on all active replicas of a shard, and any replica can serve reads or writes." Consistency. Qdrant's own write_consistency_factor parameter "defines the number of replicas that must acknowledge a write operation before responding to the client" -- it "is set to 1 by default," and can range from 1 up to the shard's own replication factor.

06 · IMPORTANT DISTINCTIONS

Sharding vs. Concept 04's IVF partitioning -- same word, two jobs

TermThe real difference
IVF partitioning (Concept 04)Splits vectors WITHIN one machine's own index, by nearest-centroid similarity -- a deliberate approximation that can miss when nprobe<nlist.
Sharding (this concept)Splits the corpus ACROSS machines, by an identity-based hash rule unrelated to vector similarity -- a query fans out to every shard, never skipping one.
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Sharding narrows the search, like IVF does."

False -- every shard is always queried in full. Sharding splits WHERE data lives, not which of it gets looked at.

"More replicas means instantly consistent."

False, per Qdrant's own documentation -- the default is eventual consistency; concurrent updates can leave replicas temporarily out of sync.

"Sharding and replication are the same lever."

False -- sharding splits the data, replication copies it. Orthogonal choices; a real deployment tunes both, separately.

09 · WHAT YOU SHOULD UNDERSTAND

Readiness check before moving on

Name sharding vs. replication vs. consistency

Sharding splits the corpus across machines; replication copies a shard onto more than one machine; consistency is what a client sees when a write has landed on some replicas but not all yet.

State the safe local_k=k rule

Setting local_k=k on every shard guarantees the correct global top-k for any query, because no single shard can ever hold more than k of the true global top-k results.

Explain the write_consistency_factor trade-off in one sentence

A lower write_consistency_factor returns faster but risks a stale read from a slow replica; a higher one waits for more replicas and is slower but safer.

04
INTUITION

A library with branches, and a photocopied catalog

Sharding is like splitting one library's catalog across several branches -- no single branch holds every book, so a librarian's own patron request has to be sent to all of them to be sure nothing's missed. Replication is like photocopying one branch's own catalog and keeping the copy at a second branch -- if the first branch closes for the day, the copy still answers requests, though the copy might not yet reflect a book that was just checked out five minutes ago at the original branch.

Analogy boundaryThe analogy explains WHY the two levers are separate and why a copy can lag, not the exact numbers -- those come from the verified worked example in Section 10.

06
MECHANISM

Three real, cited mechanisms

Sharding. Qdrant's own scaling documentation states: "Qdrant distributes points across shards in one of two ways: Automatic sharding (default): points are assigned to shards using a consistent hashing algorithm... Every node knows where all shards are stored through Raft consensus, so a search request sent to any single node automatically fans out to the rest of the cluster to gather the full result." Replication. The same page: "Writes execute in parallel on all active replicas of a shard, and any replica can serve reads or writes," with three documented replica states -- active, dead, partial -- and a direct statement of the default trade-off: "By default, Qdrant prioritizes availability and throughput, so concurrent updates to the same document can leave replicas temporarily inconsistent." Consistency. Qdrant's own consistency-guarantees page names write_consistency_factor -- "defines the number of replicas that must acknowledge a write operation before responding to the client... It is set to 1 by default... This value can range from 1 to the number of replicas you have for each shard" -- alongside read consistency (query multiple replicas, reconcile) and write ordering (route to a leader for serialized writes).

MATHEMATICS

Fan-out cost, and a sorted-ack-latency lookup

Total merge candidates ≈ S × local_k — illustrative, simplified cost model, NOT a vendor benchmark; assumes shards are large enough that none truncates below local_k
Safe merge guarantee: local_k = k ⇒ merged top-k is always correct, for any query and any shard split
write_consistency_factor lookup: sort replica ack latencies ascending, take the wcf-th value — that is the write call's own return time

The S×local_k model is this concept's own illustrative construct, clearly labeled as such -- not a number Qdrant or any vendor publishes. The safe-merge guarantee and the write_consistency_factor lookup both follow directly from Qdrant's own cited mechanism in Section 06.

Hash assignment, three local_k cases, fan-out cost, and a consistency window

Step 1 -- hash-based shard assignment (S=3). A djb2 string hash of each doc id, mod 3: Shard 0 = {doc-03, doc-06, doc-09} (3), Shard 1 = {doc-01, doc-04, doc-07, doc-11, doc-12} (5), Shard 2 = {doc-02, doc-05, doc-08, doc-10} (4). Total 12 -- an uneven 3/5/4 split, a real consequence of hashing rather than manual round-robin placement.

Step 2 -- ground truth. Full brute-force ranking for Q=(2,1), Euclidean distance, all 12 points. Top-4: doc-01 (d=1.0000), doc-02 (d=1.0000), doc-03 (d=2.2361), doc-12 (d=5.0000).

Step 3 -- fan-out/merge cost scaling (illustrative, S × k, N=1,000,000, k=10, NOT a vendor benchmark). S=1 → 10 candidates, S=2 → 20, S=4 → 40, S=8 → 80, S=16 → 160, S=32 → 320, S=64 → 640. Merge cost grows linearly with shard count -- more shards shrink each shard's own local search, but grow the coordinator's own fan-out and merge cost. A real, quantifiable trade-off, distinct from Concepts 03-05's own single-machine recall/latency/memory trade-offs.

Step 4 -- consistency window, grounded in Qdrant's own write_consistency_factor. replication_factor=3, toy replica-ack latencies: A=5ms, B=8ms, C=40ms (a slow replica). wcf=1 (Qdrant's real default) → write returns at t=5ms. wcf=2 → returns at t=8ms. wcf=3 → returns at t=40ms. At wcf=1, any read routed to replica C between t=5ms and t=40ms still sees the pre-write value -- a real, quantified 35ms staleness window in this toy example. At wcf=3 no read after t=40ms can see stale data, but every write now pays replica C's own worst latency.

Verification methodEvery candidate list, merge result, match/mismatch verdict, and consistency-window number above was produced by three separate node script runs (djb2 hash assignment + shard sizes; brute-force ranking + three local_k merges checked against ground truth; write_consistency_factor sorted-ack-latency lookup), with literal console output captured and cross-checked by hand against every number quoted here.

CONCRETE USE

A clean fit, a boundary case, and a genuine caveat

CLEAN FIT

A growing multi-tenant corpus

Once one machine can no longer hold the data or serve the read load, sharding and replication become the direct answer.

BOUNDARY CASE

Qdrant's own wcf=1 default

The out-of-the-box setting favors speed and availability over immediate consistency -- a documented default, not an oversight.

GENUINE CAVEAT

Adding shards is not free scaling

Per Section 10's own S×k model, more shards raise the coordinator's own fan-out and merge cost even as they shrink each shard's own local search.

CODE

Hash assignment and the verified merge trace, implemented directly

JAVASCRIPT · FROM SCRATCH -- REPRODUCES THIS CONCEPT'S OWN SHARD ASSIGNMENT AND MERGE TRACE EXACTLY 
// djb2 string hash, standard constants, mod S shards.
function djb2Hash(str) {
  let hash = 5381;
  for (let i = 0; i < str.length; i++) {
    hash = ((hash << 5) + hash) + str.charCodeAt(i);
    hash = hash >>> 0;
  }
  return hash;
}
function assignShard(id, S) {
  return djb2Hash(id) % S;
}

// mergeTopK: each shard independently ranks only its own points and
// forwards its own local top-(localK); the coordinator merges every
// forwarded candidate and re-sorts to produce the final top-k.
function mergeTopK(shards, localK, k) {
  const candidates = [];
  for (const shardPoints of shards) {
    const sorted = [...shardPoints].sort((a, b) => a.d - b.d);
    candidates.push(...sorted.slice(0, localK));
  }
  candidates.sort((a, b) => a.d - b.d);
  return { merged: candidates.slice(0, k).map(p => p.id), fannedOut: candidates.length };
}

const shard0 = [{id:'doc-03',d:2.2361},{id:'doc-09',d:8.0623},{id:'doc-06',d:9.4340}];
const shard1 = [{id:'doc-01',d:1.0000},{id:'doc-12',d:5.0000},{id:'doc-07',d:7.0000},{id:'doc-11',d:7.0711},{id:'doc-04',d:9.2195}];
const shard2 = [{id:'doc-02',d:1.0000},{id:'doc-10',d:6.0000},{id:'doc-08',d:8.0623},{id:'doc-05',d:9.2195}];
const groundTruth = ['doc-01','doc-02','doc-03','doc-12'];

console.assert(mergeTopK([shard0,shard1,shard2], 1, 4).merged.join() !== groundTruth.join(), "local_k=1 misses");
console.assert(mergeTopK([shard0,shard1,shard2], 3, 4).merged.join() === groundTruth.join(), "local_k=3 lucky match");
console.assert(mergeTopK([shard0,shard1,shard2], 4, 4).merged.join() === groundTruth.join(), "local_k=4 guaranteed match");
console.assert(mergeTopK([shard0,shard1,shard2], 4, 4).fannedOut === 11, "11 candidates fan back at local_k=4");

DIAGNOSIS

Failure modes

HOT SHARD

An unbalanced hash split

Symptom: one shard (Shard 1's own 5-of-12 in this concept's toy example) carries disproportionately more load than the others, even though the hash function is working correctly.

STALE READ

A read routed to a lagging replica under wcf=1

Symptom: a client reads a value that does not yet reflect a very recent write -- the real, documented consequence of Qdrant's own default.

UNDER-FETCHING SHARD

local_k set below k

Symptom: a true top-k member sitting inside one shard's own results never gets forwarded -- Section 10's own local_k=1 case.

CAREER PRACTICE

Interview questions

Conceptual: how does cross-machine sharding differ from IVF's own within-machine partitioning?
IVF splits vectors inside one machine's index by nearest-centroid similarity and can deliberately skip a cluster (nprobe<nlist); sharding splits the corpus across machines by an identity-based hash rule, and a query always fans out to every shard.
Mathematical: at N=1,000,000, k=10, recompute the S×k fan-out cost at S=128.
1,280 candidates -- doubling S from 64 (640, this concept's own last row) to 128 doubles the merge cost again, confirming the linear-in-S scaling named in Section 10.
Coding: extend mergeTopK to also return which shard each forwarded candidate came from.
Track the shard index alongside each point when building the candidates array (e.g. push {...point, shard: shardIndex} instead of just the point), then include that field in the final merged output.
System design: how would you choose shard_number, replication_factor and write_consistency_factor for a real workload?
Size shard_number and replication_factor from expected corpus growth and failure tolerance (Concept 10's own sizing formulas, named forward), then choose write_consistency_factor as the explicit speed-vs-staleness trade-off for that workload -- 1 for latency-sensitive reads that can tolerate brief staleness, higher for workloads that cannot.
Debugging: a client writes a point, then immediately reads it back and gets a 404. What do you check first?
Whether the write used a low write_consistency_factor (e.g. 1) and the immediate read got routed to a replica that had not yet received the write -- the exact staleness window quantified in Section 10's own consistency example.
