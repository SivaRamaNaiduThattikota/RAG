MODULE 09 · CONCEPT 02

Skip most of the corpus.
On purpose.

Concept 01 costed out exact search and found its real, computable price: milliseconds that grow linearly with the corpus, guaranteed correct because nothing is skipped. This concept names the alternative every later concept in the module builds on: approximate nearest-neighbour (ANN) search deliberately skips most of the corpus, trading a small, measured amount of recall for a real, often dramatic speedup. On the standard SIFT1M benchmark, one real approximate index answers queries about 112 times faster than exact search -- and misses the true nearest neighbour for roughly one query in 5.5. That trade is the whole subject here.

01 · CONCEPT FIRST

Approximate nearest-neighbour (ANN) search -- skip most of the corpus, on purpose

EXACT (Concept 01)

Score the query against every stored vector, then sort. Guaranteed correct -- nothing skipped, but the cost grows linearly with the corpus.

APPROXIMATE (this concept)

Score only a subset of the corpus, chosen by some index structure, then sort that subset. Usually correct, real speedup, real bounded chance of missing the true best match.

First memory: approximate nearest-neighbour search skips most of the corpus on purpose, trading a small, measured amount of recall for a large, real speedup.
02 · WHY IT EXISTS

Concept 01's own crossover made this necessary

Concept 01's own worked example showed exact search's crossover past a 100 ms interactive-latency budget landing between 10 million and 100 million vectors, at d=1,024 on its cited hardware. That crossover is real and reachable -- plenty of production corpora exceed it. Once a corpus passes that point, exact search's own guarantee (always correct) stops mattering if the answer no longer arrives in time. ANN search exists because that trade -- a little less guaranteed correctness for a lot more speed -- is often exactly what a real system needs.

03 · CONCRETE EXAMPLE

112.3x faster, 18.05 recall points cheaper

On FAISS's own published SIFT1M benchmark (1,000,000 base vectors, 128 dimensions, 10,000 queries, measured on an Intel Xeon E5-2680 v2), exact search ("Flat-CPU") takes 9.100 s to answer all 10,000 queries -- 0.91 ms per query, at 100% recall@1 (guaranteed, since exact search skips nothing). nmslib's HNSW index answers the same 10,000 queries in 0.081 s -- 0.0081 ms per query, about 112.3x faster -- but its recall@1 drops to 81.95%. In plain language: HNSW answers each query roughly 112 times faster, but misses the true nearest neighbour for about 1 query in every 5.5.

04 · TECHNICAL MECHANISM

Some structure narrows the candidates -- unspecified here, on purpose

An ANN index pre-organizes the corpus somehow, so that at query time only a small fraction of the n stored vectors ever get scored -- far fewer than Concept 01's exhaustive n. Exactly how that structure is built and searched is deliberately not explained at this depth: HNSW (a graph, Concept 03), IVF (a partitioning scheme, Concept 04), and quantization (a compression scheme, Concept 05) are three different real answers to "which structure," each named forward only. This concept's job is just the trade-off those structures all exist to make: fewer candidates scored, real speedup, a real bounded chance of missing the true best.

06 · IMPORTANT DISTINCTIONS

Three things beginners conflate

TermThe real difference
Exact / brute-force search (Concept 01)Scores every stored vector. Guaranteed correct, cost grows linearly with n.
Approximate nearest-neighbour search (this concept)Scores only a subset, chosen by an index structure. Usually correct, real speedup, real bounded miss rate.
Recall@k (Module 05 Concept 08, cited)The metric that measures how often approximate search's "usually correct" actually holds. Not a search method itself -- a yardstick for one.
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Approximate means unreliable or random."

False -- ANN's miss rate is a bounded, measured, tunable quantity. SIFT1M's own HNSW row misses about 1 query in 5.5, not "sometimes, unpredictably."

"100% recall is always the goal."

False -- accepting less than 100% recall in exchange for real speed is a deliberate product decision, not a failure. Section 10's own IVF16384,Flat row shows a different, equally valid choice on the same curve.

"There's one universal recall/speed number for any ANN index."

False -- the same SIFT1M corpus produces two different operating points (HNSW and IVF16384,Flat) with different recall and different speed. It's a dial, not a fixed constant.

09 · WHAT YOU SHOULD UNDERSTAND

Readiness check before moving on

Define ANN search in one sentence

Score only a subset of the corpus, chosen by some index structure, trading a bounded amount of guaranteed correctness for real speed.

State recall@k's formula from memory

Rec@k = |R_k ∩ Rel| / |Rel| -- Module 05 Concept 08's own formula, cited unchanged. In the ANN setting, |Rel| = 1 (the singleton true nearest neighbour), averaged over many queries.

Explain why a real system might choose 90% recall over 100%

Because the speedup on offer (here, up to ~112x) can be worth far more to a product's real latency budget than the last few points of recall -- a trade-off, not a defect.

  1. Why does exact search always score 100% recall@1, by definition?

06
MECHANISM

Deliberately abstract -- what this concept does NOT build

An ANN index restricts which candidates ever get scored, using some corpus-specific structure. That structure is what Concepts 03-05 build: HNSW constructs a navigable graph over the vectors (Concept 03); IVF partitions the corpus into clusters and searches only the nearest few (Concept 04); quantization compresses vectors so more of them fit in memory and get scored per unit time (Concept 05). This concept builds none of those three things. Its own mechanism is one level up: whatever the structure, the result is fewer candidates scored, a real speedup, and a real, measurable chance that the true best match was among the candidates that got skipped.

SIFT1M: one corpus, three real operating points

Source data -- FAISS's own wiki page, "Indexing 1M vectors," SIFT1M table, measured on an Intel Xeon E5-2680 v2 @ 2.80GHz, 20 threads, batch mode. The standard SIFT1M benchmark, confirmed via INRIA's texmex corpus page to have n=1,000,000 base vectors, d=128 dimensions, and a query set of 10,000 queries -- the divisor used below to turn the table's batched totals into per-query estimates.

Per-query numbers are derived, not directly tabulated. FAISS's own page reports batched totals across all 10,000 queries, not a literal per-query latency; the per-query figures above divide each total by 10,000 -- a real, computable estimate consistent with the cited hardware's batch-mode measurement, not a number FAISS states directly. The 10,000-query divisor itself was independently confirmed from a second source (INRIA's texmex corpus page), not assumed from the FAISS page alone.

Headline comparison (HNSW vs. exact). Trading recall for speed via nmslib's HNSW index costs 18.05 recall points (100% → 81.95%) in exchange for a ≈112.3x speedup (0.91 ms → 0.0081 ms per query). HNSW misses the true nearest neighbour for roughly 1 in 5.5 queries, but answers each query about 112 times faster than exact search, on the identical 1-million-vector, 128-dimension corpus.

Second operating point (IVF16384,Flat) -- the trade-off is a dial, not one fixed number. IVF16384,Flat trades away only 10.20 recall points (100% → 89.80%) for a smaller ≈16.9x speedup (0.91 ms → 0.0538 ms). HNSW is itself ≈6.64x faster than IVF16384,Flat here, but at 7.85 fewer recall points (89.80% → 81.95%). Two different real, named indexes sit at two different points on the same recall-vs-speed curve, on the identical corpus.

Recall@k, cited, not re-derived. The 1-R@1 figures above are Module 05 Concept 08's own Rec@k = |R_k ∩ Rel| / |Rel| formula, instantiated with |Rel|=1 -- the singleton true nearest neighbour for one query -- and averaged across the 10,000-query test set. FAISS's own page defines 1-R@1 as "the fraction of query vectors where the actual nearest-neighbor is ranked in the R first results," matching that formula exactly.

Only the relative numbers within this concept's own table -- the speedup ratios and recall gaps -- are meant to be compared to each other.

CONCRETE USE

A clean fit, a boundary case, and a mistake

CLEAN FIT

A chatbot's retrieval step

90% recall is often an acceptable, documented trade-off for sub-millisecond latency -- exactly IVF16384,Flat's own operating point above.

BOUNDARY CASE

A single-candidate corpus

When n=1, there's nothing to skip -- approximate and exact search are identical, since any index structure has only one candidate to consider.

MISTAKE TO AVOID

Choosing an index without measuring its real recall on your own data

SIFT1M's own numbers above don't transfer automatically to a different dataset or query distribution -- they describe this one corpus, on this one hardware, at this one moment.

CODE

A deliberately naive "toy ANN" -- the general shape only

PYTHON · FROM SCRATCH -- ILLUSTRATES THE SHAPE, NOT ANY REAL ALGORITHM (HNSW/IVF ARE CONCEPTS 03-04) 
import random

def cosine(u, v):
    dot = sum(a * b for a, b in zip(u, v))
    norm_u = sum(a * a for a in u) ** 0.5
    norm_v = sum(b * b for b in v) ** 0.5
    return dot / (norm_u * norm_v)

def exact_top1(query, vectors):
    # Concept 01's own mechanism, unchanged -- score everyone, keep the best.
    return max(vectors, key=lambda pair: cosine(query, pair[1]))

def toy_ann_top1(query, vectors, m, rng):
    # NOT a real index -- no graph, no partitioning, no quantization.
    # Scores only a random subset of size m < n, illustrating the general
    # shape (fewer candidates scored -> real chance of missing the truth)
    # without pre-empting Concepts 03-05's own real mechanisms.
    subset = rng.sample(vectors, min(m, len(vectors)))
    return max(subset, key=lambda pair: cosine(query, pair[1]))

def measure_recall(vectors, num_queries, m, dims, trials, seed=0):
    rng = random.Random(seed)
    hits = 0
    for _ in range(trials):
        query = [rng.uniform(-1, 1) for _ in range(dims)]
        true_best = exact_top1(query, vectors)
        approx_best = toy_ann_top1(query, vectors, m, rng)
        if approx_best[0] == true_best[0]:
            hits += 1
    return hits / trials

rng = random.Random(42)
dims = 8
corpus = [(i, [rng.uniform(-1, 1) for _ in range(dims)]) for i in range(200)]

# Scoring every candidate (m == n) must always match exact search.
recall_full = measure_recall(corpus, 1, len(corpus), dims, trials=20, seed=1)
assert recall_full == 1.0

# Scoring a small subset (m << n) can, sometimes, miss the true best --
# recall drops below 1.0, the exact shape this concept describes.
recall_partial = measure_recall(corpus, 1, 20, dims, trials=200, seed=2)
assert 0.0 <= recall_partial < 1.0

DIAGNOSIS

Failure modes

UNMEASURED RECALL

Deploying an ANN index without ever measuring its real recall

Symptom: the index looks fast in a demo, then quietly returns wrong answers at a rate nobody ever measured on the real, held-out query set.

BORROWED BENCHMARK

Assuming a public benchmark's recall number transfers

Symptom: SIFT1M's own 81.95%/89.80% figures get quoted for a completely different corpus and query distribution, where the true number could be meaningfully different.

REALITY

Production implications

  • Recall targets are a product/business decision, not a default -- there is no universally "correct" recall number.
  • Recall must be measured on your own held-out query set, not assumed from a public benchmark like SIFT1M's own numbers above.
  • Concept 01's own latency budgets combine directly with this concept's recall numbers to pick a real operating point.
  • HNSW, IVF and quantization (Concepts 03-05) are three different real families with different cost profiles -- none is a universal "best" approximate index.

CAREER PRACTICE

Interview questions

Conceptual: what does recall@k actually measure?
The fraction of a query's truly relevant results that the search actually returned -- Rec@k = |R_k ∩ Rel| / |Rel|. In the ANN setting, it's usually measured with |Rel|=1 (the singleton true nearest neighbour), averaged across many queries.
Mathematical: compute a speedup from two per-query ms figures.
speedup = T_exact ÷ T_approx. For SIFT1M's own IVF16384,Flat row: 0.91 ms ÷ 0.0538 ms ≈ 16.9x.
Coding: extend the toy subset-scan code to report recall across many m values.
Loop measure_recall over several values of m (e.g. 5, 20, 50, 100), holding trials and dims fixed, and plot or print recall as a function of m -- recall should rise monotonically toward 1.0 as m approaches n, the same shape SIFT1M's own three real rows show.
System design: how would you choose a recall target for a support-ticket RAG system?
Start from the product's own latency budget (Concept 01's own framing) and a labeled query set representative of real support tickets; measure recall@k on that set for candidate indexes, then pick the fastest one whose measured recall still meets a business-defined acceptable-miss-rate threshold -- not a number borrowed from a public benchmark like SIFT1M.
Debugging: a service's measured recall dropped after a corpus update, but nothing about the index changed. What do you check first?
Whether the underlying data distribution shifted -- new documents, a changed embedding model, or a query distribution that no longer matches what the index was tuned against. A benchmark's recall number, including this concept's own SIFT1M figures, describes one dataset at one point in time; it does not automatically hold after the corpus changes underneath it.
