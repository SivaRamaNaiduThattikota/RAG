MODULE 09 · CONCEPT 04

Partition first.
Search locally.

Concept 03 built HNSW's own graph-descent answer to Concept 02's trade-off. This concept builds a genuinely different real strategy: Inverted File (IVF) partitioning. The corpus is split into a fixed number of clusters ahead of time; at query time, only the few clusters nearest the query get searched at all, and the rest of the corpus is never touched. That is the whole idea -- no graph to walk, just a much smaller pile to search exhaustively. A ten-point toy corpus shows exactly where this can go wrong: a real query whose true nearest neighbour sits in the second-nearest cluster, missed entirely if only the single nearest cluster is searched.

01 · CONCEPT FIRST

IVF -- partition the corpus into clusters, probe only the nearest few

HNSW (Concept 03)

One graph, precomputed edges. Search walks the graph, greedily descending toward the query.

IVF (this concept)

The corpus is split into nlist clusters ahead of time, each with a centroid. At query time, only the nprobe clusters whose centroids are nearest the query get searched -- exhaustively, but only within those clusters.

First memory: IVF pre-sorts the corpus into nlist clusters, then at query time exhaustively searches only the nprobe clusters nearest the query -- everything else is never touched.
02 · WHY IT EXISTS

A second, genuinely different real "how"

Concept 03's HNSW narrows candidates via precomputed graph edges and greedy descent. IVF narrows candidates a completely different way: partition first, search locally second. Both are real, widely-deployed answers to Concept 02's own trade-off; neither is a special case of the other. FAISS ships both as separate, real index families (IndexHNSWFlat and IndexIVFFlat), confirmed directly from its own Faiss-indexes wiki page.

03 · CONCRETE EXAMPLE

A real miss at nprobe=1, caught at nprobe=2

Ten toy 2-D points sit in three clusters, each with a fixed centroid trained once, up front: C1 (three points near the origin), C2 (three points near (5.3,5.3), plus a fourth point at (8,4) added later and assigned to C2 since it was the nearest existing centroid at insert time), and C3 (three points near (10.3,1.3)). Query Q=(8.3, 3.7). Ranking the three centroids by distance to Q: C3 (3.1202) is nearest, C2 (3.3866) second, C1 (8.6488) a distant third. At nprobe=1, only C3's three points are searched, and the best found is C3's own (10,2) at distance 2.4042. But the true global nearest neighbour, confirmed by brute-force check across all ten points, is C2's own (8,4) point -- at distance 0.4243 -- sitting in the second-nearest cluster. nprobe=1 misses it completely. At nprobe=2, C2's cluster is probed too, and (8,4) is found -- the correct answer.

04 · TECHNICAL MECHANISM

Two named parameters, cited from FAISS's own documentation

FAISS's own Faiss-indexes wiki page names IVF's two core parameters directly. nlist is the number of clusters the corpus is partitioned into (three, in this concept's own toy example). nprobe is how many of those clusters get searched per query, chosen at query time -- "useful for measuring trade-offs between speed and accuracy," in the page's own words. The page also states the failure case in exactly the shape this concept's own worked example demonstrates: "the failure case appears when the cell of the nearest neighbor of a given query is not selected." Centroid assignment itself uses k-means-style nearest-centroid assignment, named here at reference depth only -- Module 11's own future clustering module owns k-means' full derivation.

06 · IMPORTANT DISTINCTIONS

Four terms beginners conflate

TermThe real difference
Cluster (inverted list)A group of stored vectors assigned to the same centroid. This toy example has 3, holding 3, 4 and 3 points.
CentroidOne representative point per cluster, trained once (via k-means-style assignment) and generally not recomputed per insert.
nlistThe total number of clusters the corpus is split into -- a build-time choice. This toy example: nlist=3.
nprobeHow many of the nlist clusters get searched per query -- a query-time choice. nprobe=1 misses the true answer here; nprobe=2 finds it.
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"The nearest cluster always contains the true nearest neighbour."

False -- this concept's own worked example shows the true nearest neighbour sitting in the second-nearest cluster, missed entirely at nprobe=1.

"IVF and HNSW are two versions of the same idea."

False -- IVF partitions and searches locally; HNSW walks a graph. Neither is a variant of the other; FAISS ships them as entirely separate index classes.

"Raising nprobe to nlist gives you a free speedup with full accuracy."

False -- at nprobe=nlist, every cluster gets searched, which is exactly Concept 01's own exhaustive exact search again, with zero candidates skipped and zero speedup left.

04
INTUITION

A warehouse sorted into aisles, checked by aisle

Imagine a warehouse where every item was sorted, once, into one of a fixed number of aisles based on which aisle's own "typical item" it most resembled. Looking for something new means walking straight to the aisle whose typical item looks most similar, and checking every item in that aisle by hand -- fast, since only one aisle gets checked, not the whole warehouse. But if the item you actually want was mis-filed into a neighbouring aisle because its resemblance to that aisle's typical item was a close second, checking only the top aisle misses it entirely. Checking the top two aisles instead of one catches that case, at the cost of checking twice as many items.

Analogy boundaryReal IVF deployments use far more than 3 clusters -- nlist is commonly in the hundreds to tens of thousands, following FAISS's own rule of thumb, nlist ≈ C·√n. This concept's own toy example uses nlist=3 deliberately, so the trace in Section 10 can be followed by hand.

06
MECHANISM

Construction and search, both cited from FAISS's own documentation

Construction. A coarse quantizer trains nlist centroids over a representative sample of the corpus (k-means-style nearest-centroid assignment, named at reference depth only). Every stored vector is then assigned to whichever of those nlist centroids it is nearest to, and stored in that centroid's own inverted list. Centroids are generally fixed once trained -- new vectors inserted later (like this concept's own worked example's fourth C2 point) are assigned to the nearest existing centroid, not used to retrain the centroids themselves.

Search (the mechanic this concept's own worked example demonstrates). The query is compared against all nlist centroids -- a small, cheap comparison, since nlist is far smaller than the corpus. The nprobe nearest centroids are selected, and their inverted lists are searched exhaustively (every vector in those lists gets scored directly, exactly like Concept 01's own brute-force search, just over a far smaller subset). Vectors in any unprobed cluster are never scored at all -- including, potentially, the true nearest neighbour, exactly as FAISS's own page states.

07
VISUALIZATION

A coarse filter, then a fine, exhaustive scan

Probe nprobe of nlist clustersExhaustive within probed clusters, zero outside them
Query vectorCompared against all nlist centroids first
Coarse quantizer picks nprobe clustersThe cheap, corpus-wide comparison step
Exhaustive scan inside probed clusters onlyBrute-force search (Concept 01's own mechanism), just over a smaller subset

Contrast directly with Concept 03's own Section 07: there, the search walked a graph, one edge-hop at a time, never comparing against a full layer. Here, the search makes one coarse comparison against all nlist centroids, then reverts to Concept 01's own brute-force scan -- but only inside the nprobe clusters selected.

MATHEMATICS

Two cited results, neither re-derived

Fraction of corpus scanned ≈ nprobe ÷ nlist — FAISS's own page notes this is an approximation, since inverted lists are not evenly sized
nlist ≈ C·√n — FAISS's own rule-of-thumb sizing formula, balancing centroid-comparison cost against per-cluster scan cost

Neither equation is new mathematics; both are cited directly from FAISS's own Faiss-indexes wiki page. This concept's own contribution is the worked trace in Section 10, showing exactly how a real query can fall on the wrong side of that approximation.

WORKED EXAMPLE

Ten points, three clusters, three values of nprobe

The corpus. C1 (centroid 0.3333, 0.3333): (0,0), (1,0), (0,1). C2 (centroid 5.3333, 5.3333, trained before the fourth point was added): (5,5), (6,5), (5,6), (8,4). C3 (centroid 10.3333, 1.3333): (10,1), (11,1), (10,2). Query Q=(8.3, 3.7).

Centroid ranking (the coarse filter). Distance from Q to each fixed centroid: C3=3.1202, C2=3.3866, C1=8.6488. Nearest first: C3, then C2, then C1.

nprobe=1. Only C3's inverted list is scanned: (10,1), (11,1), (10,2). Best found: (10,2) at 2.4042. This is returned as the answer -- but it is not the true nearest neighbour.

nprobe=2. C3's and C2's lists are both scanned: the seven points above C1's row. Best found: (8,4) at 0.4243 -- the true global nearest neighbour, confirmed by the brute-force ranking of all ten points in the table above. nprobe=1 missed it entirely; nprobe=2 finds it, at the cost of scanning 7 points instead of 3.

nprobe=3 (=nlist). Every cluster is scanned -- all ten points -- which is exactly Concept 01's own exhaustive exact search again. At nprobe=nlist, IVF's own speedup disappears completely: nothing is skipped, so the fraction-scanned formula from Section 09 (nprobe÷nlist) reaches 1.0, and recall is guaranteed 100%, exactly as it was in Concept 01.

Verification methodAll ten point-to-query distances were computed with two independently-structured Node.js scripts -- one iterating over a labelled point list with a shared distance function, one with fully inline manual arithmetic per point -- and both produced identical results. A third script brute-force-sorted all ten distances to confirm (8,4) is the true global minimum, and that nprobe=1's own candidate, (10,2), is only the second-best point overall, confirming the miss is real rather than assumed.
11
CONCRETE USE

A clean fit, a boundary case, and a mistake

CLEAN FIT

A memory-constrained corpus too large for a graph index

IVF's own inverted lists cost far less memory overhead per vector than HNSW's own graph edges, at a comparable recall target.

BOUNDARY CASE

nprobe=nlist

Every cluster gets probed -- IVF degenerates exactly to Concept 01's own exhaustive exact search, with no speedup left at all.

MISTAKE TO AVOID

Assuming the nearest cluster always holds the true answer

This concept's own worked example shows the true nearest neighbour sitting in the second-nearest cluster -- a real, confirmed miss at nprobe=1, not a hypothetical one.

CODE

The toy corpus's own IVF search, implemented directly

PYTHON · FROM SCRATCH -- REPRODUCES THIS CONCEPT'S OWN TEN-POINT TRACE EXACTLY 
import math

centroids = {"C1": (1/3, 1/3), "C2": (16/3, 16/3), "C3": (31/3, 4/3)}
clusters = {
    "C1": [(0, 0), (1, 0), (0, 1)],
    "C2": [(5, 5), (6, 5), (5, 6), (8, 4)],
    "C3": [(10, 1), (11, 1), (10, 2)],
}

def dist(p, q):
    return math.sqrt((p[0] - q[0]) ** 2 + (p[1] - q[1]) ** 2)

def ivf_search(query, nprobe):
    ranked_clusters = sorted(centroids, key=lambda c: dist(centroids[c], query))
    probed = ranked_clusters[:nprobe]
    candidates = [pt for c in probed for pt in clusters[c]]
    return min(candidates, key=lambda pt: dist(pt, query)), probed

query = (8.3, 3.7)

best_1, probed_1 = ivf_search(query, nprobe=1)
best_2, probed_2 = ivf_search(query, nprobe=2)

all_points = [pt for pts in clusters.values() for pt in pts]
true_best = min(all_points, key=lambda pt: dist(pt, query))

assert probed_1 == ["C3"] and best_1 == (10, 2)
assert probed_2 == ["C3", "C2"] and best_2 == (8, 4)
assert true_best == (8, 4)
assert best_1 != true_best  # nprobe=1 genuinely misses the true answer
assert best_2 == true_best  # nprobe=2 finds it

DIAGNOSIS

Failure modes

TOO FEW PROBES

nprobe set too low for the corpus's own cluster overlap

Symptom: this concept's own worked example -- a real, confirmed miss, at a rate that must be measured on real data, not assumed away.

STALE CENTROIDS

Centroids never retrained as the corpus grows

Symptom: newly inserted vectors keep getting assigned to increasingly ill-fitting existing centroids, the same pattern this concept's own fourth C2 point demonstrates at toy scale.

REALITY

Production implications

  • nprobe is the dial tuned in production, exactly like Concept 03's own ef_search -- raised until measured recall clears the product's own bar.
  • nlist is a build-time choice, sized via FAISS's own nlist ≈ C·√n rule of thumb, far more expensive to change than nprobe.
  • IVF's own memory footprint is typically lower than HNSW's -- Concept 06 (recall-latency-memory trade-offs) generalizes this comparison across all three named ANN families.
  • IVF is very commonly paired with quantization in real systems (FAISS's own IVF-PQ) -- Concept 05 builds quantization's own mechanics next.

FEEDBACK

Solution and teach-back

Open the worked solution
Distance from (4,4) to centroid (2,2) ≈ 2.8284; to centroid (8,8) ≈ 5.6569 -- cluster A (centroid (2,2)) is nearer. At nprobe=1, only cluster A is scanned: (1,1) at distance ≈4.2426, (2,3) at distance ≈2.2361, (3,2) at distance ≈2.2361. Best found: a tie between (2,3) and (3,2), both at ≈2.2361. CAREER PRACTICE

Interview questions

Conceptual: why is IVF described as a "coarse filter, then a fine scan," rather than a single search step?
Because it makes two structurally different comparisons: a cheap comparison against all nlist centroids to pick which clusters to probe, then an exhaustive, Concept-01-style brute-force scan only inside the probed clusters.
Mathematical: for nlist=1000 and nprobe=20, estimate the fraction of the corpus scanned per query.
Approximately nprobe÷nlist = 20÷1000 = 0.02, or about 2% of the corpus -- FAISS's own page notes this is an approximation, since inverted lists are rarely equal in size.
Coding: extend this concept's own ivf_search function to also return the number of points scanned.
Return len(candidates) alongside the best point and the probed cluster list -- for nprobe=1 in this concept's own worked example, that would be 3; for nprobe=2, 7.
System design: how would you choose nlist and nprobe for a new million-vector deployment?
Start from FAISS's own rule of thumb, nlist ≈ C·√n, then measure recall@k on a real held-out query set while sweeping nprobe upward from a small value, stopping once recall clears the product's own bar -- the same measure-don't-assume discipline Concept 02 already established.
Debugging: after a bulk data load, IVF recall dropped even though nprobe was unchanged. What do you check first?
Whether the newly inserted vectors are landing disproportionately in a few existing clusters (unbalanced inverted lists, exactly the pattern this concept's own fourth C2 point demonstrates), which quietly shifts the true nprobe÷nlist scanned-fraction approximation away from what was originally measured.
