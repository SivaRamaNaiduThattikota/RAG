and prompt roles

01 · CONCEPT FIRST

A prompt is a structured request, not a paragraph

A well-built prompt has four moving parts. An instruction states the task — vague or specific. Few-shot examples are worked demonstrations placed in the prompt so Concept 07's in-context learning has something concrete to condition on. Roles — system, user, and assistant — label who is "speaking" in each part of the input. And a prompt template is the reusable shape that assembles instruction, examples, retrieved context, and the live question the same way every time a real request comes in.

The roles are not a labeling convention you invented at the API layer. Concept 06 showed that supervised fine-tuning trains a model on data formatted with exactly these role delimiters, teaching it to weight system-tagged tokens as authoritative instructions and treat user-tagged tokens as the task to perform. That is why role separation changes behavior — it is a trained prior, not a cosmetic tag.

First memory: instruction, examples, and roles are three separate levers on the same prompt — and the roles only work because Concept 06's fine-tuning stage taught the model to respect them.
02 · WHY IT EXISTS

An unstructured block of text is ambiguous to fill

Concept 07 showed that a context window doesn't care what filled it — every token you send competes for the same budget, and attention treats them all as tokens to condition on. Without deliberate structure, "policy," "question," and "example answer" are indistinguishable to the model except by their content. A vague instruction like "answer well" gives the output distribution almost nothing to sharpen against; an unlabeled paragraph gives the model no signal about which part is the rule and which part is the data.

ONE UNSTRUCTURED BLOCK

Instructions, evidence, and the question run together; nothing marks which part carries authority.

A STRUCTURED PROMPT

A specific instruction, chosen examples, and role labels the model was trained to weight differently.

03 · CONCRETE EXAMPLE

Same question, two very different prompts

Prompt A: "You are a helpful assistant. Answer the user's question about leave policy using the context below and the question below." — everything in one block, one vague verb ("answer"), no worked example. Prompt B assigns a system message ("Answer only using the numbered policy sections provided. Cite the section number in parentheses. If the context does not contain the answer, say so explicitly."), a user message carrying just the retrieved sections and the question, and one assistant-role few-shot example showing the exact citation format wanted.

PROMPT A

Vague instruction, no examples, no role separation — the model has to guess what "answer well" means here.

PROMPT B

Specific instruction, one worked example, roles assigned — same underlying question, far less room for drift.

WHAT ACTUALLY CHANGED

Not the model, not the retrieved evidence — only how the exact same information was structured before the forward pass.

04 · TECHNICAL MECHANISM

What each part of the prompt is actually doing

SYSTEM ROLE

Trained to carry policy

Concept 06's fine-tuning data associates system-tagged content with instructions the model should follow ahead of the user's own phrasing.

USER ROLE

The task to perform

Carries the live question and any evidence you want treated as this turn's input, not as a standing rule.

ASSISTANT ROLE

Prior output — and few-shot demos

Normally the model's own past turns; also used to plant worked example answers the model conditions on via Concept 07's in-context learning.

INSTRUCTION SPECIFICITY

Narrows what "good" means

"Cite the section number in parentheses" gives the output distribution something concrete to sharpen toward; "answer well" does not.

FEW-SHOT EXAMPLES

Concept 07's mechanism, used deliberately

Each example is attended over like any other prompt token — no fine-tuning job, just a demonstration placed where the forward pass can use it.

PROMPT TEMPLATE

The reusable shape

Fixes where the instruction, examples, and role boundaries sit so every real request gets assembled the same way.

07 · COMMON MISTAKES

What beginners often misunderstand

"Role labels are just formatting the API happens to want."

They correspond to a distinction the model was trained on during Concept 06's fine-tuning stage — removing them changes behavior, not just appearance.

"A longer instruction is a more specific instruction."

Specificity means stating the exact rule and format wanted; padding a vague instruction with more words does not add that.

"More few-shot examples always helps."

Each example costs tokens against Concept 07's fixed budget, and returns diminish well before the window fills.

"Putting the whole policy document in the user role works the same as a system instruction."

Both are tokens the model attends over, but only system-tagged content carries the trained instruction-following weight.

"The system role guarantees compliance."

It strongly conditions the output distribution; it does not force a particular token to be chosen every time.

"A prompt template is a nice-to-have, not a real artifact."

It is the thing that actually gets versioned, tested, and reused across every request — treat it like code.

04
INTUITION

A labeled work order versus one paragraph of notes

Imagine handing a new hire a labeled work order — a "policy" section, a "reference materials" section, a "task" section — instead of one unlabeled paragraph that mixes all three. The labeled version isn't just tidier; a hire who was specifically trained to treat "policy" sections as binding will follow them more reliably than the same words with no label at all. Prompting works the same way: role labels aren't decoration, they're read by something that was trained to read them a specific way.

Analogy boundaryA new hire's training happened in a classroom somewhere else; a model's happened in Concept 06's fine-tuning stage, over actual chat-formatted training examples with these same role delimiters. The analogy explains why labels can matter to a reader — it does not explain the mechanism. That mechanism is a trained statistical prior, not comprehension, and Section 09 formalizes it as a weight on the model's own logits.

06
MECHANISM

Two different clocks: designing the template, filling it in

TEMPLATE DESIGN TIME — DONE ONCE
Draft a specific instruction stating the exact rule and format wanted
Choose a small number of few-shot examples that demonstrate that format
Assign system role to policy/instruction, user role to question and evidence
Save the template as a versioned artifact, not an inline string
REQUEST TIME — DONE EVERY CALL
Retrieved chunks and the live question are dropped into the user-role slot
The filled template is tokenized with its role delimiters intact
The forward pass conditions attention more heavily on system-tagged tokens (Concept 06's trained prior)
Few-shot examples, if present, condition the output via Concept 07's in-context learning

Design time decides the shape; request time decides the content. A bug in either lane produces a different failure — Section 16 separates them.

09
MATHEMATICS

Formalizing "the budget" and "the trained weight"

A template's token cost is the sum of its parts, and it has to leave room for Concept 07's reserved output:

tokens_template = tokens_system + tokens_instruction + n_shot·tokens_per_example + tokens_context + tokens_question
tokens_template + tokens_reserved_output ≤ n_max (Concept 07's context-window ceiling, cited, not re-derived)

Separately, role separation's effect can be sketched as an additive bias on the model's own next-token logits — a simplified stand-in for what Concept 06's fine-tuning actually learned to do:

logit'_i = logit_i + w_role · specificity(instruction, token_i)

logit_i is the token's raw score before this effect (Concept 05); specificity(instruction, token_i) is how strongly a candidate token matches what the instruction concretely asked for, scored higher for a specific instruction than a vague one; w_role is a learned coefficient — large when the instruction sits in a system-tagged position the fine-tuning stage trained to matter, near zero when the same words sit in an untagged or data-only position. This is not the model's real internal computation, only a way to reason about why identical wording produces a different outcome depending on where it sits.

10
WORKED EXAMPLE

Budgeting a template, then comparing two instructions

An Oracle RAG answer template: a 180-token system instruction, one 220-token few-shot example, three retrieved sections totaling 1,200 tokens, and a 40-token question.

tokens_template = 180 + 220·1 + 1200 + 40 = 1,640
1,640 + 400 (reserved output) = 2,040 ≤ 8,000 (n_max) — comfortably inside the window

Now compare two versions of the instruction using Section 09's logit-bias sketch, with an illustrative w_role = 3 for content correctly placed in the system role: a vague instruction ("answer well") scores specificity ≈ 0.2, giving a logit shift of about 0.6; a specific instruction ("cite the section number in parentheses after every claim") scores specificity ≈ 0.9, giving a shift of about 2.7 — more than four times larger, for a token count that barely changed. Specificity, not instruction length, is what actually moves this number.

CODE

A from-scratch prompt template assembler

PYTHON · FROM-SCRATCH PSEUDOCODE 
def estimate_tokens(text, chars_per_token=4):
    return max(1, round(len(text) / chars_per_token))

def build_prompt(system_instruction, few_shot_examples, retrieved_context, question,
                  context_window=8000, reserved_output=400):
    # Roles are assembled as a list of tagged messages, not one flat string —
    # the tag is what a fine-tuned chat model was trained to read differently.
    messages = [{"role": "system", "content": system_instruction}]

    for example in few_shot_examples:
        messages.append({"role": "user", "content": example["question"]})
        messages.append({"role": "assistant", "content": example["answer"]})   # few-shot, not the model's own prior turn

    evidence_block = "\n\n".join(retrieved_context)                            # data — never given a "system" tag
    messages.append({"role": "user", "content": f"{evidence_block}\n\nQuestion: {question}"})

    total_tokens = sum(estimate_tokens(m["content"]) for m in messages)
    budget_ok = (total_tokens + reserved_output) <= context_window
    if not budget_ok:
        raise ValueError(f"Template needs {total_tokens + reserved_output} tokens, "
                          f"window only allows {context_window}")             # fail before the call, per Concept 07
    return messages

SYSTEM = ("Answer only using the numbered policy sections provided. "
          "Cite the section number in parentheses after every claim. "
          "If the sections do not contain the answer, say so explicitly.")     # specific, checkable — Section 09's high-specificity case

FEW_SHOT = [{"question": "What is the notice period for resignation?",
             "answer": "The standard notice period is two weeks (3.2)."}]

prompt = build_prompt(SYSTEM, FEW_SHOT,
                       retrieved_context=["(3.2) Employees must give two weeks' written notice..."],
                       question="How much notice must I give before resigning?")

DIAGNOSIS

Failure modes

VAGUE INSTRUCTION

Underspecified output distribution

"Answer well" gives the model nothing concrete to sharpen toward — outputs drift in format and completeness across calls.

ROLE CONFLATION

Instructions placed in the user role

The words are present, but without the system-tagged weighting, they compete with the question instead of governing it.

FEW-SHOT OVERLOAD

Diminishing returns, real cost

Extra examples add tokens against Concept 07's budget and quadratic attention cost, past the point they still change the output.

STALE EXAMPLES

Format drift over time

Few-shot examples written for an old answer format keep steering new requests toward a shape that's no longer wanted.

UNTAGGED CONTEXT TREATED AS INSTRUCTION

Prompt-injection preview

A sentence inside retrieved text that reads like an instruction can get partial trained weight it should never have — Module 20 covers full defenses; only named as a boundary here.

UNVERSIONED TEMPLATE EDITS

Untracked behavior change

Editing the live instruction or examples without versioning makes a behavior shift indistinguishable from a model or data change.

18
REALITY

Production implications

  • Version prompt templates the same way code is versioned — a changed instruction or example set is a behavior change worth a diff and a review.
  • Keep retrieved context in the user role by default; treat any text that reads like an instruction inside it as a signal to investigate, not obey.
  • Budget few-shot examples against Concept 07's token cost and quadratic attention cost — measure whether an added example still changes the output before keeping it.
  • Test instruction changes against a fixed evaluation set before shipping them; a "small wording tweak" can shift output format noticeably.
  • Log which template version produced which answer — the same reproducibility discipline Module 01 already applied to decoding parameters.
  • None of this substitutes for retrieval quality or grounding — a perfectly structured prompt around wrong or missing evidence still produces a wrong answer.

RECALL

Knowledge check

Why does the system role change model behavior rather than just labeling content?
Because Concept 06's supervised fine-tuning trained the model on data using these exact role delimiters, teaching it to weight system-tagged content as instruction — the effect is a trained prior, not a property of the label itself.
What distinguishes a specific instruction from a vague one?
A specific instruction states a concrete, checkable rule and format; a vague instruction states only a general goal, giving the output distribution nothing precise to sharpen toward.
Are few-shot examples a form of fine-tuning?
No — they work entirely through Concept 07's in-context learning, conditioning one forward pass with zero change to any stored weight.
Why is retrieved context kept in the user role rather than the system role?
Because it is evidence for this turn, not a standing instruction; giving it system-role placement would grant it trained instruction-following weight it should not have.

FEEDBACK

Solution and teach-back

Open one defensible template design
A workable system instruction: "Given the described employee scenario and the numbered policy sections, list only the exceptions that apply, citing the section number for each. If no exception applies, say so explicitly." One few-shot example is usually enough here — the task is narrow and mostly about format (a cited list), so a second example would mostly add tokens rather than more format signal. Role assignment: the instruction above sits in the system role; the retrieved policy sections and the employee scenario sit together in the user role as evidence plus question; a worked "scenario → cited exception list" pair sits in the assistant role as the single few-shot demonstration. For a rough budget with a 160-token system instruction, one 200-token example, 900 tokens of retrieved sections, and a 70-token question: 160 + 200 + 900 + 70 = 1,330 tokens; adding the 500 reserved for output gives 1,830, comfortably under the 6,000-token window.

PORTABLE MEMORY

Concept card

The mechanism

Instruction specificity, few-shot placement (Concept 07's in-context learning), and system/user/assistant roles (meaningful because of Concept 06's fine-tuning) combine into a versioned prompt template.

Selection rule

  • State a checkable rule, not a general goal
  • Keep policy in the system role, evidence and question in the user role
  • Add few-shot examples until format compliance stops improving, not further
  • Version the template; never treat retrieved text as an instruction
23
CAREER PRACTICE

Interview questions

Explain why system/user/assistant roles affect model output rather than being purely organizational.
Because the model was fine-tuned (Concept 06) on chat-formatted data using these exact delimiters, it learned to weight system-tagged content as instruction more heavily than the same words in an untagged or user-tagged position — a trained behavioral prior, not a labeling convention the API layer invented.
A colleague says adding five more few-shot examples can only help. How do you respond?
Each example costs real tokens against the context window and adds to attention's quadratic cost (Concept 07); format compliance from additional examples diminishes well before the window is full, so the right question is whether the next example still measurably changes the output, not whether there's room for it.
Why should retrieved context never be placed in the system role?
The system role carries trained instruction-following weight; placing retrieved, potentially untrusted text there would grant it authority a passage of evidence should never have — the same boundary that motivates prompt-injection defenses later in the course.
What's the difference between a prompt and a prompt template?
A prompt is one fully assembled input for a single model call; a template is the reusable, versioned structure — instruction, example slots, and role boundaries — that produces a new prompt each time it is filled with a live question and retrieved context.
