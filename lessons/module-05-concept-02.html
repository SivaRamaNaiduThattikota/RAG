MODULE 05 · CONCEPT 02

The inverted index.
Flip the mapping, skip the scan.

Concept 01 defined a corpus, a document, a query, and relevance — but built nothing. Parsing a document naturally gives you a forward index: document → the words it contains. An inverted index flips that mapping around: term → the sorted list of documents containing it, called a postings list. That flip is the entire idea, and it's why a query for one term never has to read a single document's text — it jumps straight to that term's postings list. No scoring, no ranking yet — this concept only builds the data structure and proves it beats a full scan.

2 CONCEPTS COMPLETED

PROGRESSIVE BEGINNER CORE

One flip, one data structure, one big speed-up

Everything in this concept follows from a single move: instead of asking "what words does this document contain?" (easy to produce while parsing, useless for search), ask "what documents contain this word?" — and precompute the answer for every word, once, before any query arrives.

01 · CONCEPT FIRST

Term → documents, not documents → terms

FORWARD INDEX

Document → its words. D8 → {boolean, search, over, an, inverted, index}. This is what parsing gives you for free — and it's the wrong direction for a query.

INVERTED INDEX

Term → the documents containing it. "index" → [D2, D4, D5, D8]. This is what a query actually needs — and it doesn't exist until you build it.

First memory: an inverted index is just the forward index, flipped and sorted by term instead of by document — a dictionary of terms, each pointing to a postings list of document IDs.
02 · WHY IT EXISTS

A query shouldn't have to read every document

Without an inverted index, answering "which documents contain the term index?" means opening every one of the corpus's N documents and scanning its full text for a match — work that repeats, from scratch, for every single query, even when the corpus never changed between queries. An inverted index pays that scanning cost exactly once, while the corpus is being ingested, and turns every future query for that term into a direct lookup — no document text touched at query time at all.

03 · CONCRETE EXAMPLE

The same eight-document corpus, indexed

Concept 01's corpus, unchanged. Tokenizing all eight documents and flipping the mapping produces this inverted index (partial — full table in Section 10):

"index" →

[D2, D4, D5, D8] — 4 documents, out of 8 total

"search" →

[D1, D3, D4, D5, D8] — 5 documents

"inverted" →

[D2, D4, D8] — 3 documents

"dense" →

[D1, D3, D6] — 3 documents

A query for "index" now costs one dictionary lookup plus reading a 4-entry list — never opening D1, D3, D6, or D7, whose text is completely irrelevant to that term and was never touched.

04 · TECHNICAL MECHANISM

Two moving parts: a dictionary, and postings lists

THE DICTIONARY

Every distinct term seen across the corpus, held in a structure that supports fast lookup (a hash table or sorted tree) — "does this term exist, and where is its list?"

THE POSTINGS LIST

For each term, a list of document IDs, kept in sorted order. Sorted order is not cosmetic — it's exactly what makes Section 06's merge algorithm work in one pass.

ANSWERING A SINGLE-TERM QUERY

Look up the term in the dictionary (fast), then return its postings list directly — no document text is read at query time.

ANSWERING A MULTI-TERM QUERY

Look up each term's postings list, then merge the sorted lists — intersect for AND, union for OR — walking each list with a pointer instead of comparing every pair.

06 · IMPORTANT DISTINCTIONS

Four pairs this concept depends on keeping separate

TermIs NOTWhy it matters
Inverted indexThe forward indexThe forward index (document → words) is what parsing produces; the inverted index (term → documents) is a deliberately built, separate structure — b01's flip.
TermA token, in generalThis concept treats "term" and "word" as interchangeable for a simple example; real systems apply tokenization rules (Module 02, Concept 02) before a word becomes an index term — not rebuilt here.
Postings listA relevance scoreA postings list only answers "does this document contain the term?" — it says nothing about how important that term is to the document. That starts at Concept 04's term frequency.
Boolean retrievalRanked retrievalThis concept's merge produces an unordered set of matching documents (in or out) — not a ranking. Ranking by relevance begins once term weighting exists, Concept 04 onward.
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"An inverted index also stores how relevant each document is."

A plain postings list only stores document IDs — no counts, no weights. Concept 04 adds term frequency as a separate number stored alongside each posting.

"Intersecting two postings lists means comparing every pair of entries."

That would be O(|A|·|B|). Because both lists are sorted, Section 06's two-pointer merge does it in O(|A|+|B|) — never re-comparing an entry twice.

"Building the index happens at query time, just like the lookup."

Index construction happens once, offline, during ingestion. Query time only ever does dictionary lookups and list merges — that split is the entire performance argument.

"This is how Module 04's vector retrieval works too, just with different data."

No — vector retrieval has no discrete terms to invert; it needs a geometric structure (approximate nearest-neighbor search, Module 09), a genuinely different mechanism, not a relabeled version of this one.

ORACLE TEXTAn inverted index, maintained by the database

Oracle Text builds and maintains exactly this term-to-document structure over stored text columns — the mechanism this concept just built by hand, running inside the database engine (Module 10, Concept 07, forward reference).

KEYWORD FILTERING IN TEXT-TO-SQLLIKE and CONTAINS lean on this structure

A generated SQL clause that filters rows by keyword is, underneath, a query against a database-maintained inverted index — this concept names the mechanism those SQL functions hide.

WHAT'S STILL MISSINGAny notion of ranking or weighting

This concept can only say "in" or "out" for a query term — Concepts 04-06 add the term-frequency and BM25 machinery needed to rank the "in" set by how relevant each document actually is.

09 · WHAT YOU SHOULD UNDERSTAND

Readiness check before moving on

The flip

Inverted index = term → sorted list of document IDs (a postings list) — the reverse of the forward index parsing naturally produces.

Why it's fast

Built once offline; every later query is a dictionary lookup plus a list read, never a full document scan.

The merge

Sorted postings lists intersect (AND) or union (OR) with a pointer walk in O(|A|+|B|), not a pairwise comparison.

What's not here yet

No term weights, no relevance scores, no ranking — this is Boolean retrieval only, membership in or out.

04
INTUITION

A book's index at the back, not its table of contents

A table of contents is a forward index: chapter → what it covers, in the order the book was written. The index at the back of a textbook is inverted: a term, alphabetically, followed by every page number where it appears. Nobody reads a textbook front to back looking for a term — they check the back index and jump straight to the listed pages. An inverted index is that back-of-the-book index, built for an entire corpus instead of one book, with the "page numbers" being document IDs instead.

Analogy boundaryA book's back index doesn't tell you which listed page is most important — neither does a plain postings list. That limitation carries over exactly, which is why Concept 04 exists.

06
MECHANISM

Building the index, then merging two postings lists

Tokenize every document — D1…D8 each become a set of terms (Concept 01's corpus, unchanged).
For each (document, term) pair, append the document ID to that term's list — the forward index, inverted one pair at a time.
Sort and deduplicate every term's list — postings("index") becomes [2, 4, 5, 8], ready for merging.
A query for "search" AND "inverted" arrives — look up both postings lists: [1,3,4,5,8] and [2,4,8].
Walk both lists with two pointers, i and j, starting at 0 — advance whichever pointer is behind; record a match when the values are equal.
Stop when either pointer runs off the end of its list — result = [4, 8], found in 6 comparisons, never opening a single document.

09
MATHEMATICS

Why the merge is O(|A|+|B|), not O(|A|·|B|) or O(N)

Using Module 04 Concept 09's own complexity notation, applied to this concept's mechanism for the first time:

brute_force_scan(N, L) = O(N · L) -- read every one of N documents, each of length L dictionary_lookup(t) = O(1) or O(log M) -- hash table or sorted tree over M vocabulary terms merge(A, B) = O(|A| + |B|) -- one pointer pass over two sorted postings lists, never O(|A|·|B|)

The merge is linear in the combined length of the two lists because each comparison advances at least one pointer, and neither pointer ever moves backward or revisits an index — a strict decrease in remaining work every single step, which is exactly why the loop is guaranteed to terminate within |A|+|B| steps.

11
CONCRETE USE

Two clean fits, a boundary case, a mistake

CLEAN FIT

Multi-keyword search over log files or tickets

"error" AND "timeout" over millions of support tickets is exactly Section 06's merge, at real scale — never opening a ticket that lacks either word.

CLEAN FIT

Filtering an Oracle Text or Elasticsearch query

A CONTAINS or match_phrase clause is answered by walking a database-maintained inverted index, not by scanning table rows.

BOUNDARY CASE

A term that appears in every document

If postings(t) = every document ID, intersecting with it changes nothing — the merge still runs correctly, it just does no useful narrowing (Section 16 names this directly).

MISTAKE TO AVOID

Assuming an unsorted postings list still merges in one pass

Section 09's O(|A|+|B|) bound relies entirely on both lists being sorted — an unsorted list forces re-scanning, losing the guarantee.

12
CODE

Building the index and merging, from scratch

PYTHON · NO LIBRARIES 
corpus = {
    1: "vector search over dense embeddings",
    2: "sparse retrieval with an inverted index",
    3: "dense embeddings for semantic search",
    4: "keyword search using an inverted index",
    5: "vector index for approximate search",
    6: "sparse and dense retrieval combined",
    7: "embeddings from a neural encoder",
    8: "boolean search over an inverted index",
}

def build_inverted_index(corpus):
    index = {}
    for doc_id, text in corpus.items():
        for term in set(text.split(" ")):          # set() avoids duplicate postings within one doc
            index.setdefault(term, []).append(doc_id)
    for term in index:
        index[term].sort()                          # sorted order is required by intersect() below
    return index

def intersect(postings_a, postings_b):
    i, j, result = 0, 0, []
    comparisons = 0
    while i < len(postings_a) and j < len(postings_b):
        comparisons += 1
        if postings_a[i] == postings_b[j]:
            result.append(postings_a[i])
            i += 1
            j += 1
        elif postings_a[i] < postings_b[j]:
            i += 1
        else:
            j += 1
    return result, comparisons

index = build_inverted_index(corpus)
assert index["search"] == [1, 3, 4, 5, 8]
assert index["inverted"] == [2, 4, 8]

result, comparisons = intersect(index["search"], index["inverted"])
assert result == [4, 8]
assert comparisons == 6

# Edge case: a term that appears in no document at all.
empty_result, empty_comparisons = intersect(index.get("summarization", []), index["search"])
assert empty_result == [] and empty_comparisons == 0
13
ECOSYSTEM

Where production systems run the identical structure

Apache Lucene (and the search engines built on it, like Elasticsearch and Solr) stores an inverted index per field, with postings lists that add positions and term frequencies alongside the bare document IDs this concept used. Oracle Text builds and maintains the same structure directly inside the database, queryable through SQL's CONTAINS operator (Module 10, Concept 07, forward reference). PostgreSQL's GIN indexes serve the identical purpose for full-text search columns. None of these change the core idea from Section 06 — they add compression, positions, and scoring on top of the same term-to-postings mapping.

16
DIAGNOSIS

Failure modes

USELESS TERM

A term whose postings list is nearly the whole corpus

Intersecting with a term everyone shares narrows almost nothing — the mechanism still works, but its filtering value depends on how selective the term actually is (a preview of Concept 04's idf, which quantifies exactly this).

VOCABULARY MISMATCH

The relevant document uses a different word entirely

A postings list can only ever be found by the exact term used to build it — a synonym or a paraphrase produces zero matches, a limitation dense retrieval (Concept 03) doesn't share.

UNSORTED POSTINGS

A postings list that isn't kept sorted

Breaks the two-pointer merge's correctness and its O(|A|+|B|) guarantee alike — Section 09's bound assumes sorted order, not just any order.

17
CORRECTION

Misconceptions

Incorrect beliefCorrection
"Inverted" means the documents are stored backwards or reversedFalse — "inverted" describes flipping the document→term mapping into a term→document one; nothing about a document's content is reversed.
Postings list order doesn't affect correctness, only speedFalse — Section 06's two-pointer merge produces a wrong or incomplete result on unsorted lists, not just a slower one.
An inverted index tells you how relevant a document is to a termFalse — a plain postings list encodes membership only; Concept 04 is the first concept to attach a relevance-related number to a posting.
18
REALITY

Production implications

  • Index construction is a batch cost paid during ingestion, amortized across every future query — the same trade this concept's b02 argument makes, now with a name: pay once, benefit on every subsequent lookup.
  • Postings lists at real scale (millions of documents) are compressed, not stored as plain integer lists, since storing every document ID in full is expensive at that size — a forward reference to Module 09's storage trade-offs, not solved by this concept.
  • Adding or removing a document means updating every postings list for every term that document contains — an update-cost concern with a direct analogue in Module 09, Concept 08 ("Updates, deletes and tombstones") for vector indexes.
19
RECALL

Knowledge check

What does an inverted index map, and in which direction?
Term → the sorted list of document IDs containing that term (a postings list) — the reverse of the document → words mapping parsing naturally produces.
Why must both postings lists be sorted for the two-pointer merge to work correctly?
Because the merge advances whichever pointer is behind and never revisits an entry — that only produces a correct intersection when both lists are in the same, consistent order (Section 09).
Does a postings list, on its own, tell you which matching document is most relevant?
No — it only encodes membership (in or out). Ranking by relevance requires term weights, which Concept 04 adds on top of this exact structure.

CAREER PRACTICE

Interview questions

Explain what an inverted index is to someone who has never heard the term, in under thirty seconds.
It's a lookup table built the opposite way from how you'd naturally read a document: instead of "this document contains these words," it stores "this word appears in these documents," so a search for a word jumps straight to its list instead of scanning every document.
Why is intersecting two sorted postings lists O(|A|+|B|) instead of O(|A|·|B|)?
Because a single pass with two pointers, each only ever advancing forward, is enough — comparing every pair would waste time re-checking relationships already resolved by sort order.
Write the pseudocode for intersecting two sorted lists with a two-pointer merge.
Initialize i=j=0; while both pointers are in range, compare a[i] and b[j]: if equal, record a match and advance both; if a[i] is smaller, advance i; otherwise advance j; stop when either pointer runs past the end of its list — Section 12's intersect() function is exactly this.
Design question: a colleague wants to skip building an inverted index and just grep every document at query time. When, if ever, is that a reasonable choice?
Only when the corpus is small enough, or queried rarely enough, that the full-scan cost per query is acceptable — Section 18's amortization argument only pays off once query volume or corpus size makes the one-time build cost worth it; for a handful of documents queried occasionally, a full scan can be entirely reasonable.
