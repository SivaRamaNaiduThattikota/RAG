PROGRESSIVE BEGINNER CORE

An interface is a promise about the caller, not about the vendor

This concept adds no new vendor and re-derives no fact from Concepts 01-13. What it adds is a boundary: one small contract -- upsert, query, delete -- that every store this module named can implement, so the code that calls a vector store never has to know or care which one is underneath. The promise is narrow on purpose: it covers exactly those three operations, and nothing about schema, indexing, or tenant isolation, because Concepts 11 and 12 already proved those three things don't share syntax across any two of these systems.

01 · CONCEPT FIRST

Three methods, one contract, three real bodies underneath

A store-agnostic interface names the operations a caller needs -- upsert(chunk_id, embedding), query(vector, tenant_id, k), delete(chunk_id) -- and says nothing about how any one system performs them. Concept 01 already cited a real version of exactly this idea: LangChain's own VectorStore abstract base class, with methods add_texts, similarity_search, and delete, "an abstraction other backends implement, not storage itself." This concept builds a smaller version of that same idea using this module's own three real systems -- Oracle, pgvector, Pinecone -- as the backends.

First memory: the interface is a promise about the caller's code. It says nothing about the vendor's schema, index, or tenant mechanism -- those stay the adapter's own problem, every single time.
02 · WHY IT EXISTS

Concept 13 chose a store. Nobody asked what a later change costs.

Concept 13's own framework picked Oracle for Profile A, Pinecone for Profile B, and Milvus for Profile C -- a real, defensible choice per workload. But every one of Concepts 05-12's own code examples called that system's real SDK directly from application code. If a Profile-B team's workload later needs Profile A's governance, or a startup outgrows Pinecone's own cost curve, every caller of the vector store has to be found and rewritten. An interface moves that risk into one place -- the adapter -- instead of scattering it through the whole codebase.

03 · CONCRETE EXAMPLE

The same three lines, three completely different real bodies

Caller code, unchanged regardless of which adapter is wired in: store.upsert("c007", embedding), then store.query(query_embedding, tenant_id="acme", k=5), then store.delete("c007"). Underneath, Oracle's adapter runs cursor.execute("insert into embeddings...", [...]) (Concept 08's own cited syntax); pgvector's adapter runs cur.execute("INSERT INTO embeddings... VALUES (%s, %s)", (...)) through psycopg, a real Python driver never cited in this course before now; Pinecone's adapter runs index.upsert(vectors=[...], namespace="acme") (Concept 12's own cited syntax). Three real bodies, one caller.

04 · TECHNICAL MECHANISM

The interface hides the call shape. It cannot hide the setup.

Each adapter satisfies the same three-method contract using that vendor's own real API, so the caller's three lines never change. But three things sit above and outside every adapter's method bodies, done once at setup time, not per call: the column/type declaration for the embedding itself (Oracle's VECTOR(384, FLOAT32), Concept 05; pgvector's vector(384), Concept 11; Pinecone's index-level dimension=384 parameter, Concept 12 -- not a column at all); the index that makes search fast (Oracle's CREATE VECTOR INDEX, Concept 06; pgvector's CREATE INDEX ... USING hnsw, Concept 11; Pinecone's ServerlessSpec(...), Concept 12 -- no DDL, fully managed); and the tenant-isolation mechanism (Oracle's DBMS_RLS.ADD_POLICY, Concept 10; pgvector's native CREATE POLICY, Concept 11; Pinecone's namespace argument, Concept 12). None of those three is a method on the interface. All three must be redone by hand, in that vendor's own real syntax, every time the adapter changes.

06 · IMPORTANT DISTINCTIONS

What the interface covers versus what it never touches

LayerWhat lives there
Interface (portable)Exactly three methods -- upsert, query, delete. Callable identically no matter which of the three real adapters is wired in.
Adapter (not portable)The real SDK call bodies (Section 12), plus the schema DDL, index DDL, and tenant mechanism (Section 04) -- rewritten from that vendor's own docs every time, never templated from another adapter.
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"An interface makes the whole system vendor-neutral."

Only the three named operations port. Schema, indexing, and tenant isolation were never part of the contract -- Section 04 names exactly three things that must be rewritten by hand for every new adapter, every time, with no shortcut the interface provides.

"Once one adapter is written, the next one is a quick copy."

Concept 12 already established zero shared syntax across four non-Oracle vendors. Each adapter is written from that vendor's own real documentation, the same way Concept 12 verified all four live -- not templated from a sibling adapter.

04
INTUITION

The interface is the part that stops moving

Every one of Concepts 05-12's own code examples called a real vendor SDK directly. That's fine for demonstrating what each vendor's own API looks like, which was those concepts' own job. It's a real liability if that same direct-call pattern is what application code actually ships with, because Concept 13 already showed three different real workloads landing on three different real winners -- meaning a real team's own store choice can legitimately change. An interface is the one piece of the system designed to not change when that happens: the caller keeps calling upsert/query/delete, and only the adapter underneath is swapped.

DIRECT SDK CALLS (Concepts 05-12's own examples)

Correct for showing one vendor's real syntax. A real liability if application code calls the vendor SDK directly everywhere, because every call site must be found and rewritten to switch vendors.

THIS CONCEPT'S INTERFACE

One contract, three adapters. Switching vendors means writing or swapping one adapter, not finding every call site in the application.

Scope noteThis concept does not claim its own three-method contract is the only correct shape for a retrieval interface -- LangChain's own real ABC has more methods than these three. It claims only that the same underlying idea, kept deliberately small, is enough to prove the point: the caller's code can stay fixed while the vendor underneath changes completely.

This concept's own three methods map directly onto those three real jobs, kept intentionally smaller so all three adapters below fit in one lesson.

CODE

All three adapters, in full

PYTHON · ORACLE ADAPTER (python-oracledb, Concepts 08-09's own cited syntax) 
import oracledb
import array

class OracleAdapter:
    def __init__(self, connection):
        self.connection = connection

    def upsert(self, chunk_id, embedding):
        cursor = self.connection.cursor()
        cursor.execute(
            "insert into embeddings (chunk_id, embedding) values (:1, :2)",
            [chunk_id, array.array("f", embedding)],
        )
        self.connection.commit()

    def query(self, vector, tenant_id, k):
        cursor = self.connection.cursor()
        cursor.execute(
            f"""
            SELECT c.chunk_id, VECTOR_DISTANCE(e.embedding, :qv, COSINE) AS dist
            FROM chunks c JOIN embeddings e ON e.chunk_id = c.chunk_id
            WHERE c.tenant_id = :tenant
            ORDER BY dist
            FETCH FIRST {k} ROWS ONLY
            """,
            qv=array.array("f", vector), tenant=tenant_id,
        )
        return cursor.fetchall()

    def delete(self, chunk_id):
        cursor = self.connection.cursor()
        cursor.execute("delete from embeddings where chunk_id = :1", [chunk_id])  # child first
        cursor.execute("delete from chunks where chunk_id = :1", [chunk_id])      # parent second
        self.connection.commit()
PYTHON · PGVECTOR ADAPTER (psycopg, real driver newly cited this session) 
import psycopg

class PgvectorAdapter:
    def __init__(self, conninfo):
        self.conn = psycopg.connect(conninfo)

    def upsert(self, chunk_id, embedding):
        with self.conn.cursor() as cur:
            cur.execute(
                "INSERT INTO embeddings (chunk_id, embedding) VALUES (%s, %s)",
                (chunk_id, str(embedding)),
            )
        self.conn.commit()

    def query(self, vector, tenant_id, k):
        with self.conn.cursor() as cur:
            cur.execute(
                """
                SELECT chunk_id, embedding <=> %s AS dist
                FROM embeddings
                WHERE tenant_id = %s
                ORDER BY dist
                LIMIT %s
                """,
                (str(vector), tenant_id, k),
            )
            return cur.fetchall()

    def delete(self, chunk_id):
        with self.conn.cursor() as cur:
            cur.execute("DELETE FROM embeddings WHERE chunk_id = %s", (chunk_id,))  # child first
            cur.execute("DELETE FROM chunks WHERE chunk_id = %s", (chunk_id,))      # parent second
        self.conn.commit()
PYTHON · PINECONE ADAPTER (Concept 12's own citations, plus one new delete citation) 
class PineconeAdapter:
    def __init__(self, index):
        self.index = index

    def upsert(self, chunk_id, embedding):
        self.index.upsert(
            vectors=[{"id": chunk_id, "values": embedding}],
            namespace="acme",
        )

    def query(self, vector, tenant_id, k):
        results = self.index.query(
            vector=vector, top_k=k, namespace=tenant_id, include_metadata=True,
        )
        return results.matches

    def delete(self, chunk_id):
        self.index.delete(ids=[chunk_id], namespace="acme")

All three classes satisfy the identical contract -- upsert(chunk_id, embedding), query(vector, tenant_id, k), delete(chunk_id) -- with three completely different real method bodies. The caller code from Section 10 works unmodified against any one of the three.

16
DIAGNOSIS

Failure modes

ASSUMED FULL PORTABILITY

A team swaps the Oracle adapter for Pinecone and expects a zero-work migration

Cause: believing the interface makes the whole system vendor-neutral. Fix: Section 04's own three things -- schema, index, tenant mechanism -- were never part of the contract. Pinecone's own ServerlessSpec setup and namespace-based tenancy must be configured by hand, same as if no interface existed.

COPIED A FILTER ACROSS ADAPTERS

A team writes the pgvector adapter's WHERE tenant_id = %s clause inside the Pinecone adapter's query method

Cause: assuming the tenant check is portable because both adapters satisfy the same interface method. Fix: Pinecone's real mechanism is the namespace= argument (Concept 12) -- there is no WHERE clause to write, and passing one is simply not part of Pinecone's own real API.
