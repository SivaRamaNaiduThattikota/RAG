MODULE 08 · CONCEPT 01

Module 07 used the mechanism
without ever naming it. Here it is.

Six different Module 07 concepts hand-built a small vocabulary, hand-picked coordinates, and ran cosine similarity over the result -- without ever saying what that mechanism actually was, or why geometric proximity should mean anything semantically. An embedding is a learned dense vector representation of an input, positioned in a continuous space so that geometric proximity approximates semantic similarity. The word that matters most in that sentence is "learned" -- every one of Module 07's own vectors was hand-assigned, not learned, and this concept makes that distinction numeric on a 5-word vocabulary: a hand-built one-hot model ties every pair at exactly cosine 0.0000, always. A learned-style model instead gives kitten-cat=0.9945 and car-truck=0.9903 -- and every single nearest-neighbor answer is the semantically sensible one.

01 · CONCEPT FIRST

A vector whose coordinates came from training, not typing

THIS CONCEPT

An embedding is a learned dense vector representation of an input (word, chunk, query -- anything), positioned in a continuous space so geometric proximity approximates semantic similarity.

NOT THIS CONCEPT

How text actually becomes a vector mechanically (Concept 02), bi-encoders/asymmetric query-vs-document embeddings (Concept 03), contrastive training (Concept 04), pooling (Concept 06) -- all named forward only.

First memory: "learned, not hand-built" is the one fact this concept exists to establish.
02 · WHY IT EXISTS

Module 07 leaned on the mechanism without naming it

Module 07 (Concepts 01, 04, 05, 07, 08, 09, by name) used informal toy vector models the whole way through -- hand-picked topic axes, bag-of-words counts -- without ever saying what an embedding formally is or why its geometry should mean anything. Module 05 Concept 11 already proved lexical/exact-term matching hits a hard wall at vocabulary mismatch: a fixed, hand-built representation has no way to generalize past exact wording. This concept names the general fix: don't hand-build the representation, learn it.

03 · CONCRETE EXAMPLE

Same three words, same formula, one number versus three

Three words (cat, dog, car). Hand-built one-hot model: cosine(cat,dog) = cosine(cat,car) = cosine(dog,car) = 0.0000, every pair, always. Illustrative learned-style model (verified, not real published word2vec numbers): cosine(cat,dog) = 0.9272, cosine(cat,car) = 0.1564, cosine(dog,car) = 0.5150. Same words, same cosine formula (Module 04 Concept 03, unchanged) -- only the source of the coordinates differs.

04 · TECHNICAL MECHANISM

Outcome and contrast only -- not the training procedure itself

An embedding is a vector in a fixed-size space (dimension set by the model, named forward to Concept 06) whose coordinates are set by a training procedure that optimizes some objective over data -- not typed in by a person. This concept does not derive that training procedure; Concept 04 (contrastive learning) does. Here only the OUTCOME (learned coordinates) and the CONTRAST (versus hand-built) matter.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"A hand-built vector with enough dimensions is basically an embedding."

False -- dimensionality isn't the distinguishing property; the SOURCE of the coordinates is.

"Geometric closeness always means semantically similar."

False in general -- it's an approximation the training objective aims for, not a guarantee (Concept 07 covers where it breaks).

"Embeddings replace cosine similarity/dot products with something new."

False -- Module 04's exact same formulas apply unchanged; only what's being compared is new.

MECHANISM

Two lanes: who assigns the coordinates

HAND-BUILT LANE

A person or a fixed rule assigns each item's vector directly -- one-hot, hand-picked topic axes, bag-of-word counts.

LEARNED LANE

A model's parameters are fit against data by a training objective so the resulting vector positions correlate with a target notion of similarity -- the objective itself is Concept 04's job, not derived here.

10
WORKED EXAMPLE

The full 5-word, 10-pair matrix

Vocabulary: kitten, cat, dog, car, truck. Hand-built one-hot (R^5): each word a unique standard basis vector -- cosine(any two distinct words) = 0/(1×1) = exactly 0.0000, for all 10 pairs, by construction (two distinct standard basis vectors have zero dot product by definition).

Learned-style (illustrative 2D unit vectors, NOT real published word2vec/GloVe numbers -- an explicitly labeled simplified stand-in, in the same spirit as Module 07 Concept 01's own illustrative topic vectors): kitten=8°, cat=14°, dog=36°, car=95°, truck=103°.

Nearest neighbor by cosine, per word: kitten→cat (0.9945), cat→kitten (0.9945), dog→cat (0.9272), car→truck (0.9903), truck→car (0.9903) -- every nearest-neighbor answer is semantically sensible, and the two clusters {kitten,cat,dog} vs. {car,truck} separate cleanly (all cross-cluster cosines ≤0.5150, all within-cluster cosines ≥0.8829). kitten–truck even goes slightly negative (−0.0872): geometric proximity can express dissimilarity, not just weaker similarity, once vectors aren't restricted to hand-built non-negative basis vectors.

VERIFICATION: computed once via an explicit 2D dot-product/norm cosine function applied to unit vectors at each angle, then independently cross-checked via a second, differently-coded formula applying the trigonometric angle-difference identity cos(θ_a − θ_b) directly on the raw angles, bypassing vector construction entirely -- every one of the 10 pairs matched to 4-5 decimal places between the two methods. The one-hot model's 0.0000 result was confirmed the same way, and is also algebraically guaranteed.

12
CODE

One-hot vs. learned, from scratch

PYTHON · REUSES MODULE 04'S OWN COSINE FORMULA 
import math

def cosine(u, v):
    dot = sum(a * b for a, b in zip(u, v))
    nu = math.sqrt(sum(a * a for a in u))
    nv = math.sqrt(sum(a * a for a in v))
    return dot / (nu * nv) if nu and nv else 0.0

def one_hot(index, dim=5):
    v = [0] * dim
    v[index] = 1
    return v

def learned_vec(angle_deg):
    r = math.radians(angle_deg)
    return [math.cos(r), math.sin(r)]

ANGLES = {"kitten": 8, "cat": 14, "dog": 36, "car": 95, "truck": 103}
ONEHOT = {"kitten": 0, "cat": 1, "dog": 2, "car": 3, "truck": 4}

assert round(cosine(one_hot(ONEHOT["cat"]), one_hot(ONEHOT["dog"])), 4) == 0.0
assert round(cosine(learned_vec(ANGLES["kitten"]), learned_vec(ANGLES["cat"])), 4) == 0.9945
assert round(cosine(learned_vec(ANGLES["car"]), learned_vec(ANGLES["truck"])), 4) == 0.9903

TensorFlow's word-embeddings guide states plainly that embedding coordinates are "learned during training" and are dense, versus a hand-built/one-hot sparse vector.

REALITY

Production implications

  • Real embedding models are trained artifacts with a version and a fixed dimensionality that downstream schema/index code must match exactly (named forward to Concept 11's versioning/drift and Module 10's schema design).

19
RECALL

Knowledge check

Why can one-hot vectors never encode meaning, regardless of dimension count?
The assignment rule never looked at what the words mean -- each word just gets a unique, orthogonal basis vector. Adding more dimensions only adds more orthogonal directions; it never introduces the semantic signal the rule was never designed to capture.
Why is "learned" the operative word here, not "vector" or "dense"?
A vector can be hand-built and still dense (this concept's own learned-style 2D example is dense too). What actually determines whether something is an embedding is whether its coordinates came from a training process fit to data, versus being manually assigned.
What do Module 04's cosine/dot-product formulas need to change to work with real embeddings?
Nothing -- the exact same formulas apply unchanged. Only the object being plugged into them is new (a vector with learned, rather than hand-assigned, coordinates).

23
CAREER PRACTICE

Interview questions

Conceptual: what makes a vector an embedding rather than just a vector?
Whether its coordinates were produced by a training process fit to data (an embedding) versus manually assigned by a person or a fixed rule (just a vector) -- dimensionality and density are not the distinguishing property.
Mathematical: state the formal v=f(x) vs. g(x) contrast.
An embedding is v = f(x) where f's parameters θ are learned (fit to data). A hand-built representation is v = g(x) where g's mapping is manually specified. The same downstream formulas (cosine, dot product) apply to both -- only the source of f versus g differs.
Coding: implement the one-hot vs. learned cosine comparison.
A shared cosine(u,v) helper, an one_hot(index, dim) generator producing orthogonal basis vectors, and a learned_vec(angle) generator producing unit vectors from an angle -- Section 12 gives the full from-scratch implementation with matching asserts.
Debugging: a "semantic search" demo behaves like exact-match. What's the first thing to check?
Whether the representation is actually learned, or secretly one-hot/keyword-based underneath a semantic-sounding name -- a hand-built representation ties everything that doesn't share an exact token, exactly like this concept's own one-hot result.
System design: how would you verify a vendor's "embedding model" is actually learned and not a dressed-up keyword index?
Feed it two texts with no shared vocabulary but identical meaning (a paraphrase pair) and check the similarity score is meaningfully above zero -- a hand-built/keyword-based system will score it at or near zero, the same failure mode this concept's own one-hot model demonstrates.
