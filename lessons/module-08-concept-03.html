MODULE 08 · CONCEPT 03

Same encoder, two separate calls.
They only ever meet at cosine.

Concept 02 walked one piece of text through a real four-stage forward pass. This concept is the first to put two texts through it: a query and a document, each embedded completely independently, with zero attention computed between a query token and a document token. That independence -- and the single similarity score where the two vectors finally meet -- is what a bi-encoder is. A cross-encoder, named forward only to Module 16, instead reads both texts jointly in one pass. This concept also previews, without teaching the full mechanics yet, that some real models change the QUERY'S input text before embedding it -- a small prepended string, the same mechanical move Module 07 Concept 09 already proved shifts a vector.

01 · CONCEPT FIRST

Separate calls, one score at the end

THIS CONCEPT

A bi-encoder embeds a query and a document SEPARATELY, through the exact same encoder from Concept 02, meeting only at Module 04 Concept 03's cosine similarity. A cross-encoder (named forward only, Module 16 Concept 09) instead embeds them JOINTLY in one pass, letting every query token attend to every document token directly.

NOT THIS CONCEPT

Contrastive training -- HOW the encoder's parameters get learned (Concept 04); pooling strategy (Concept 06); the full mechanics of which real prefixes exist and why (Concept 08).

First memory: same encoder, two separate calls, one similarity score at the end -- that's a bi-encoder.
02 · WHY IT EXISTS

Retrieval compares one query against many documents

A cross-encoder's joint pass can't be precomputed -- it needs both texts present at the same time, so scoring an entire corpus against one query would mean re-running the whole encoder once per document, every single query. Sentence-BERT's own abstract states the real cost of that: finding the closest pair among just 10,000 sentences needs "about 50 million inference computations (~65 hours)" with a BERT cross-encoder, cut to "about 5 seconds" once a bi-encoder's embeddings are precomputed and compared with cosine similarity.

03 · CONCRETE EXAMPLE

"Order late" finds "The order shipped late," not "Refund policy updated"

Query "order late" and Concept 02's own document "The order shipped late" are embedded completely independently, using the identical four-stage pipeline -- and land at cosine 0.9998. The same query against a new, unrelated document "Refund policy updated" lands at cosine -0.9504. Neither document's vector was ever computed WITH the query present.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"A bi-encoder must be two different models."

False -- it's the same encoder, called twice, on different input text.

"Cross-encoders are just slower bi-encoders."

False -- they're structurally different. A cross-encoder produces no separate, precomputable vectors at all.

"The query prefix is one exotic model's quirk."

False -- E5 and BGE use two genuinely different real conventions (Section 13), which is why Concept 08 exists as its own topic.

09 · WHAT YOU SHOULD UNDERSTAND

Readiness check before moving on

Recite what's separate vs. shared in a bi-encoder

The encoder function is shared (identical weights, called twice); the two forward passes and their input tokens are separate; only the final cosine step ever combines them.

Explain why a cross-encoder's score can't be precomputed

It needs both texts present in the same forward pass -- there's no per-document vector to store ahead of time.

State what an asymmetric prefix changes and doesn't change

Changes the input text fed to the encoder; the encoder itself stays identical.

Teach-back questions

  1. Why can a bi-encoder's document vectors be computed overnight, in bulk, before any query exists?
  2. What's the one and only place a query vector and a document vector ever interact?
  3. If E5 prepends "query: " to queries and "passage: " to passages, is that two models or one?

04
INTUITION

Two clerks, reading separately vs. discussing together

A bi-encoder is like two clerks each reading their own copy of a note separately, then comparing summaries afterward. A cross-encoder is like two clerks discussing the same note together in one room before giving a single verdict.

Analogy boundaryThe clerks explain the SHAPE of the difference -- separate reads vs. a joint discussion. They don't state the actual arithmetic; Section 10 gives that precisely.

09
MATHEMATICS

sim(q,d) = cos(f(q), f(d)), f applied twice

sim(q,d) = cos(f(q), f(d)), where f is the SAME function -- Concept 02's tokenize → embed → contextualize → pool pipeline -- applied independently to each side
score(q,d) = g([q;d]) -- a cross-encoder processing the concatenated sequence jointly (named, not derived)

No new formula is introduced beyond Module 04 Concept 03's own cosine and Concept 02's Attention(Q,K,V), both reused unchanged. The only new fact is WHERE the two independently-produced vectors interact: once, at cos(·,·), and nowhere else.

CONCRETE USE

A clean fit, a boundary case, and a mistake

CLEAN FIT

A production retrieval system precomputing millions of document vectors overnight

Then embedding each incoming query once at request time, comparing against the stored set with cosine.

BOUNDARY CASE

A corpus small enough to score entirely with a cross-encoder

Named forward to Module 16 Concept 08, "Candidate generation versus reranking" -- feasible only when the document count stays small.

MISTAKE TO AVOID

Feeding a real E5/BGE-style prefix to a symmetric model never trained on that convention

Previewing, not teaching, Concept 08's territory -- an untrained model has no reason to benefit from a prefix it never saw during training.

CODE

The same pipeline, called twice, compared once

PYTHON · REUSES CONCEPT 02'S EXACT FUNCTIONS UNCHANGED 
import math

def tokenize(text):
    return text.lower().rstrip(".").split()

def dot(u, v):
    return u[0] * v[0] + u[1] * v[1]

def softmax(xs):
    m = max(xs)
    exps = [math.exp(x - m) for x in xs]
    s = sum(exps)
    return [e / s for e in exps]

def attention_contextualize(tokens, embed, d_k=2):
    scale = math.sqrt(d_k)
    out = {}
    for ti in tokens:
        scores = [dot(embed[ti], embed[tj]) / scale for tj in tokens]
        weights = softmax(scores)
        cx = sum(w * embed[tj][0] for w, tj in zip(weights, tokens))
        cy = sum(w * embed[tj][1] for w, tj in zip(weights, tokens))
        out[ti] = (cx, cy)
    return out

def pool_mean(vectors):
    n = len(vectors)
    return (sum(v[0] for v in vectors) / n, sum(v[1] for v in vectors) / n)

def embed_bi_encoder(text, embed):
    """Thin wrapper -- just calls Concept 02's pipeline. No shared attention
    step ever runs between two separate embed_bi_encoder() calls."""
    tokens = tokenize(text)
    contextualized = attention_contextualize(tokens, embed)
    return pool_mean(list(contextualized.values()))

def cosine(u, v):
    dp = dot(u, v)
    nu = math.sqrt(dot(u, u))
    nv = math.sqrt(dot(v, v))
    return dp / (nu * nv)

DOC_EMBED = {"the": (0.10, 0.10), "order": (2.00, 0.40),
             "shipped": (1.80, 1.90), "late": (0.30, 2.10)}
QUERY_EMBED = {"order": (2.00, 0.40), "late": (0.30, 2.10)}
IRRELEVANT_EMBED = {"refund": (-1.60, 0.50), "policy": (-0.40, -1.50),
                     "updated": (0.60, -1.70)}

doc1Vec = embed_bi_encoder("The order shipped late.", DOC_EMBED)
q1Vec = embed_bi_encoder("order late", QUERY_EMBED)
doc2Vec = embed_bi_encoder("refund policy updated", IRRELEVANT_EMBED)

assert round(doc1Vec[0], 4) == 1.3842 and round(doc1Vec[1], 4) == 1.5025
assert round(q1Vec[0], 4) == 1.1292 and round(q1Vec[1], 4) == 1.2708
assert round(doc2Vec[0], 4) == -0.4077 and round(doc2Vec[1], 4) == -0.9372
assert round(cosine(q1Vec, doc1Vec), 4) == 0.9998
assert round(cosine(q1Vec, doc2Vec), 4) == -0.9504

ECOSYSTEM

Real siamese structure, and two real asymmetric conventions

Sentence-BERT's abstract is cited here for a different part of the same paper Concept 02 used (which drew only on Section 3's architecture description): the abstract's own siamese/bi-encoder structure claim and its cross-encoder-cost figure -- finding the closest pair among 10,000 sentences needs "about 50 million inference computations (~65 hours)" with BERT, cut to "about 5 seconds" with SBERT's "siamese and triplet network structures" plus cosine similarity. E5-base's model card shows the real asymmetric-prefix convention: its usage examples prepend "query: " to the search query and "passage: " to every candidate passage before calling the same encoder. BGE-large-en-v1.5's model card shows a genuinely different real convention: its usage examples prepend the instruction "Represent this sentence for searching relevant passages: " to queries ONLY -- passages get no prefix at all. Two real models, two different asymmetric rules -- proof the pattern is model-specific, not one fixed convention (full mechanics deferred to Concept 08).

DIAGNOSIS

Failure modes

MISMATCHED CHECKPOINTS

Using different encoder checkpoints for query vs. document

Breaks the "same function" assumption entirely -- the two vector spaces are no longer comparable.

WRONG OR ONE-SIDED PREFIX

Feeding a real model's expected prefix to only one side, or the wrong prefix

Mechanically changes the token sequence and hence the vector in an untrained, unpredictable way -- Concept 08 covers the correct convention per model.

18
REALITY

A real latency-budget asymmetry

  • Precomputing document embeddings is a one-time or incremental (Module 06 Concept 09) batch job -- it can run overnight, in bulk, with no user waiting.
  • Query embedding must happen synchronously, on every request -- there's no way to precompute a query nobody has typed yet.
  • SBERT's own figures make the scale of this concrete: ~65 hours of cross-encoder computation to search 10,000 sentences once, vs. ~5 seconds with a bi-encoder's precomputed embeddings -- the same asymmetry, at corpus scale.
19
RECALL

Knowledge check

Why can't a cross-encoder's score be precomputed?
It needs both the query and the document tokens present in the same forward pass, with cross-attention between them -- there's no per-document vector that exists independently of a specific query, so nothing can be stored ahead of time.
What changes and what stays the same when a query prefix is added?
The input TEXT changes (an extra token like "query: " is prepended before tokenization), which changes the token sequence and therefore the pooled vector. The encoder itself -- its weights, its architecture -- stays exactly the same.
Why did "order" and "late" get different contextualized vectors in the query vs. the document?
Because contextualization depends on every other token in the same sequence -- "order" in a 2-token query only has "late" to attend to, while "order" in the 4-token document also has "the" and "shipped" nearby, producing a different weighted blend each time.

CAREER PRACTICE

Interview questions

Conceptual: why can bi-encoder document vectors be precomputed but not cross-encoder scores?
A bi-encoder produces one vector per document independently of any query, so it can be computed and stored ahead of time. A cross-encoder's score is a function of the query AND the document together -- it doesn't exist until both are known, so nothing can be precomputed.
Mathematical: write sim(q,d)=cos(f(q),f(d)) and state what f is.
f is Concept 02's four-stage forward pass -- tokenize, embed, contextualize, pool -- applied independently to the query text and to the document text. The two resulting vectors are compared with Module 04 Concept 03's cosine similarity.
Coding: implement embed_bi_encoder and call it on two independent token lists.
embed_bi_encoder(text, embed) tokenizes, runs attention_contextualize, and pool_means the result -- Section 12 gives the full implementation, called once on a query string and once on a document string with no shared attention step between the two calls.
Debugging: a retrieval system's scores look randomly shuffled after a model upgrade. What's the first thing to check?
Whether the query side and document side are using a matching prefix convention -- an upgrade that introduces or changes an expected prefix on only one side will silently shift vectors in an untrained, unpredictable direction.
System design: how would you verify a vendor's embedding endpoint is actually a bi-encoder and not secretly cross-encoding?
Send a batch of query+passage pairs and check whether embedding a document ever changes when paired with a different query -- a true bi-encoder's document vector is fixed regardless of which query it's later compared against; a hidden cross-encoder's score would depend on the pairing itself.
