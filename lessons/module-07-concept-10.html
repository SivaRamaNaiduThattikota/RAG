MODULE 07 · CONCEPT 10

Nine choices made.
Now measure whether any of them worked.

Concepts 02 through 09 each picked or fixed something about how chunks get built. This concept builds nothing new. It asks a plainer question: given a chunking scheme -- any combination of those nine choices -- how do you actually know it's good? Three checks answer it on one fixed scheme, applied uniformly across a fresh 3-passage corpus: does the answer even fit inside a retrievable chunk (fact coverage), does retrieval actually surface that chunk for a real query (recall@k), and what did the scheme cost along the way (a combined accounting of every cost axis this module has priced). The twist is in the second check: the exact same corpus, same scheme, same 9 chunks score a perfect 100%/100% recall on queries phrased like the source text -- and collapse to 33.3%/66.7% on paraphrased queries asking for the identical thing.

01 · CONCEPT FIRST

Grading a scheme, not building a new one

THIS CONCEPT

Three independent empirical checks against ONE fixed chunking scheme: fact coverage (can the answer ever be found), recall@k (does retrieval actually surface it), and cost (what did this scheme cost across every axis Concepts 04/06/07/08 already priced).

NOT THIS CONCEPT

Introducing a tenth chunking method. Every technique used here already exists from Concepts 02-09.

First memory: a scheme isn't good or bad in the abstract -- it's only as good as the query set it's actually measured against.
02 · WHY IT EXISTS

Intuition alone already failed once

Concept 06's own 40%→50% overlap regression already proved that intuition alone can't be trusted to say whether a chunking choice helps. Only measurement catches this -- and the measurement itself has to be trustworthy, or it just replaces one bad guess with another.

03 · CONCRETE EXAMPLE

One scheme, three passages, a perfect score that isn't

Three short Oracle Order Management passages (P1 reused verbatim from Concept 06, P2 and P3 new), each holding one target fact, all chunked the same way: fixed-size, N=100 characters, 0% overlap -- Concepts 02/06's own baseline. Fact coverage: 2 of 3 facts land fully inside one chunk (66.67%). For 3 queries phrased close to the source text, recall@1 = recall@3 = 100%. For 3 paraphrased queries asking the exact same thing in different words, recall@1 drops to 33.3% and recall@3 to 66.7% -- same corpus, same chunks, same scheme, only the wording changed.

06 · IMPORTANT DISTINCTIONS

Three orthogonal axes, not one score

CheckWhat it does NOT tell you
Fact coverageWhether retrieval will actually FIND the chunk that contains the fact -- containment and retrievability are different questions
Recall@kWhat the scheme cost to build and index -- a scheme can retrieve perfectly and still be expensive
Cost accountingWhether the scheme actually answers real queries -- cheap and wrong is still wrong
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"A scheme that scores well on my test queries is good."

False if those queries were written to match the chunking scheme you already chose -- this concept's own central point.

"High fact-coverage guarantees retrieval will find it."

False -- P2 and P3's facts are fully contained, yet a badly-worded query (Q3') can still miss the right chunk entirely.

"Cheaper is always better, or pricier is always better."

False -- the cost table is four independent axes, not one ranking. Late chunking's real gain (Concept 08) wouldn't even help this corpus's actual failure.

09
MATHEMATICS

Recall@k and fact-coverage, stated precisely

recall@k = (queries where correct_chunk ∈ top_k(ranked_chunks)) / total_queries
fact_coverage = (facts where contains_fact(chunk_fixed(passage), fact) is true for some chunk) / total_facts

recall@k matches LlamaIndex's own Recall/HitRate metric definition (expected_ids vs. retrieved_ids); fact_coverage reuses Concept 06's own contains_fact()/chunk_fixed() functions unchanged.

CODE

Recall@k and fact-coverage, from scratch

PYTHON · REUSES CONCEPT 06'S OWN FUNCTIONS 
# chunk_fixed() and contains_fact() are Concept 06's own functions, reused unchanged.
def fact_coverage(passages_and_facts):
    hits = sum(1 for text, fact_start, fact_end in passages_and_facts
               if contains_fact(chunk_fixed(text, 100, 100), fact_start, fact_end))
    return hits / len(passages_and_facts)

def tokenize(text, stopwords):
    words = text.lower().replace("-", " ").split()
    return {w.strip(".,?!") for w in words if w.strip(".,?!") not in stopwords}

def cosine_overlap(a, b):
    if not a or not b:
        return 0.0
    return len(a & b) / (len(a) * len(b)) ** 0.5

def recall_at_k(queries, chunks, k):
    hits = 0
    for query_tokens, correct_id in queries:
        scored = sorted(chunks.items(), key=lambda kv: -cosine_overlap(query_tokens, kv[1]))
        top_k_ids = [cid for cid, _ in scored[:k]]
        if correct_id in top_k_ids:
            hits += 1
    return hits / len(queries)

# Reproduces this concept's own Section 10 result
P1 = "Oracle Order Management lets a customer cancel an order within a fixed period after purchase. The order-cancellation grace period is 14 days from the ship date. Once it elapses, the order status locks to CLOSED and refunds stop processing automatically. Support agents must file a manual override."
P2 = "Oracle Order Management issues a prepaid return shipping label once a customer opens a return request. The label must be used to ship the item back within 21 days of issuance. Returns received after that window are rejected and the original order remains billed in full."
P3 = "Oracle Order Management assigns every support ticket a priority level based on order value and customer tier. Tickets above priority level three are routed to a senior queue automatically. A senior queue ticket receives its first response within two business hours of assignment."
passages_and_facts = [
    (P1, 94, 160),   # NOT contained -- crosses the C11/C12 boundary
    (P2, 103, 175),  # contained inside C22
    (P3, 110, 188),  # contained inside C32
]
assert round(fact_coverage(passages_and_facts), 4) == 0.6667

ECOSYSTEM

The real metric library, and where full evaluation frameworks live

LlamaIndex's retrieval-metrics source confirms HitRate, MRR, and Recall classes computed from expected_ids vs. retrieved_ids -- the production-grade counterpart of this concept's own recall@k check. RAGAS ("Automated Evaluation of Retrieval Augmented Generation") is named forward to Module 18's evaluation-framework concept -- it grounds the point that a chunking scheme's measured quality is only as good as the test-query set it's measured against. Train/validation/test methodology grounds the general discipline point: a scheme that looks good against the data used to tune it can still fail against data from a different distribution -- exactly what the primary-vs-paraphrased split demonstrates.

DIAGNOSIS

Failure modes

SOURCE-PHRASED QUERIES ONLY

Testing only on queries that echo the source text

Produces an inflated recall score that collapses the moment real users paraphrase.

CONTAINMENT MISTAKEN FOR SUFFICIENCY

Treating fact-coverage as if it guaranteed retrievability

A contained fact can still be missed by a poorly-matching query -- two different failure surfaces.

WRONG COST-TABLE ROW

Fixing the wrong axis because the failure was misdiagnosed

19
RECALL

Knowledge check

Why is fact coverage not the same question as retrievability?
Fact coverage asks whether the answer CAN structurally exist inside a single retrievable chunk. Retrievability asks whether an actual query will surface that chunk. P2 and P3's facts are both fully contained, yet Q3′ still misses P3's chunk entirely -- containment doesn't guarantee a matching query will find it.
Why does Q1′ tie all 9 chunks at cosine 0.0000?
The word "cancellation" never survives as a whole token anywhere in the corpus -- P1's own chunk boundary splits it mid-word into "der-cancellation," and Q1′'s paraphrased wording shares no other content word with any chunk. Zero vocabulary overlap means zero cosine score for every chunk.
Why would spending on overlap or parent-child indexing not fix this concept's own measured recall drop?
The paraphrased-query failures (Q1′, Q3′) are vocabulary-mismatch problems -- the correct words simply don't appear in the query. Overlap and parent-child indexing both fix boundary/context problems, not lexical mismatch, so neither would move these specific scores.

CAREER PRACTICE

Interview questions

Conceptual: why isn't a single "chunking quality score" enough?
Fact coverage, recall@k, and cost each catch a different failure mode -- a scheme can be cheap and comprehensive yet still fail real queries, or expensive and precise yet cover almost no real facts. Collapsing them into one number would hide which axis actually failed.
Mathematical: define recall@k and fact-coverage precisely.
recall@k = (queries where the known-correct chunk appears in the top k ranked results) / total queries. fact_coverage = (facts fully contained in some single chunk, via Concept 06's contains_fact/chunk_fixed) / total facts.
Coding: implement recall_at_k reusing an existing cosine-overlap scorer.
Rank all chunks by cosine-overlap score against the query, take the top k chunk ids, and check whether the query's known-correct chunk id is among them -- Section 12 gives the full implementation.
Debugging: a chunking scheme scores 95% recall in testing but users report frequent misses. What's the likely cause?
The test query set was probably phrased close to the source text -- exactly this concept's own primary-vs-paraphrased gap. Re-test against a held-out set of real, paraphrased user queries before trusting the 95% figure.
System design: how would you build a repeatable chunk-quality evaluation pipeline?
Maintain a versioned test-query set with known-correct chunk ids (refreshed periodically as usage drifts), run fact-coverage and recall@k against it on every chunking-scheme change, and tabulate the relevant cost axes before committing to any fix -- diagnosing which check failed before spending on a mitigation.
