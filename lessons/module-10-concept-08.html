MODULE 10 · CONCEPT 08

SQL was never the missing piece.
A program that can send it, was.

Concepts 03 through 06 wrote real Oracle SQL by hand: five tables, a real VECTOR(384, FLOAT32) column, a real VECTOR_DISTANCE query, a real vector index. None of it runs by itself. This concept adds the missing layer -- python-oracledb, the driver that turns a Python value into a bind variable, sends it to Oracle, and turns the rows that come back into Python values again. Three real facts anchor it: connections default to Thin mode, VECTOR columns bind through array.array() objects, and nothing is durable until you call commit().

01 · CONCEPT FIRST

The layer between the lesson and the database

python-oracledb is Oracle's own Python driver. It opens a connection, carries bind values from Python into a SQL statement, and carries rows back out. Everything Concepts 03-06 wrote as SQL text becomes runnable through exactly three objects: a Connection, a Cursor, and a bind value.

First memory: connect() opens the door, cursor() gives you a hand to pass things through it, execute() sends the SQL and the values, and nothing is saved until commit().
02 · WHY IT EXISTS

A VECTOR value is not a normal Python value

Binding a string or a number into SQL is old, well-understood territory. A VECTOR column is not old territory -- it is a typed array Oracle stores in one of four formats (Concept 05). python-oracledb has to know a Python value is meant to become a VECTOR bind, and that mapping is not automatic for every Python type. This concept exists to show exactly which Python types map cleanly and which don't.

03 · CONCRETE EXAMPLE

Binding this course's own chunk

Concept 03's dataset has a real chunk, chk_9f21_2_03 ("To reset a vendor account, an admin must..."). In Python: vector_data = array.array("f", [0.6, 0.8, 0.0]) then cursor.execute("insert into embeddings (chunk_id, embedding) values (:1, :2)", ["chk_9f21_2_03", vector_data]). That's a real array.array object, per python-oracledb's own documentation, standing in for the real 384-dimension embedding -- shrunk to 3 dimensions here so the numbers can be checked by hand.

04 · TECHNICAL MECHANISM

execute() takes the SQL and the values together

One call does the work: cursor.execute(sql_text, bind_values). Named binds (:query_embedding) or positional binds (:1, :2) both work; python-oracledb matches them to the values you pass. Rows come back through the same cursor -- iterate it directly, or call cursor.fetchall() once all rows fit in memory.

05 · ARCHITECTURE / FLOW

Nothing is saved until you say so

INSERT sent, row exists in this transaction only→ connection.commit() — now durable→ or connection.rollback() — discarded, as if it never ran

Per python-oracledb's own transaction-management documentation (already cited in Concept 02): "By default, python-oracledb does not commit this transaction to the database." An INSERT that runs without a following commit() is not an error -- it is just not saved yet.

06 · IMPORTANT DISTINCTIONS

array.array is not a Python list

Python valueWorks as a VECTOR bind in Thin mode?
array.array("f", [0.6, 0.8, 0.0])Yes -- the documented Thin-mode bind type for a FLOAT32 vector column.
[0.6, 0.8, 0.0] (plain Python list)Not the documented bind type -- fetched rows can be converted to a list with an output type handler, but that is the read side, not the write side.
numpy.array([0.6, 0.8, 0.0], dtype=numpy.float32)Only after an input type handler converts it to array.array first.
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"A Python list of floats is a fine VECTOR bind value."

Not in Thin mode. python-oracledb's own documentation binds VECTOR columns with array.array() objects; a plain list is not the same type and is not the documented insert path.

"cursor.execute() saves the row immediately."

It doesn't. python-oracledb does not autocommit by default -- the row exists only inside the current transaction until connection.commit() runs.

04
INTUITION

The waiter, not the menu

Concepts 03-06 wrote the menu -- real Oracle SQL, in a language a database engine understands. But a menu on a table doesn't cook anything. python-oracledb is the waiter: it carries your order (the SQL text and its bind values) to the kitchen (the database), and carries the finished plates (result rows) back to your table. A VECTOR column is a dish with a very specific required container -- hand it over in the wrong container (a plain Python list, say) and the waiter won't accept the order, not because the kitchen refuses vectors, but because that's not the container the menu specifies for this dish.

06
MECHANISM

Five calls carry the whole round trip

Per python-oracledb's own documentation, a standalone connection is created by calling oracledb.connect(), passing a username, password, and a data source name (dsn) identifying the host and service. This runs in Thin mode by default -- python-oracledb's own connection-handling guide states plainly that "python-oracledb's default Thin mode" needs no separately installed Oracle Client libraries. From that connection, connection.cursor() returns a cursor; cursor.execute(sql, binds) sends the SQL text and its bind values in one round trip; rows are read back by iterating the cursor directly or calling cursor.fetchone(), cursor.fetchmany(), or cursor.fetchall(). None of this is specific to VECTOR columns -- what is specific is the Python type used as the bind value, covered in Section 10.

WORKED EXAMPLE

Insert, query, and verify chk_9f21_2_03's own round trip

Two rows go in: chk_9f21_2_03, the real chunk from Concept 03's doc_9f21 dataset ("To reset a vendor account, an admin must..."), and chk_9f21_2_04, a second row invented for this lab only, not part of the original doc_9f21 dataset, to give the query something to rank against. Both get a small 3-D stand-in embedding in place of the real 384-D all-MiniLM-L6-v2 vector.

PYTHON · CONNECT AND INSERT TWO EMBEDDINGS 
import oracledb
import array

connection = oracledb.connect(user=user, password=pwd, dsn=dsn)  # Thin mode, default
cursor = connection.cursor()

rows = [
    ("chk_9f21_2_03", array.array("f", [0.6, 0.8, 0.0])),  # real chunk, toy 3-D stand-in
    ("chk_9f21_2_04", array.array("f", [0.0, 0.0, 1.0])),  # lab-only contrast row
]
for chunk_id, vec in rows:
    cursor.execute(
        "insert into embeddings (chunk_id, embedding) values (:1, :2)",
        [chunk_id, vec],
    )
connection.commit()  # not durable until this line runs

Neither INSERT is saved until connection.commit() runs -- per python-oracledb's own transaction-management documentation, already cited in Concept 02, this is a deliberate default, not an omission.

PYTHON · QUERY WITH A BOUND VECTOR PARAMETER 
query_embedding = array.array("f", [0.8, 0.6, 0.0])

cursor.execute(
    """
    SELECT c.chunk_id, c.text,
           VECTOR_DISTANCE(e.embedding, :qv, COSINE) AS dist
    FROM chunks c
    JOIN embeddings e ON e.chunk_id = c.chunk_id
    WHERE c.chunk_id IN ('chk_9f21_2_03', 'chk_9f21_2_04')
    ORDER BY dist
    """,
    qv=query_embedding,
)
for chunk_id, text, dist in cursor.fetchall():
    print(chunk_id, round(dist, 4))

Verification methodBoth distances were computed independently by a standalone node script, not typed in by hand: dot([0.8,0.6,0.0],[0.6,0.8,0.0]) = 0.96, both vectors have norm 1, so cosine distance = 1 − 0.96 = 0.04 exactly; dot([0.8,0.6,0.0],[0.0,0.0,1.0]) = 0, so cosine distance = 1 − 0 = 1 exactly. The script also re-ran both vectors through Math.fround() to simulate float32 rounding -- the same precision array.array("f", ...) and Oracle's own FLOAT32 storage actually use -- and got 0.03999999332428039 and 1, confirming the float32 storage format used throughout this course does not change which row ranks first. The printed output above rounds to 4 decimal places, matching the Python round(dist, 4) call in the code above.

The result set comes back ordered exactly as VECTOR_DISTANCE was told to order it -- chk_9f21_2_03 first, because its toy embedding sits far closer in cosine terms to the query vector than the lab-only contrast row does. Nothing about ordering changed from Concept 05 or 06; what's new here is that a Python program, not a SQL client, submitted the bound parameter and read the ranked rows back.

outconverter=list on a cursor.var(oracledb.DB_TYPE_VECTOR, ...) turns fetched array.array rows into plain Python lists, if that's the shape the rest of the code expects.

12
CODE

The numpy round trip, in python-oracledb's own pattern

Per python-oracledb's own "Using VECTOR Data" documentation, here is the full input/output type-handler pair that lets numpy arrays act as VECTOR binds and lets fetched VECTOR columns come back as numpy arrays -- reproduced from the docs, not this concept's own invention.

PYTHON · NUMPY INPUT AND OUTPUT TYPE HANDLERS (per python-oracledb's own documentation) 
import numpy
import array

def numpy_converter_in(value):
    if value.dtype == numpy.float64:
        dtype = "d"
    elif value.dtype == numpy.float32:
        dtype = "f"
    elif value.dtype == numpy.uint8:
        dtype = "B"
    else:
        dtype = "b"
    return array.array(dtype, value)

def input_type_handler(cursor, value, arraysize):
    if isinstance(value, numpy.ndarray):
        return cursor.var(
            oracledb.DB_TYPE_VECTOR,
            arraysize=arraysize,
            inconverter=numpy_converter_in,
        )

def numpy_converter_out(value):
    return numpy.array(value, copy=False, dtype=value.typecode)

def output_type_handler(cursor, metadata):
    if metadata.type_code is oracledb.DB_TYPE_VECTOR:
        return cursor.var(
            metadata.type_code,
            arraysize=cursor.arraysize,
            outconverter=numpy_converter_out,
        )

connection.inputtypehandler = input_type_handler
connection.outputtypehandler = output_type_handler

With both handlers registered, a numpy array can be passed directly as a bind value, and every VECTOR column comes back as a numpy array instead of array.array -- useful given Module 08's own embeddings are produced by all-MiniLM-L6-v2 as numpy arrays in the first place.

REPETITION

The three facts, restated

  • oracledb.connect(user=, password=, dsn=) opens a standalone connection in Thin mode by default -- no separately installed Oracle Client libraries required.
  • A FLOAT32 VECTOR column binds through array.array("f", [...]) in Thin mode -- not a plain Python list, and not a bare numpy array without a type handler.
  • Nothing is durable until connection.commit() runs -- python-oracledb does not autocommit by default, per its own transaction-management documentation.
16
DIAGNOSIS

Failure modes

SILENTLY MISSING ROW

INSERT ran with no error, but the row isn't there later

Cause: no connection.commit() was called, so the row lived only inside a transaction that was later rolled back or lost on disconnect. Fix: commit explicitly, or use a with-block pattern that commits before closing.

WRONG BIND TYPE FOR VECTOR

A numpy array or plain list passed as a VECTOR bind raises a type error or is silently mishandled

Cause: Thin mode's documented VECTOR bind type is array.array, not a bare Python list or numpy ndarray. Fix: convert explicitly, or register an input type handler per Section 12's own numpy_converter_in.

21
FEEDBACK

Solution and teach-back

Open the worked solution
array.array("f", [1.0, 0.0, 0.0]) is the correct Thin-mode bind. dot([1,0,0],[0.6,0.8,0.0]) = 0.6, norms are 1 and 1, so cosine distance = 1 − 0.6 = 0.4. dot([1,0,0],[0,0,1]) = 0, so cosine distance = 1 − 0 = 1.0. Since 0.4 < 1.0, chk_9f21_2_03 still ranks first -- a different query vector, same winner, because chk_9f21_2_03's embedding still has a nonzero component along the query's own direction and chk_9f21_2_04's does not.

Teach-back: why does python-oracledb need to know a value is meant for a VECTOR column at all, instead of just accepting any sequence of numbers?

Interview questions

Conceptual: what Python type does python-oracledb use to bind a FLOAT32 VECTOR column in its default Thin mode?
A Python array.array() object of type "f" (32-bit float) -- per python-oracledb's own "Using VECTOR Data" documentation.
Conceptual: does cursor.execute() on an INSERT statement save the row immediately?
No -- python-oracledb does not autocommit by default. The row is only durable in the database after connection.commit() runs.
