01 · CONCEPT FIRST

An assembly line, not a single "index everything" button

Ingestion is not one operation -- it's six fixed stations a document passes through in order: hash check, chunk, embed, write, build index, query-ready. Every station reuses a mechanism Modules 06-10 already built; this concept's own job is the order and the handoffs between them.

First memory: nothing here is a new mechanism -- it's the same six stations Modules 06-10 already built, run in a fixed sequence for the first time.
02 · WHY IT EXISTS

Without a workflow, ingestion is an ad-hoc script re-run by hand

Without a defined workflow, chunking, embedding, writing, and indexing would be separate scripts re-run manually every time a document changes, with no consistent rule for whether a document is new, unchanged, or an update to something that already exists. Getting that rule wrong either wastes work re-ingesting unchanged files, or silently skips a real update.

03 · CONCRETE EXAMPLE

One real document, six stages, one real hash

Take POLICY-REFUND-001 v2, this course's own running document since Module 06 Concept 07: "Refund requests must be submitted within 45 days of purchase." Its SHA-256 hash, 2be6d94f...071dd9d, is computed and compared against the stored hash for that same doc_id -- a mismatch means treat this as a new version, not an unchanged document and not a brand-new document.

04 · TECHNICAL MECHANISM

Six stages, each already covered by name

Hash check (Module 06) decides new / unchanged / new-version before any other work runs. Chunk (Module 07) splits the document, sizing overlap so no single fact spans a chunk boundary. Embed (Module 08) runs each chunk through all-MiniLM-L6-v2 with the document-side passage: prefix -- embedded once, offline, unlike a query which is embedded live per request. Write (Module 10) inserts the new rows into the five-table schema as one committed batch, never row by row. Build index (Module 10) rebuilds or refreshes the vector index only after the write commits -- never as part of each row insert. Query-ready is the state the document is in once all five prior stages finish.

06 · IMPORTANT DISTINCTIONS

Ingestion is batch. Retrieval is live.

Ingestion runs once per document, offline, well before any question arrives -- it can afford to be slower and heavier, since nobody is waiting on it in real time. Retrieval (Concepts 05-06) runs once per incoming question, live, and has to be fast. Confusing the two -- for instance, embedding a query with the same batch-oriented assumptions as a document -- is exactly what Module 08's bi-encoder asymmetry (query-side vs. document-side prefixes) exists to prevent.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Skip the hash check -- just always re-ingest."

Wasteful and risky: re-ingesting an unchanged document duplicates work for nothing, and doing it carelessly can create duplicate rows if the version logic isn't handled correctly.

"Build the index before the write commits."

Backwards -- Module 10's own transaction rule (no autocommit by default) means the index should only be built or refreshed once the new rows are durably committed, not while the write is still in flight.

04
INTUITION

An assembly line, not a single button

Ingestion works like a factory assembly line, not a single "index everything" button: a part (the document) moves through fixed stations in a fixed order -- inspect, cut, coat, bolt on, inspect again -- and skipping a station or running them out of order produces a broken part, not a faster one.

Analogy boundaryThe assembly-line picture explains the fixed ordering, not the actual mechanism at each station -- that comes from Section 06's own traced example, not from the analogy.

06
MECHANISM

Six stages, traced on one real document

POLICY-REFUND-001 v2: "Refund requests must be submitted within 45 days of purchase." (61 characters, 10 words).

  1. Hash check -- SHA-256 of the incoming text, 2be6d94f38532cc9a4070b0edf7882b25f0d3fa73d7473cbf3d9858c3071dd9d, compared against the stored hash for doc_id=POLICY-REFUND-001 (the v1/45-day-vs-30-day text's own hash). A mismatch means proceed as a new version.
  2. Chunk -- at this course's own cited chunk-size range (roughly 200-500 tokens), a 10-word sentence fits trivially inside one chunk -- no recursive split, no overlap logic triggered.
  3. Embed -- the single chunk is embedded once, offline, using the document-side passage:-style prefix, producing a 384-dimensional vector via all-MiniLM-L6-v2.
  4. Write -- a new row lands in document_versions (v2, current), one row in chunks, one row in embeddings with the vector bound via array.array("f", embedding); the FK chain documents → document_versions → chunks → embeddings stays intact. Superseded v1 rows are either tombstoned (Module 09 Concept 08) or hard-deleted in child-first order (Module 10 Concept 09) -- both are valid paths, not a single canonical choice.
  5. Build index -- once the write commits, the existing HNSW or IVF index either absorbs the new row automatically or is explicitly rebuilt/refreshed, per Module 10 Concepts 05-06's own syntax.

TECHNICAL MECHANISM

Change detection, in detail

Comparison resultWhat happens next
Hash matches stored hashDocument is unchanged -- skip re-ingestion entirely, no further stages run.
Hash differs, doc_id already existsTreat as a new version -- proceed through chunk/embed/write, mark the old version superseded.
doc_id has never been seenTreat as a brand-new document -- proceed through every stage from scratch.

TECHNICAL MECHANISM

Chunking, recapped

Fixed-size and recursive chunking (Module 07 Concept 02) and the chunk-size precision/context trade-off (Concept 05) apply here unchanged -- ingestion doesn't introduce a new chunking rule, it's the point where whichever rule the project already chose actually runs against real incoming text.

10
TECHNICAL MECHANISM

Overlap sizing

Overlap (Module 07 Concept 06) is sized so no single fact spans a chunk boundary undetected -- relevant during ingestion whenever a real document is long enough to require more than one chunk, unlike this concept's own deliberately short worked example.

11
MECHANISM

The embedding pass, in detail

Each chunk runs through the real forward pass confirmed in Module 08 Concept 02: tokenize → embed → contextualize → pool, using the document-side prefix convention (Module 08 Concepts 03 and 08) rather than the query-side one -- because ingestion embeds text once, in a batch, ahead of any question, while a live query embeds text once, per request, in real time. That asymmetry is the literal reason this stage is called "ingestion."

13
DIAGNOSIS

Superseded versions -- two valid paths

Tombstone vs. hard deleteSuperseded v1 rows can either be tombstoned and cleaned up asynchronously (Module 09 Concept 08's own mechanic), or hard-deleted in the child-table-first order Module 10 Concept 09 requires (embeddings and chunks before documents, or Oracle raises ORA-02292). Which path a project takes depends on its own re-ingestion strategy -- this concept presents both as valid, not one as canonical.
14
TECHNICAL MECHANISM

Index construction, and the one open question

SQL · HNSW REBUILD (Module 10 Concept 05's own syntax) 
CREATE VECTOR INDEX embeddings_hnsw_idx ON embeddings (embedding)
  ORGANIZATION INMEMORY NEIGHBOR GRAPH
  DISTANCE COSINE
  WITH TARGET ACCURACY 95;
Open, unverified point -- carried forward, not resolvedOracle's own documentation states that IVF index accuracy "may diminish over time due to DML operations" and names DBMS_VECTOR.INDEX_ACCURACY_QUERY/REBUILD_INDEX as the remediation (Module 10 Concept 09). No equivalent staleness statement was found for HNSW in this course's own cited references. This concept states that gap explicitly rather than assuming HNSW behaves the same way as IVF.
15
DIAGNOSIS

What "query-ready" actually means

A document is query-ready once all five prior stages finish: its rows exist in the five-table schema, and the vector index has actually incorporated them -- present-in-the-table alone is not sufficient if the index hasn't caught up. Live query-time retrieval against a query-ready document is Concepts 05-06's own territory, not built here.

DIAGNOSIS

A deliberately trivial worked example

CORRECTION

Misconceptions

Incorrect beliefCorrection
Ingestion and indexing are the same stepFalse -- ingestion (hash/chunk/embed/write) produces rows; index construction is a separate, later step that makes those rows actually reachable by search.
The hash check is optional overheadFalse -- skipping it means every ingestion run redoes chunking/embedding/writing for documents that never changed, and risks duplicate rows if version logic isn't otherwise handled.
19
CAREER PRACTICE

Interview questions

Conceptual: why is ingestion considered a batch job rather than a live operation?
It runs once per document, offline, well before any question arrives -- nobody is waiting on it in real time, so it can afford heavier processing than the live retrieval path can.
Conceptual: what specifically triggers re-ingestion of an already-seen document?
A SHA-256 hash mismatch against the stored hash for that document's doc_id -- an unchanged hash means skip re-ingestion entirely.
System design: why build or refresh the vector index after the write commits, rather than during it?
Indexing rows that are still inside an uncommitted transaction risks indexing data that could be rolled back -- the index should only reflect durably committed state.
20
REALITY

Production implications

  • Hash-based change detection scales to large document sets far better than manual tracking -- it's the same mechanism regardless of how many documents are ingested per run.
  • Whether superseded rows are tombstoned or hard-deleted is a real operational choice with different cleanup costs, not a detail to decide arbitrarily per document.
  • HNSW's own DML-staleness behavior remaining unconfirmed (Section 14) is a real production risk to monitor directly rather than assume away, until Oracle's own documentation states otherwise.
