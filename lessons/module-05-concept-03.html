MODULE 05 · CONCEPT 03

Two vector families.
One retrieval box.

Concept 02 built the inverted index without ever naming the family it belongs to. Module 04 separately built the dot product and cosine similarity without naming its family either. This concept names both explicitly and puts them side by side for the first time: sparse retrieval represents a query and a document as a vector over the whole vocabulary — almost all zeros, one entry per term actually present — and matches by exact term overlap. Dense retrieval represents them as a short, fully-populated embedding vector and matches by geometric similarity. No scoring formula is derived here — Concept 04 introduces the first two real weights, term frequency and inverse document frequency, for the sparse side specifically.

3 CONCEPTS COMPLETED

PROGRESSIVE BEGINNER CORE

Same query, two mechanisms, two different result sets

Every idea in this concept reduces to one question: what kind of vector represents a document, and how are two of those vectors compared? Sparse and dense retrieval answer that question completely differently, and the difference explains every disagreement between their results.

01 · CONCEPT FIRST

Two words for two kinds of vector

SPARSE

A vector as long as the entire vocabulary, almost all zeros — one nonzero entry per term the document actually contains. Concept 02's postings lists are exactly this representation, stored the efficient way instead of as a literal zero-filled vector.

DENSE

A short, fixed-length vector (e.g. 384 numbers) where every single entry is a nonzero float, produced by an embedding model. Module 04 Concept 03's dot product and cosine similarity operate on exactly this kind of vector.

First memory: sparse retrieval matches by shared exact words; dense retrieval matches by closeness in a learned geometric space. Same "Retrieval" box, two different vector representations feeding it.
02 · WHY IT EXISTS

Two mechanisms already exist — nothing had named or compared them yet

Concept 02 built the inverted index. Module 04 built cosine similarity. Both are real, working mechanisms, built in isolation, with no concept so far stating that they belong to two different families or explaining when one should be preferred over the other. This concept exists purely to draw that line explicitly, before Concepts 04-06 spend three concepts making the sparse side rank its results — otherwise a learner could easily assume sparse retrieval is "the old, unranked way" and dense retrieval is simply its upgrade, which is not the relationship between them.

03 · CONCRETE EXAMPLE

The same query, two different result sets, on Concept 02's own corpus

Query: "vector search". Concept 02 already computed the sparse side of this: postings("vector") = [D1, D5], postings("search") = [D1, D3, D4, D5, D8], so the Boolean AND result is exactly [D1, D5] — no document lacking both exact words can ever appear, no matter how relevant its topic is.

D1 — "vector search over dense embeddings"

Sparse: MATCH (has both terms). Dense (illustrative score, not from a trained model): 0.91 — highest on both mechanisms.

D5 — "vector index for approximate search"

Sparse: MATCH. Dense (illustrative): 0.78 — still high on both.

D3 — "dense embeddings for semantic search"

Sparse: NO MATCH — missing the exact word "vector". Dense (illustrative): 0.74 — nearly as high as D5, despite the sparse mechanism excluding it entirely.

D7 — "embeddings from a neural encoder"

Sparse: NO MATCH — shares neither exact word. Dense (illustrative): 0.52 — a moderate score a Boolean merge cannot express at all: this document is either "in" or "out", never "somewhat".

D3 and D7 are exactly the divergence this concept is about: topically related to "vector search" without using either literal word, invisible to the sparse mechanism, visible (to different degrees) to the dense one. Section 14's lab lets you try other queries from this same corpus and watch where the two mechanisms agree and disagree.

04 · TECHNICAL MECHANISM

Two matching rules over two different vector spaces

SPARSE MATCHING

Tokenize the query, look up each term's postings list (Concept 02), then merge with AND or OR. Matching is symbolic and exact — a term either equals another term or it doesn't; there is no partial credit.

DENSE MATCHING

Embed the query into the same fixed-size space the documents were embedded into (an embedding model — Module 08, forward reference), then rank every document by cosine similarity (Module 04 Concept 03, cited directly). Matching is geometric — every document gets a real-valued score.

WHAT'S THE SAME

Both mechanisms turn a query and a set of documents into vectors, then compare vectors — that shared shape is exactly why both sit inside the same "Retrieval" box in the pipeline.

WHAT'S DIFFERENT

Sparse compares discrete, vocabulary-sized vectors by overlap; dense compares small, continuous vectors by angle. Neither mechanism is a special case of the other.

05 · ARCHITECTURE / FLOW

Two parallel paths into the same box

Documents↓Chunks↓Inverted index (sparse) / Embeddings + vector index (dense) — two parallel offline structures↓Retrieval↓Context↓LLM↓Answer

Module 04 built the dense-side math; Concept 02 built the sparse-side data structure. Neither replaces the other inside the "Retrieval" box — Module 16 will eventually show how to run both paths and fuse their results, but that combination is out of scope until this module and Module 09's vector-index material are both complete.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Dense retrieval is strictly better because it understands meaning."

Not for exact identifiers, codes, names, or rare technical terms — a paraphrase-tolerant embedding can rank a wrong-but-topical document above the one exact match a sparse query would have found immediately.

"Sparse retrieval can't be ranked, only filtered."

Concept 02's plain postings lists can't, but Concepts 04-06 add ranking directly on top of the same sparse mechanism — ranking is a missing ingredient, not a missing capability.

"A system has to pick one of the two, permanently."

Hybrid retrieval (Module 16, forward reference) runs both mechanisms and fuses their results — this concept only establishes what's being fused, not how.

"Dense retrieval has no vocabulary at all."

The embedding model still has a fixed tokenizer vocabulary underneath (Module 02, Concept 02) — what dense retrieval lacks is exact-term matching as its comparison rule, not text processing altogether.

09 · WHAT YOU SHOULD UNDERSTAND

Readiness check before moving on

The two vectors

Sparse = vocabulary-sized, almost all zeros, exact terms only. Dense = small, fixed-size, fully populated, from an embedding model.

The two match rules

Sparse merges postings lists (AND/OR, symbolic). Dense ranks by cosine similarity (Module 04 Concept 03, geometric).

Why results diverge

Sparse can only see documents sharing an exact term; dense can score any document, including paraphrases sparse never considers.

What's not here yet

No scoring formula for either side — Concept 04 adds the first two real weights, specifically to the sparse mechanism.

04
INTUITION

A card catalog versus a librarian who reads for meaning

Sparse retrieval behaves like a library's old card catalog, indexed strictly by the exact words printed on each card — search "vector search" and you get every card with both of those exact words typed on it, nothing more, nothing less. Dense retrieval behaves like a librarian who has actually read every book and can point you to something relevant even when your request uses none of the book's exact words, because they matched on what the book is about, not on printed text.

Analogy boundaryA real librarian's judgment is not literally "distance in a coordinate space" — that geometric mechanism is Module 04's cosine similarity specifically, not a general property of "understanding meaning." The analogy explains the outcome, not the computation.

06
MECHANISM

The same query, traced through both mechanisms

Query arrives — "vector search", identical text fed to both mechanisms.
Sparse path: tokenize, then look up — postings("vector") = [1,5], postings("search") = [1,3,4,5,8] (Concept 02's own numbers, reused).
Sparse path: merge — AND intersection gives {D1, D5}; an unordered set, nothing else.
Dense path: embed the query — produces one fixed-size vector, in the same space every document was embedded into ahead of time.
Dense path: score every document — cosine similarity against all eight document vectors, not just the two containing an exact term.
Dense path: rank — sort by score descending; D1 and D5 land near the top, but D3 and D7 — invisible to the sparse merge — also receive a real score.

09
MATHEMATICS

Two vector spaces, no new formula

This concept introduces no derivation of its own — it only places Concept 02's and Module 04's existing notation side by side:

v_sparse(d) ∈ R^|V| -- one dimension per vocabulary term, nonzero only where the term occurs v_dense(d) ∈ R^d -- fixed size d, set by the embedding model, every entry populated score_sparse(q,d) = 1[postings match] -- Concept 02: membership only, no weight score_dense(q,d) = cos(v_dense(q), v_dense(d)) -- Module 04, Concept 03: a real number in [-1, 1]

The structural difference that drives every later comparison in this module: |V| grows with the corpus and is mostly zero per document; d is fixed by the embedding model and never zero per document. Concept 04 will attach the first real weight to score_sparse's currently-binary indicator — it will not touch score_dense at all.

11
CONCRETE USE

Two clean fits, a boundary case, a mistake

CLEAN FIT — SPARSE

Looking up an exact order number or error code

"ORA-00942" is a single unambiguous token — an exact postings lookup answers it directly, with no risk of an embedding drifting toward a similar-looking but wrong code.

CLEAN FIT — DENSE

A user question phrased nothing like the source document

"How do I get my money back?" retrieving a document titled "Refund policy and eligibility" shares almost no exact words — a case sparse retrieval alone would likely miss.

BOUNDARY CASE

A query that is itself a rare exact phrase used verbatim in one document

Both mechanisms can succeed here — sparse via an exact postings hit, dense because the matching document is also the closest embedding — b03's D1 and D5 are this case.

MISTAKE TO AVOID

Assuming a high dense-similarity score means the document actually answers the query

A high score means "geometrically close," not "correct" or "sufficient" — Concept 04 onward gives the sparse side comparable caution about term weight not equalling relevance either.

CODE

Both mechanisms, from scratch, on the same corpus

PYTHON · NO LIBRARIES 
corpus = {
    1: "vector search over dense embeddings",
    2: "sparse retrieval with an inverted index",
    3: "dense embeddings for semantic search",
    4: "keyword search using an inverted index",
    5: "vector index for approximate search",
    6: "sparse and dense retrieval combined",
    7: "embeddings from a neural encoder",
    8: "boolean search over an inverted index",
}

# Sparse side: reuses Concept 02's index and intersect exactly.
def build_inverted_index(corpus):
    index = {}
    for doc_id, text in corpus.items():
        for term in set(text.split(" ")):
            index.setdefault(term, []).append(doc_id)
    for term in index:
        index[term].sort()
    return index

def intersect(a, b):
    i, j, result, comparisons = 0, 0, [], 0
    while i < len(a) and j < len(b):
        comparisons += 1
        if a[i] == b[j]:
            result.append(a[i]); i += 1; j += 1
        elif a[i] < b[j]:
            i += 1
        else:
            j += 1
    return result, comparisons

index = build_inverted_index(corpus)
sparse_result, comparisons = intersect(index["dense"], index["search"])
assert sparse_result == [1, 3]
assert comparisons == 5

# Dense side: no real embedding model here, so this stands in for one --
# a fixed, hand-set vector per document, purely to show the *shape* of the
# mechanism (score every document, then sort), not to claim real accuracy.
mock_dense_scores = {1: 0.91, 5: 0.78, 3: 0.74, 7: 0.52, 4: 0.33, 6: 0.30, 8: 0.28, 2: 0.19}

def rank_dense(scores):
    return sorted(scores.items(), key=lambda pair: pair[1], reverse=True)

dense_ranking = rank_dense(mock_dense_scores)
assert dense_ranking[0] == (1, 0.91)          # highest-scoring document first
assert dense_ranking[-1] == (2, 0.19)         # lowest-scoring document last

# The comparison this whole concept is about: which documents does sparse
# see that dense's top-4 also sees, and which does dense see that sparse can't?
dense_top4 = {doc for doc, _ in dense_ranking[:4]}
sparse_and = set(intersect(index["vector"], index["search"])[0])   # {1, 5}, Concept 02's numbers
assert sparse_and == {1, 5}
assert dense_top4 == {1, 5, 3, 7}
assert dense_top4 - sparse_and == {3, 7}      # exactly b03's divergence, reproduced in code

16
DIAGNOSIS

Failure modes

SPARSE BLIND SPOT

The correct document uses different words entirely

b03's D7 is exactly this — zero exact overlap with the query terms, so the sparse merge can never surface it at any rank, regardless of corpus size.

DENSE BLIND SPOT

A near-identical embedding for a factually wrong document

Two documents about "refund eligibility" and "refund fraud policy" can embed close together despite opposite intents — cosine similarity measures topical closeness, not correctness.

FALSE CONFIDENCE FROM AGREEMENT

Assuming overlap between the two mechanisms proves relevance

b03's D1 and D5 satisfy both mechanisms for this query, but that agreement is a property of this specific example, not a general guarantee either mechanism is right.

17
CORRECTION

Misconceptions

Incorrect beliefCorrection
Dense retrieval is a newer, strictly improved version of sparse retrievalFalse — they are two different representations with two different, non-overlapping blind spots, not one mechanism superseding the other.
Sparse vectors and dense vectors differ only in how many zeros they containFalse — sparse dimensionality equals vocabulary size and grows with the corpus; dense dimensionality is fixed by the embedding model, independent of corpus size.
A production system must choose exactly one of the two mechanismsFalse — Module 16's hybrid retrieval runs both and fuses the results; this concept only names what gets fused, it doesn't yet show how.
18
REALITY

Production implications

  • Running both mechanisms means maintaining two separate offline structures — an inverted index and a vector index — each with its own build, storage, and update cost, a forward reference to Modules 09-10's operational material.
  • An embedding model's blind spots are silent: a dense-only system that misses an exact-identifier query fails without an obvious error, whereas a sparse-only system missing a paraphrase also fails silently — both failure modes need dedicated evaluation, not just a working query path (Module 18, forward reference).
  • Choosing sparse-only, dense-only, or hybrid is a cost and latency decision as much as a quality one — two mechanisms to query and fuse is strictly more expensive than one, a trade-off Module 16 addresses directly.
19
RECALL

Knowledge check

What determines a sparse vector's dimensionality, and what determines a dense vector's?
Sparse: the size of the corpus vocabulary, |V|, which grows as the corpus grows. Dense: the embedding model's fixed output size, d, which does not change with the corpus.
Why can a dense retriever return a document that a sparse retriever's AND merge can never return, for the same query?
Because dense retrieval scores every document by geometric similarity regardless of exact-term overlap, while a sparse AND merge only ever considers documents present in every query term's postings list.
Does this concept say how to combine sparse and dense results into one ranking?
No — that is hybrid retrieval, covered in Module 16. This concept only compares the two mechanisms independently.

23
CAREER PRACTICE

Interview questions

Explain the difference between sparse and dense retrieval to someone who has never heard either term, in under thirty seconds.
Sparse retrieval matches documents that use the exact same words as the query, using a lookup table built from those words. Dense retrieval matches documents that mean something similar to the query, using a geometric closeness score, even if the exact words differ.
Give a concrete query where sparse retrieval would succeed and dense retrieval could plausibly fail, and vice versa.
An exact error code or order number favors sparse — an embedding could drift toward a similar-looking wrong code. A conversationally-phrased question with no vocabulary overlap with the source document favors dense — sparse would return nothing at all.
Why isn't dense retrieval simply "sparse retrieval, but better"?
They compare fundamentally different vector shapes with different, non-overlapping blind spots — sparse vectors are vocabulary-sized and exact-match only; dense vectors are fixed-size and similarity-based. One does not generalize the other.
Design question: a stakeholder asks why the system doesn't "just use both and pick whichever gives more results." What's wrong with that plan?
More results isn't the same as better-ranked or more relevant results — the two mechanisms produce differently-shaped outputs (a set versus a score) that can't be merged by simple concatenation without a defined fusion method, which is exactly what Module 16's hybrid retrieval provides and this concept does not.
