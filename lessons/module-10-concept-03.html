01 · CONCEPT FIRST

The concrete answer to "what does persistence look like as real tables"

This concept is the literal, buildable schema a RAG-backed database uses to store identity, edit history, content, vectors, and "where did this claim come from." Five tables -- documents, document_versions, chunks, embeddings, citations -- and nothing more. Every one of the five is a plain SQL table you could create today.

First memory: five tables, one chain. documents → document_versions → chunks → embeddings, with a second branch off chunks into citations.
02 · WHY IT EXISTS

Persistence's identity half and content-plus-vector half, made real

Concept 02 split the database's owned jobs into persistence, transactional consistency and query execution. Persistence itself has two halves: an identity half (what document is this, and which edit of it) and a content-plus-vector half (what text, what embedding, what citation points back at it). Without concrete tables, "the database persists data" stays an abstract claim. Concept 01's own category boundary is also why this is even possible here: a full ACID DBMS supports real foreign keys and atomic multi-table commits, not just a bare vector index.

03 · CONCRETE EXAMPLE

One KB article, walked through the whole chain

A knowledge-base article gets written and stored as a document. Someone edits it once -- that edit produces a second version row, stamped CURRENT, while the original version flips to SUPERSEDED (it isn't deleted, just marked old). The current version gets split into a chunk. That chunk gets turned into an embedding vector. Later, a generated answer quotes that chunk, and a citation row records exactly which chunk backed that claim.

DOCUMENT → VERSION

One thread of identity (the article), two rows of history (before the edit, after the edit) -- the old one kept, not thrown away.

VERSION → CHUNK → EMBEDDING

The current text gets split and vectorized -- the same two stages Module 07 and Module 08 already built, now landing in a real table.

CHUNK → CITATION

Sometimes, later, a generated answer points back at exactly this chunk as its source.

04 · TECHNICAL MECHANISM

Two ideas that hold the five tables together

First: a foreign key is a column that must point at a row that actually exists in another table, and referential integrity is the rule that this must always hold -- a chunk's foreign key always resolves to a real document version, never a dangling reference. Second: a version row is never overwritten or deleted. Each edit adds a new row stamped CURRENT while the prior one flips to SUPERSEDED -- the same pattern already established as SCD Type 2. Every one of the five tables also gets a surrogate key -- a stable ID like doc_id or chunk_id that never changes even though the content behind it does.

05 · ARCHITECTURE / FLOW

One forward chain, one branch

Two forward branches leave chunks. The embeddings branch always gets populated -- every chunk gets vectorized. The citations branch only sometimes gets populated -- a chunk is cited only if some later generated answer actually quoted it.

07 · COMMON MISTAKES

What beginners often get wrong with this exact schema

"Just update the version row in place when the document changes."

False -- overwrite the old row and its history is gone. Stamp the old row SUPERSEDED and insert a new CURRENT row instead.

"citations should have a foreign key into an answers table."

Not a bug -- a documented scope choice. Storing generation events is out of this concept's scope, so answer_id is deliberately not a foreign key here.

"Any version_id will do, as long as the chunk points at some version."

False -- a chunk's version_id must belong to the same doc_id the chunk itself is tagged with. A chunk from one document pointing at another document's version is exactly the defect class the verification script below checks for.

01
ORIENTATION

From "the database owns persistence" to "here are its tables"

Concept 02 named persistence, transactional consistency and query execution as the database's three owned jobs, with zero schema syntax. This concept builds the concrete tables for job one, persistence -- both halves of it: identity (which document, which edit) and content-plus-vector (what text, what embedding, what citation points back at it). Concept 01's own category boundary is why this is even possible here at all: a full ACID DBMS, not a bare vector store, is what allows real foreign keys and atomic multi-table commits.

02
DESIGN RATIONALE

Why five separate tables, not one wide table

Database normalization is the practice of organizing a schema to reduce redundancy and improve data integrity. Identity, version history, content, vectors and provenance each change independently and at different rates -- a document rarely changes, a version is added on every edit, a chunk is fixed once its version is fixed, an embedding is recomputed only if the model changes, a citation appears only when some later answer quotes the chunk. Splitting these into five normalized tables, rather than one wide table repeating a document's identity on every chunk and citation row, is what that principle recommends here.

03
TABLE 1

documents -- the stable thread identity

One row per real-world document. This is the identity that survives every edit -- the thread the version rows below all hang off of.

ColumnTypePurpose
doc_idVARCHAR PKSurrogate key -- a stable, meaningless-value ID that survives every future edit.
source_idVARCHARProvenance -- which upstream system this document came from.
source_typeVARCHARProvenance -- what kind of source (KB article, complaint narrative, policy doc, ...).
authorVARCHARProvenance -- who owns/wrote it.
created_atTIMESTAMPWhen the document thread itself was first created.

The surrogate key pattern behind doc_id and the provenance fields (source_id/source_type/author) are both reused directly from Module 06 -- not re-derived here.

04
TABLE 2

document_versions -- one row per edit, never overwritten

Every edit to a document produces a new row here instead of modifying an existing one -- the Slowly changing dimension Type 2 pattern already established in Module 06 Concept 07, reused directly rather than re-derived.

ColumnTypePurpose
version_idVARCHAR PKSurrogate key for this specific edit.
doc_idVARCHAR FK → documentsWhich document thread this version belongs to.
version_numberINT1, 2, 3, ... in edit order; UNIQUE together with doc_id.
statusVARCHAR CHECK IN ('CURRENT','SUPERSEDED')Exactly one CURRENT row per doc_id at any time; all older ones flip to SUPERSEDED.
content_hashVARCHARSHA-256 change-detection hash (Module 06 Concepts 06-07).
ingested_at / updated_at / superseded_atTIMESTAMPModule 06 Concept 08's three provenance timestamp fields.
05
TABLE 3

chunks -- Module 07's output, made persistent

One row per chunk. A chunk carries two foreign keys, not one: doc_id and version_id together, because a chunk belongs to one specific version, not just to a document in the abstract -- the same document can have chunks scattered across two different versions at once (an old SUPERSEDED version's chunks and a new CURRENT version's chunks), and the schema needs to distinguish them.

ColumnTypePurpose
chunk_idVARCHAR PKSurrogate key for this chunk.
doc_idVARCHAR FK → documentsWhich document thread.
version_idVARCHAR FK → document_versionsWhich specific edit this chunk was split from.
chunk_indexINTOrder of this chunk within its version.
char_start / char_endINTCharacter offsets into the version's text.
chunk_textTEXTThe chunk's actual content.
06
TABLE 4

embeddings -- Module 08's output, made persistent

One row per chunk's embedding. The VECTOR(384) column is explicitly a generic, vendor-neutral placeholder, not Oracle's own VECTOR syntax -- that's Concept 05's job. The pattern is reused verbatim from pgvector's own README: CREATE TABLE items (id bigserial PRIMARY KEY, embedding vector(3)); -- a portable precedent for "a vector is just another typed column."

ColumnTypePurpose
embedding_idVARCHAR PKSurrogate key for this embedding.
chunk_idVARCHAR FK → chunksWhich chunk this vector represents.
model_nameVARCHARe.g. all-MiniLM-L6-v2 (Module 08 Concept 06).
dimINT384 for all-MiniLM-L6-v2; 768 and 1536 are the other already-cited alternatives.
embeddingVECTOR(384)Generic placeholder type -- Oracle's own native VECTOR type is Concept 05's job.
07
TABLE 5

citations -- the concrete realization of "provenance"

Module 03 Concept 04 already defined a citation as "a citation tag pointing a claim back to the passage that backed it" -- this table is that definition, made concrete as rows. answer_id is deliberately not a foreign key into any answers table: storing generation events (the answers themselves) is out of this concept's scope, a documented boundary, not an oversight.

ColumnTypePurpose
citation_idVARCHAR PKSurrogate key for this citation.
chunk_idVARCHAR FK → chunksWhich chunk backed the claim.
answer_idVARCHARWhich generated answer cited it -- intentionally not FK'd to anything.
rankINTThis citation's rank among the answer's own citations.
created_atTIMESTAMPWhen the citation was recorded.
08
REFERENCE BLOCK

The full DDL, all five tables together

Every section below points back to this one block.

sql — five-table schema 
CREATE TABLE documents (
  doc_id        VARCHAR(32) PRIMARY KEY,
  source_id     VARCHAR(64),
  source_type   VARCHAR(32),
  author        VARCHAR(128),
  created_at    TIMESTAMP NOT NULL
);

CREATE TABLE document_versions (
  version_id      VARCHAR(32) PRIMARY KEY,
  doc_id          VARCHAR(32) NOT NULL REFERENCES documents(doc_id),
  version_number  INT NOT NULL,
  status          VARCHAR(10) NOT NULL CHECK (status IN ('CURRENT','SUPERSEDED')),
  content_hash    VARCHAR(64) NOT NULL,
  ingested_at     TIMESTAMP NOT NULL,
  updated_at      TIMESTAMP,
  superseded_at   TIMESTAMP,
  UNIQUE (doc_id, version_number)
);

CREATE TABLE chunks (
  chunk_id     VARCHAR(32) PRIMARY KEY,
  doc_id       VARCHAR(32) NOT NULL REFERENCES documents(doc_id),
  version_id   VARCHAR(32) NOT NULL REFERENCES document_versions(version_id),
  chunk_index  INT NOT NULL,
  char_start   INT NOT NULL,
  char_end     INT NOT NULL,
  chunk_text   TEXT NOT NULL
);

CREATE TABLE embeddings (
  embedding_id  VARCHAR(32) PRIMARY KEY,
  chunk_id      VARCHAR(32) NOT NULL REFERENCES chunks(chunk_id),
  model_name    VARCHAR(64) NOT NULL,
  dim           INT NOT NULL,
  embedding     VECTOR(384)
);

CREATE TABLE citations (
  citation_id  VARCHAR(32) PRIMARY KEY,
  chunk_id     VARCHAR(32) NOT NULL REFERENCES chunks(chunk_id),
  answer_id    VARCHAR(32) NOT NULL,
  rank         INT NOT NULL,
  created_at   TIMESTAMP NOT NULL
);
09
PK/FK WALKTHROUGH

Four foreign-key edges, formally

A foreign key is a column that must reference a row that actually exists in another table. Referential integrity is the rule that this must always hold, for every row, at every point in time. This schema has four such edges: document_versions.doc_id → documents.doc_id; chunks.doc_id → documents.doc_id and chunks.version_id → document_versions.version_id together; embeddings.chunk_id → chunks.chunk_id; citations.chunk_id → chunks.chunk_id. Every one of these must resolve for the schema to be considered sound.

WORKED EXAMPLE

One document, one edit, one chunk, one embedding, one citation

sql — worked INSERTs 
INSERT INTO documents VALUES
  ('doc_9f21', 'kb-042', 'kb_article', 'support-team', '2026-01-05 09:00:00');
-- the KB article is created

INSERT INTO document_versions VALUES
  ('ver_9f21_1', 'doc_9f21', 1, 'SUPERSEDED', 'a1b2c3...', '2026-01-05 09:00:00', NULL, '2026-02-11 14:20:00'),
  ('ver_9f21_2', 'doc_9f21', 2, 'CURRENT',    'd4e5f6...', '2026-02-11 14:20:00', '2026-02-11 14:20:00', NULL);
-- the article is edited once: version 1 flips to SUPERSEDED, version 2 becomes CURRENT

INSERT INTO chunks VALUES
  ('chk_9f21_2_03', 'doc_9f21', 'ver_9f21_2', 3, 640, 910, 'To reset a vendor account, an admin must...');
-- the CURRENT version is split into chunks; this is chunk index 3

INSERT INTO embeddings VALUES
  ('emb_9f21_2_03', 'chk_9f21_2_03', 'all-MiniLM-L6-v2', 384, '[0.021, -0.114, ...]');
-- that chunk is embedded, 384 dimensions

INSERT INTO citations VALUES
  ('cit_5501', 'chk_9f21_2_03', 'ans_7734', 1, '2026-03-02 11:05:00');
-- a generated answer (ans_7734) cites this exact chunk, at rank 1
11
TRACING JOIN

One query, citation back to document version

sql — tracing JOIN 
SELECT d.doc_id, dv.version_number, dv.status,
       c.chunk_id, c.chunk_text,
       e.model_name, e.dim,
       ci.citation_id, ci.answer_id, ci.rank
FROM citations ci
JOIN chunks c            ON ci.chunk_id = c.chunk_id
JOIN document_versions dv ON c.version_id = dv.version_id
JOIN documents d          ON dv.doc_id = d.doc_id
JOIN embeddings e         ON e.chunk_id = c.chunk_id
WHERE ci.citation_id = 'cit_5501';

Two join chains meet at chunks: one walks backward through document_versions to documents, the other walks sideways to embeddings -- both anchored on the same chunk_id.

DISTINCTION 3

This concept's version rows vs. Module 09 Concept 08's tombstones

These are different layers. This concept's SCD-Type-2 version rows are a row-level history mechanism sitting inside document_versions. Module 09 Concept 08's tombstone-then-compact mechanism operates one level lower, inside the vector index itself, handling physical delete/update of index entries. Neither re-explains the other; the boundary is simply marked here.

18
COMMON MISTAKES

The SQL-literate version of Section b07's list

  • Overwriting an existing document_versions row in place instead of inserting a new SUPERSEDED/CURRENT pair -- the whole point of SCD Type 2 is that the old row survives.
  • Adding a foreign key from citations.answer_id into a table that doesn't exist in this schema -- an intentional scope boundary (Section 07), not something to "fix."
  • Letting a chunk's version_id resolve to a version belonging to a different doc_id than the chunk's own doc_id column -- the exact defect class Section 13's verification script checks for.

PROJECT MAPPING

How CFPB Complaint Copilot and OpsRAG instantiate this exact shape

In CFPB Complaint Copilot, a complaint narrative is the document; a corrected or re-ingested narrative is a new version; its retrieved chunks and their embeddings feed the answer; a generated answer's citations point back at the specific complaint text that backed each claim.
