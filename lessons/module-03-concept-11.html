MODULE 03 · CONCEPT 11

The RAG
failure chain.

Concept 10 cleared the ground before this concept can even start: it asked whether one specific question, against one specific corpus, was answerable at all. This concept only picks up the case Concept 10 confirmed as answerable — and asks a different question entirely: if that answerable question still came back wrong, at which of three links in the pipeline did it actually break? A query can fail at retrieval (the wrong evidence, or none, gets found), at augmentation (the right evidence is found but assembled or truncated badly before the model ever sees it), or at generation (the right evidence sits in context and the model still gets it wrong — Concept 04's grounded-misread mechanism). This concept is the first to name all three as one ordered chain and show how to tell them apart.

11 CONCEPTS COMPLETED

PROGRESSIVE BEGINNER CORE

A chain is only as strong as its weakest link

An answerable question that still comes back wrong looks like one failure from the outside. It is actually three different possible failures wearing the same disguise, and this concept is about telling them apart.

01 · CONCEPT FIRST

Three links, in a fixed order

LINK 1 · RETRIEVAL

Given the query, does the necessary evidence chunk actually land in the retrieved candidate set? If not — wrong chunk, no chunk, buried too far down — nothing downstream can recover it.

LINK 2 · AUGMENTATION

Given a retrieved candidate set that does contain the evidence, does that evidence survive intact into the exact context the model is handed? Truncation, bad ordering, or a consolidation bug can drop it even after retrieval succeeded.

LINK 3 · GENERATION

Given evidence that is correctly, intact, in the model's context, does the model actually use it correctly? This is Concept 04's grounded-misread mechanism, replayed here as the last possible place things go wrong.

THE CHAIN AS A WHOLE

All three links must hold for a correct, grounded answer. One broken link is enough to produce a wrong or missing answer, no matter how well the other two performed.

First memory: an answerable question that comes back wrong broke at exactly one of three places — retrieval, augmentation, or generation — and the fix is different at each one.
02 · WHY IT EXISTS

Without the chain, every fix looks the same

Concept 10 already cleared the "is this even possible" question — this concept is only useful once that answer is yes. Without naming the three links separately, a wrong answer on an answerable question triggers the same reflex every time: re-tune the retriever, add a reranker, tweak the prompt — often aimed at a link that was never broken. Concept 04 already gave the generation link its mechanism (grounded-misread: evidence present, model still wrong) and Concept 10 already gave the answerability gate its two-question test. This concept's job is narrower than either: given that the question is answerable, name the three places a specific run can still fail, in the fixed order a query actually passes through them.

WITHOUT THE FAILURE CHAIN

One catch-all label — "RAG got it wrong" — covers three causes that need three different fixes: re-chunk and re-embed, fix the context assembler, or improve the generation prompt and model.

WITH THE FAILURE CHAIN

A wrong answer gets localized to exactly one link before any fix is attempted, because the fix for a retrieval miss does nothing for a truncation bug, and the fix for a truncation bug does nothing for a grounded-misread.

03 · CONCRETE EXAMPLE

One query, broken three different ways

Reuse Concept 10's small Oracle HR corpus and its confirmed-answerable question: "How many remote workdays per week are employees allowed?" The remote-work policy states the fact directly — "up to 3 days per week" — so Concept 10 already cleared this as a fair test. Now imagine three separate runs of that same query, each one failing at a different link.

RUN A · RETRIEVAL BREAKS

The remote-work document never appears in the top-k candidates at all — a vocabulary mismatch between "remote" in the query and "telecommute" in the document's phrasing. The model, correctly given no relevant evidence, hedges instead of stating a number.

RUN B · AUGMENTATION BREAKS

The remote-work document is retrieved at rank 1 — retrieval worked. But a context-assembly bug discards it as a near-duplicate of an unrelated boilerplate chunk before the prompt is built. The model again sees no number and hedges — from the outside, this looks identical to Run A.

RUN C · GENERATION BREAKS

The remote-work document is retrieved at rank 1 and its exact text — "up to 3 days per week" — sits intact in the model's context. The model answers "5 days" anyway. This is Concept 04's grounded-misread case, replayed for a new query.

Three different broken links, and two of them (Runs A and B) even produce the same visible symptom. Section 04's test is what actually tells them apart.

04 · TECHNICAL MECHANISM

Three checks, in the order a query actually travels

CHECK 1

Was the evidence retrieved?

Inspect the retrieval log: did the chunk containing the needed fact appear anywhere in the candidate set actually returned? If no, stop — this is a retrieval failure, regardless of what happens afterward.

CHECK 2

Did the evidence survive into context?

Only asked if check 1 is yes. Inspect the exact assembled context sent to the model: is the retrieved evidence still there, intact and legible, or did truncation, ordering, or consolidation drop it? If no, this is an augmentation failure.

CHECK 3

Did the model use the evidence correctly?

Only asked if checks 1 and 2 are both yes. The evidence is confirmed present, intact, in context — if the answer still contradicts it, this is a generation failure, Concept 04's mechanism at work.

05 · ARCHITECTURE / FLOW

Three links overlaid on the same skeleton

Query↓Retrieval — Link 1↓Context — Link 2 (augmentation)↓LLM — Link 3 (generation)↓Answer

This isn't a new skeleton — it's Concept 06's same nine boxes, with three of them renamed as failure links rather than as pipeline stages. Retrieval, Context, and LLM were always there; what this concept adds is the claim that a wrong answer traces to exactly one of those three boxes, never to Query or Answer themselves, and never (on an answerable question) to more than one box being the root cause worth fixing first.

06 · IMPORTANT DISTINCTIONS

Where beginners collapse separate failures into one

ThisIs notBecause
The failure chain (this concept)Concept 10's answerability checkAnswerability asks whether a correct answer is possible at all; the chain presupposes "yes" and asks where a specific run's answer went missing
A retrieval failureConcept 10's coverage gapA coverage gap means the fact was never in the corpus at all; a retrieval failure means the fact was in the corpus but this run's candidate set missed it — confirming which one happened requires checking the whole corpus, not just one run's log
An augmentation failureA generation failureAugmentation failure means the evidence never reached the model's context intact; generation failure means it did reach the model intact and the model still misused it — Concept 04's grounded-misread is specifically the second case, never the first
Any one link breakingA vague "the pipeline is broken"Each link has a different owner and a different fix; treating all three as one undifferentiated failure means applying the wrong fix at least two-thirds of the time
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"A wrong answer means retrieval failed."

Not necessarily — Run C in Section 03 had perfect retrieval and still produced the wrong number. Retrieval is only one of three links, and often not the broken one.

"If the model hedges instead of answering, that proves retrieval failed."

Runs A and B in Section 03 produce the identical visible symptom — a hedge with no number — for two completely different underlying reasons. The symptom alone never tells you which link broke.

"Running this chain first is always the right move."

Only after Concept 10 confirms the question was answerable. Running the failure chain on a genuinely unanswerable question wastes effort diagnosing links that were never going to produce a correct answer regardless.

"If context assembly looks fine, generation must be the problem."

Confirm the exact evidence text is actually present in the prompt sent to the model, not just that "some context" was assembled — a truncated or malformed chunk can look present while missing the one sentence that mattered.

08 · YOUR PROJECT MAPPING

Localizing three broken runs of the same Oracle query

RETRIEVAL FAILURERun A never surfaces the remote-work document

Fix: improve chunking or query phrasing so "remote" and "telecommute" resolve to the same evidence — Modules 07-16's territory, not this concept's.

AUGMENTATION FAILURERun B retrieves correctly but drops the chunk during assembly

Fix: repair the context assembler's consolidation logic — Concept 17's territory, a completely different codepath from retrieval.

GENERATION FAILURERun C has correct, intact evidence and still answers wrong

Fix: this is Concept 04's grounded-misread — prompting and model-level remedies, not a retrieval or assembly change.

THE POINTSame query, same wrong-looking outcome, three different owners

Localizing the link before choosing a fix is what keeps engineering effort aimed at the actual cause.

The three links

Fixed order, single root cause

A query passes through the links in that order; on an answerable question, exactly one link is the one worth fixing first.

04
INTUITION

A package that never arrives correctly used

A package can fail to reach its recipient three different ways. The warehouse can pick the wrong item off the shelf, or none at all — nothing else that happens afterward matters once that's true. The right item can be picked correctly, then damaged or lost in transit before it reaches the door — the warehouse did its job, the courier didn't. Or the right, undamaged item can arrive intact, and the recipient can still misread the label and use it wrong. Only the third case is the recipient's fault; the first two never gave them a fair chance.

Analogy boundaryWarehouses and couriers don't have embeddings, token budgets, or attention weights. The point of the analogy is the structural claim only — three sequential opportunities to fail, each with a different owner — not anything about logistics.

PRECISION

Formal definitions

TermDefinitionBoundary
Retrieval failureGiven an answerable (question, corpus) pair, the chunk containing the needed fact does not appear in the candidate set the retriever actually returnsDistinct from a coverage gap: the fact is present somewhere in the corpus, but this run's candidate set missed it

06
MECHANISM

Tracing all four outcomes of one query

Intact run — retrieval surfaces the remote-work chunk at rank 1; augmentation assembles it intact into context; generation states "3 days," matching the evidence. All three links hold.
Run A, retrieval breaks — the remote-work chunk never enters the candidate set at all (vocabulary mismatch). Augmentation and generation never get a fair chance — there is nothing correct to assemble or use.
Run B, augmentation breaks — the remote-work chunk is retrieved at rank 1, but a consolidation bug discards it before the prompt is built. Retrieval held; the model, correctly, never saw the fact.
Run C, generation breaks — the remote-work chunk is retrieved and sits intact in context. Retrieval and augmentation both held. The model states "5 days" anyway — Concept 04's grounded-misread, replayed.
07
VISUALIZATION

One diagnostic hub, three possible verdicts

Retrieval failureevidence absent from the candidate set — check first, cheapest to rule out
Inspect the assembled context actually sent to the modelSection 04's fastest branch point
Augmentation failureevidence retrieved, dropped before reaching context
Generation failureevidence intact in context, model still wrong

The hub above is the required flow: inspecting the exact assembled context first is the fastest branch point, because its presence or absence of the needed fact instantly rules two of the three links in or out. Section 14's lab makes this concrete across four runs of the same query.

09
MATHEMATICS

A conjunction, not a disjunction

Concept 10's answerability predicate was a disjunction — a question was answerable if either of two conditions held. This concept's predicate is the opposite shape: a conjunction, because every link must hold for a correct answer. Let R(q) be 1 if the needed evidence chunk is in the retrieved candidate set, A(q) be 1 if that evidence survives intact into the assembled context, and G(q) be 1 if the generated answer correctly uses evidence present in context. Then, given Answerable(q, C) = 1 from Concept 10:

Correct(q) = R(q) ∧ A(q) ∧ G(q)

Read left to right: a correct answer requires all three terms to be true at once. A single false term — anywhere — drives the whole expression to false, exactly like a physical chain: strength is bounded by the weakest link, not averaged across the others. Locating which term is false is Section 04 and Section 07's diagnostic; this equation only states why checking all three, in order, is necessary rather than optional.

11
CONCRETE USE

Four cards: a clean fit, a boundary case, a counterexample, and a mistake

CLEAN FIT

Run C, from Section 06

Retrieval and augmentation both confirmed intact by inspection; the wrong answer is unambiguously the generation link's fault — exactly the case Concept 04's grounded-misread mechanism was built to explain.

BOUNDARY CASE

The evidence is split across two chunks, only one retrieved

If a fact requires combining two separate chunks and only one is retrieved, is that a retrieval failure or a partial one? By this concept's definition, yes — the full needed evidence was not in the candidate set, so it is a retrieval failure, even though part of it arrived.

COUNTEREXAMPLE

A wrong answer that is actually Concept 10's territory

If the fact is genuinely absent from the whole corpus, running this chain at all is a mistake — that is a coverage gap, decided before this concept ever applies, not a retrieval-link failure inside it.

MISTAKE TO AVOID

Diagnosing generation failure from the final answer alone

Runs A and B in Section 06 produce the same visible symptom as each other. Only inspecting the actual assembled context — not just the final answer — distinguishes a generation failure from the other two.

CODE

The failure-chain diagnostic, from scratch

PYTHON · LOCALIZE A BROKEN RUN TO EXACTLY ONE LINK 
def diagnose_failure(evidence_in_candidates, evidence_in_context, answer_matches_evidence):
    # Section 09's conjunction, spelled out as ordered branches --
    # the branch taken doubles as the localized link. Assumes
    # Concept 10 already confirmed the question is answerable.
    if not evidence_in_candidates:
        return "retrieval_failure"
    if not evidence_in_context:
        return "augmentation_failure"
    if not answer_matches_evidence:
        return "generation_failure"
    return "correct"


# Section 10's four runs, as boolean facts about each one
runs = [
    dict(evidence_in_candidates=True,  evidence_in_context=True,  answer_matches_evidence=True),   # intact
    dict(evidence_in_candidates=False, evidence_in_context=False, answer_matches_evidence=False),  # run A
    dict(evidence_in_candidates=True,  evidence_in_context=False, answer_matches_evidence=False),  # run B
    dict(evidence_in_candidates=True,  evidence_in_context=True,  answer_matches_evidence=False),  # run C
]

for run in runs:
    print(diagnose_failure(**run))
# correct
# retrieval_failure
# augmentation_failure
# generation_failure

assert diagnose_failure(False, False, False) == "retrieval_failure"
assert diagnose_failure(True, False, False) == "augmentation_failure"
assert diagnose_failure(True, True, False) == "generation_failure"
assert diagnose_failure(True, True, True) == "correct"
13
ECOSYSTEM

Where the three-link taxonomy comes from

Gao, Xiong, Gao et al. (2023/2024) structure their whole survey of RAG techniques around exactly this split — retrieval, augmentation, and generation as the three stages every improvement technique targets — which is the taxonomy this concept adopts directly rather than inventing a new one. Barnett, Kurniawan, Thudumu, Brannelly & Abdelrazek (2024) enumerate seven concrete failure points from production RAG systems that map onto this concept's three links: "missed the top-ranked documents" and "missing content" are retrieval-side; "not in context — consolidation strategy limitations" is exactly this concept's augmentation link, described at production scale; "not extracted," "wrong format," and "incorrect specificity" are generation-side, alongside Concept 04's grounded-misread. Chen, Lin, Han & Sun (2023), the RGB benchmark, isolates one of those generation-side failure modes for direct measurement — testing whether a model can resist noisy retrieved passages and correctly reject a question when the retrieved evidence doesn't actually support an answer, a generation-link capability distinct from anything retrieval or augmentation controls.

16
DIAGNOSIS

Failure modes — of the diagnostic itself

SKIPPED GATE

Running this chain before confirming answerability

Section 11's counterexample is the risk here — a genuine coverage gap can look like a chain failure until Concept 10's whole-corpus check rules it out first.

SYMPTOM-ONLY DIAGNOSIS

Judging the link from the final answer alone

Section 06's Runs A and B produce an identical visible symptom for different underlying reasons — the final answer alone cannot distinguish them.

UNVERIFIED CONTEXT

Assuming "context was assembled" means the fact survived

A context can be non-empty and still be missing exactly the sentence that mattered — confirm the specific needed text, not just that some text made it through.

MULTI-LINK BLINDNESS

Stopping at the first plausible-looking link

This concept's checks are ordered so an earlier failure makes later ones moot — but jumping straight to a guess about generation without confirming retrieval and augmentation first can misattribute a break that happened earlier in the chain.

CORRECTION

Misconceptions

Incorrect beliefCorrection

Augmentation failures and generation failures are the same problemAn augmentation failure means the model never had the evidence in front of it; a generation failure means it did and still got it wrong — different owners, different fixes.

18
REALITY

Production implications, at introductory depth

  • This entire diagnostic depends on logging that most systems don't get for free: the exact retrieved candidate list, the exact assembled context, and the exact model response — all three, per query, not just the final answer shown to the user.
  • Without context-level logging specifically, Section 07's fast hub check is unavailable, and every diagnosis falls back to the slower link-by-link strategy from Section 15 — or, worse, becomes a guess.
  • Module 19's distributed tracing gives each link its own observable span in a production system — forward-referenced here only, since building that instrumentation is out of this concept's scope.
19
RECALL

Knowledge check

Name the three links of the failure chain, in the order a query passes through them.
Retrieval, then augmentation, then generation — a query is retrieved, the retrieved evidence is assembled into context, and the model generates from that context, in that fixed order.
Why do Runs A and B in Section 06 produce the same visible symptom despite breaking at different links?
In both runs the model ends up with no usable evidence for the fact — in Run A because retrieval never found it, in Run B because augmentation dropped it after retrieval succeeded. The final answer alone can't reveal which happened; only inspecting the intermediate retrieval log and assembled context can.
Why is a generation-link failure the only one of the three that implicates the model itself?
Retrieval and augmentation failures both mean the model was never given a fair input — it behaved correctly given what it received. Only when the correct evidence is confirmed intact in context and the answer is still wrong does the failure trace to the model's own use of that evidence.

23
CAREER PRACTICE

Interview questions

A user reports a wrong answer from a RAG system on a question you've confirmed is answerable. Walk through how you would localize the failure to one of three links before changing any code.
Inspect the exact assembled context first — its content instantly rules two of three links in or out. If the needed fact is absent from context, check the retrieval log next to distinguish a retrieval failure (never in the candidate set) from an augmentation failure (retrieved, then dropped). If the fact is confirmed present and intact in context and the answer still contradicts it, it's a generation failure — only then does prompting or model choice become the right lever.
Why would "add a reranker" fix a retrieval-link problem but do nothing for a generation-link problem?
A reranker only reorders candidates that retrieval already found — it can improve which evidence makes it into the top-k, addressing a retrieval-link failure. It has no effect once the correct evidence is already in context and intact; a generation-link failure happens after reranking's job is already done.
Design question: what logging would you add to a production RAG system specifically to make this three-link diagnosis possible without manual reproduction?
Log, per query: the full ranked candidate list with scores (for the retrieval check), the exact final assembled context string sent to the model (for the augmentation check), and the raw model response alongside which context it was conditioned on (for the generation check). Without all three captured per request, diagnosing a failure after the fact requires reproducing it live, which isn't always possible.
