MODULE 06 · CONCEPT 03

Nothing here sits still
long enough to be opened.

Concept 02 opened five file formats, each one a fixed set of bytes with a format-specific parser. This concept covers four sources that are not files at all: a relational database (structured across tables, reachable only by a query), a REST or GraphQL API (a live system whose answer can change between two identical calls), a support ticket (structured fields wrapped around a free-text thread that keeps growing), and a code repository (source code plus a commit history, a very different kind of "prose" than a PDF). None of the four hand you their complete content by simply opening one thing.

01 · CONCEPT FIRST

Extraction from a queried or called source, not a parsed file

QUERYING / CALLING (THIS CONCEPT)

Getting usable knowledge out of a database (by writing a query), an API (by making a call), a ticket system (by reading its object model), or a code repository (by reading its history) — none of which sit still as one static file waiting to be opened.

NOT THIS CONCEPT (CONCEPT 02)

Opening a static file — PDF, HTML, .docx, .xlsx, or Markdown — that already contains everything it will ever tell you, and running a format-specific parser over its fixed bytes.

First memory: four sources, none of them a file — a query, a call, a growing case thread, and a revision history — and each one hides its usable knowledge behind something a file parser was never built to touch.
02 · WHY IT EXISTS

Some knowledge only exists behind a question, not inside a file

Concept 01's source inventory already assumed knowledge doesn't only live in files. A refund policy might be a PDF, but the actual refund a specific customer received is a row in an orders database — nobody wrote it down anywhere else. The current shipping status of a package is whatever a carrier's API says right now, not a downloaded snapshot from this morning. The real fix for a tricky bug is often buried three comments deep in a support ticket, not in the product's official documentation. And the reason a piece of business logic is written the way it is might live in a two-year-old commit message, not in any onboarding guide. None of these four sit still as one static file with an internal format to parse — you have to ask a database a question, call a live system, read a whole case thread, or read a revision history, not just open one thing.

03 · CONCRETE EXAMPLE

One fact, four sources, four reasons "just open it" doesn't apply

Suppose the fact you need is: "Customer #4471's refund was processed on day 40 of the 45-day window." That exact fact could live in any of these four sources, and none of them let you get it by simply opening something:

DATABASE

There is no "refund file" to open — the fact is a value split across columns in an orders table, invisible until a query with the right conditions and joins asks for it.

API

Calling the same order-status endpoint twice can return two different answers. Yesterday it said "processing"; today it says "refunded." There is no static copy to parse — only whatever the live system currently reports.

TICKET

The ticket's title says "Refund taking too long." The actual answer — "refunded on day 40, delay was our address-verification queue" — is comment #7 of 9, not the ticket's own summary field.

CODE REPO

The number 45 lives in refund_policy.py as a bare constant. The reason it's 45 and not 30 is in a commit message from fourteen months ago, not anywhere in the code itself.

Four sources, one fact, four different reasons a naive "open it and read it" never gets you there.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"A database is basically a big spreadsheet — read the whole table into one document."

Normalization means a single customer's full story is usually split across several joined tables, not sitting in one row of one table.

"An API response can be captured once and treated like a downloaded file from then on."

That only holds if the underlying data is genuinely static. For anything that changes, a one-time capture goes stale, and someone has to decide a refresh cadence — Concept 09's job, not this one's.

"A ticket's title and description are the whole story."

The real answer is very often in a later comment, not the opening fields — extracting only the summary can capture the problem and lose the fix.

"The code itself is the knowledge worth indexing."

Often the commit messages, docstrings, and comments around the code carry more retrievable meaning than the syntax itself.

04
INTUITION

A filing cabinet, a phone line, a growing case folder, a diary in code

A file is a sealed letter: open it once and you have everything it will ever tell you. A database is a filing cabinet with a clerk — the clerk won't hand you a whole drawer, only the specific slips you ask for by name and by relation to other slips; phrase the request slightly wrong and you get the wrong slips, or the same slip handed to you more than once. An API is a phone line to a live person, who might genuinely have a different answer if you call back in an hour, through no fault of the line itself. A support ticket is a case folder that keeps growing new pages after the first one was written, and it's very often the last page, not the first, that actually matters. A code repository is a diary written mostly in a foreign language — the code itself — except for margin notes (comments and docstrings) and the entry written beside each edit (the commit message), which are the parts actually written in the language you understand.

Analogy boundaryNone of these four is inherently harder than a file, just differently shaped. Each one hands back exactly what you ask for, or exactly what happened, on its own terms — not on a fixed page you can simply turn to.

06
MECHANISM

Four branches, one shared shape

Identify the source type — database, API, ticket system, or code repository — before choosing which extraction action applies.
Database lane — write a query, often a join across foreign keys, run it, and serialize each returned row or grouped row-set into a text record (Section 09's rule governs exactly what a join returns).
API lane — call the endpoint, handle authentication and pagination, and snapshot the response together with a capture timestamp.
Ticket lane — read the case's structured fields, then read the full comment thread in order, and decide the retrievable unit: the opening ticket alone, the resolving comment alone, or the whole thread.
Code lane — read the current file tree for structure, read the commit history for author-written messages, and keep code, comments, and commit messages as distinct signal types rather than one flattened blob.
Handoff — every lane still ends at the same place: raw, unclean, unchunked records, passed forward to Concept 05, exactly like Concept 02's five file lanes.

09
MATHEMATICS

How many rows a join actually returns

Let a left-side table L have rows l₁,…,l_n, and let m(l) be the number of rows in a related table R that match row l on a foreign key. An INNER JOIN and a LEFT JOIN return different row counts from the exact same two tables:

rows_inner = Σ m(l) over all l where m(l) > 0 contributes m(l), and m(l) = 0 contributes 0 rows_left = Σ max(m(l), 1) every l contributes at least one row

Two consequences follow directly from that sum. First, any row l with m(l) = 0 contributes exactly 0 to rows_inner — an INNER JOIN doesn't flag it, it simply never appears in the result at all, which is why the count of dropped rows is |{l : m(l) = 0}|. Second, any row l with m(l) > 1 contributes more than one row to either join, repeating every one of l's own columns once per match — the count of duplicated rows is |{l : m(l) > 1}|. This is the exact formal reason "one returned row = one retrievable document" is a shape mismatch whenever the underlying relationship isn't strictly one-to-one.

WORKED EXAMPLE

Joining customers to orders, by hand

Four customers, 101–104, with these order counts: m(101) = 2, m(102) = 1, m(103) = 0, m(104) = 3. Applying Section 09's formulas:

CustomerOrders m(l)Rows in INNER JOINRows in LEFT JOIN
101222
102111
103001 (with NULL order fields)
104333

rows_inner = 2 + 1 + 0 + 3 = 6. rows_left = max(2,1) + max(1,1) + max(0,1) + max(3,1) = 2 + 1 + 1 + 3 = 7. Listing the six INNER JOIN rows explicitly confirms it: (101,orderA), (101,orderB), (102,orderC), (104,orderD), (104,orderE), (104,orderF) — customer 103 never appears at all, and customers 101 and 104 each appear more than once. Treating "one row = one document" here would produce two near-duplicate documents repeating customer 101's own profile fields, three repeating customer 104's, and zero documents ever mentioning customer 103 — even though customer 103 exists in the source of truth.

11
CONCRETE USE

Four cases: two clean fits, a boundary case, a mistake

CLEAN FIT

A one-to-one lookup query

"SELECT plan_name, price FROM plans WHERE plan_id = 7" returns exactly one row — no fan-out risk at all, because the match count is always exactly one by construction.

CLEAN FIT

A ticket closed by its second comment

Treating the fields plus the full two-comment thread as one retrievable unit loses nothing and adds no noise — the thread is short enough that "the whole thing" and "the resolution" are the same content.

BOUNDARY CASE

A GraphQL query nesting related objects in one call

Nesting avoids REST's multiple-round-trip pagination problem, but a single response can still mix several levels of one-to-many relationships at once — the same join-style duplication risk from Section 09 applies inside one API response, not only inside a SQL result set.

MISTAKE TO AVOID

Feeding raw .py files through Concept 02's document parsers

Source code is syntax, not prose; running it through an HTML or Markdown parser either produces meaningless "documents" or silently skips the commit messages and docstrings that actually carried the retrievable knowledge.

12
CODE

Join fan-out, from scratch

This is the mechanism behind Section 09's formulas, applied to Section 10's exact customer/order counts — not a real SQL engine, but the same row-multiplication logic a database performs internally when it executes a join.

PYTHON · SIMULATING INNER AND LEFT JOIN ROW COUNTS 
from collections import defaultdict

customers = [101, 102, 103, 104]
orders = [
    (101, "orderA"), (101, "orderB"),
    (102, "orderC"),
    (104, "orderD"), (104, "orderE"), (104, "orderF"),
]

orders_by_customer = defaultdict(list)
for cust_id, order_id in orders:
    orders_by_customer[cust_id].append(order_id)

def inner_join(customers, orders_by_customer):
    return [(c, o) for c in customers for o in orders_by_customer.get(c, [])]

def left_join(customers, orders_by_customer):
    return [(c, o) for c in customers for o in (orders_by_customer.get(c) or [None])]

inner_rows = inner_join(customers, orders_by_customer)
left_rows = left_join(customers, orders_by_customer)

assert len(inner_rows) == 6                       # 2 + 1 + 0 + 3
assert len(left_rows) == 7                        # 2 + 1 + 1 + 3

dropped = [c for c in customers if not orders_by_customer.get(c)]
assert dropped == [103]                           # zero-order customer vanishes from INNER only

duplicated = [c for c in customers if len(orders_by_customer.get(c, [])) > 1]
assert duplicated == [101, 104]                   # each appears once per order in either join

# Edge case: a customer with exactly one order never drops or duplicates.
assert orders_by_customer[102] == ["orderC"]

ECOSYSTEM

The same four branches, in real tools

Database: python-oracledb connects directly to Oracle and runs SQL; SQLAlchemy and pyodbc offer the same query-and-serialize pattern across other relational engines. API: requests and httpx handle REST calls, pagination, and auth headers; a GraphQL client (e.g. gql) issues nested queries in one round trip instead of many. Ticket systems: Jira, Zendesk, and ServiceNow each expose a REST API returning a ticket's structured fields alongside its comment thread as separate, readable objects. Code repositories: git log and GitPython read commit history and messages directly from a local clone; platform APIs (GitHub, GitLab) expose the same history remotely; a syntax-aware reader such as tree-sitter parses source code into a structure that can isolate docstrings and comments without treating the surrounding syntax as prose. Framework-level connectors (LangChain, LlamaIndex — Modules 12 and 14) wrap several of these behind one common loader interface, trading fine-grained query control for a consistent call shape across source types, the same trade Concept 02 named for file loaders.

16
DIAGNOSIS

Failure modes

SILENT ROW LOSS

An INNER JOIN drops a zero-match row without any error

Section 09 showed why: a row with m(l) = 0 contributes nothing to the sum and simply isn't in the output — indistinguishable from "this record was never in the source" unless someone checks the join type used.

STALE SNAPSHOT

A captured API response is never refreshed

Nothing about a stored snapshot looks wrong, because there's no file to look wrong — it just keeps answering with an outdated state until a refresh cadence (Concept 09) is defined and run.

WRONG RETRIEVABLE UNIT

Only a ticket's opening description gets indexed

Retrieval finds "the problem" described at the start but never "the fix," because the resolving comment several messages later was never made part of the retrievable record.

CORRECTION

Misconceptions

Incorrect beliefCorrection
A database export is the same shape as a documentFalse — Section 10's worked example: a joined result set can duplicate rows for a one-to-many match and silently drop rows for a zero match, neither of which a file parser ever does.
An API's response is a fixed thing, capturable once like a fileFalse — Section 04's intuition: unless the underlying resource is genuinely static, the exact same call can return a different answer at a later time, through no defect in the request.
The code is the knowledge worth retrievingFalse — Section 06's mechanism: for RAG purposes, the retrievable knowledge is very often the commit message or comment beside the code, not the syntax itself.
18
REALITY

Production implications

  • Query cost and load are real constraints — a poorly written join or a full-table export run on a schedule can put meaningful load on a production database, so ingestion queries usually run against a read replica or with explicit throttling, not directly against the live transactional system.
  • Auth, pagination, and rate limits are first-class ingestion logic, not edge cases — every API-backed extraction has to handle token expiry, paginated responses, and rate-limit backoff as part of the extraction step itself.
  • Refresh cadence is a real decision that has to be made explicitly — unlike a file, nothing forces anyone to notice when a database or API's underlying data changed, so "how often do we re-pull this" needs an actual answer, previewed by Concept 09's incremental and event-driven ingestion.
19
RECALL

Knowledge check

Why does an INNER JOIN between customers and orders silently drop a customer with zero orders?
Because rows_inner = Σ m(l), and a customer with m(l) = 0 contributes exactly 0 to that sum — the customer never appears in the result set at all, with no error or warning marking the absence.
What can a second, identical API call return that a second read of a downloaded file never can?
A different answer. A file's bytes don't change between two reads; a live API's underlying resource can change between two calls, so the same request can legitimately return two different current states.
Why might a ticket's opening description be the wrong field to treat as its retrievable summary?
Because the actual resolution — the fact someone searching would actually want — is very often written in a later comment, not in the fields captured when the ticket was first opened.

23
CAREER PRACTICE

Interview questions

Why can a SQL join change how many times a customer's data appears in your extracted output, and what's the fix?
A one-to-many relationship makes a customer's row repeat once per matching row on the other side (fan-out) or vanish entirely under an INNER JOIN if there are zero matches. The fix is deciding the retrievable unit deliberately — e.g. aggregate all matches into one record per customer, or explicitly choose LEFT JOIN plus a "no matches" placeholder, rather than treating each returned row as automatically one document.
You need to ingest a support ticket system into a RAG corpus. What's wrong with treating each ticket's description field as its whole retrievable content?
The description captures the reported problem at the moment the ticket was opened, but the actual resolution is very often written in a later comment. Indexing only the description means retrieval can surface the problem but never the answer that closed it.
Design question: how would you decide how often to re-extract from a REST API that updates several times a day?
Weigh how quickly staleness actually harms answers against the API's rate limits and the extraction job's cost; for status-like data, an event-driven or short-interval poll (Concept 09) is often justified, while for slower-moving reference data a longer fixed schedule is enough — the decision has to be explicit rather than defaulted to "whenever we happened to run ingestion last."
A teammate wants to index a git repository by feeding every .py file through Concept 02's HTML/Markdown parser. What's wrong with that plan?
Source code is syntax governed by a formal grammar, not prose — a document parser has no way to distinguish meaningful code structure from arbitrary text, and running one over .py files either yields meaningless extracted "documents" or silently skips the commit messages and docstrings that actually carry retrievable knowledge.
