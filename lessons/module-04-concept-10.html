02 · WHY IT EXISTS

Nine correct facts don't automatically prove they connect

Each earlier concept's worked example used its own numbers, chosen to make that one formula clear. Nothing in Module 04 so far has shown the OUTPUT of one concept feeding directly into the INPUT of the next, on the same data, end to end. This concept exists purely to close that gap — after this, Module 05 can build on "this module's math works as one pipeline," not just "nine separate formulas were each individually correct."

03 · CONCRETE EXAMPLE

One query, two candidates, geometric stage

Query A = (3, 4). Candidates: B = (6, 8), C = (4, 3). Same numbers, run through Concepts 02-04 in order.

NORMS · CONCEPT 02

‖A‖ = 5, ‖B‖ = 10, ‖C‖ = 5. (B is exactly twice A — same direction, different length.)

COSINE SIMILARITY · CONCEPT 03

cos(A, B) = 1.0 (identical direction) · cos(A, C) = 0.96 — B looks more similar by direction.

RAW DISTANCE · CONCEPT 04

dist(A, B) = 5.0 · dist(A, C) = 1.4142 — by raw distance, C looks CLOSER. Raw distance and cosine disagree.

NORMALIZED DISTANCE · CONCEPTS 02 + 04

Normalize first: dist(Â, B̂) = 0.0 · dist(Â, Ĉ) = 0.2828 — now B is closer, agreeing with cosine. Normalizing resolved the disagreement, exactly as Concept 04 proved it always does.

04 · TECHNICAL MECHANISM

The same three points, probabilistic and cost stages

SOFTMAX · CONCEPT 06

Treat [cos(A,B), cos(A,C)] = [1.0, 0.96] as raw scores: softmax gives [0.5100, 0.4900] at T=1 — a genuine distribution, still favoring B, exactly as cosine did.

ENTROPY · CONCEPT 07

H(P) ≈ 0.6929 nats — this distribution is close to uniform, reflecting how close cos(A,B) and cos(A,C) actually are (1.0 vs. 0.96).

CROSS-ENTROPY · CONCEPT 07

If B is the actually-correct candidate: −ln(0.5100) ≈ 0.6733 nats — a moderate loss, since the distribution is only mildly confident.

RANKING & COST · CONCEPTS 08-09

Ranking B > C needs only the raw scores, no softmax (Concept 08). For n=2 candidates at d=2 dimensions: one score is 2 operations, brute-force search is 4, sorting is 2 comparisons, storage is 16 bytes (Concept 09) — every cost formula, evaluated at this example's actual size.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Each concept's math is independent of the others."

b04's softmax input is literally b03's cosine output — the probabilistic thread consumes the geometric thread's numbers directly, not a fresh example.

"The raw-distance-vs-cosine disagreement in Concept 04 was a one-off, contrived example."

The identical disagreement reappears here with the same A, B, C — it's a structural fact about un-normalized vectors, not a coincidence of one example.

"Softmax, entropy and cross-entropy only matter with a big corpus."

b04 computes all three from just 2 candidates — the formulas don't require scale, scale only changes Concept 09's cost.

"This concept adds a new example to memorize."

It reuses the numbers to prove a connection, not to introduce new content — the takeaway is the chain, not the specific coordinates.

Every stage in Section 06 composes into a single function of the query and candidates:

12
CODE

The entire pipeline, end to end, from scratch

PYTHON · NO LIBRARIES 
import math

A, B, C = (3.0, 4.0), (6.0, 8.0), (4.0, 3.0)

def norm(v): return math.sqrt(v[0]**2 + v[1]**2)                     # Concept 02
def dot(u, v): return u[0]*v[0] + u[1]*v[1]
def cosine(u, v): return dot(u, v) / (norm(u) * norm(v))             # Concept 03
def distance(u, v): return math.sqrt((u[0]-v[0])**2 + (u[1]-v[1])**2)  # Concept 04
def normalize(v):
    n = norm(v)
    return (v[0]/n, v[1]/n) if n > 0 else (0.0, 0.0)

def softmax(z, T=1.0):                                               # Concept 06
    m = max(z)
    exps = [math.exp((x - m) / T) for x in z]
    total = sum(exps)
    return [e / total for e in exps]

def entropy(p): return -sum(x * math.log(x) for x in p if x > 0)     # Concept 07
def cross_entropy(p, correct_idx): return -math.log(p[correct_idx])  # Concept 07

# The chain, run once, in order:
n_a, n_b, n_c = norm(A), norm(B), norm(C)
cos_ab, cos_ac = cosine(A, B), cosine(A, C)
raw_ab, raw_ac = distance(A, B), distance(A, C)
norm_ab, norm_ac = distance(normalize(A), normalize(B)), distance(normalize(A), normalize(C))
probs = softmax([cos_ab, cos_ac])
h = entropy(probs)
ce_b = cross_entropy(probs, 0)
ranking = "B > C" if cos_ab >= cos_ac else "C > B"

assert (n_a, n_b, n_c) == (5.0, 10.0, 5.0)
assert round(cos_ab, 2) == 1.0 and round(cos_ac, 2) == 0.96
assert raw_ab > raw_ac                     # raw distance disagrees with cosine's ranking
assert norm_ab < norm_ac                   # normalized distance agrees with cosine's ranking
assert round(probs[0], 4) == 0.5100
assert round(ce_b, 4) == 0.6733
assert ranking == "B > C"

n, d = 2, 2                                # Concept 09, at this example's actual size
assert n * d == 4 and n * math.log2(n) == 2 and n * d * 4 == 16

16
DIAGNOSIS

Failure modes

SKIPPING NORMALIZATION

Using raw distance to rank when cosine was the intended metric

b03's own numbers show this can silently flip a ranking — C would look closer than B by raw distance alone, the wrong answer for this example's intended similarity notion.

MIXING UP STAGES

Feeding a raw score into a formula expecting a probability, or vice versa

Section 06's ranking function wants raw scores directly (no softmax); Section 07's cross-entropy wants a softmax output — swapping them produces a number that parses but means nothing.

TESTING ONLY THE FINAL OUTPUT

Checking only the final ranking, never the intermediate values

Section 10's full table is exactly the fix — a pipeline that returns the right final ranking by accident (e.g., two compensating bugs) would still fail an intermediate-value check.

FORGETTING THE COST SCALES

Assuming this example's trivial cost generalizes to any size

Section 15's contrast is the reminder — the formulas don't change, but Concept 09's cost terms grow from trivial to dominant as n and d grow.

Production implications

FEEDBACK

Solution and teach-back

Open the worked solution
‖D‖ = √(4+36) = √40 ≈ 6.3246. dot(D,B) = 12+48 = 60, so cos(D,B) = 60/(6.3246×10) ≈ 0.9487. dot(D,C) = 8+18 = 26, so cos(D,C) = 26/(6.3246×5) ≈ 0.8225. Raw distance: dist(D,B) = √(16+4) = √20 ≈ 4.4721; dist(D,C) = √(4+9) = √13 ≈ 3.6056 — C is raw-closer, while B has higher cosine similarity, so raw distance and cosine DISAGREE, same pattern as b03. Final ranking by cosine (and by softmax's larger share): B > C.

CAREER PRACTICE

Interview questions

Walk through, end to end, what happens when a query vector is compared against a set of candidate document vectors in a dense retrieval system.
Compute each candidate's norm and the query's norm (Concept 02), score each candidate by cosine similarity or distance (Concepts 03-04), optionally convert those scores to a distribution via softmax for a training signal (Concept 06), measure that distribution's uncertainty and its agreement with a known-correct label via entropy and cross-entropy during training (Concept 07), and rank candidates directly from the raw scores at inference (Concept 08) — all at a cost governed by Concept 09's O(n·d) and O(n log n) terms.
Why might a system that ranks correctly still fail an end-to-end pipeline test?
Because two compensating errors in intermediate stages (Section 16) can still produce a correct final ranking by coincidence — Section 10's full-table test catches this by checking every intermediate value, not just the final output.
Design question: you're asked to write a regression test suite for a retrieval pipeline. What should it check, based on this concept?
