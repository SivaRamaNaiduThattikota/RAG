Every mechanism wins one axis.

Concepts 02-05 each measured HNSW, IVF and quantization on at most two of three axes -- recall, latency, memory. This concept builds no new mechanism, corpus or algorithm at all. 02 · WHY IT EXISTS

Four concepts, four partial views -- this is the first full one

Concept 03 (HNSW) and Concept 04 (IVF) each measured recall and latency for their own mechanism, but neither one ever cited a memory number. Concept 05 (quantization) measured memory precisely -- and explicitly scoped recall and latency out, stating directly that "this widget shows memory cost only... that three-way generalization is Concept 06's own subject." This concept is that payoff: the first pass in the module that puts recall, latency and memory numbers from four different concepts side by side, on the same page, at the same time.

04 · TECHNICAL MECHANISM

Which cited dial moves which axis-pair

Sort every dial this module has built by which axis-pair it actually moves, per this module's own citations. ef_search (HNSW, Concept 03) and nprobe (IVF, Concept 04) both trade recall against latency, with memory roughly fixed -- turning either dial up buys recall points at a latency cost, and turning it down does the reverse. nbits and M (quantization, Concept 05) trade memory only -- Concept 05 built and cited the byte-cost formula for that dial, but never cited what happens to recall or latency when it moves. That is not an oversight; it is this module's own honest citation gap, restated directly rather than filled in with a guess.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"One system can be optimal on all three axes at once."

False, per the table -- among the seven cited rows, the recall winner is the latency loser, the latency winner gives up the most recall, and the memory winner has no cited recall or latency number at all.

"The cost of the next recall point is always the same."

False -- the derived marginal-cost figures (Section 09/10) rise sharply near 100%: IVF→Flat's next recall point costs roughly 14.4x more than HNSW→IVF's own next point.

"Quantization has zero effect on recall in practice."

Neither asserted nor denied here -- this module never measured it. Flagged honestly as unmeasured, not filled in with a plausible-sounding guess.

INTUITION

A three-resource budget, grounded in this module's own numbers

Think of recall, latency and memory as three separate budgets a system spends against at once -- the way time, money and space compete against each other in almost any real plan. Spending more of one (accepting slower queries, in exchange for higher recall) doesn't refund the other two for free; Concept 05's own quantization dial spends memory specifically, without any cited receipt for what it costs on the other two budgets.

The IVF→Flat step's own marginal recall point costs about 14.42x more than the HNSW-nmslib→IVF step's own marginal point (0.0839 ÷ 0.0058). The IVF→Flat step also costs about 10.65x more than the ef_search 16→256 dial's own marginal point, and that dial's own point costs about 1.35x more than the HNSW-nmslib→IVF step's -- three different dials, three different marginal prices, all rising as recall approaches 100%. CODE

Recomputing every marginal-cost figure from the cited operating points

PYTHON · FROM SCRATCH -- REPRODUCES THIS CONCEPT'S OWN MARGINAL-COST NUMBERS EXACTLY 
# Every input below is a direct citation from Concepts 02-03; only the
# division/subtraction combining them is new to this concept.
rows = {
    "flat":   {"recall": 100.00, "latency_ms": 0.91},    # Concept 02
    "ivf":    {"recall": 89.80,  "latency_ms": 0.0538},  # Concept 02
    "hnsw_nmslib": {"recall": 81.95, "latency_ms": 0.0081},  # Concept 02
    "hnsw_ef16":   {"recall": 87.40, "latency_ms": 0.011},   # Concept 03
    "hnsw_ef256":  {"recall": 99.20, "latency_ms": 0.104},   # Concept 03
}

def cost_per_point(lo_key, hi_key):
    lo, hi = rows[lo_key], rows[hi_key]
    d_recall = hi["recall"] - lo["recall"]
    d_latency = hi["latency_ms"] - lo["latency_ms"]
    return d_latency / d_recall

ivf_to_flat = cost_per_point("ivf", "flat")
hnsw_to_ivf = cost_per_point("hnsw_nmslib", "ivf")
ef16_to_ef256 = cost_per_point("hnsw_ef16", "hnsw_ef256")

assert round(ivf_to_flat, 4) == 0.0839
assert round(hnsw_to_ivf, 4) == 0.0058
assert round(ef16_to_ef256, 4) == 0.0079
assert round(ivf_to_flat / hnsw_to_ivf, 2) == 14.42
assert round(ivf_to_flat / ef16_to_ef256, 2) == 10.65
assert round(ef16_to_ef256 / hnsw_to_ivf, 2) == 1.35

speedup_ef256_vs_flat = rows["flat"]["latency_ms"] / rows["hnsw_ef256"]["latency_ms"]
recall_gap_ef256_vs_flat = rows["flat"]["recall"] - rows["hnsw_ef256"]["recall"]
assert round(speedup_ef256_vs_flat, 2) == 8.75
assert round(recall_gap_ef256_vs_flat, 2) == 0.80

CAREER PRACTICE

Interview questions

Conceptual: why is it misleading to ask "which vector index is best" without qualification?
Because "best" depends on which of recall, latency and memory is the binding constraint -- per this concept's own table, no cited mechanism wins on more than one axis, so "best" always means "best for this specific constraint."
Mathematical: given recall/latency pairs (89.80%, 0.0538 ms) and (81.95%, 0.0081 ms), compute the marginal cost-per-recall-point between them.
Δrecall = 89.80 - 81.95 = 7.85 points. Δlatency = 0.0538 - 0.0081 = 0.0457 ms. Cost/point = 0.0457 / 7.85 ≈ 0.0058 ms/point -- exactly this concept's own HNSW-nmslib→IVF figure.
Coding: extend Section 12's script to compute the marginal cost-per-recall-point between row 1 (Flat) and row 5 (ef_search=256) directly.
Δrecall = 100.00 - 99.20 = 0.80 points. Δlatency = 0.91 - 0.104 = 0.806 ms. Cost/point = 0.806 / 0.80 ≈ 1.0075 ms/point -- far higher than any other step in the table, showing the last 0.80 recall points toward exact search are the single most expensive ones cited anywhere in this concept.
System design: a team wants "IVF's speed with Flat's recall." What does this concept's own table say about that request?
No cited row offers both -- the table's own headline is that no mechanism wins recall and latency simultaneously among the cited numbers. The real answer is to pick an explicit operating point (e.g. row 5, HNSW ef_search=256) that trades a small, named amount of recall for a large, named amount of speed, or to measure a combined mechanism like IVF-PQ that this module never built.
Debugging: a system measured only memory before shipping quantization, and recall regressed in production. What does this concept's own table say went wrong?
Exactly the gap rows 6-7 flag directly -- quantization's own recall/latency impact was never cited or measured in this module, so shipping on the memory number alone, without measuring recall separately, is the precise mistake this concept warns against.
