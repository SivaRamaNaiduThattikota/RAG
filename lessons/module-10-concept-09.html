MODULE 10 · CONCEPT 09

UPDATE doesn't touch the index.
It touches the row -- and leaves the index to catch up.

Every INSERT since Concept 03 assumed the corpus only grows. Real corpora also change: a bad embedding gets corrected, a row gets deleted for good. This concept writes real UPDATE and DELETE SQL against this course's own chunks and embeddings tables, wraps them in real multi-statement transactions, and checks what Oracle's own documentation says happens to Concept 06's own vector index once those statements commit. Two verified facts anchor it: an IVF index's accuracy "may diminish over time due to DML operations," per Oracle's own guidelines page, and a DELETE that violates a foreign key raises ORA-02292 -- "child record found" -- before it ever reaches commit.

PROGRESSIVE BEGINNER CORE

The corpus doesn't just grow

Concepts 03-08 only ever added rows. This concept covers the other half of a real system's life: correcting a row that's already there (UPDATE), removing one for good (DELETE), doing both inside a real transaction, and what happens to the vector index sitting on top once that transaction commits.

01 · CONCEPT FIRST

The commit boundary and the index are two different things

An UPDATE or DELETE runs inside a transaction, same as the INSERTs in Concept 08 -- nothing is durable until connection.commit() runs, and connection.rollback() discards it as if it never happened. That commit boundary is a real, Oracle-enforced guarantee about the row. It says nothing at all about the vector index (Concept 06) sitting on top of that row -- Oracle's own documentation treats index freshness as a separate, asynchronous concern.

First memory: COMMIT makes the row change durable. It does not, by itself, rebuild or refresh the vector index -- that's a second, separate step this concept names explicitly.
02 · WHY IT EXISTS

An Oracle DELETE is not an ANN-library tombstone

Module 09 Concept 08 already covered updates, deletes and tombstones -- but at the generic ANN-library level: FAISS, Weaviate, Qdrant. There, a deleted row typically stays physically present, flagged invalid, until a later compaction pass. This concept is about what an Oracle-real DELETE does to rows in this course's own five tables (they're just gone, once committed -- no tombstone), and, separately, what Oracle's own documentation says happens to an already-built vector index once the rows under it mutate.

03 · CONCRETE EXAMPLE

Correcting a bad embedding, in place

Ops discovers chk_9f21_2_03's embedding was produced by a defective pooling step in the embedding pipeline -- the chunk_text itself ("To reset a vendor account, an admin must...") never changed, only its vector was wrong. The fix is a real UPDATE: cursor.execute("update embeddings set embedding = :1 where chunk_id = :2", [array.array("f", [0.0, 1.0, 0.0]), "chk_9f21_2_03"]), then connection.commit(). Nothing about the chunk's identity changes -- same chunk_id, same row -- only the embedding column.

04 · TECHNICAL MECHANISM

UPDATE and DELETE, the same cursor.execute() pattern

Both statements use the exact call shape Concept 08 already established: cursor.execute(sql_text, bind_values), then connection.commit() or connection.rollback(). What's new is the SQL itself -- UPDATE ... SET ... WHERE chunk_id = :1 and DELETE FROM ... WHERE chunk_id = :1 -- and one rule that only matters for DELETE: a foreign key means order inside the transaction is not optional.

05 · ARCHITECTURE / FLOW

Delete the child first, or Oracle stops you

DELETE FROM embeddings WHERE chunk_id='chk_9f21_2_04' — child row, safe→ DELETE FROM chunks WHERE chunk_id='chk_9f21_2_04' — parent row, now safe too→ COMMIT — both gone, for good

Reverse that order and the second statement never runs. Per Oracle's own error-help documentation: "ORA-02292: integrity constraint (string.string) violated - child record found. Cause: attempted to delete a parent key value that had a foreign key dependency. Action: delete dependencies first then parent or disable constraint." embeddings.chunk_id REFERENCES chunks.chunk_id (Concept 03) is exactly that dependency.

06 · IMPORTANT DISTINCTIONS

Three ways a row can change, and they are not the same

OperationWhat it's actually for
INSERT a new document_versions row (Concept 03's own CURRENT/SUPERSEDED pattern)The document's content changed. Old chunks/embeddings stay put, untouched, so old citations still resolve -- nothing here is an UPDATE or a DELETE.
UPDATE embeddings.embedding in place (this concept)The content didn't change -- the embedding pipeline produced a bad vector for it and needs correcting. Same chunk_id, same row.
DELETE FROM embeddings / chunks (this concept)The row itself should no longer exist at all -- not superseded, not corrected, gone. Requires child-before-parent order.
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"I can delete rows in whatever order I want, as long as both statements run."

Not with a foreign key in place. embeddings.chunk_id REFERENCES chunks.chunk_id means the child row (embeddings) must go first -- deleting the parent (chunks) while the child still exists raises ORA-02292, per Oracle's own error-help page.

"COMMIT also refreshes the vector index."

It doesn't. COMMIT is a guarantee about the row's durability. Per Oracle's own guidelines-using-vector-indexes documentation, an IVF index's accuracy "may diminish over time due to DML operations" -- checking and fixing that is a separate, explicit step, not a side effect of COMMIT.

INTUITION

The filing-cabinet folder and the card catalog

Correcting a folder inside a filing cabinet -- swapping out the wrong document for the right one -- is a fast, local edit. The card catalog sitting in the lobby, telling visitors where to find things, doesn't know that happened. It's still accurate about which cabinet and drawer the folder lives in; it just doesn't know the contents changed. An UPDATE or DELETE against embeddings is the folder edit. Concept 06's own vector index is the card catalog -- it isn't wrong about where the row lives, but per Oracle's own documentation, its own sense of which rows are near which other rows can drift out of date the more the underlying folders get edited.

06
MECHANISM

Same execute()/commit() shape, two new statement types

Concept 08 established the round trip: cursor.execute(sql, binds), then connection.commit() or connection.rollback(). UPDATE and DELETE use that exact shape -- only the SQL text changes. UPDATE embeddings SET embedding = :1 WHERE chunk_id = :2 corrects one row without touching its identity. DELETE FROM embeddings WHERE chunk_id = :1 followed by DELETE FROM chunks WHERE chunk_id = :1 removes a row for good -- in that order, because embeddings.chunk_id REFERENCES chunks.chunk_id (Concept 03) makes chunks the parent. Per python-oracledb's own transaction-management documentation, already cited in Concepts 02 and 08: "By default, python-oracledb does not commit this transaction to the database." That is exactly as true of two DELETE statements sharing one transaction as it was of a single INSERT -- neither is durable until commit() runs, and both can be undone together by one rollback().

The same cosine distance, recomputed after a mutation

cosine_distance(a, b) = 1 − (a · b) / (‖a‖ ‖b‖) — unchanged from Concept 08. This concept adds no new formula; it only recomputes the same distance after one bind value in one row changes, and checks whether the ranking that follows still matches what a full, exact recomputation would say.

WORKED EXAMPLE

Correct one row, remove another, verify both

Starting state, inherited exactly from Concept 08: chk_9f21_2_03 at [0.6, 0.8, 0.0] (dist 0.04 to query_embedding = [0.8, 0.6, 0.0], rank 1) and chk_9f21_2_04 at [0.0, 0.0, 1.0] (dist 1.00, rank 2, the lab-only contrast row Concept 08 invented). Two things happen to this state, in two separate transactions.

PYTHON · TRANSACTION B — DELETE chk_9f21_2_04, CHILD BEFORE PARENT 
cursor.execute("delete from embeddings where chunk_id = :1", ["chk_9f21_2_04"])  # child row -- safe
cursor.execute("delete from chunks where chunk_id = :1", ["chk_9f21_2_04"])      # parent row -- now safe too
connection.commit()
# chk_9f21_2_04 no longer exists in either table -- not tombstoned, not flagged, gone
Reverse the order and this happens instead
cursor.execute("delete from chunks where chunk_id = :1", ["chk_9f21_2_04"])
# raises before this line is ever reached:
# ORA-02292: integrity constraint (...) violated - child record found
cursor.execute("delete from embeddings where chunk_id = :1", ["chk_9f21_2_04"])
Per Oracle's own error-help documentation for this exact code, confirmed live: "Cause: attempted to delete a parent key value that had a foreign key dependency. Action: delete dependencies first then parent or disable constraint." embeddings.chunk_id REFERENCES chunks.chunk_id (Concept 03) is that dependency -- the statement fails at cursor.execute() time, before commit or rollback ever becomes a question.

After both transactions commit: one row remains, chk_9f21_2_03, embedding [0.0, 1.0, 0.0], and it is trivially first (and only) against the same query. Neither the UPDATE nor the DELETE touched embeddings_ivf_idx directly -- per Oracle's own guidelines-using-vector-indexes documentation, that index's own accuracy "may diminish over time due to DML operations being performed on the underlying table," checked with the INDEX_ACCURACY_QUERY function and corrected with the REBUILD_INDEX function, both provided by the DBMS_VECTOR package. That guidance is stated for the IVF index specifically -- the same page makes no equivalent claim about embeddings_hnsw_idx, and this concept does not assume one without a citation.

CODE

The full transaction, with the failure path included

A single function showing all three outcomes this concept covers -- commit, rollback, and the referential-integrity failure that never reaches either -- against this course's own two rows.

PYTHON · UPDATE, DELETE, AND THE ORDER-SENSITIVE FAILURE 
import oracledb
import array

connection = oracledb.connect(user=user, password=pwd, dsn=dsn)
cursor = connection.cursor()

# Transaction A: correct chk_9f21_2_03's own embedding
cursor.execute(
    "update embeddings set embedding = :1 where chunk_id = :2",
    [array.array("f", [0.0, 1.0, 0.0]), "chk_9f21_2_03"],
)
connection.commit()

# Transaction B: delete chk_9f21_2_04, child table first
cursor.execute("delete from embeddings where chunk_id = :1", ["chk_9f21_2_04"])
cursor.execute("delete from chunks where chunk_id = :1", ["chk_9f21_2_04"])
connection.commit()

# The order-sensitive failure -- do NOT run this against a live chunk that still has an embedding row
try:
    cursor.execute("delete from chunks where chunk_id = :1", ["chk_9f21_2_03"])
except oracledb.DatabaseError as e:
    connection.rollback()  # nothing partial survives -- the whole transaction is discarded
    print("delete failed, rolled back:", e)

python-oracledb surfaces the ORA-02292 failure as an oracledb.DatabaseError -- catching it and calling rollback() is the same pattern Concept 08 already established for any failed multi-statement transaction, applied here to a specific, real, foreign-key-shaped failure instead of a hypothetical one.

15
REPETITION

The two facts, restated

  • UPDATE and DELETE use the exact same cursor.execute(sql, binds) / commit()/rollback() shape as Concept 08's INSERTs -- nothing is durable until commit, and multiple statements can share one commit or one rollback.
  • embeddings.chunk_id REFERENCES chunks.chunk_id means DELETE order matters -- child before parent, or Oracle raises ORA-02292 before the transaction ever reaches commit, per Oracle's own error-help page.
  • Per Oracle's own guidelines-using-vector-indexes documentation, an IVF index's accuracy "may diminish over time due to DML operations" -- DBMS_VECTOR.INDEX_ACCURACY_QUERY checks it, DBMS_VECTOR.REBUILD_INDEX fixes it. COMMIT alone does neither.
16
DIAGNOSIS

Failure modes

ORA-02292

A DELETE fails, and the transaction never even reaches commit

Cause: the parent row (chunks) still has a dependent child row (embeddings). Fix: delete embeddings for that chunk_id first, per Section 10's own verified order.

SILENTLY STALE RANKINGS

Queries keep running fine, but an IVF index's approximate answers quietly drift

Cause: DML has been committed against the underlying table with no rebuild since. Fix: run DBMS_VECTOR.INDEX_ACCURACY_QUERY to measure the gap, then DBMS_VECTOR.REBUILD_INDEX if it's too large -- both named on Oracle's own guidelines page.

UNUSABLE AFTER TRUNCATE

A bulk wipe breaks the index outright, not just its accuracy

Per Oracle's own guidelines page: "If a table is truncated, any IVF index created on the table is marked as UNUSABLE... You must rebuild or recreate the IVF index before using the index in a query again." A more severe version of the same underlying gap.

FEEDBACK

Solution and teach-back

Open the worked solution
dot([0.8,0.6,0.0],[1.0,0.0,0.0]) = 0.8. Both vectors have norm 1, so cosine distance = 1 − 0.8 = 0.2. Since 0.2 < 1.00, chk_9f21_2_03 still outranks chk_9f21_2_04 -- and this correction actually improved its distance versus the [0.0, 1.0, 0.0] state from Section 10 (0.4 → 0.2), because [1.0, 0.0, 0.0] sits closer, in cosine terms, to the query vector's own dominant direction.

Conceptual: what real Oracle error fires when a DELETE hits a parent row that a foreign key still depends on, and what does it actually mean?
ORA-02292, "integrity constraint (...) violated - child record found" -- per Oracle's own error-help page, it means a parent key value with a live foreign-key dependency was targeted for deletion; the fix is deleting the dependent (child) rows first.
Conceptual: does committing an UPDATE against an indexed vector column also refresh that vector index?
No -- COMMIT is a guarantee about row durability only. Per Oracle's own guidelines-using-vector-indexes documentation, an IVF index's accuracy "may diminish over time due to DML operations" and has to be checked and rebuilt separately, via DBMS_VECTOR's own functions.
Coding: write the minimal real code to correct one embeddings row and commit it.
cursor.execute("update embeddings set embedding = :1 where chunk_id = :2", [array.array("f", [0.0, 1.0, 0.0]), "chk_9f21_2_03"]); connection.commit()
System design: why would a production system schedule periodic DBMS_VECTOR.INDEX_ACCURACY_QUERY checks rather than rebuilding a vector index after every single DML statement?
Rebuilding on every DML would make each UPDATE/DELETE pay the full cost of restructuring the index, which does not scale; per Oracle's own guidelines page, accuracy diminishes gradually with accumulated DML, so a periodic accuracy check followed by a batched REBUILD_INDEX only when the gap is large enough is the documented, cheaper pattern -- the same defer-then-batch shape Module 09 Concept 08 already established for ANN-library tombstone compaction, now grounded in Oracle's own real functions instead.
