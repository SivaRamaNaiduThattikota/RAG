MODULE 11 · CONCEPT 08

A prompt string isn't an answer yet.
Decoding the response the model actually reads out.

Concept 07 assembled one 954-token string -- system instructions, five boundary-marked chunks, the query -- and handed it off. This concept is the very next step: the model reads that exact string, computes a probability over every possible next token, picks one, repeats until it stops, and the pipeline attaches a citation to whatever came out. Same evidence set, same instructions, two different outcomes -- because the model can only ever answer from what actually survived into the string it read.

PROGRESSIVE BEGINNER CORE

Concept 07 built the string. This concept is what happens when the model reads it.

Everything up through Concept 07 is preparation: hash, chunk, embed, store, rank, select, assemble. Nothing has generated an answer yet. This concept is the step where the model actually reads the assembled string, computes probabilities over its vocabulary one token at a time, and produces the text a user will actually see.

01 · CONCEPT FIRST

Reading the letter, not writing it

Concept 07 wrote the letter -- instructions, cited evidence, the question, in that order. This concept is someone reading that exact letter and answering, out loud, one word at a time, based only on what's actually written on the page in front of them -- not on what they might otherwise know or guess. Generation is the step where the LLM turns retrieved evidence plus a question into a written final answer, token by token.

First memory: generation is decoding from the string that was actually assembled -- not from the corpus, not from the model's own general knowledge, from that one string.
02 · WHY IT EXISTS

An assembled string is not an answer

Retrieval alone only finds passages -- something still has to read them and produce a human-readable sentence, and that's the generator's job. Without this concept, Concept 07's 954-token string would just sit there. Something has to turn it into a response: run it through the model, get a probability distribution over the next token, choose one, append it, and repeat until the model decides to stop. That loop, plus the final citation attachment, is this concept.

03 · CONCRETE EXAMPLE

Same question, two different evidence realities

The query, continued from Concept 06/07, is "What is the return window after the grace period?" The evidence set includes c007's child chunk -- the exact grace-period sentence, per Module 07 Concept 06, but one that concept already flagged as liable to be cut mid-sentence without enough overlap. Given the assembled prompt from Concept 07 (query plus evidence cA/c007_child/cB/cC/cE), the model decodes the answer "14 days" one token at a time -- if the number survived the cut. If it didn't, decoding "14" anyway would be a hallucination, not a grounded answer -- the same instructions and the same evidence-set label, two very different honest outcomes.

04 · TECHNICAL MECHANISM

Logits, softmax, argmax, repeat

At each position, the model produces one logit per vocabulary token (Module 02 Concept 05). Softmax turns those logits into a probability distribution that sums to 1. Greedy decoding picks the highest-probability token (argmax); the chosen token is appended and the whole string -- prompt plus everything generated so far -- is fed back in for the next position. This repeats until a stop token or length limit ends it.

06 · IMPORTANT DISTINCTIONS

Generation is the decode loop, nothing upstream of it

Generation is not retrieval and not augmentation -- it's strictly the decode loop that happens after the prompt is already built, distinct from Concepts 05-07's upstream steps. A model doesn't "decide" to hallucinate or "decide" to ground itself -- it always just decodes the highest-probability continuation of whatever string it was actually given. Whether that continuation happens to match reality depends entirely on whether the true answer was in the string. "Grounded" is a property of the prompt and the decode, not of the model's intent.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"A grounded prompt guarantees a grounded answer."

Not automatically -- Module 03 Concept 04 already stated this precisely: grounding reduces hallucination risk, it does not eliminate it. A well-assembled prompt lowers the odds of a fabricated answer; it doesn't remove the model's ability to decode a wrong token anyway.

"Citations are free once the evidence was retrieved."

Not automatically -- the ALCE benchmark found that even the strongest LLM systems lack complete citation support roughly half the time on open-domain QA (ELI5). Having the right chunk in the prompt is necessary for a correct citation; it isn't sufficient for one.

Readiness check before moving on

Describe the decode loop

Logits over the vocabulary, softmax to probabilities, argmax (or sampling) to pick one token, append, repeat until stop.

Explain why the same evidence-set label can honestly produce either outcome

Whether the true answer's text survived into the assembled prompt -- not the model's "intent" -- decides whether the same evidence-set label can honestly yield a correct numeral in one case and a grounded refusal in another.

State what a citation tag does and doesn't guarantee

It marks which source the model is claiming to draw from -- ALCE shows it does not, by itself, prove the claim actually appears there roughly half the time even in strong systems.

EVIDENCE + CONTROL

What the generator can and can't control

Module 11 Concept 07's own worked example is the exact prompt this concept decodes: a 954-token assembled string made of 35 tokens of system instructions, five boundary-marked chunks (cA, c007's child, cB, cC, cE, 880 tokens total), and a 9-token query -- "What is the return window after the grace period?" -- against a 3,584-token prompt budget. CODE

The softmax function, and the two logit sets it runs on

JAVASCRIPT · SOFTMAX (also the lab's own code) 
function softmax(logits) {
  const keys = Object.keys(logits);
  const vals = keys.map(k => logits[k]);
  const max = Math.max(...vals);
  const exps = keys.map(k => Math.exp(logits[k] - max));
  const sum = exps.reduce((a, b) => a + b, 0);
  return Object.fromEntries(keys.map((k, i) => [k, exps[i] / sum]));
}
// Scenario A -- intact: {"14": 5.1, "7": 1.2, "30": 0.8, "an": 0.3}
// Scenario B -- cut mid-sentence: {"not": 4.8, "14": 1.5, "30": 1.1, "7": 0.9}

Neither logit set is a real model's output -- both are illustrative, exactly the same status Concept 06's own cA-cG scores carried. What is real and load-bearing is the softmax arithmetic run on them, verified in Section 08.

09
CONCRETE USE

What generation guarantees, and what it doesn't

Generation guarantees a fluent answer shaped by the prompt it was given. It does not guarantee that the answer is correct, and it does not guarantee that its citations are complete. The ALCE benchmark (arxiv.org/abs/2305.14627) put a number on that second gap: asking strong LLM systems to answer open-domain questions with attached citations, and checking whether the cited text actually supports each claim, it found that even the best models lack complete citation support fifty percent of the time on ELI5. A model can decode a fluent, confident-sounding sentence and still fail to back half of it with a citation that actually holds up -- which is exactly why Section 20's read-back check treats a citation tag as a claim to verify, not a guarantee to trust.

17
CAREER PRACTICE

Interview questions

Conceptual: why can the same evidence-set label yield two different honest answers?
Because "honest" is defined relative to what text actually survived into the assembled prompt, not relative to the label on the evidence set. If the supporting text didn't make it in (e.g. cut mid-chunk), decoding the true fact anyway would be a hallucination, not a correct grounded answer -- declining is the honest output in that case.
Conceptual: what does softmax guarantee about a probability distribution?
Only that the outputs are non-negative and sum to exactly 1 -- it says nothing about whether the highest-probability token is actually correct; that depends entirely on what the underlying logits reflect.
System design: what did ALCE find about citation completeness in top systems, and what's the practical fix for a pipeline that trusts citation tags on sight?
ALCE found even the best models lack complete citation support roughly half the time on ELI5. The fix is a read-back/string-match check between each generated claim and the text of its cited chunk before the answer ships -- the citation tag alone is not proof.

EVIDENCE + CONTROL

Citation attachment is a separate, checkable step

Once decoding stops, the pipeline attaches a [SOURCE n] tag identifying which evidence chunk a claim is being attributed to -- Concept 07's own boundary-tag scheme, reused here at the output side instead of the input side. Attaching a tag mechanically means pointing decoded text back to a specific evidence chunk id, such as c007, rather than just producing prose. Attaching the tag is mechanical and cheap; it is not, by itself, proof the claim is supported. The check that matters is whether the cited chunk's actual text contains what the claim states -- in Scenario A, c007's child literally contains "14 days from the ship date," so [SOURCE 2] is a true citation. In Scenario B, no chunk in the evidence set states a number at all, so the honest output attaches no numeric citation and says so plainly instead.

21
CROSS-REFERENCE

Position inside the 954 tokens still matters

Module 02 Concept 10 established that models don't attend to every position in a long prompt equally -- evidence buried in the middle of a long context is recalled less reliably than evidence near the start or end (the "lost in the middle" effect). That fact doesn't disappear just because Concept 07 finished assembling the prompt: where a chunk sits inside the 954-token string can still affect whether the model attends to it strongly enough to actually decode the grounded token, even when the chunk's text is fully intact. Section 08 of Module 11 Concept 07 already showed this concretely by moving c007's child from the front of the evidence block to its middle; this concept is the reason that positioning risk matters at all -- it changes what actually gets decoded.

22
CROSS-REFERENCE

The k reaching generation isn't necessarily a clean k

Module 09 Concept 07 established that tenant filtering forces deliberate over-fetching -- a 3.4x figure, top-17 candidates fetched to guarantee five survive filtering for k=5. Concept 06 then cut that pool down with a score cutoff and a redundancy filter before it ever reached Concept 07's assembly step. By the time a prompt reaches this concept, trimming may already have happened more than once upstream. A wrong or missing fact in the final answer is not automatically a generation failure -- it can just as easily be evidence that never survived Concept 05's over-fetch or Concept 06's cutoff, and generation should not be blamed for a defect it didn't cause.

23
EVIDENCE + CONTROL

Telling a generation failure apart from the other two

Module 03 Concept 11's three-link failure chain says a wrong final answer traces back to a retrieval failure, an augmentation failure, or a generation failure. This concept gives the concrete tool for telling them apart: check whether the correct evidence was ever retrieved (retrieval), check whether it survived selection and assembly into the prompt (augmentation, Concepts 05-07), and only if both of those check out, treat a wrong decode as a genuine generation failure. Section 07's Scenario B is a case that looks like a generation problem on the surface -- the model declined to answer -- but traces back to an augmentation failure (the chunk was cut) rather than a flaw in the decode loop itself.
