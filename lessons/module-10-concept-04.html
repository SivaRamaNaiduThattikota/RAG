01 · CONCEPT FIRST

One new column closes a real gap

Concept 03 built five tables -- documents, document_versions, chunks, embeddings, citations -- and none of them has any notion of "who is allowed to see this row." A real RAG system serving multiple customers must never let one tenant's search results leak rows belonging to another tenant, no matter how similar those rows are to the query vector.

First memory: add tenant_id to documents, not to every other table -- access control is a document-level property, and chunks already reach it transitively via doc_id.
02 · WHY IT EXISTS

Module 09's two named strategies, now literal SQL

Module 09 Concept 07 already named two strategies for combining a metadata constraint with a vector search: pre-filtering (narrow the row set first, then rank) and post-filtering (rank everything first, then discard non-matches) -- cited directly, not redefined. This concept is the first to write real, executable SQL for both, against Concept 03's own schema.

03 · CONCRETE EXAMPLE

The schema extension

ALTER TABLE documents ADD tenant_id VARCHAR(64) NOT NULL; -- one column, on documents only. document_versions, embeddings, and citations are untouched; chunks reaches tenant_id transitively through its own doc_id foreign key back to documents.

04 · TECHNICAL MECHANISM

Two SQL shapes, same two ingredients

Pre-filter shape: the tenant WHERE clause is evaluated as part of the same join/scan that produces the candidate set, so the vector-distance ORDER BY only ever sees rows that already passed the tenant check. Post-filter shape: an inner subquery ranks by distance across ALL tenants first, with no tenant awareness at all, and the tenant WHERE clause runs on the OUTSIDE, after the ranking -- and after an inner row limit has already discarded whatever didn't make the cut.

06 · IMPORTANT DISTINCTIONS

An application WHERE clause vs. engine-enforced row security

TermThe real difference
WHERE-clause tenant filter (this concept)Correctness depends on every query author remembering to add the predicate.
Row-level security (named, not built here)The database engine itself refuses any row access not covered by a policy, regardless of what the caller's query says -- PostgreSQL's own ENABLE ROW LEVEL SECURITY + CREATE POLICY, cited.
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Both queries have a tenant filter, so both are equally safe."

False -- the post-filter shape can discard a true match before the tenant WHERE clause ever sees it, a failure mode the pre-filter shape structurally cannot produce.

"The <-> operator here is real Oracle syntax."

False -- it's a deliberate, generic placeholder for "a vector-distance comparison happens here." Concept 05 supplies Oracle's own real operator.

04
INTUITION

Checking IDs at the door vs. after everyone's already seated

Pre-filtering is checking IDs at the door -- only eligible guests are ever considered. Post-filtering is letting everyone in first and checking IDs table by table afterward -- and if the venue only keeps the first 17 arrivals on the guest log before the ID check even starts, a legitimate guest who arrived 20th is already gone by the time anyone checks.

Analogy boundaryThis restates Module 09 Concept 07's own analogy at the SQL level -- the actual risk comes from Section 10's own worked queries, not from the analogy.

06
MECHANISM

The schema extension and both queries, in full

SQL · SCHEMA EXTENSION 
ALTER TABLE documents ADD tenant_id VARCHAR(64) NOT NULL;
SQL · PRE-FILTER SHAPE (illustrative <-> placeholder -- real Oracle syntax at Concept 05) 
SELECT c.chunk_id, c.text
FROM chunks c
JOIN documents d ON c.doc_id = d.doc_id
JOIN embeddings e ON e.chunk_id = c.chunk_id
WHERE d.tenant_id = :tenant_id
ORDER BY e.embedding <-> :query_embedding
FETCH FIRST 5 ROWS ONLY;
SQL · POST-FILTER SHAPE (illustrative <-> placeholder -- real Oracle syntax at Concept 05) 
SELECT ranked.chunk_id, ranked.text
FROM (
  SELECT c.chunk_id, c.text, c.doc_id, e.embedding <-> :query_embedding AS dist
  FROM chunks c
  JOIN embeddings e ON e.chunk_id = c.chunk_id
  ORDER BY dist
  FETCH FIRST 17 ROWS ONLY
) ranked
JOIN documents d ON d.doc_id = ranked.doc_id
WHERE d.tenant_id = :tenant_id
FETCH FIRST 5 ROWS ONLY;

10
WORKED EXAMPLE

Both queries, clause by clause, against the same corpus

Reusing Module 09 Concept 07's own 20-chunk, 30%-selectivity corpus unchanged: 6 of 20 chunks belong to tenant "Acme," at ranks {3, 7, 9, 14, 17, 20}. Target k=5.

Pre-filter shape. The WHERE d.tenant_id predicate is evaluated as part of the same join/scan that produces the candidate set -- so the ORDER BY vector-distance comparison only ever sees Acme's own 6 rows. Fetched: 6 rows touched, top 5 returned, 1 discarded (the 6th-ranked Acme row itself, not a wrong-tenant row).

Post-filter shape. The inner ranked subquery has no tenant awareness at all -- it fetches the top 17 rows by distance across ALL tenants (Concept 07's own already-verified fetch depth for this exact selectivity/k), THEN the outer WHERE filters by tenant. Fetched: 20 rows touched by the base scan feeding the subquery's own ORDER BY, 17 rows survive the inner limit, of which 5 are Acme (ranks 3,7,9,14,17) and 12 are discarded (Concept 07's own number, cited). Acme's own 6th match, at global rank 20, never enters the inner ranked result at all -- it was cut by FETCH FIRST 17 ROWS ONLY before the outer tenant WHERE clause ever ran. This is a real, structural failure mode the pre-filter shape cannot produce: pre-filtering never even considers a non-eligible row, so it can never accidentally cut off an eligible one via an unrelated row limit.

Verification methodBoth queries were checked for well-formedness manually: every foreign-key reference resolves against Concept 03's own schema (chunks.doc_id→documents.doc_id, embeddings.chunk_id→chunks.chunk_id), clause ordering is valid standard SQL, parentheses around the derived table balance, and FETCH FIRST n ROWS ONLY is confirmed as the real, portable SQL:2008 row-limiting clause (not vendor-specific LIMIT/TOP). The 17/3.4x/12-discarded figures are Module 09 Concept 07's own already-verified numbers, cited directly, not recomputed.
11
CONCRETE USE

A clean fit, a boundary case, and a genuine caveat

CLEAN FIT

A low-selectivity tenant filter

Pre-filtering keeps cost fixed at the eligible subset's own size, exactly as Module 09 Concept 07 already established.

BOUNDARY CASE

The post-filter shape's own inner row limit

Raising the inner FETCH FIRST value reduces (but does not eliminate) the leak-by-omission risk -- at the cost of scanning even more rows.

GENUINE CAVEAT

A WHERE clause is only as reliable as the caller

Forgetting the tenant predicate in either query shape is a real, catastrophic risk -- row-level security (Section 06, cited) removes that dependency entirely.

CODE

The schema extension, reproduced directly

SQL · SCHEMA EXTENSION AND BOTH QUERY SHAPES, TOGETHER 
-- Step 1: add the access-control column (this concept's own contribution).
ALTER TABLE documents ADD tenant_id VARCHAR(64) NOT NULL;

-- Step 2a: pre-filter shape -- WHERE before ORDER BY.
SELECT c.chunk_id, c.text
FROM chunks c
JOIN documents d ON c.doc_id = d.doc_id
JOIN embeddings e ON e.chunk_id = c.chunk_id
WHERE d.tenant_id = :tenant_id
ORDER BY e.embedding <-> :query_embedding
FETCH FIRST 5 ROWS ONLY;

-- Step 2b: post-filter shape -- ORDER BY (with its own inner limit) before WHERE.
SELECT ranked.chunk_id, ranked.text
FROM (
  SELECT c.chunk_id, c.text, c.doc_id, e.embedding <-> :query_embedding AS dist
  FROM chunks c
  JOIN embeddings e ON e.chunk_id = c.chunk_id
  ORDER BY dist
  FETCH FIRST 17 ROWS ONLY
) ranked
JOIN documents d ON d.doc_id = ranked.doc_id
WHERE d.tenant_id = :tenant_id
FETCH FIRST 5 ROWS ONLY;

ECOSYSTEM

Real production sources for tenant isolation

PostgreSQL's own Row Security Policies documentation describes engine-enforced access control (ALTER TABLE ... ENABLE ROW LEVEL SECURITY + CREATE POLICY) as a real, distinct alternative to the WHERE-clause approach built in this concept. Qdrant's own multitenancy documentation confirms a tenant field with a dedicated indexed predicate is treated as a mandatory, pre-filter-shaped constraint in that engine -- a second-vendor confirmation that pre-filtering on tenant is the production-recommended default. Pinecone's own multitenancy guide shows a contrasting pattern: physically separate namespaces per tenant, rather than a shared table filtered per query -- a different way of solving the identical isolation requirement. pgvector's own README (reused from Concept 03) is the generic-SQL precedent for pairing a vector-distance ORDER BY with WHERE-clause filtering.

DIAGNOSIS

Failure modes

LEAK-BY-OMISSION

Post-filter's own inner row limit drops a true match

Exactly Acme's own rank-20 match in this concept's own worked example -- discarded before the tenant WHERE clause ever runs.

FORGOTTEN PREDICATE

A caller omits the WHERE tenant_id clause entirely

In either shape, this is a real, catastrophic cross-tenant data leak -- the exact risk row-level security (Section 06) is designed to remove.

REALITY

Production implications

  • Choosing pre-filter vs. post-filter SQL shape per query is a real design decision -- Module 09 Concept 07's own cost framing applies directly to which one is worth the SQL complexity.
  • Row-level security (Section 06, cited) is worth adopting specifically when the cost of a forgotten WHERE clause is unacceptable, independent of which filter shape is otherwise used.
  • Namespace-per-tenant (Pinecone's own pattern, cited) is a real alternative to logical filtering entirely -- physical isolation instead of a shared table.

RECALL

Knowledge check

Write the schema extension from memory.
ALTER TABLE documents ADD tenant_id VARCHAR(64) NOT NULL;
Why can the post-filter shape discard a true match that the pre-filter shape never would?
The post-filter shape's inner subquery ranks and limits rows with zero tenant awareness; a true match outside that inner limit is gone before the outer tenant WHERE clause ever runs. The pre-filter shape never considers ineligible rows in the first place, so it has no equivalent unrelated cutoff to lose an eligible row to.
What real, engine-enforced mechanism removes the "caller must remember the WHERE clause" risk?
Row-level security -- PostgreSQL's own ENABLE ROW LEVEL SECURITY plus CREATE POLICY, where the database itself refuses any row access not covered by a policy, regardless of what the caller's query says.

TRANSFER

21
FEEDBACK

Solution and teach-back

Open the worked solution
At 70% selectivity, Concept 07's own table shows the 5th match landing at rank 7 -- so the post-filter shape's own inner FETCH FIRST value would be 7, not 17. The pre-filter shape is unaffected by selectivity in structure, still WHERE-then-ORDER-BY-then-FETCH-FIRST-5. The leak-by-omission risk is LOWER at 70% selectivity -- with matches so common, an inner limit of 7 is far less likely to cut off a true match than an inner limit of 17 was at 30% selectivity, since matches are packed more densely near the top of the ranking.

Teach-back: as selectivity approaches 100%, what happens to the post-filter shape's own inner FETCH FIRST value, and why does that shrink the leak-by-omission risk toward zero?

23
CAREER PRACTICE

Interview questions

Conceptual: why does clause order matter in SQL when both queries "have" the same WHERE filter?
SQL clauses execute against whatever result set exists at that point in the query plan -- a WHERE clause applied after an ORDER BY/FETCH FIRST limit only ever sees what survived that limit, which is not the same as applying the WHERE clause before any ranking happened.
Mathematical: at 50% selectivity (10 of 20 chunks matching) with k=5, what should the post-filter shape's own inner FETCH FIRST value be?
Per Module 09 Concept 07's own 50%/k=5 row, the 5th match lands at rank 11 -- so FETCH FIRST 11 ROWS ONLY, cited directly, not recomputed here.
Coding: rewrite the post-filter query to also return how many rows were discarded by the outer WHERE.
Wrap the outer query in a second derived table with a COUNT(*) OVER () window before the outer FETCH FIRST 5 ROWS ONLY, then subtract 5 from that count to get the discarded total -- or simpler, run the outer query twice: once for the actual rows, once with COUNT(*) instead of the row list.
System design: your team wants to guarantee tenant isolation even if a developer forgets a WHERE clause. What do you build?
Row-level security (Section 06, cited) -- an engine-enforced policy that refuses any row access outside the caller's own tenant, regardless of what WHERE clause (or lack of one) the query itself contains.
