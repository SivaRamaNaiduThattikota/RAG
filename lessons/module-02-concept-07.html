Context windows
and in-context learning

Concept 06 traced what changes a model's weights. 01 · CONCEPT FIRST

A context window is a token budget, not a memory

The context window is the maximum number of tokens — positions — that a given model's block stack (Concept 03) can accept and process in one forward pass. Every token you send in — system instructions, retrieved evidence, conversation history, few-shot examples, the user's question — competes for space inside that one fixed budget. In-context learning is what happens when some of those tokens are worked examples: the model conditions its next-token distribution on them, in that single forward pass, without any weight in the block stack or output head being touched.

Both ideas share one root cause: the context window exists because Concept 04's self-attention lets every token look at every other token in the window, and that all-pairs comparison is what in-context learning exploits — and exactly what makes longer windows expensive.

First memory: the context window is how much fits in one forward pass; in-context learning is what that one forward pass can still do with what fits, without updating anything.
02 · WHY IT EXISTS

A fixed architecture has to draw a line somewhere

Concept 04 showed every token attending to every other token inside a block. That mechanism does not stop working past some length — it keeps working, but its cost grows faster than the length itself does. A model is trained and shipped with one specific maximum length in mind; positions beyond it either were never trained on, or would demand attention compute and memory the serving hardware was never sized for. The context window is the practical and architectural line that gets drawn.

WHAT CONCEPT 04 GAVE YOU

Attention scores every pair of positions inside a block, every block, every step.

WHAT THIS CONCEPT ADDS

A hard ceiling on how many positions can exist at once — and a reason that ceiling isn't just "make it bigger."

03 · CONCRETE EXAMPLE

One Oracle RAG prompt, packed to the edge

Say a toy model's context window is 8,000 tokens. A support query about leave-policy carryover arrives with: a 300-token system instruction, three 900-token retrieved policy chunks, a 600-token slice of conversation history, two 250-token worked examples of the answer format you want followed, and the 60-token question itself. That totals 4,010 tokens — comfortably inside the 8,000-token window, with room left for the model's generated answer. Push it to five retrieved chunks instead of three, and the same prompt now needs 5,810 tokens before generation even starts — still fits, but the margin for a long answer has shrunk a lot.

WHAT FILLS THE WINDOW

System instruction, retrieved chunks, history, worked examples, and the question — all counted together.

WHAT DOESN'T FILL IT

Nothing outside this one prompt — no memory of yesterday's session, no weight anywhere changed.

WHAT THE TWO WORKED EXAMPLES DO

Nudge the answer's format toward what they demonstrate — in-context learning, covered next.

04 · TECHNICAL MECHANISM

What actually enforces the limit, and what happens inside it

TOKEN COUNT, NOT WORD COUNT

Concept 02's tokenizer decides

The window is measured in tokens; the exact same sentence can cost more or fewer tokens depending on the tokenizer.

POSITION SCHEME LIMIT

Concept 04's positional information

A model's positional encoding — RoPE or otherwise — was set up assuming positions up to some maximum; going past it is unreliable or unsupported.

ATTENTION OVER THE WHOLE WINDOW

Every token can attend to every earlier token

Concept 04's mechanism, applied across the full set of positions currently in the window — nothing new about the attention formula itself.

IN-CONTEXT LEARNING

Attention over the worked examples

When examples sit inside the window, later positions' attention can weight those example tokens' key/value vectors heavily — shifting the next-token distribution toward what the examples demonstrate.

ZERO WEIGHT CHANGE

Concept 06's inference-only lane

All of this happens in the forward-only path Concept 06 already named — no loss, no gradient, no backward pass, no updated matrix.

WHAT'S NOT REMEMBERED

The window resets between calls

Nothing about this conditioning persists once the request ends — a new call with a different prompt starts from the same fixed weights, fresh.

07 · COMMON MISTAKES

What beginners often misunderstand

"In-context learning updates the model's weights a little."

It updates nothing — Concept 06's weight groups are exactly as frozen during this as during any other inference call.

"The model remembers my few-shot examples for next time."

Nothing persists past the forward pass that used them; a new call without them gets no benefit from that conditioning.

"A bigger context window means the model reasons better over long documents."

It means more tokens fit; whether the model uses everything in that window equally well is a separate question this course returns to later.

"Context window and max output tokens are the same setting."

They're usually distinct limits — one bounds the total conversation, the other bounds just the generated reply.

"Doubling the context window doubles the compute cost."

Concept 04's attention cost grows quadratically with sequence length, so doubling the window costs roughly four times the attention compute, not two.

"In-context learning is basically instant fine-tuning."

Fine-tuning (Concept 06) changes stored weights permanently; in-context learning changes only this one forward pass's output.

04
INTUITION

A desk of fixed size, and what you can still do on it

Picture a desk with a fixed amount of surface area — the context window. You can cover it with reference documents, sticky-note examples, your running notes, and the question you're actually trying to answer, but the desk itself never grows mid-task. In-context learning is what happens when some of those sticky notes are worked examples: you read them, and your next answer looks more like them — but you haven't learned anything permanently, and the desk is wiped clean before the next task begins.

Analogy boundaryThe desk doesn't explain why reading more of it gets disproportionately slower. That part is not an analogy — it's Concept 04's attention mechanism scoring every pair of items on the desk against each other, which Section 09 quantifies directly.

MECHANISM

Two things happening in the same forward pass

FILLING THE WINDOW
Every input source gets tokenized (Concept 02)
Total token count is checked against n_max before the call proceeds
If it fits, every position enters the block stack together
If it doesn't, something must be cut before the call can run at all
IN-CONTEXT LEARNING, INSIDE THAT SAME PASS
Worked examples occupy some of those positions
Concept 04's attention lets later positions read those examples' key/value vectors
The output head's logits (Concept 05) shift toward what the examples demonstrate
No loss, no gradient, no backward pass — Concept 06's inference lane, unchanged

Both lanes are one forward pass. The window decides whether the examples even get in; attention decides what happens to the output once they do.

09
MATHEMATICS

Why the ceiling isn't just "raise it"

Concept 04 already derived self-attention's per-layer cost as O(n²·d), where n is sequence length and d is the hidden dimension — that formula is cited here, not re-derived.

relative attention cost when length changes from n to k·n: (k·n)² / n² = k²

Doubling the context length (k=2) costs roughly 2²=4 times the attention compute of the original length; quadrupling it (k=4) costs roughly 16 times as much. This is exactly the curve that makes "just support a much longer window" a real engineering decision, not a free configuration flag.

KV-cache memory during generation grows as O(n) per generated token, on top of the O(n²) attention cost already paid to build it

The KV cache — the stored key/value vectors for every position already processed — is what lets each new generated token avoid recomputing attention over the whole window from scratch; it still grows linearly with how much of the window is already filled, adding a second, separate cost dimension.

10
WORKED EXAMPLE

Estimating the compute multiplier for a real prompt-size jump

Take Section 03's Oracle RAG prompt: 4,010 tokens with three retrieved chunks. Adding two more chunks — the second scenario from the beginner core — pushes it to roughly 5,810 tokens.

k = 5810 / 4010 ≈ 1.45
relative attention cost ≈ k² ≈ 1.45² ≈ 2.1

Two extra retrieved chunks, only a 45% increase in token count, cost roughly twice the attention compute of the shorter prompt — not 45% more. That gap between "how much longer the prompt got" and "how much more it costs" is the practical consequence of Concept 04's quadratic term, made concrete on this lesson's own running example.

CODE

A toy forward pass that "learns" only in-context

PYTHON · NUMPY-STYLE PSEUDOCODE 
import numpy as np

# Fixed, frozen "model" — nothing here is ever mutated below.
FROZEN_WEIGHTS = {"bias_toward_number_words": 0.0}   # never assigned to again

def count_examples_favoring(pattern, context_examples):
    # a toy stand-in for "attention conditions on whatever examples are present"
    return sum(1 for ex in context_examples if ex["label"] == pattern)

def toy_forward_pass(context_examples, candidate_labels):
    # NOTE: this function only ever reads FROZEN_WEIGHTS, never writes it —
    # the same weight-change test from Concept 06, applied to this toy model.
    base_logit = FROZEN_WEIGHTS["bias_toward_number_words"]
    logits = []
    for label in candidate_labels:
        support = count_examples_favoring(label, context_examples)
        logits.append(base_logit + support)          # more matching examples -> higher logit
    logits = np.array(logits, dtype=float)
    probs = np.exp(logits - logits.max())
    return probs / probs.sum()

candidates = ["numeral_format", "spelled_out_format"]

# Zero examples: no in-context signal, close to a flat distribution
p0 = toy_forward_pass([], candidates)

# Three worked examples, all demonstrating "numeral_format"
examples = [{"label": "numeral_format"}] * 3
p3 = toy_forward_pass(examples, candidates)

# FROZEN_WEIGHTS is identical before and after both calls —
# only the input (the examples) changed, exactly Concept 06's inference-only lane.
assert FROZEN_WEIGHTS["bias_toward_number_words"] == 0.0

ECOSYSTEM

What production tooling actually calls this

Token-counting libraries such as OpenAI's tiktoken compute the exact figure a context-window check is measured against, ahead of any API call. LangChain's message-trimming utilities (for example trim_messages) and LlamaIndex's context-window-aware node parsers exist specifically to keep a prompt's token count under a target checkpoint's window before it ever reaches the model. None of these tools change what in-context learning is — they manage the same budget this concept defines so that the examples and retrieved evidence you actually want in the window survive the trim.

DIAGNOSIS

Failure modes

SILENT TRUNCATION

Oldest or lowest-priority content dropped

Some client libraries silently cut history or chunks to fit the window rather than raising an error — verify the trimming behavior in use.

EXAMPLE ORDER SENSITIVITY

In-context learning is not order-invariant

Reordering or reformatting the same worked examples can shift the resulting distribution noticeably.

COST BLOWUP

Underestimating the quadratic term

Treating a 2x longer prompt as roughly 2x the cost, when Section 09 shows it is closer to 4x.

OVER-TRUSTING A LARGE WINDOW

Assuming uniform use of the full budget

A model can hold a token in-window without weighting it usefully — Concept 10 covers this failure mode in depth; only named as a boundary here.

SENSITIVE DATA IN EXAMPLES

Few-shot examples are still just tokens

Worked examples placed in-context are visible to the model and any logging exactly like any other prompt content.

CONFUSING TWO CAPS

Hitting the output cap, not the window cap

A reply that stops early may have hit max output tokens, not the context window itself — check which limit actually fired.

18
REALITY

Production implications

  • Attention cost and KV-cache memory both grow with context length, so a longer window is a direct latency and infrastructure cost, not just a quality lever.
  • Silent truncation of history, retrieved chunks, or examples is a common, hard-to-notice source of degraded answers — log and alert on prompts that approach the window limit.
  • Few-shot examples baked into a shared prompt template are visible to every request that reuses it — treat them with the same care as any other prompt content, including logs.
  • Token-counting utilities should run before a request is sent, not discovered as an error after the call fails.
  • Context-window size varies by checkpoint and by provider configuration — verify the actual limit for the exact model version deployed, not the model family's marketing figure.
  • None of this changes anything about training cost — this concept's budget and effect are entirely inference-time, exactly Concept 06's forward-only lane.
19
RECALL

Knowledge check

What exactly does a context window put a ceiling on?
The total number of token positions — input plus generated output — that a specific checkpoint's block stack can process together in one forward pass.
Why does doubling the context length cost roughly four times the attention compute?
Because Concept 04's self-attention cost scales as O(n²·d); doubling n multiplies the attention term by 2² = 4, not by 2.
Does in-context learning change any stored weight?
No — it is a change in the model's output distribution caused entirely by the current input, computed within one forward pass, with zero parameter update.
Why must conversation history be re-sent every turn instead of remembered?
Because nothing about a prior forward pass is retained by the model; any continuity a caller wants has to be re-included as tokens inside the next request's context window.

21
FEEDBACK

Solution and teach-back

Open one worked reasoning pattern
For a 50% length increase, k = 1.5 and the relative attention cost is 1.5² = 2.25 — more than double, for a prompt only half again as long. For a 200% increase, the new length is three times the original (k = 3), giving a relative cost of 3² = 9 — nine times the attention compute for a prompt three times as long. For in-context learning to count as fine-tuning instead, some function would have to write a new value into a persisted weight matrix as a result of processing the prompt — exactly the backward-pass, gradient-driven update Concept 06 traced. Because the toy forward pass (and every real one) only reads FROZEN_WEIGHTS and never assigns to it, no such write occurs; the effect lives entirely in what gets computed from the input, not in anything stored afterward.

PORTABLE MEMORY

Concept card

The mechanism

Context window: max token positions one forward pass holds. Attention cost ∝ n². In-context learning: output shifts from examples in the prompt, zero weight change — Concept 06's inference lane, applied to few-shot conditioning.

Selection rule

  • Everything in the prompt shares one fixed token budget
  • Doubling length ≈ quadrupling attention compute

23
CAREER PRACTICE

Interview questions

Explain what a context window is and what determines its size.
It is the maximum number of token positions a specific checkpoint's block stack and positional encoding scheme can process in one forward pass — fixed by the model's architecture and training, not adjustable per request beyond that ceiling.
Why is context length a bigger cost lever than it first appears?
Self-attention's per-layer cost scales as O(n²·d), so cost grows quadratically with sequence length — a prompt that gets modestly longer can cost substantially more compute, and KV-cache memory grows linearly with length on top of that.
A colleague says few-shot prompting is a lightweight form of fine-tuning. How do you respond?
Fine-tuning writes a gradient-driven update into stored weights; few-shot prompting changes only the current forward pass's output by conditioning attention on examples already in the input — no weight in the model is read differently or written to afterward.
Where would you look first if a long-running chat session started giving worse answers?
Whether history, retrieved chunks, or examples are being silently truncated to fit the context window, and whether the growing prompt length is quietly increasing latency and cost per the quadratic attention term.
