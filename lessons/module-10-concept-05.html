01 · CONCEPT FIRST

Recall the placeholder, and its own warning label

Concept 04's SQL wrote e.embedding <-> :query_embedding in its ORDER BY clause, and said plainly that this was a generic placeholder, not real Oracle syntax. That warning turns out to be half right: <-> is real Oracle syntax after all -- it just isn't the metric this course needs.

First memory: "generic placeholder" and "real syntax" aren't opposites here -- <-> is both real AND the wrong choice, which is precisely the trap this concept exists to name.
02 · WHY IT EXISTS

Two placeholders, one real vendor's syntax

Concept 03 used a generic VECTOR(384) type; Concept 04 used a generic <-> distance comparison. Both were explicitly named as stand-ins. This concept replaces both with Oracle AI Database's own real syntax -- the VECTOR column type and the VECTOR_DISTANCE function -- so the schema and queries this course has been building stop being illustrative and start being executable against a real engine.

03 · CONCRETE EXAMPLE

The real column type

ALTER TABLE embeddings MODIFY (embedding VECTOR(384, FLOAT32)); -- 384 is the same dimension Module 08's all-MiniLM-L6-v2 embeddings have used throughout this course; FLOAT32 is one of four real Oracle format tokens. This swaps Concept 03's placeholder VECTOR(384) type for Oracle's own real one.

04 · TECHNICAL MECHANISM

The real distance function

VECTOR_DISTANCE(expr1, expr2 [, metric]) -- takes two vector expressions and an optional metric name, returns a plain number where lower means more similar. That's the same ORDER BY ... ASC pattern this course has used since Concept 04, just with a real function name and a metric argument now spelled out.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"<-> isn't real Oracle syntax, so it's safe to ignore."

False -- it is real, and it works. It resolves to the Euclidean metric, which silently produces a different ranking than the cosine convention this course has used since Module 04.

"Since VECTOR_DISTANCE's own default metric is cosine, the metric argument can be left out."

Technically true today, but this course writes COSINE explicitly anyway -- what the default resolves to once a vector index exists on the column is Concept 06's own territory, not settled here.

MECHANISM

The real VECTOR type's grammar

Oracle's real grammar is VECTOR(number_of_dimensions, dimension_element_format [, DENSE|SPARSE]). The third parameter defaults to DENSE and is not exercised in this concept. Optional flavor, not load-bearing: non-BINARY dimension counts must fall in the 1-65535 range, and BINARY dimension counts must be a multiple of 8 up to 65528, with Oracle raising ORA-51801/ORA-51813 outside those bounds -- cited as a documented boundary, not something this concept's own worked example needs.

09
MATHEMATICS

Seven real metric tokens, one default

VECTOR_DISTANCE(expr1, expr2 [, metric]) -- metric ∈ {COSINE, DOT, EUCLIDEAN, EUCLIDEAN_SQUARED, HAMMING, MANHATTAN, JACCARD}
Lower return value = more similar, for every metric -- matches the ORDER BY ... ASC pattern already used since Concept 04
Default-metric hedgePer Oracle's own documentation, the default metric is COSINE when omitted (HAMMING for BINARY inputs). What happens to that default once a vector index exists on the column is Concept 06's own territory -- not verified or claimed here. This course writes COSINE explicitly for exactly that reason, not because the default is expected to be unsafe.

WORKED EXAMPLE

Both of Concept 04's SQL shapes, one substitution

Reusing Concept 04's own 20-chunk, 30%-selectivity corpus and rank list unchanged: 6 of 20 chunks belong to tenant "Acme," at ranks {3, 7, 9, 14, 17, 20}. Target k=5. Only the distance expression changes -- from Concept 04's placeholder <-> to Oracle's real VECTOR_DISTANCE(e.embedding, :query_embedding, COSINE).

Pre-filter shape. Unchanged from Concept 04 except for the ORDER BY expression: the tenant WHERE clause still runs before the vector-distance ORDER BY, so only Acme's own 6 rows are ever touched. Fetched: 6 rows touched, top 5 returned, 1 discarded (Acme's own 6th-ranked row).

Post-filter shape. Unchanged from Concept 04 except for the inner subquery's dist column expression: the inner subquery still fetches the top 17 rows by distance across all tenants before the outer tenant WHERE runs. Fetched: 20 rows touched, 17 survive the inner limit (5 of which are Acme, at ranks 3,7,9,14,17), 12 discarded. Acme's own 6th match, at global rank 20, still never enters the inner result at all -- that structural fact is Concept 04's own finding and is unaffected by which real metric expression fills the ORDER BY.

Verification methodBoth real syntax claims in this concept -- VECTOR(384, FLOAT32) and VECTOR_DISTANCE(...,COSINE) -- were confirmed by live curl against Oracle's own create-tables-using-vector-data-type.html and vector_distance.html documentation pages this session. COSINE is written explicitly here rather than relied on as the default because the default's own behavior can shift once a vector index exists on the column -- that interaction is Concept 06's own territory and is not verified or claimed here.

CODE

The central trap, called out directly

Concept 04's own placeholder characters, <->, are real Oracle syntax.

They resolve to the Euclidean metric, not a generic "vector distance" stand-in. Reusing them literally in a real query would silently switch this project's retrieval metric away from the cosine convention used since M04 Concept 03, M08, and M09 -- with no error, and a plausible-looking but differently-ordered result.

SQL · PRE-FILTER SHAPE (real syntax -- correct substitution) 
SELECT c.chunk_id, c.text
FROM chunks c
JOIN documents d ON c.doc_id = d.doc_id
JOIN embeddings e ON e.chunk_id = c.chunk_id
WHERE d.tenant_id = :tenant_id
ORDER BY VECTOR_DISTANCE(e.embedding, :query_embedding, COSINE)
FETCH FIRST 5 ROWS ONLY;
SQL · POST-FILTER SHAPE (real syntax -- correct substitution) 
SELECT ranked.chunk_id, ranked.text
FROM (
  SELECT c.chunk_id, c.text, c.doc_id,
         VECTOR_DISTANCE(e.embedding, :query_embedding, COSINE) AS dist
  FROM chunks c
  JOIN embeddings e ON e.chunk_id = c.chunk_id
  ORDER BY dist
  FETCH FIRST 17 ROWS ONLY
) ranked
JOIN documents d ON d.doc_id = ranked.doc_id
WHERE d.tenant_id = :tenant_id
FETCH FIRST 5 ROWS ONLY;
SQL · WRONG SUBSTITUTION -- REAL SYNTAX, WRONG METRIC (shown, not used) 
-- Runs without error. Silently ranks by EUCLIDEAN instead of COSINE.
ORDER BY e.embedding <-> :query_embedding

DIAGNOSIS

Failure modes

SILENT METRIC SWITCH

Results plausible but ranking differs from earlier cosine-based work

Cause: <-> or VECTOR_DISTANCE(...,EUCLIDEAN) used in place of the cosine convention. Fix: switch to explicit COSINE, or <=>, or COSINE_DISTANCE().

DIMENSION OUT OF BOUNDS

ORA-51801 / ORA-51813 on table create or alter

Cause: dimension count outside the 1-65535 (or 65528-multiple-of-8 for BINARY) range. Flagged as optional detail, not verified as load-bearing for this concept's own 384-dimension example.

FEEDBACK

Solution and teach-back

Open the worked solution
The rewritten dist column is e.embedding <=> :query_embedding. Since <=> resolves to the same COSINE metric as VECTOR_DISTANCE(...,COSINE), the ranking is identical -- so the touched/survives/discarded counts (20/17/12) from Concept 04's own worked example do NOT change. Only expressions that resolve to a different metric (like <-> or VECTOR_DISTANCE(...,EUCLIDEAN)) would risk changing which rows land in the top 17.

Teach-back: why does swapping to a same-metric shorthand (<=> or COSINE_DISTANCE()) never change the ranking, while swapping to <-> can?

23
CAREER PRACTICE

Interview questions

Conceptual: what is VECTOR_DISTANCE's default metric, and what changes it?
Per Oracle's own documentation, the default is COSINE when the metric argument is omitted (HAMMING for BINARY inputs). Whether the presence of a vector index on the column changes that default behavior is a separate question this concept does not verify or claim to answer.
Mathematical: what is the difference between <-> and <=>?
<-> is the real Euclidean-distance shorthand operator (≡ L2_DISTANCE / VECTOR_DISTANCE(...,EUCLIDEAN)). <=> is the real cosine-distance shorthand operator (≡ COSINE_DISTANCE / VECTOR_DISTANCE(...,COSINE)). Both are real; they are simply locked to different metrics.
Coding: rewrite Concept 04's pre-filter query using the real VECTOR_DISTANCE function.
SELECT c.chunk_id, c.text FROM chunks c JOIN documents d ON c.doc_id = d.doc_id JOIN embeddings e ON e.chunk_id = c.chunk_id WHERE d.tenant_id = :tenant_id ORDER BY VECTOR_DISTANCE(e.embedding, :query_embedding, COSINE) FETCH FIRST 5 ROWS ONLY;
System design: why write the metric explicitly instead of relying on VECTOR_DISTANCE's own documented default?
The default's own interaction with the presence of a vector index on the column is not verified in this concept -- writing COSINE explicitly keeps the chosen metric visible in the query text and independent of index state, deferring that unverified interaction to Concept 06.
