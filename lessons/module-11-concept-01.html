02 · WHY IT EXISTS

Five isolated toolkits, no mental model connecting them

Modules 06-10 each taught one stage abstractly and separately, with no product or pipeline attached to any of them. That was the right teaching order, but it leaves a real gap: a learner who finishes Module 10 has five separate toolkits and no picture of how a real question actually gets answered end to end. This concept closes that gap before Module 11 goes on to build each stage out concretely.

03 · CONCRETE EXAMPLE

One question, traced through a document this course already built

Take the exact question "What is the grace period length for canceling an order?" against doc_9f21, the Order Management document this course has used as its running example since Module 10 Concept 03. The chunk that answers it is one already verified word-for-word in Module 07: "The order-cancellation grace period is 14 days from the ship date. Once it elapses, the order status locks to CLOSED and refunds stop processing automatically. Support agents must file a manual override." Nothing about this chunk, this document, or this question is new -- what's new is watching it move through every stage in order.

04 · TECHNICAL MECHANISM

Six stages, in order, each already covered by name

Ingest -- doc_9f21 is read and versioned (Module 06's own territory). Chunk -- the grace-period passage becomes one chunk with a stable chunk_id (Module 07). Embed -- that chunk is embedded with all-MiniLM-L6-v2, this course's own standing convention since Module 08 Concept 06, into a 384-dimensional dense vector -- confirmed directly on the model's own card ("maps sentences & paragraphs to a 384 dimensional dense vector space") and independently corroborated in this course's own byte-math table (Module 08 Concept 06: "384 dim (all-MiniLM-L6-v2) → 1.536 GB"). Store -- the vector, chunk_id, and tenant_id are persisted through Module 10 Concept 14's closing upsert/query/delete interface into the five-table schema documents → document_versions → chunks → embeddings → citations. Retrieve -- the incoming question is embedded the same way and query() runs nearest-neighbor search. Generate -- the retrieved chunk would be injected into a prompt and cited, named here but not built until Concepts 07-09.

06 · IMPORTANT DISTINCTIONS

Online path vs. offline path -- both previewed, neither built here

The online path (traced above) runs once per incoming question, in real time: embed the question, retrieve, generate. The offline path (ingest → chunk → embed → store) runs once per document, ahead of time, well before any question arrives -- Concepts 02-04 build that path out in depth. This concept previews both but is itself neither in depth; it exists to show how they fit together, not to build either one.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"The vector database is doing the RAG."

False -- Module 10 Concept 02 already drew this exact boundary: the database owns persistence, transactional consistency, and query execution only. Chunking, embedding, and generation all happen outside it, in the pipeline this concept traces.

"Chunking and embedding are basically the same step."

False -- they're different modules for a reason. Chunking (Module 07) decides what text becomes one retrievable unit; embedding (Module 08) decides how that unit becomes a vector. Confusing the two hides where each kind of design decision actually lives.

06
MECHANISM

Six stages, traced on one real question

Question: "What is the grace period length for canceling an order?" Traced against doc_9f21, the Order Management document established in Module 10 Concept 03.

  1. Ingest -- doc_9f21 is read and versioned. Nothing is chunked, embedded, or stored yet; this stage belongs to Module 06's own territory (parsing, versioning, provenance), named but not re-taught.
  2. Chunk -- the answer-bearing passage, verified verbatim in Module 07 Concepts 06 and 07: "The order-cancellation grace period is 14 days from the ship date. Once it elapses, the order status locks to CLOSED and refunds stop processing automatically. Support agents must file a manual override." It becomes one chunk with a stable chunk_id.
  3. Embed -- the chunk is embedded with all-MiniLM-L6-v2, this course's own standing convention since Module 08 Concept 06, reused unbroken through Module 09 Concept 07 and every schema/adapter example in Module 10. The model's own card states it "maps sentences & paragraphs to a 384 dimensional dense vector space" -- confirmed independently here, not solely from the in-course citation.
  4. Store -- the vector, chunk_id, and tenant_id are persisted via upsert(), Module 10 Concept 14's own closing abstraction, into the five-table schema documents → document_versions → chunks → embeddings → citations (Module 10 Concepts 03-04). This is the exact point where Module 10 Concept 02's database-boundary triad becomes concrete -- this concept is what reconnects what that boundary drew a line around.
  5. Retrieve -- the incoming question is embedded with the query-side prefix (bi-encoder asymmetry, Module 08 Concepts 03 and 08), then query() runs nearest-neighbor search. Module 09 Concept 07's own tenant-filter fact -- a 20-chunk corpus, 30% selectivity, k=5, matches at ranks {3,7,9,14,17,20}, forcing a scan to rank 17, a 3.4x over-fetch (17 ÷ 5 = 3.4 exactly) -- is named here as a forward-pointer to what filtered retrieval costs, without building it in this concept.
  6. Generate -- named forward, not built: context injection, prompt construction, generation, and citations are Concepts 07-09's own territory. This concept stops at "the retrieved chunk would be injected and cited."

What's needed for orientation only

ECOSYSTEM

Where real frameworks draw the identical six boundaries

Real frameworks (LangChain, LlamaIndex, and others explored in Module 12's own concepts) draw these same six seams -- a document loader, a splitter, an embedding model, a vector-store interface, a retriever, and a generation chain -- as separate, swappable components. This concept names that this boundary-drawing is universal, without endorsing or deep-diving any one framework here; Module 11 Concept 11's own "end-to-end framework-free implementation" is the deliberate contrast to build against.

15
TRADE-OFFS

A fixed seam vs. tightly-coupled code

Module 10 Concept 14's upsert/query/delete seam exists precisely so that stage boundaries stay swappable -- a project could change its embedding model, its vector store, or its chunking strategy independently, as long as each stage still speaks through the same seam. Code that skips the seam and calls a specific vendor's API directly from inside the chunking stage trades that flexibility for less indirection, at the cost of a harder later migration.

16
DIAGNOSIS

What breaks when a stage boundary is violated

LEAKED RESPONSIBILITY

Embedding logic inside the store layer

Module 10 Concept 02 already drew this boundary -- the database owns persistence/consistency/query execution only. Embedding logic that leaks into that layer becomes untestable independently of the database.

VENDOR-SPECIFIC RETRIEVAL

Retrieval code assuming one vendor's query syntax

Bypassing Module 10 Concept 14's generic query() interface to call a specific vendor's syntax directly reintroduces the exact lock-in that interface was built to remove.

18
REALITY

Production implications

  • Latency budget is spent across all six stages, not just retrieval -- Module 09's own recall/latency trade-off table applies specifically to the retrieve stage, and each other stage has its own separate cost.
  • Caching helps most where a stage's output is reused across many questions -- embeddings of a fixed document corpus, for instance -- rather than uniformly across every stage.
  • A stage boundary violated early (Concept 16 above) is a real migration cost paid later, not immediately -- the same lesson Module 10 Concept 01 named for category choice, restated here for pipeline seams.

23
CAREER PRACTICE

Interview questions

Conceptual: walk me through what happens end-to-end when a RAG system receives a query.
The question is embedded with the same model used at index time, a nearest-neighbor query runs against the stored vectors, the top-k matching chunks are retrieved, and those chunks are injected into a prompt along with the question for the generation step to answer from and cite.
System design: why keep the embedding model identical between indexing time and query time?
Different models produce different, generally incomparable vector spaces -- nearest-neighbor search only means anything when the query vector and the stored vectors were produced by the same embedding function.
Debugging: retrieval returns plausible-looking but wrong chunks. Which stage boundary would you check first, and why?
Whether the embedding model used at query time matches the one used at ingest time -- a silent model mismatch is one of the most common causes of confidently-wrong-looking retrieval, and it's invisible unless the two stages are checked against each other directly.
Coding: extend Section 08's skeleton to log which module owns each call.
Wrap each call with a comment or log line naming its owning concept (as in Section 12's annotated version) -- the point being that every call in a real pipeline should be traceable back to a specific, already-understood design decision, not an unexamined default.
