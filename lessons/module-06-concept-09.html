PROGRESSIVE BEGINNER CORE

Full batch, incremental, or event-driven — someone has to pick

Concept 03 raised this question twice and deferred it both times: sources keep changing after first ingestion, so something has to decide when the pipeline notices. This concept names the three ways that decision gets made, and shows exactly what each one costs and how stale it lets the index get.

01 · CONCEPT FIRST

Three strategies, one decision

THIS CONCEPT

Full batch re-ingestion — re-run every document on a fixed schedule, whether it changed or not. Incremental ingestion — re-run only documents that changed since the last checkpoint, still on that same fixed schedule, using Concept 07's own timestamp/hash machinery. Event-driven ingestion — a webhook or CDC event fires the instant a source changes; no schedule at all.

NOT THIS CONCEPT

Concept 07's WHAT-happens-once-a-change-is-detected mechanics — a new version, a new effective_at. This concept only decides WHEN and WHICH SCOPE gets rechecked; it is reused here, not re-taught.

First memory: full batch and incremental both run on a schedule and differ only in scope; event-driven has no schedule and reacts immediately. Two independent axes — trigger and scope — not one strategy dial.

Concept 03 deferred this question twice — this is where it gets answered

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Incremental and event-driven are the same thing."

False — they are orthogonal axes. Incremental narrows the SCOPE of what a scheduled run reprocesses; event-driven changes the TRIGGER mechanism entirely. The worked example uses incremental on a fixed schedule, proving the two are independent.

"Event-driven is strictly better."

False — many sources have no event API at all. A legacy file share or an old internal database may only support being polled, not subscribed to.

"Batch re-ingestion's simplicity makes its waste harmless."

False per the worked example: full batch reprocesses 12 document-instances for only 3 real changes over the same horizon — 9 wasted reruns, a 75% cost reduction incremental captures for free on the identical schedule.

09 · WHAT YOU SHOULD UNDERSTAND

Readiness check before moving on

Three strategies, two axes

Trigger (schedule vs. event) and scope (all documents vs. only changed ones) are independent choices, not one dial with three positions.

Incremental fixes cost, not staleness

Incremental and full batch share the exact same schedule and therefore the exact same detection lag — incremental only shrinks how much gets reprocessed at each tick.

Event-driven fixes both

Because there is no schedule to wait for, event-driven matches incremental's already-optimal cost while dropping detection lag to (idealized) zero.

Not every source supports every strategy

Event-driven requires a source that can push a notification. Sources that can only be polled are limited to full batch or incremental.

Teach-back questions

  1. Why does incremental ingestion's average detection lag equal full batch's, even though its reprocessing cost is 75% lower in the worked example?
  2. D5 changes on day 9 under a 7-day batch_interval. Which day does a scheduled strategy (full batch or incremental) actually notice that change, and why not day 9 itself?
  3. Name one real source type that cannot support event-driven ingestion, and explain what strategy it is limited to instead.

04
INTUITION

A security guard's three ways of noticing something moved

Picture a building security guard with three different ways of working. Full batch is a guard who walks every single room on the hour, every hour, regardless of whether anything in any of those rooms actually changed since the last round. Incremental is the same hourly round, but the guard only stops to check rooms a motion sensor flagged since the last round — same schedule, far less wasted walking. Event-driven is an alarm that pages the guard the instant a door actually opens, with no fixed round at all.

Analogy boundaryThe guard analogy explains why the three strategies differ in trigger and effort. It does not explain how to compute a reprocessing cost or a detection lag in days — Sections 05 and 09 give those formally.

06
MECHANISM

Two lanes: poll on a schedule, or wait for a push

SCHEDULE-TRIGGERED LANE

Poll the source every τ days. Full batch reprocesses ALL documents at every tick; incremental reprocesses only CHANGED-ONLY documents at every tick, using Concept 07's timestamp/hash comparison to decide which ones qualify.

EVENT-TRIGGERED LANE

Push, not poll. A CDC event's path: source commit → change stream → listener → a single-document ingestion job → Concepts 02-08's whole chain runs for that one document → a new lineage event is appended, a direct Concept 08 callback.

09
MATHEMATICS

Lag, cost, and an idealization that deliberately doesn't match the sample

detection_lag = trigger_time − change_time
full_batch_cost = ticks × N
incremental_cost = Σ (documents changed since previous checkpoint)
event_driven_cost = number of real change events
waste = full_batch_cost − actual_changes

Under a uniform-arrival assumption, the idealized average detection lag for a scheduled strategy is approximately τ/2 — half the batch interval, on average, if changes land uniformly at random within each window. This is explicitly an idealization, not a prediction: the worked example's three change events land at days 2, 5 and 9 against a 7-day interval, giving an empirical average lag of exactly 4.0 days, not the 3.5-day figure τ/2 = 7/2 would suggest. Three discrete events are too small a sample for the uniform-arrival approximation to land exactly, and that gap is the point — it is a deliberate caution against over-fitting a clean formula to a small, real sample.

WORKED EXAMPLE

Cost 12 vs. 3 vs. 3; average lag 4.0 vs. 4.0 vs. 0.0 days

Corpus: D1 (POLICY-REFUND-001) through D6, N = 6. Horizon: 14 days. Changes: D3 on day 2, D1 on day 5, D5 on day 9. batch_interval = 7 days, so scheduled runs occur at day 7 and day 14.

StrategyCostPer-change detection lagAverage lag
Full batch (2 runs × 6 docs)12D3: 7−2=5d · D1: 7−5=2d · D5: 14−9=5d4.0 days
Incremental (2 docs at day 7, 1 doc at day 14)3D3: 7−2=5d · D1: 7−5=2d · D5: 14−9=5d4.0 days
Event-driven (1 job per real change)3D3: 0d · D1: 0d · D5: 0d0.0 days

Full batch's cost of 12 against only 3 real changes leaves 12 − 3 = 9 wasted reruns — a 75% cost reduction available simply by switching to incremental on the identical schedule. Incremental's average lag is unchanged from full batch's, 4.0 days in both cases, because incremental only narrows WHAT gets reprocessed at each tick, not WHEN the tick happens — it is still schedule-triggered. Event-driven matches incremental's already-optimal cost of 3 while dropping average lag to 0.0 days, because there is no schedule to wait for at all. Every figure here was computed once via an executed Node.js script and independently reproduced via an executed Python script run through the py launcher; both runs printed identical results for every number in this table.

11
CONCRETE USE

Two clean fits, a boundary case, a mistake

CLEAN FIT

Nightly full batch on a small, slow-changing wiki

When the corpus is small and edits are rare, full batch's simplicity beats the modest waste — there is no engineering cost to justify against a small number of wasted reruns.

CLEAN FIT

CDC/webhook-driven ingestion of a support-ticket feed

A live agent-assist system needs a resolved ticket reflected immediately — event-driven ingestion off the ticketing system's own change stream is the natural fit.

BOUNDARY CASE

A source with no event API but too costly for full batch

Scheduled incremental via an API's own "modified since" filter — revisiting Concept 03's API source discussion — reprocesses only what changed without needing the source to support push notifications at all.

MISTAKE TO AVOID

Assuming every source can support event-driven

Legacy databases and file shares often expose no change stream or webhook mechanism whatsoever — they are limited to full batch or incremental by construction, not by choice.

12
CODE

All three strategies over the fixed corpus, from scratch

PYTHON · NO LIBRARIES 
CHANGES = [("D3", 2), ("D1", 5), ("D5", 9)]
DOCS = ["D1", "D2", "D3", "D4", "D5", "D6"]
HORIZON = 14
BATCH_INTERVAL = 7

def full_batch_cost(horizon, interval, n_docs):
    ticks = horizon // interval
    return ticks * n_docs

def scheduled_ticks(horizon, interval):
    ticks, t = [], interval
    while t <= horizon:
        ticks.append(t)
        t += interval
    return ticks

def incremental_cost_and_lag(changes, ticks):
    cost, lags, checkpoint = 0, [], 0
    for tick in ticks:
        changed_this_window = [day for _, day in changes if checkpoint < day <= tick]
        cost += len(changed_this_window)
        lags += [tick - day for day in changed_this_window]
        checkpoint = tick
    return cost, lags

def event_driven_cost_and_lag(changes):
    return len(changes), [0 for _ in changes]

ticks = scheduled_ticks(HORIZON, BATCH_INTERVAL)
batch_cost = full_batch_cost(HORIZON, BATCH_INTERVAL, len(DOCS))
inc_cost, inc_lags = incremental_cost_and_lag(CHANGES, ticks)
evt_cost, evt_lags = event_driven_cost_and_lag(CHANGES)
batch_lags = inc_lags  # full batch shares incremental's schedule, so shares its lag

assert batch_cost == 12
assert inc_cost == 3
assert evt_cost == 3
assert sum(batch_lags) / len(batch_lags) == 4.0
assert sum(evt_lags) / len(evt_lags) == 0.0
assert batch_cost - len(CHANGES) == 9  # wasted reprocessing

print("full batch:", batch_cost, batch_lags)
print("incremental:", inc_cost, inc_lags)
print("event-driven:", evt_cost, evt_lags)

CONTRAST

Full batch vs. incremental vs. event-driven

StrategyStrengthWeakness
Full batchSimplest to build — no change detection logic at all12 reprocessings for 3 real changes in the worked example — 75% wasted effort

16
DIAGNOSIS

Failure modes

MISSED WEBHOOK DELIVERY

A dropped push is silently never retried

Event-driven's single point of failure — unlike polling, which always eventually rechecks a source, a missed webhook delivery has no built-in second chance unless something else notices.

CHECKPOINT DRIFT

A wrong or unpersisted "last checkpoint" timestamp

Can silently skip boundary-time changes in incremental ingestion — ties directly to Concept 07 and Concept 08's own monotonicity concerns about ordered timestamps.

THUNDERING HERD

Load spikes at scheduled batch time

A production/latency concern when many sources or documents are all reprocessed at the same scheduled tick — named forward to Module 19.

REALITY

Production implications

  • Even under an event-driven design, periodic incremental reconciliation runs are needed for missed-event recovery — a scheduled safety net underneath the push mechanism, not a contradiction of it.
  • Backfill and catch-up after downtime is a real operational need: when a listener has been offline, the gap has to be reconciled, typically by running an incremental pass over the missed window.
  • detection_lag feeds Module 19's "Freshness and reliability SLOs" directly, and the index-side consequences of a detected change are Module 19's "Document updates and incremental indexing" — both named forward only here.
19
RECALL

Knowledge check

Why does incremental ingestion's average detection lag equal full batch's exactly, in the worked example?
Both strategies poll on the same fixed schedule, so a change is noticed at the same next tick either way. Incremental only reduces how many documents get reprocessed at that tick, not when the tick happens — cost and lag are genuinely independent quantities here.
Why is a scheduled strategy's average lag not exactly τ/2 in this lesson's own worked example?
τ/2 assumes changes arrive uniformly at random across the interval. With only three discrete change events at days 2, 5 and 9 against a 7-day interval, the empirical average (4.0 days) does not match the idealized 3.5-day figure — a small, real sample simply doesn't have to match a clean statistical approximation.
Why can't every source support event-driven ingestion?
Event-driven requires the source itself to emit a notification — a webhook call or a CDC stream off a transaction log. Legacy databases and file shares often expose neither mechanism, leaving full batch or incremental as the only options.

FEEDBACK

Solution and teach-back

Open the worked solution
Scheduled runs occur at day 5 and day 10 (2 ticks). Full batch cost = 2 ticks × 4 docs = 8. E2 (day 3) is caught at the day-5 tick, lag = 5 − 3 = 2 days. E4 (day 7) is caught at the day-10 tick, lag = 10 − 7 = 3 days. Average lag = (2 + 3) / 2 = 2.5 days — the same for full batch and incremental, since both share this schedule. Incremental cost = 1 document caught at day 5, plus 1 document caught at day 10 = 2, versus full batch's 8 — a waste of 8 − 2 = 6 reruns for full batch. Event-driven cost = 2 (one job per real change), with 0.0-day average lag, since each change is caught the instant it happens.

Teach-back: explain, in your own words, why incremental's cost of 2 and full batch's cost of 8 can coexist with an identical 2.5-day average detection lag for both.

23
CAREER PRACTICE

Interview questions

Conceptual: what's the real difference between incremental and event-driven ingestion?
They sit on independent axes. Incremental narrows scope (only changed documents) but keeps a schedule. Event-driven changes the trigger itself (a push, not a poll) and has no schedule at all. A system can be scheduled-and-incremental, as this lesson's worked example is, without being event-driven.
Mathematical: derive the cost and lag formulas for each strategy.
full_batch_cost = ticks × N; incremental_cost = sum of documents changed within each tick's window since the previous checkpoint; event_driven_cost = number of real change events. detection_lag = trigger_time − change_time, computed per change and averaged; full batch and incremental share the same trigger times, so share the same lag distribution.
Coding: implement a change-since-checkpoint filter for incremental ingestion.
Track a persisted checkpoint timestamp. At each tick, select documents whose source_last_modified_at (or content hash) differs from what was recorded at the previous checkpoint, reprocess only those, then advance the checkpoint to the current tick time.
Debugging: a webhook-driven pipeline is missing updates for one source. How do you diagnose it?
Check whether the webhook is actually configured and firing at the source; check the listener's own logs for dropped or failed deliveries; and run a one-off incremental reconciliation pass to find documents whose source_last_modified_at is newer than their last recorded ingested_at — exactly Section 16's missed-webhook failure mode.
System design: design a mixed-strategy ingestion trigger layer for a multi-source RAG corpus.
Reuse Concept 01's source inventory to tag each source with its available trigger mechanisms. Route sources with a webhook or CDC stream to event-driven ingestion, sources that are pollable but lack push support to incremental, and small slow-changing sources to full batch — all feeding the same Concepts 02-08 chain regardless of which trigger fired it.
