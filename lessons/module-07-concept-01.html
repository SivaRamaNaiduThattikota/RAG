MODULE 07 · CONCEPT 01

One document.
Too big to embed as one piece.

Module 06 closed with nine concepts' worth of parsing, cleaning, deduplication, versioning and provenance — a pipeline that turns a messy source into one clean, traceable document. None of that says what happens when a model has to turn that document into a single vector. This concept names the two ways skipping that step fails: the document is either too large to embed at all, or it embeds fine as one vector so diluted it can't be found or cited precisely. Module 07 exists to fix both.

PROGRESSIVE BEGINNER CORE

A document that never gets split has nowhere to hide its size

Every concept in Module 06 assumed a document eventually gets embedded and retrieved. None of them said how a document that runs pages long actually becomes one embeddable, retrievable unit. This concept names why that question can't be skipped, before Concepts 02 through 04 answer how.

01 · CONCEPT FIRST

Chunking is the WHY, not yet the HOW

THIS CONCEPT

Why a document has to be split into smaller pieces before it can be embedded and retrieved at all — the two concrete ways skipping that step fails, and the numbers that make each failure visible.

NOT THIS CONCEPT

Which splitting method to use — fixed-size, recursive, sentence/paragraph, semantic, proposition-based. Those are Concepts 02 through 04's job, reused here only by name.

First memory: chunking exists because of two independent failures — a document can be too big to embed at all, or it can embed fine as one vector so diluted it stops being useful. Fixing one doesn't fix the other.
02 · WHY IT EXISTS

Module 06 produced a clean document. It never said how big a "unit" can be.

Concept 09 closed Module 06 by naming this module by name: "Module 07, 'Chunking & document representation,' opens next with 'Why chunk documents?' — named here only, not yet built." Concepts 01 through 09 gave a document a stable identity, a clean parse, a dedup check, a version, and a provenance trail. Every one of those concepts operated on a document as a whole. Embedding models don't. Module 02 Concept 07 already established that a transformer's block stack processes a bounded number of tokens per forward pass — a hard ceiling, not a suggestion. This concept is where that ceiling stops being an abstract limit and starts being a design problem.

03 · CONCRETE EXAMPLE

A 7,000-token handbook, a 512-token embedding cap

An onboarding handbook runs 7,000 tokens end to end. The embedding model in use — a representative, round figure for many smaller sentence-embedding models — accepts at most 512 tokens per input. Feed the whole handbook in as one unit and the model doesn't error. It truncates: the first 512 tokens go in, the remaining 6,488 are silently dropped, no warning raised. That's 92.69% of the document gone before retrieval ever gets a chance to work with it.

04 · TECHNICAL MECHANISM

The second failure: embeds fine, but as one diluted average

Raise the cap and the truncation problem shrinks. It does not disappear, and it does not touch a second, independent failure. Module 04 Concept 03 already showed cosine similarity between two toy vectors. Reuse that machinery here: Topic A ("benefits enrollment") sits at unit vector (1, 0); Topic B ("expense reimbursement") — a genuinely different topic — sits at (0, 1). A query about benefits enrollment is (1, 0), so it matches Topic A alone with cosine similarity exactly 1.0. Average the two topics into one whole-document vector and normalize it: the result is (0.7071, 0.7071), and its similarity to that same query drops to 0.7071 — a 29.29% relative loss, with no arithmetic error anywhere. Averaging two legitimate topics geometrically pulls the vector toward their midpoint, which is provably farther from either topic than either topic is from itself.

Failure modeWhat happensWhat fixes it
(a) Too large to embed at allSilent truncation past the model's max input lengthA smaller unit that fits under the cap
(b) One diluted vectorEmbeds fine, but the single vector averages unrelated content togetherA smaller unit that stays on one topic

Both fixes point the same direction: split the document into smaller pieces before embedding. That's chunking — the mechanism itself starts at Concept 02.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"A model with a bigger max input length makes chunking unnecessary."

False — it only shrinks failure mode (a). Failure mode (b) is a property of averaging unrelated content, not of any token ceiling, and a bigger model does nothing to fix it.

"If the whole document fits under the cap, there's nothing to worry about."

False per Section 14's lab: a 2-topic document well under any reasonable cap still loses 29.29% of its retrievability to dilution alone.

"Chunking is a minor preprocessing detail."

False — it decides the actual unit every later retrieval and citation operates on. Get it wrong and no downstream fix (better embeddings, better reranking) fully recovers what was lost.

09 · WHAT YOU SHOULD UNDERSTAND

Readiness check before moving on

Two independent failure modes

Truncation (too large to embed) and dilution (embeds fine, but as one averaged vector) are separate problems with separate causes.

A bigger cap only fixes one of them

Raising the embedding model's max input length shrinks truncation loss but leaves dilution completely untouched.

Both failures point to the same fix

Splitting a document into smaller, more topically-focused pieces before embedding addresses both — this module's actual subject, starting at Concept 02.

This concept picks no method

Fixed-size, recursive, semantic and proposition-based chunking are all still ahead, in Concepts 02 through 04.

02
OUTCOMES

Operational objectives

NAME

Name and distinguish the two failure modes

Truncation (too large to embed at all) and dilution (embeds fine, but as one averaged vector) — independent problems with independent causes.

COMPUTE

Compute a token-loss figure and a similarity-dilution figure

Given a document length and an embedding cap, or a set of topic vectors, derive the exact loss either failure mode produces.

DECIDE

Recognize when raising a cap does and doesn't help

A bigger max input length shrinks truncation loss and has zero effect on dilution — knowing which failure you're looking at determines which fix applies.

MAP

Place chunking correctly between ingestion and embedding

Chunking decides the unit of text; it does not clean documents (Module 06) or turn text into vectors (Module 08).

04
INTUITION

A translator with one index card

Picture a translator asked to summarize an entire book onto a single index card. One option: write as much of the opening chapters as fits, and leave everything past that point off the card entirely — failure mode (a), truncation. The other option: write one blurry sentence that tries to average every chapter's theme into a single line — technically covers the whole book, but is too vague to answer a question about any one chapter precisely. Failure mode (b), dilution, is that second option: nothing was dropped, but nothing survived clearly either.

Analogy boundaryThe index-card analogy explains why either shortcut fails. It does not explain how to compute a token-loss percentage or a cosine-similarity drop — Sections 05 and 09 give those formally.

06
MECHANISM

Two lanes, two causes, two independent fixes

TRUNCATION LANE

Caused by a hard token-count ceiling. Grows with document length, shrinks with a larger cap. Silent by default — most embedding APIs truncate rather than error.

DILUTION LANE

Caused by averaging unrelated content into one vector. Grows with topic count packed into one unit, completely unaffected by the cap — a document well under any reasonable length limit can still dilute badly.

09
MATHEMATICS

Truncation loss and dilution loss, stated formally

tokens_lost = max(0, docLen − cap)
pct_lost = tokens_lost / docLen
windows_needed = ⌈docLen / cap⌉
mean(v₁..v_N) = (1/N) · Σ vᵢ
dilution_drop = 1 − cos(q, normalize(mean(v₁..v_N)))

Truncation loss depends only on docLen and cap — raise the cap and pct_lost falls, with no effect on anything else. Dilution depends only on how many distinct topics get averaged into one vector and how far apart those topics are — raise the cap all you like and dilution_drop does not move, because dilution never depended on cap in the first place.

WORKED EXAMPLE

92.69% truncation loss; 29.29% dilution loss — from two unrelated causes

Every figure above was computed once via an executed Node.js script and independently reproduced via a separately executed Python script; both runs printed identical results for tokens_lost, pct_lost, windows_needed, and every cosine value shown. Note what the two results do not share: nothing about docLen or cap appears anywhere in the dilution computation, and nothing about topic count appears anywhere in the truncation computation — confirming the two failures really are independent, not two views of the same number.

11
CONCRETE USE

A clean fit, a boundary case, a mistake

CLEAN FIT

A short, single-topic FAQ entry

Already well under any reasonable cap and about one topic — chunking still applies for pipeline consistency, but neither failure mode is a real risk here.

BOUNDARY CASE

A document a few hundred tokens over the cap

Truncation loss is small in percentage terms, but still silent — a document that "mostly" fits is exactly the case most likely to go unnoticed without deliberate chunking.

MISTAKE TO AVOID

Assuming a larger-context embedding model removes the need to chunk

It removes failure mode (a) for that document. Failure mode (b) — dilution from mixing topics into one vector — is untouched, and Section 14's lab shows it degrading further as more unrelated topics get packed in, regardless of model size.

12
CODE

Both failure modes, from scratch

PYTHON · NO LIBRARIES 
import math

def truncation_loss(doc_len, cap):
    lost = max(0, doc_len - cap)
    pct_lost = lost / doc_len
    windows = math.ceil(doc_len / cap)
    return lost, pct_lost, windows

def mean_vector(vectors):
    n = len(vectors)
    sx = sum(v[0] for v in vectors)
    sy = sum(v[1] for v in vectors)
    return (sx / n, sy / n)

def cosine_to_query(mean_vec, query=(1, 0)):
    norm = math.sqrt(mean_vec[0] ** 2 + mean_vec[1] ** 2)
    if norm < 1e-9:
        return None
    return (mean_vec[0] * query[0] + mean_vec[1] * query[1]) / norm

lost, pct_lost, windows = truncation_loss(7000, 512)
assert lost == 6488
assert round(pct_lost * 100, 2) == 92.69
assert windows == 14

topics = [(math.cos(i * math.pi / 2), math.sin(i * math.pi / 2)) for i in range(2)]
doc_vec = mean_vector(topics)
cos_doc = cosine_to_query(doc_vec)
assert round(cos_doc, 5) == 0.70711
drop_pct = (1 - cos_doc) * 100
assert round(drop_pct, 2) == 29.29

print("truncation:", lost, round(pct_lost * 100, 2), windows)
print("dilution cos:", round(cos_doc, 5), "drop%:", round(drop_pct, 2))

ECOSYSTEM

Chunking as a first-class concern in real tooling

LangChain ships text splitters as a named, first-class abstraction — chunking is not an implementation detail teams invent from scratch, but a documented, reusable layer real production pipelines rely on. Sentence-Transformers' own documentation states a fixed max_seq_length and truncates beyond it by default, the exact mechanism behind failure mode (a). Pinecone's own chunking-strategies guide frames the same motivation this concept opened with: a document has to be split to be usable by a retrieval system at all, independent of which specific method a team ultimately picks.

16
DIAGNOSIS

Failure modes

SILENT TRUNCATION

Most embedding APIs truncate, they don't error

A document over the cap doesn't fail loudly — it just quietly loses everything past the limit, which is precisely why it's easy to miss without deliberate handling.

WASTED EMBEDDING COST

A diluted vector still costs a full embedding call

Embedding an unsplit, multi-topic document pays the same compute cost as embedding a well-scoped chunk, for a vector that retrieves worse.

INCONSISTENT UNITS

Some documents chunked, others left whole

A pipeline that only chunks documents it happens to notice are "too long" leaves silently-diluted short-but-multi-topic documents unaddressed — named forward to Concept 09's chunk-quality evaluation.

REALITY

Production implications

  • Silent truncation is easy to ship unnoticed — a retrieval system can run for months before someone traces a "the model should have known this" complaint back to content that was truncated away long before retrieval ever ran.
  • Embedding cost scales with the number of chunks produced, not the number of source documents — a real budget line Module 19's cost material returns to, named forward only here.
  • Chunk size, chunk overlap, and chunk-quality evaluation (Concepts 05, 06 and 09) all build on this concept's conclusion that some splitting decision is unavoidable, not optional.
19
RECALL

Knowledge check

Why doesn't raising the embedding model's max input length fix dilution?
Dilution comes from averaging multiple topics into one vector, not from a token-count ceiling. Section 09's formula shows dilution_drop depends only on the topic vectors and the query — cap never appears in it at all.
A 7,000-token document is fed to a 2,048-token-cap model instead of a 512-token one. Does truncation loss reach zero?
No — tokens_lost = 7000 − 2048 = 4,952, still 70.74% lost. A bigger cap shrinks the loss; it doesn't eliminate it unless the cap exceeds the document's full length.
What does this concept decide that Module 08's embedding step does not?
This concept decides what the unit of text handed to an embedding model should be. Module 08 decides how any given unit of text, once chosen, gets turned into a vector at all.

FEEDBACK

Solution and teach-back

Open the worked solution
Truncation: tokens_lost = 3000 − 400 = 2,600; pct_lost = 2600/3000 = 86.67%; windows_needed = ⌈3000/400⌉ = 8. Dilution: with topics at 0°, 90° and 180°, the mean vector is (0, 1/3) — its x-component is exactly 0, so cosine similarity to a query at (1, 0) is exactly 0.0000: the mean vector is well-defined and nonzero, but sits exactly orthogonal to the query. A query that would perfectly match a Topic-1-only chunk retrieves nothing at all from this document.

Teach-back: explain, in your own words, why a mean vector can be nonzero and still produce a cosine similarity of exactly zero.

PORTABLE MEMORY

Concept card

Why chunk documents?

  • Failure (a) — truncation: too large to embed at all; a token-count ceiling silently drops the excess
  • Failure (b) — dilution: embeds fine, but as one vector averaging unrelated content together
  • Core relation: a bigger embedding cap fixes (a) only; splitting into smaller, topically-focused pieces fixes both

Memorable example

A 7,000-token handbook against a 512-token cap loses 92.69% of itself to silent truncation. Two unrelated topics averaged into one vector drop query similarity from 1.0000 to 0.7071 — a 29.29% loss with no arithmetic error anywhere, purely from averaging.

CAREER PRACTICE

Interview questions

Conceptual: what's the real difference between the two chunking failure modes?
Truncation is caused by a hard token-count ceiling and depends only on document length versus cap. Dilution is caused by averaging unrelated content into one vector and depends only on topic count and topic separation — the two causes share no variables at all.
Mathematical: derive the truncation-loss and dilution-drop formulas.
tokens_lost = max(0, docLen − cap); pct_lost = tokens_lost / docLen; windows_needed = ⌈docLen / cap⌉. dilution_drop = 1 − cos(q, normalize(mean(v₁..v_N))), where mean(v₁..v_N) = (1/N)·Σvᵢ.
Coding: implement a check that flags a document as at-risk for truncation before it's embedded.
Tokenize the document, compare the token count against the target embedding model's documented max_seq_length, and flag any document whose token count exceeds that cap before it reaches the embedding call — exactly the guard Section 16's silent-truncation failure mode argues for.
Debugging: retrieval keeps missing an answer that's clearly present in a source document. What do you check first?
Whether the relevant passage survived embedding at all — check the document's token count against the embedding model's cap for truncation, and check whether the passage shares its chunk with unrelated topics for dilution. Either failure mode alone can explain a present-but-unretrievable answer.
System design: how would you decide whether a corpus needs aggressive chunking or can mostly stay whole?
Profile the corpus for two signals: document length relative to the embedding cap (truncation risk) and topic homogeneity within documents (dilution risk). Short, single-topic documents need little to no chunking; long or multi-topic documents need it regardless of whether they individually exceed the cap.
