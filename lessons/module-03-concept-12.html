MODULE 03 · CONCEPT 12

When RAG
should not be used.

Concepts 02, 07, and 08 each ruled out one alternative to RAG by name — asking the model directly, stretching the context window, fine-tuning, search, or tool use — always in RAG's favor. Concept 11 then assumed RAG was the right tool and diagnosed where an already-answerable query's pipeline actually broke. This concept asks the mirror question neither of those settled: even implemented well, with every one of Concept 11's three links holding, is RAG ever the wrong tool to reach for in the first place? Four independent conditions can each say yes on their own — the task isn't knowledge-intensive at all, the corpus has no coverage of the domain whatsoever, the query volume or latency budget makes retrieval's overhead not worth paying, or the answer must be guaranteed correct with zero tolerance for the residual risk Concept 11's chain describes. Any single gate is enough; a perfect pipeline doesn't rescue a task that never needed one.

01 · CONCEPT FIRST

Four independent gates, any one enough

GATE 1 · NOT KNOWLEDGE-INTENSIVE

The task doesn't depend on a specific outside fact at all — Concept 10's first failure reason, now used up front as a disqualifying gate instead of a diagnostic applied after the fact. No fact needed means retrieval has nothing to retrieve for.

GATE 2 · NO DOMAIN COVERAGE AT ALL

Every source that could possibly answer this whole class of question is absent from any corpus available to build — not one missing fact inside an otherwise-covered domain (Concept 10's coverage gap), but an entire domain nobody has ingested for any question at all.

GATE 3 · OVERHEAD NOT WORTH IT

Embedding a query, searching an index, and assembling context all cost time on every single call. At high enough volume or tight enough latency budgets, that fixed overhead can cost more than it returns — even when retrieval works perfectly.

GATE 4 · ZERO TOLERANCE FOR RESIDUAL RISK

Concept 11 showed that any of three links can still break even in a well-built pipeline. A task that needs a guaranteed-correct answer with no room for that residual risk is the wrong shape for RAG, no matter how rarely the chain actually fails.

First memory: RAG being implemented well is a separate question from whether RAG belongs here at all — any single one of four independent conditions is enough to say no, regardless of how the other three come out.
02 · WHY IT EXISTS

Ruling out the tool itself, not just its rivals

Concepts 02, 07, and 08 each ruled out one specific alternative to RAG by name — asking the model directly, stretching the context window, fine-tuning, search, or tool use — always in RAG's favor. None of them asked the question this concept asks: whether RAG itself, compared against not building a retrieval system at all, is worth the cost for a given task. Concept 11 already gave one reason this question is worth asking before implementation rather than after: a well-diagnosed, well-fixed pipeline still can't rescue a task it should never have been asked to do in the first place.

WITHOUT THIS GATE

Every task defaults to "build a RAG pipeline for it," and Concept 11's failure chain gets used later to explain why it underperforms — even when no version of that pipeline was ever going to be worth its cost.

WITH THIS GATE

A task is checked against four independent conditions before any retrieval, chunking, or embedding work begins. Only a task that clears all four is worth building RAG for at all.

03 · CONCRETE EXAMPLE

Four new requests for the Oracle assistant, each disqualified a different way

None of these four requests reuse Concept 10's or Concept 11's remote-workdays, PTO, or farewell-note examples — they're new tasks, chosen so each one trips exactly one gate.

"REWRITE THIS SELF-REVIEW IN A FRIENDLIER TONE"

Gate 1 trips: the full text to rewrite is already in the request. No outside fact is needed, so no corpus, however complete, changes the output.

"WHAT DOES OUR PATENT PORTFOLIO SAY ABOUT WATERMARKING?"

Gate 2 trips: the assistant's entire corpus is three HR policy documents. Nothing about patents has ever been ingested, for any question in that domain — not just this one.

LIVE TYPEAHEAD SUGGESTIONS WHILE TYPING, SUB-50MS, THOUSANDS OF TIMES A SECOND

Gate 3 trips: even if every keystroke's tiny query needed a fact, embedding and searching on every keystroke at this volume and latency budget costs more than it could ever return.

"CALCULATE AND ISSUE THIS PAYCHECK'S EXACT FEDERAL TAX WITHHOLDING"

Gate 4 trips: the number has legal consequences and needs one deterministic calculation, with zero room for Concept 11's grounded-misread risk.

Four different tasks, four different reasons — and none of them are fixed by chunking better, embedding better, or improving the reranker.

04 · TECHNICAL MECHANISM

Four independent checks, in any order

CHECK 1

Does this need an outside fact?

If no, stop — Gate 1 trips regardless of what any corpus contains. This is Concept 10's first failure reason, reused as an up-front disqualifier.

CHECK 2

Does any corpus cover this whole domain?

If nothing has ever been ingested for this class of question — not just this one fact — Gate 2 trips. Wider than Concept 10's per-question coverage gap.

CHECK 3

Does volume and latency clear retrieval's overhead?

If the query rate or latency budget can't absorb an embedding-plus-search round trip, Gate 3 trips, even with a perfectly correct retriever.

CHECK 4

Can this tolerate any residual chain risk?

If the answer must be guaranteed correct with zero tolerance for Concept 11's three-link residual risk, Gate 4 trips.

ANY ONE TRIPS

Then RAG shouldn't be attempted here

The four checks don't have to run in this order and don't require each other — one "yes" to any of them is already a complete answer, no matter how the other three come out.

05 · ARCHITECTURE / FLOW

A gate that decides whether the skeleton gets built at all

Task request↓RAG-fit gate (this concept)↓Concept 06's nine-box skeleton↓Answer

Concept 10's answerability gate and Concept 11's failure chain both assume a pipeline already exists to run the check against. This concept's gate sits one level earlier: before any of Concept 06's nine boxes are even proposed for a task, these four conditions decide whether building that skeleton is worth attempting at all. A "no" on all four sends the task into the skeleton exactly as later modules build it; a "yes" on any one sends it to a non-RAG alternative instead — direct generation, better ingestion, a cache, or a deterministic rule, depending on which gate tripped.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"If RAG can technically retrieve something relevant, it must be worth using."

Section 03's typeahead example retrieves something relevant to every keystroke and still trips Gate 3 — relevance doesn't mean the overhead is worth paying.

"A coverage gap and 'no domain coverage at all' are the same thing."

Concept 10's coverage gap is one fact missing from an otherwise-covered domain; Gate 2 is a whole domain that was never ingested for any question — a much stronger condition.

"High query volume is only a cost problem, not a fit problem."

At Section 03's scale, no amount of caching the embedding call changes the architecture decision — the fix is to not run per-call retrieval, not to make it cheaper.

"If the pipeline usually gets it right, zero-tolerance tasks are fine."

"Usually" isn't "guaranteed" — Concept 11 showed even a well-built chain has three separate places to fail, and Gate 4 is exactly about tasks that can't absorb any of them.

04
INTUITION

Deciding whether to hire a researcher, before judging how well they'd work

Before hiring a research assistant to answer your questions, four checks come before judging how good a hire they'd be. Does the question need research at all, or just a quick reply from what you already know? Does any library even hold material on the topic? Do you need the answer faster than any researcher, however skilled, could physically search for it? And can you tolerate a competent researcher occasionally citing the wrong page? A "no" to research being needed, to any library existing, to the timeline allowing a search, or to any risk of a wrong citation — any single one — and the hire doesn't make sense, no matter how good the researcher would turn out to be once hired.

Analogy boundaryA research assistant doesn't have embeddings, token budgets, or a retrieval index. The point of the analogy is the structural claim only — four independent reasons a hire could be the wrong call before ever judging the hire's skill — not anything about staffing decisions.

09
MATHEMATICS

A four-term disjunction, and Phase 1's math motifs meeting at the door

Let G1(t) through G4(t) each be 1 if gate i trips for task t, and 0 otherwise. Whether RAG should be attempted is:

UseRAG(t) = ¬G1(t) ∧ ¬G2(t) ∧ ¬G3(t) ∧ ¬G4(t)

Read left to right: RAG is worth attempting only if none of the four gates trips — every term must be the negation of a trip for the whole expression to hold. Equivalently, by De Morgan's law, the disqualifying condition itself is a plain disjunction over the four gates:

¬UseRAG(t) = G1(t) ∨ G2(t) ∨ G3(t) ∨ G4(t)

This is worth noticing precisely because it closes a small loop across Module 03's math: Concept 10's answerability predicate was a disjunction over two terms (not knowledge-intensive, or covered), and Concept 11's correctness predicate was a conjunction over three terms (retrieved, survived, used correctly). This concept's disqualifying condition is the De Morgan dual of its own "worth attempting" conjunction — the same underlying structure, at a fourth scale, closing the module's last new mathematical idea on the same note it opened with.

11
CONCRETE USE

Four cards: a clean fit, a boundary case, a counterexample, and a mistake

CLEAN FIT

Remote workdays per week, from Section 10

A real fact is needed, the corpus covers it, the volume and latency budget leave room for retrieval, and the task can tolerate the chain's small residual risk — the one case genuinely worth building Concept 06's skeleton for.

BOUNDARY CASE

A task at "medium" query volume, with no stated latency ceiling

Gate 3 isn't naturally binary — someone still has to pick a volume and latency threshold below which retrieval's overhead is acceptable. Treat this as a deployment decision to make explicitly, not a fact to discover.

COUNTEREXAMPLE

A calculated number that a human always reviews before it's final

Looks like it should trip Gate 4, but if a mandatory human-review step absorbs the residual risk before the number becomes binding, the task's actual tolerance for the chain's risk is higher than the model's output alone suggests — the gate is about the full system's tolerance, not the model's.

MISTAKE TO AVOID

Stopping the analysis the instant one gate trips

The verdict is already settled once any gate trips, but skipping the other three checks in production planning can hide a second, independently disqualifying reason that would matter if the first one were later engineered away.

CODE

The RAG-fit checker, from scratch

PYTHON · DECIDE WHETHER TO ATTEMPT RAG FOR A TASK 
def should_use_rag(is_knowledge_intensive, domain_is_covered,
                    overhead_is_acceptable, tolerates_residual_risk):
    # Section 09's disjunction, spelled out as ordered branches --
    # any single "no" is a complete, sufficient answer on its own.
    if not is_knowledge_intensive:
        return "skip_rag", "gate_1_not_knowledge_intensive"
    if not domain_is_covered:
        return "skip_rag", "gate_2_no_domain_coverage"
    if not overhead_is_acceptable:
        return "skip_rag", "gate_3_overhead_not_worth_it"
    if not tolerates_residual_risk:
        return "skip_rag", "gate_4_zero_tolerance"
    return "use_rag", "all_four_gates_clear"


# Section 10's five tasks, as boolean facts about each one
tasks = [
    dict(is_knowledge_intensive=False, domain_is_covered=True,  overhead_is_acceptable=True,  tolerates_residual_risk=True),   # self-review rewrite
    dict(is_knowledge_intensive=True,  domain_is_covered=False, overhead_is_acceptable=True,  tolerates_residual_risk=True),   # patent question
    dict(is_knowledge_intensive=True,  domain_is_covered=True,  overhead_is_acceptable=False, tolerates_residual_risk=True),   # sub-50ms typeahead
    dict(is_knowledge_intensive=True,  domain_is_covered=True,  overhead_is_acceptable=True,  tolerates_residual_risk=False),  # tax withholding
    dict(is_knowledge_intensive=True,  domain_is_covered=True,  overhead_is_acceptable=True,  tolerates_residual_risk=True),   # remote workdays
]

for task in tasks:
    print(should_use_rag(**task))
# ('skip_rag', 'gate_1_not_knowledge_intensive')
# ('skip_rag', 'gate_2_no_domain_coverage')
# ('skip_rag', 'gate_3_overhead_not_worth_it')
# ('skip_rag', 'gate_4_zero_tolerance')
# ('use_rag', 'all_four_gates_clear')

assert should_use_rag(False, True, True, True) == ("skip_rag", "gate_1_not_knowledge_intensive")
assert should_use_rag(True, True, True, True) == ("use_rag", "all_four_gates_clear")

ECOSYSTEM

Where each gate's grounding comes from

Mallen, Asai, Zhong et al. (2022) sharpen Gate 1 beyond a binary fact-needed test: they show parametric memory already answers questions about popular entities about as well as retrieval-augmented models do, and retrieval only reliably helps on long-tail, less-popular facts — meaning "knowledge-intensive" is itself a matter of degree relative to what a given model already knows reliably, not a fixed property of the question's wording. Li, Li, Zhang et al. (2024) ground Gate 3 directly: their comparison of RAG against long-context LLMs finds each one winning under different volume, latency, and context-length conditions, with RAG's extra retrieval machinery paying off only when those conditions favor it — a controlled empirical version of this concept's overhead check. Asai, Wu, Wang et al. (2023), Self-RAG, previews Module 23's territory rather than this concept's: they train a model to decide, per query, whether retrieval is worth invoking at all — turning Gate 3's per-task, human-made judgment into a per-query, learned one, forward-referenced here only.

16
DIAGNOSIS

Failure modes — of the gate check itself

REFLEXIVE BUILD

Skipping the gate and building RAG by default

Section 02's risk: a task that would fail Gate 1 or Gate 3 gets a full pipeline anyway, then Concept 11's failure chain is misapplied to explain underperformance no pipeline change could fix.

CONFLATED GATES

Treating Gate 2 as Concept 10's coverage gap

Confirming one fact is missing is not the same as confirming an entire domain was never ingested — Section 06's distinction table is the check to rerun here.

STALE THRESHOLD

Treating Gate 3's threshold as fixed forever

Section 11's boundary case applies over time too — a volume or latency budget that clears Gate 3 today can trip it after traffic grows, without anyone revisiting the decision.

ASSUMED SAFETY NET

Assuming human review always covers Gate 4

Section 11's counterexample only holds if a review step genuinely exists and is enforced — assuming one is there without confirming it is a different mistake from confirming it correctly.

18
REALITY

Production implications, at introductory depth

  • Revisit all four gates on a fixed schedule, not only at initial design time — Section 16's stale-threshold risk means a task that once cleared Gate 3 can later trip it as traffic grows, without any code change triggering a review.
  • Document which gate, if any, disqualified a task that was considered and rejected for RAG — this record prevents the same rejected idea from being reconsidered without re-checking whether the disqualifying condition has actually changed.
  • Gate 4 decisions have compliance and legal weight in regulated domains (payroll, benefits eligibility, medical guidance) — treat a "zero tolerance" determination as a decision worth a paper trail, not just an engineering judgment call.
19
RECALL

Knowledge check

Name the four gates, and state which two directly reuse Concept 10's reasons.
Not knowledge-intensive, no domain coverage at all, overhead not worth it, and zero tolerance for residual risk. Gates 1 and 2 reuse Concept 10's two reasons — Gate 1 unchanged, Gate 2 widened from one missing fact to an entire uningested domain.
Why is checking all four gates in a fixed order unnecessary, unlike Concept 11's failure chain?
Concept 11's links are causally ordered — a query passes through retrieval before augmentation before generation. This concept's four gates are independent conditions about the task itself, so any single "yes" disqualifies RAG regardless of which gate is checked first.
Why doesn't a low historical failure rate on Concept 11's chain satisfy Gate 4?
Gate 4 is about the task's tolerance for any failure at all, not the pipeline's observed failure rate. A chain that fails rarely still fails Gate 4 if the task requires a guaranteed-correct answer with zero acceptable risk.

All four gates clear, so the verdict is "use RAG" — a good candidate for Concept 06's skeleton, unlike Section 03's tax-withholding example, which failed Gate 4 specifically because no review step was described.

Teach-back: explain, in your own words, why the same kind of task (a number with financial consequences) can pass Gate 4 here but trip it in Section 03's tax-withholding example.

Four independent gates, any one enough

  • Gate 1: not knowledge-intensive — no outside fact needed
  • Gate 2: no domain coverage at all — nothing ingested for this whole domain
  • Gate 3: overhead not worth it — volume or latency rules out retrieval
  • Gate 4: zero tolerance — no room for the failure chain's residual risk

Memorable example

CAREER PRACTICE

Interview questions

A product manager asks you to add RAG to a new feature. Walk through how you'd decide whether to, before writing any retrieval code.
Check the feature against four independent gates: does it need a specific outside fact at all, does any available corpus cover that domain, does the expected query volume and latency budget leave room for a retrieval round trip, and can the task tolerate any residual risk from a well-built pipeline still occasionally failing. Any single "yes" is enough to route the feature to an alternative — direct generation, more ingestion, caching, or a deterministic rule — without building a RAG pipeline first and discovering the mismatch later.
Why can't a lower observed error rate ever fully satisfy a genuinely zero-tolerance requirement?
A zero-tolerance requirement is about acceptable risk, not measured frequency — Concept 11 showed a well-built chain still has three places it can fail. No non-zero failure rate, however small, satisfies a requirement that accepts none, so the correct response is to remove the probabilistic step entirely rather than to keep improving its accuracy.
Design question: how would you build a lightweight review process so Gate 3's volume and latency threshold doesn't silently go stale as a feature's traffic grows?
Log the feature's actual query volume and observed latency against the threshold that justified the original RAG-fit decision, and set a recurring review trigger — for example, a quarterly check or an alert when traffic crosses some fraction of the original threshold — so the fit decision gets revisited on a schedule instead of only when someone happens to notice degraded performance.
