MODULE 11 · CONCEPT 04

Computed is not the same as saved.
Where the 384 numbers actually land.

An embedding exists the instant it's computed -- in process memory, nowhere else, until something writes it somewhere that outlives the call. This concept names exactly where that write can land: a vector store (often nowhere durable at all), a vector database (a real table row), or a search engine (a committed index segment) -- and shows, concretely, which of those three actually survives a restart.

01 · CONCEPT FIRST

A note in your head, versus a note saved to a file

An embedding fresh out of the model is like a thought you just had -- real, but gone the moment you stop thinking about it, unless you write it down somewhere. This concept names the three places a computed embedding can actually be written: a vector store, a vector database, or a search engine index -- and only some of them count as "written down" by default.

First memory: "the embedding was computed correctly" and "the embedding is saved anywhere" are two completely different claims.
02 · WHY IT EXISTS

Concept 03 produced a vector. It has to land somewhere.

Without naming where the embedding goes, "chunking and embedding flow" (Concept 03) would produce a vector that simply vanishes when the process exits. This concept closes that gap before Concept 05 needs to read that same vector back for a live query.

03 · CONCRETE EXAMPLE

Chunk c007, and where its vector actually goes

Take chunk c007, the same chunk id used in Module 10 Concept 14's own adapter code, with its 384-dimensional all-MiniLM-L6-v2 vector already computed. In a vector store (LangChain's own InMemoryVectorStore, confirmed in Module 10 Concept 01 to ship with no persistence by default), that vector lives in process RAM only. In a vector database, it's written into the embeddings table's VECTOR(384, FLOAT32) column and committed -- a real, durable row.

04 · TECHNICAL MECHANISM

Three destinations, one question: does it survive a restart?

Vector store -- often RAM only, per Module 10 Concept 01's own citation of LangChain's InMemoryVectorStore. Vector database -- written into a real table row via a committed INSERT, using Module 10 Concept 05's own VECTOR(384, FLOAT32) column type and Module 10 Concept 14's upsert() call. Search engine -- written into a committed index segment file on disk, per that category's own origin story (Module 10 Concept 01).

06 · IMPORTANT DISTINCTIONS

"Durable" is a precise claim, not a vibe

Durable means specifically: the data survives past the current call and is visible to a later, separate read -- not just that the computation was correct, and not just that a search API exists on top of it. A system can offer excellent similarity search (a vector store's whole job) while offering zero durability guarantee at all -- those are two independent properties, not one.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"It has a similarity-search API, so it must be saving my data."

False -- a vector store's search API and its persistence guarantee are separate concerns; LangChain's own InMemoryVectorStore has excellent search and zero persistence.

"Once the vector is in the table, it's automatically durable."

Not quite -- it's durable once the write is committed. An uncommitted transaction can still be rolled back, per Module 10 Concept 08's own no-autocommit-by-default rule.

What's stored where

Only chunk_id and the 384 floats live in the embeddings row. Chunk text and other metadata stay in the separate chunks row (Module 10 Concept 03) -- reusing Module 07 Concept 09's own distinction that structured metadata is never embedded into the vector itself, only carried alongside it.

WORKED EXAMPLE

Chunk c007, ready to be written

Chunk c007, the running example already used in Module 10 Concept 14's own adapter code, with a 384-dimensional all-MiniLM-L6-v2 vector already computed by the embedding stage. The question this section answers: what actually happens when that vector gets written.

CODE

The write path, verbatim from Module 10 Concept 14

PYTHON · ORACLE WRITE (python-oracledb) 
cursor.execute(
    "insert into embeddings (chunk_id, embedding) values (:1, :2)",
    ["c007", array.array("f", embedding)]
)
connection.commit()
PYTHON · PGVECTOR WRITE (psycopg) 
cur.execute(
    "INSERT INTO embeddings (chunk_id, embedding) VALUES (%s, %s)",
    ("c007", str(embedding))
)
conn.commit()
11
MECHANISM

Commit is the concrete meaning of "durable"

connection.commit() / conn.commit() is the exact line that turns a pending write into a durable one -- per Module 10 Concept 08's own no-autocommit-by-default rule, nothing before this line is guaranteed to survive.

EVIDENCE + CONTROL

The read-back guarantee

Once committed, chunk c007's row is queryable via VECTOR_DISTANCE(e.embedding, :qv, COSINE) (Oracle, Module 10 Concept 05) or embedding <=> %s (pgvector, Module 10 Concept 11) from a completely separate later call -- that's what "durably written" concretely means here, contrasted directly against LangChain's own InMemoryVectorStore, which offers no equivalent guarantee once the process exits.

14
CONCRETE USE

Compression as an optional cost reduction, not a persistence change

Module 09 Concept 05's own SQ8 (4.00x) and PQ (32.00x) compression figures reduce the byte cost computed above without changing whether the write is durable -- compression and persistence are independent decisions, the same way search-API quality and persistence were shown to be independent in Section 04.

22
CAREER PRACTICE

Interview questions

Conceptual: why doesn't a vector store's similarity-search capability imply persistence?
They're independent properties -- search quality is about the indexing/comparison mechanism, persistence is about whether the underlying data outlives the process. A system can excel at one while offering nothing on the other.
System design: a production RAG system's vector store loses all data on every container restart. What's the likely fix?
It's very likely running a bare in-memory wrapper under the assumption it behaves like a database -- migrate to a genuine vector database with a committed write path, or add an explicit persistence layer.
