MODULE 11 · CONCEPT 09

A tag isn't a source.
What a citation actually points at, and what checking it actually means.

Concept 08 named citation attachment as a mechanical, checkable step, then stopped at one sentence: a [SOURCE n] tag pointing at a chunk id is cheap, and it isn't proof. This concept goes one level deeper on exactly that gap -- what the identifier behind the tag actually is, how several citations to the same document get merged into one thing a person sees, how that merged thing gets rendered as a bracket, a footnote, or a link, and what a concrete pass/fail check against the cited chunk's real text looks like when it's actually run.

PROGRESSIVE BEGINNER CORE

Concept 08 attached a tag. This concept is what the tag is made of, and how to check it.

Concept 08 ended with a citation tag attached to a generated answer and one honest warning: attaching the tag is cheap, checking it is the part that matters. This concept unpacks the tag itself -- the internal id it actually points to, the document and locator a person would need to go find that id, what happens when several tags point at the same document, how the result gets shown to a user, and the concrete check that separates a citation that holds up from one that doesn't.

01 · CONCEPT FIRST

An identifier is an address, not a receipt

A [SOURCE 2] tag resolves to a chunk id, c007 -- an address the pipeline can follow. Following that address to the actual chunk row and reading what it says is a second, separate act. Knowing where a claim is supposed to come from and confirming the claim is actually supported by what's there are two different checks, and Concept 08 already flagged that only the first one is cheap.

First memory: a source identifier gets you to the right row. It does not tell you, by itself, whether that row backs the sentence attached to it.
02 · WHY IT EXISTS

"Attach a citation" was never one identifier

Concept 08 treated the citation tag as a single black box -- [SOURCE n] pointing at some chunk. In a real pipeline that box unpacks into at least four separate things: a chunk id (which exact passage), a document id and version id (which source, which edit of it -- Module 10 Concept 03's own schema), and a human-facing locator (a page, a section, a URL) that a reader could actually go check. Without naming these separately, "the pipeline attaches a citation" hides exactly where a reviewer should look when a citation turns out to be wrong.

03 · CONCRETE EXAMPLE

Four tags, three that hold up

Continuing Concept 06/07/08's own evidence set and query, the generated answer carries four citation tags: [SOURCE 2] (grace period is 14 days), [SOURCE 4] (order locks to CLOSED after), [SOURCE 1] (standard 30-day refund window), and [SOURCE 5] (claims cancellations after the grace period convert into a free-shipping return). A node-run check against each cited chunk's actual text passes the first three at full word support and fails the fourth at half -- the cited chunk is real and on-topic, but it says cancellations after the grace period are refused outright, not converted into anything. Section 07 runs this for real.

04 · TECHNICAL MECHANISM

Four identifiers, one chain

A citation's identifier chain has four links: chunk_id (the exact passage the model was actually shown), doc_id (which source document that passage came from), version_id (which edit of that document -- CURRENT or SUPERSEDED, Module 10 Concept 03's own version-history pattern), and a resolved locator (page, section, or URL -- whatever lets a human find the same passage without touching the database). The first three are foreign keys that already exist in Module 10 Concept 03's schema. The fourth, as Section 20 shows, doesn't live in that schema as a column at all.

06 · IMPORTANT DISTINCTIONS

Four identifiers, easy to collapse into one

chunk_id identifies one passage inside one version of one document -- the narrowest, most internal identifier. doc_id survives every edit; it's what "the same source, cited twice" actually means when two different chunk ids merge into one reference. version_id answers "which edit" -- a citation to a SUPERSEDED version is a real, distinct fact from a citation to CURRENT. A locator answers none of those; it's a separate, human-facing coordinate, resolved after the fact, not one of the three foreign keys.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Every cited chunk gets its own footnote."

Not in this worked example -- c007 and c008 both come from doc_9f21, so their two chunk-level citations merge into one rendered, numbered reference. A user sees one footnote for one document, not one per chunk.

"A resolvable locator is proof enough."

Not automatically -- [SOURCE 5] resolves cleanly to a real chunk in a real document at a real page. It still fails the read-back check, because resolving is not the same claim as supporting.

04
EVIDENCE + CONTROL

What an identifier can and can't guarantee

A source identifier guarantees exactly one thing: that a specific, resolvable row exists, and the tag points at it. It guarantees nothing about whether the claim attached to that tag is actually what the row says. [SOURCE 5] below resolves perfectly -- a real chunk id, a real document, a real page -- and still fails the check that matters. The identifier is necessary for a citation to be checkable at all; it is never sufficient for the citation to be correct.

06
CODE

Locator resolution and the read-back check

JAVASCRIPT · LOCATOR RESOLUTION + READ-BACK CHECK (node-run, see Section 09) 
// chunks.char_start/char_end are the only locator fields the schema
// actually persists (Module 10 Concept 03's own CREATE TABLE -- no
// page/section/url column exists). A locator is resolved separately,
// against a per-document section index keyed by character ranges.
function resolveLocator(chunk) {
  const ranges = sectionIndex[chunk.doc_id] || [];
  const hit = ranges.find(r => chunk.char_start >= r.from && chunk.char_start <= r.to);
  return { page: hit ? hit.page : null, section: hit ? hit.section : null };
}

// Word-overlap heuristic, not real entailment/NLI -- flagged as such
// in Section 09. Numbers are kept as content words; stopwords dropped.
function readBackCheck(claim, chunkText) {
  const claimWords = contentWords(claim);
  const chunkWords = new Set(contentWords(chunkText));
  const missing = claimWords.filter(w => !chunkWords.has(w));
  const fraction = (claimWords.length - missing.length) / claimWords.length;
  return { fraction, missing };
}

Both functions ran for real against the five rows in Section 07 -- neither is illustrative pseudocode. The threshold applied to fraction (0.8) and the exact stopword list are this concept's own design choices, named explicitly rather than hidden inside the function.

Four citations, one read-back check each

Continuing Concept 06/07/08's evidence set exactly: cA=c_a01 (doc_4b12, "Refund & Returns Policy"), c007's child=c007 (doc_9f21, "Order & Account Management Policy"), cB=c_b01 (doc_6c88, "Shipping Confirmation Template"), cC=c008 (doc_9f21), cE=c_e01 (doc_c390, "Cancellations FAQ"). 09
MATHEMATICS

The verification standard: run it, don't eyeball it

Verification methodEvery number in Sections 07-08 came from a throwaway node script (kept outside this course's lessons/ folder, run once, discarded) that modeled all five rows across documents, document_versions, and chunks exactly as Module 10 Concept 03's own DDL defines them, plus a small per-document section index used only to resolve locators. For each of the four cited claims it split both the claim and its cited chunk's text into lowercased content words (stopwords dropped, numbers kept), measured what fraction of the claim's words appear in the chunk's word set, and printed the exact support fraction, the missing-word list, and a pass/fail verdict against a 0.8 threshold -- printed and read back, not asserted. It then grouped the passing citations by doc_id, resolved each surviving group's locator, and printed the final two-reference render plus five sanity assertions (3 pass, 1 fails, the failure is SOURCE 5, exactly 2 references remain, doc_9f21's two citations merge) -- all five passed on the run this page's numbers are drawn from.
A caveat this check does not close: word overlap is not entailment. A claim that reused nearly all of a chunk's own words while flipping a single negation -- "will be honored" instead of "will not be honored" -- would score almost identically high under this exact check and pass when it shouldn't. SOURCE 5 happens to fail here because it substitutes vocabulary, not because this check can catch every way a claim can misrepresent its source. That's a real limitation of a lexical check, not a rounding error, and it's why Section 23 treats "resolves and passes this check" as still short of a formal attribution guarantee.

CORRECTION

Misconceptions

Incorrect beliefCorrection
A citation identifier is one thingNo -- it's a chain of at least four: chunk_id, doc_id, version_id, and a separately resolved locator, only the first three of which are actual foreign keys.
Every cited chunk becomes its own footnoteNo -- Section 08 shows two chunk-level citations from the same document merging into one rendered reference.

CAREER PRACTICE

Interview questions

Conceptual: what four identifiers actually sit behind a single citation tag?
chunk_id (the exact cited passage), doc_id (which source document), version_id (which edit of it), and a separately resolved human-facing locator (page/section/URL) -- only the first three are schema foreign keys.
Conceptual: why does SOURCE 5 fail the read-back check even though its identifier resolves cleanly?
Because resolving to a real, on-topic chunk only proves the identifier is valid -- it says nothing about whether the specific claim attached to that identifier matches what the chunk's text actually says. SOURCE 5's claim inverts the chunk's meaning while the identifier itself is completely sound.
System design: how would you design the merge step so two citations to the same document don't render as two separate footnotes?
Group passing chunk-level citations by doc_id before assigning reference numbers, combine each group's locators (a page range or a joined section list), and assign one reference number per group -- not per underlying chunk id.

20
CROSS-REFERENCE

The locator isn't a column -- and neither is the document title

Module 10 Concept 03's own CREATE TABLE chunks statement has exactly seven columns: chunk_id, doc_id, version_id, chunk_index, char_start, char_end, chunk_text. No page, section, or URL column exists anywhere in that schema. Every locator on this page was resolved after the fact, against a small per-document section index keyed by character-range -- c007's char_start of 920 and c008's char_start of 987 both happen to fall inside the same indexed range, which is the actual, mechanical reason they resolve to the identical page and section in Section 08. The same is true of the document title a reader sees: Module 10 Concept 03's documents table stores doc_id, source_id, source_type, and author -- no title column. "Order & Account Management Policy" is resolved from source_id/source_type by a lookup this concept's worked example keeps separately, the same category of derived-not-stored fact as the locator.

A real caveat this creates: a section index built once at ingestion can go stale. If a document is re-chunked after an edit and section boundaries shift, a chunk's char_start can end up on the wrong side of an old index boundary -- the foreign keys (chunk_id → doc_id → version_id) stay perfectly valid the whole time, but the page number shown to a reader can quietly point at the wrong section. A broken locator and a broken citation are two different failure modes, and only one of them shows up as a database error.

22
CROSS-REFERENCE

A citation-accuracy failure is its own checkable thing

Module 03 Concept 11's three-link failure chain -- retrieval, augmentation, generation -- and Concept 08's Section 23 already used it to localize a wrong answer to one of three stages. [SOURCE 5] above doesn't fit cleanly into any of the three: retrieval found a real, on-topic chunk; augmentation assembled it correctly into the prompt; generation decoded a fluent, plausible-sounding sentence. The defect is narrower than all three -- one specific claim's relationship to one specific cited chunk, catchable by checking that one pair without re-auditing retrieval, augmentation, or the rest of the decode loop at all.

23
EVIDENCE + CONTROL

Interpretable and attributable are two different requirements

Bohnet et al.'s AIS framework (Attributable to Identified Sources, 2022) splits exactly the distinction this concept has been drawing all along into two named requirements: a citation is interpretable if a person can actually find the source it points to, and attributable if that source actually supports the claim. [SOURCE 5] is fully interpretable -- the chunk id resolves, the document is real, the locator is resolvable -- and fails attribution outright. An identifier chain, no matter how many links it has, only ever buys interpretability. The read-back check in Sections 07-09 is this concept's own concrete attempt at the second, harder requirement -- and Section 09's negation caveat is exactly why AIS treats attribution as something that needs real evaluation, not something a resolvable link can grant for free.
