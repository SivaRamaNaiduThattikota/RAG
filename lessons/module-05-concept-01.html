MODULE 05 · CONCEPT 01

What is information
retrieval, really?

Module 04 built the mathematics — vectors, similarity, distance, probability — that later concepts will use to score a document against a query. Before any of that scoring exists, information retrieval (IR) needs four plain words defined precisely: a corpus is the fixed collection you search; a document is one retrievable unit inside it; a query is the surface expression of what someone is trying to find; and relevance is the judgment of how well a given document actually satisfies that need. No index, no formula, no ranking yet — this concept only fixes the vocabulary Module 05 will spend the next ten concepts building mechanisms for.

01 · CONCEPT FIRST

A collection, a unit, a need, and a judgment

CORPUS & DOCUMENT

The corpus is the whole fixed collection — every file, row, or chunk you're willing to search. A document is one retrievable unit inside it.

QUERY & RELEVANCE

The query is the text someone actually typed or asked. Relevance is not a property of a document by itself — it's a judgment about how well one specific document answers one specific query.

First memory: information retrieval is the problem of finding, inside a fixed corpus, the documents that are relevant to a query — where "relevant" is a judgment call, not a lookup.
02 · WHY IT EXISTS

Relevance isn't an exact match — a SQL WHERE clause can't ask this question

A database query like WHERE title = 'inverted index' has an exact, provable answer: a row matches or it doesn't. "Which documents are relevant to how do search engines answer boolean queries fast?" has no such exact answer — two careful readers can disagree on whether a given document counts, and both can be reasonable. Information retrieval exists because most real information needs are judgments of degree over a large, fixed collection, not exact-match lookups over a small one — and someone still has to build a system that returns a useful answer anyway.

04 · TECHNICAL MECHANISM

What IR takes in, and what it must return

INPUT

A fixed corpus C = {d₁, d₂, … , d_N} and a query q — just the collection and the request, nothing precomputed yet.

OUTPUT

A subset or ranking of C, ordered by estimated relevance to q — an estimate, because true relevance lives in the asker's head, not in the documents.

WHAT'S DEFERRED

How that estimate gets computed — matching terms fast (Concept 02), weighting them (Concepts 04-06), or comparing meaning as geometry (already covered in Module 04) — is the rest of this module's job, not this concept's.

06 · IMPORTANT DISTINCTIONS

Four pairs beginners routinely blur

TermIs NOTWhy it matters
CorpusAn indexThe corpus is the raw collection; an index (Concept 02) is a derived structure built from it to answer queries fast — the corpus can exist with zero indexes built over it.
DocumentAlways a whole fileIn a RAG system a "document" for retrieval purposes is usually a chunk (Module 07) — one passage, not one PDF.
QueryThe information need itselfThe query is the literal text typed or spoken; the need is what's actually wanted, and the two can differ (vocabulary mismatch) — a forward reference, not solved here.
RelevanceCorrectness or truthA document can be relevant (on-topic, useful) without directly answering the question, and a technically true document can be irrelevant if it doesn't address this need.
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Relevance is an objective property of a document."

It's a relationship between a document and a specific query — the same document can be highly relevant to one query and useless for another.

"A bigger corpus is always more useful."

A corpus full of near-duplicate or off-topic material can make relevant documents harder to find, not easier — size alone isn't quality.

"The query text always says exactly what the user wants."

Wording, typos, and ambiguity mean the literal query and the true information need are related but distinct — this module's later query-understanding concepts (Module 15) exist because of that gap.

"IR means the specific algorithm my search box uses."

IR is the whole problem — corpus, query, relevance — of which term-matching (this module) and vector geometry (Module 04) are two different mechanisms, not the definition itself.

08 · YOUR PROJECT MAPPING

Naming the Oracle RAG project's four parts

Every row, ticket, or chunk the Oracle-backed system has agreed to search — fixed at query time, even though it changes over time via ingestion.

DOCUMENT & QUERYOne stored chunk; one user question

A document is one retrievable chunk in the database; the query is the natural-language question a user actually asks the system.

RELEVANCE — DEFERREDWhich chunks should be surfaced, and how well that's measured

04
INTUITION

A library, a question, and a librarian's judgment

A corpus is a library's entire collection. A document is one book on a shelf. A query is the question you actually ask the librarian out loud. Relevance is the librarian's judgment about whether a specific book actually helps with that specific question — not whether the book is good, popular, or true in general, and not fixed once and for all: a different question about the same collection gets a different set of relevant books.

Analogy boundaryThe library captures the four relationships, not the mechanism — a real system doesn't have a librarian's judgment available at query time, which is exactly why Concept 02 onward builds computable estimates of relevance instead.
05
PRECISION

Formal definitions

TermDefinitionNotation
CorpusThe fixed, finite collection of documents being searchedC = {d₁, d₂, …, d_N}
DocumentOne retrievable unit inside the corpusd_i ∈ C
QueryThe literal text expressing an information needq
Information needWhat the asker actually wants, which q only approximates(unobservable directly)
RelevanceA judgment of how well d_i satisfies the need behind qrel(d_i, q) ∈ {0,1} or a graded scale

rel is a function of a pair — a document and a query together — never of a document alone. That single fact is the source of most of Section 17's misconceptions.

06
MECHANISM

The relationship, traced step by step

An information need forms — something the asker wants to know, not yet written down.
The need is expressed as a query q — text or speech, an approximation of the need, not the need itself.
An IR system receives (C, q) — the fixed corpus and the query, nothing else.
The system returns a subset or ranking of C — its estimate of which documents are relevant.
The asker judges the actual relevance — the true rel(d,q) the system was only ever estimating.

09
MATHEMATICS

Relevance as an unspecified function — deliberately

This concept states rel(d,q) as a function with a domain and a range, and stops there on purpose:

rel: C × Q → {0, 1} (binary relevance) rel: C × Q → {0, 1, 2, ..., k} (graded relevance, k grades)

No formula computes rel here. Concept 04 gives term frequency its first numeric estimate of relevance; Concept 06 (BM25) is the first complete scoring function this module builds. Stating the function's signature now — what goes in, what comes out — is what makes every later concept's formula recognizable as "one way to approximate rel," rather than a fact handed down without context.

11
CONCRETE USE

Four cases: two clean fits, a boundary case, a mistake

CLEAN FIT

Web search

Corpus = crawled pages, document = one page, query = the search box text, relevance = whether a human would click and be satisfied.

CLEAN FIT

Enterprise knowledge search

Corpus = an Oracle-backed knowledge base, document = one indexed chunk, query = an employee's typed question, relevance = whether that chunk actually helps answer it.

BOUNDARY CASE

Zero relevant documents

A query can legitimately have no relevant document anywhere in the corpus — "no relevant results" is a correct IR outcome, not a system failure, when the corpus genuinely lacks the answer (Module 03's answerability concept, cited directly).

MISTAKE TO AVOID

Treating "mentions the same word" as "relevant"

D5 in Section 10 mentions "index" but isn't relevant to this query — term overlap is a useful signal (Concept 02 onward), never a definition of relevance itself.

CODE

Modeling the vocabulary as data — no retrieval algorithm yet

This concept's code deliberately stops short of computing anything: it represents a corpus, a query, and a relevance judgment as plain data, with no matching mechanism attached. Building that mechanism is Concept 02's job.

PYTHON · DATA ONLY, NO RETRIEVAL LOGIC 
corpus = {
    1: "vector search over dense embeddings",
    2: "sparse retrieval with an inverted index",
    3: "dense embeddings for semantic search",
    4: "keyword search using an inverted index",
    5: "vector index for approximate search",
    6: "sparse and dense retrieval combined",
    7: "embeddings from a neural encoder",
    8: "boolean search over an inverted index",
}

query = "what technique lets you answer boolean search queries over documents quickly?"

# A hand-assigned relevance judgment: doc id -> grade (0, 1 or 2).
# Nothing here computed this -- it is Section 10's table, typed in directly.
relevance_judgment = {1: 0, 2: 1, 3: 0, 4: 1, 5: 0, 6: 0, 7: 0, 8: 2}

assert set(relevance_judgment) == set(corpus)          # every document was judged
assert all(g in (0, 1, 2) for g in relevance_judgment.values())
relevant_docs = [d for d, g in relevance_judgment.items() if g > 0]
assert relevant_docs == [2, 4, 8]

ECOSYSTEM

The same four words, inside real tools

LangChain's Document object pairs page content with metadata — the same "document" this concept defines, just with a class name attached. A retriever interface (LangChain, LlamaIndex, Elasticsearch, Oracle Text) always takes a query string and a fixed corpus and returns a ranked list — the same (C, q) → ranking shape from Section 06, regardless of which mechanism computes the ranking underneath. Recognizing that shape now is what will make every framework's retriever interface look familiar rather than arbitrary, once Module 12 introduces them directly.

CONTRAST

Binary vs. graded relevance

ApproachWhat it capturesWhen it's enough
Binary (relevant / not relevant)A single yes-or-no split of the corpusFast prototyping, and metrics like precision/recall (Module 18) that only need a cutoff
Graded (e.g., 0-2 or 0-4 scale)How strongly a document satisfies the need, not just whether it doesRanking quality metrics like nDCG (Module 18) and rigorous test collections (Concept 10 of this module)
16
DIAGNOSIS

Failure modes

MISSING COVERAGE

The corpus never contained a relevant document

No retrieval mechanism, however good, can return a relevant document that was never ingested — a corpus-coverage problem, not a retrieval-mechanism problem.

QUERY-NEED MISMATCH

The literal query doesn't capture the real need

A poorly worded query can make even a perfect relevance judge return the wrong subset — Module 15's query understanding concepts address this directly, later.

GRANULARITY MISMATCH

The relevant information is split across chunks

If "document" is defined too coarsely or too finely for the need, no single retrievable unit may fully satisfy it — a chunking decision (Module 07), not a relevance-definition problem.

17
CORRECTION

Misconceptions

Incorrect beliefCorrection
A document is relevant or not, independent of any queryFalse — relevance is always with respect to a specific query; Section 05's rel(d,q) takes both arguments.
Sharing a word with the query makes a document relevantFalse — Section 10's D5 shares "index" with a boolean-query need but isn't relevant; word overlap is a signal, not a definition.
"No relevant documents found" always means the system failedFalse — Section 11's boundary case: it can correctly mean the corpus never had the answer.
18
REALITY

Production implications

  • Corpus curation — what gets ingested, and what doesn't — bounds every retrieval mechanism built afterward; no algorithm compensates for missing coverage.
  • Collecting graded relevance judgments at scale (Concept 10, test collections) costs real annotator time and money — most teams start with cheap binary judgments and add grades only where it changes a decision.
  • "Relevant to this user" can differ by tenant or access level even for an identical query string — a governance concern Module 20 addresses directly, flagged here as a forward reference only.
19
RECALL

Knowledge check

Is rel(d,q) a function of the document alone, the query alone, or both together?
Both together — Section 05 defines it as a function on the pair (d,q); a document's relevance can change entirely when the query changes.
What's the difference between a corpus and an index?
A corpus is the raw fixed collection; an index is a derived structure built from the corpus specifically to answer queries fast — Concept 02 builds the first one.
Why is "no relevant documents were found" sometimes the correct answer, not a bug?
Because a corpus can genuinely lack any document that satisfies a given need — Section 11's boundary case and Module 03's answerability concept both cover this directly.

23
CAREER PRACTICE

Interview questions

Define information retrieval without using the word "search."
The problem of returning, from a fixed collection, the items that best satisfy an expressed information need — where "best satisfies" is a judgment, not an exact match.
Why does IR need a separate notion of "information need" distinct from "query"?
Because query text is an imperfect, sometimes ambiguous or mis-worded approximation of what the asker actually wants — treating them as identical hides real failure modes like vocabulary mismatch (Module 15).
A stakeholder says "just return every document that contains the query's words." What's wrong with that as a definition of relevance?
It conflates term overlap with relevance — Section 10's D5 and Section 17's table both show a document can share vocabulary with a query while being judged not relevant to the actual need.
Design question: how would you build a small test set to evaluate a future retrieval mechanism, using only this concept's vocabulary?
Fix a corpus, write a set of queries, and collect a relevance judgment (binary or graded) for every document against every query — exactly Concept 10's "test collections," built from nothing more than this concept's four terms.
