01 · CONCEPT FIRST

Parsing: getting raw text out of one specific format

PARSING (THIS CONCEPT)

Format-specific extraction: opening a PDF, HTML page, .docx, .xlsx, or Markdown file and pulling out its actual text content, using a method that understands that format's own internal layout.

NOT PARSING (LATER CONCEPTS)

Reading text off a scanned image (Concept 04's OCR) and fixing whitespace, encoding, or boilerplate in text that's already been extracted (Concept 05's cleaning) — both assume parsing already happened.

First memory: five formats, five different reasons "just open the file" fails, and one standard tool per format that actually works.
02 · WHY IT EXISTS

Each format hides its text a different way

A source inventory (Concept 01) might list an HR policy as a PDF, a wiki page as HTML, an onboarding guide as a .docx, a benefits table as a .xlsx, and a README as Markdown. If you tried to open all five the same way — reading the raw bytes as plain text — you'd get five different kinds of failure: a PDF gives you binary drawing instructions, not sentences. An HTML page gives you real sentences buried inside navigation and ad markup. A .docx or .xlsx gives you a zip archive's compressed header, not a paragraph. Only Markdown comes back looking close to readable — and even it still has syntax markers a naive read can't tell apart from real content. Parsing exists because "one universal way to read a file" does not exist; it has to be format-aware.

03 · CONCRETE EXAMPLE

The same sentence, five files, five outcomes

Suppose the exact same policy sentence — "Refunds are accepted within 45 days of purchase." — exists in all five formats. Naively opening each file (reading its raw bytes) gives five different failures:

PDF

Binary content-stream instructions and positioned glyph codes — not readable characters at all without a parser that understands PDF's drawing model.

HTML

The sentence is there, but wrapped in tags, sitting next to a navigation bar and an ad banner your naive read can't distinguish from the real content.

DOCX / XLSX

A zip archive's binary header (PK\x03\x04…) — Word and Excel files aren't text files, they're compressed folders of XML.

MARKDOWN

"Refunds are accepted within **45 days** of purchase." — almost right, except the ** markers are still sitting in the text as literal characters.

Five files, one sentence, five reasons a naive open-and-read doesn't reliably return "Refunds are accepted within 45 days of purchase." and nothing else.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"A PDF is basically a text file."

It's a page-description format: positioned glyphs and drawing instructions, not paragraphs. Reading order has to be reconstructed, not assumed.

"I'll decode the .docx or .xlsx bytes as text."

Both are zip archives of XML — decoding the raw bytes as characters returns the zip header's binary noise, not a single word of the document.

"Markdown is just text, so I can skip a real parser."

It's close, but a blind find-and-replace on #, *, and - also mangles code blocks and ordinary sentences that happen to contain those characters — a real Markdown parser is still the safer standard tool.

"If a PDF returns no text, run OCR right away."

First confirm the format actually lacks a text layer — many PDFs have one, and reaching for OCR (Concept 04's tool) before checking wastes effort and can be less accurate than the text that was already there.

It gets raw text out of a format. It does not fix that text (Concept 05) and does not read text off an image (Concept 04).

Files aren't all "just text"

04
INTUITION

Five sealed boxes, five different keys

Picture five sealed boxes, each holding the same note. One box is a printed photograph of the note — you can see the words, but there's no "note" data inside, just an image of ink positions (that's closer to a scanned page than to any format in this concept, but it's the right mental picture for PDF's glyph-position problem: the words are visually present but not structurally marked as words). One box is the note taped inside a gift box full of packing paper and promotional flyers (HTML: the real note is in there, buried in everything else). Two boxes are zip-locked bags holding shredded, labeled strips that reassemble into the note only if you know the reassembly pattern (DOCX and XLSX, both zip archives of structured parts). The last box just has the note folded up with a few marks in the margin noting "this word is a heading" (Markdown) — read directly, mostly fine, except those margin marks look like part of the sentence if you don't know to treat them separately.

Analogy boundaryNone of these five boxes is actually sealed shut with no way in — every one of them has an extractable text layer once you use the right key. A box with literally no note inside, just a photograph and nothing else, is Concept 04's OCR problem, not this concept's.

06
MECHANISM

Five branches, one shared shape

Detect the format — a file extension or magic-byte check decides which of the five branches applies before any parsing starts.
PDF branch — read the content stream, collect each glyph's position, and sort into reading order (Section 09's rule).
HTML branch — parse into a DOM tree, then select the nodes that hold real content rather than markup, navigation, or boilerplate.
DOCX / XLSX branch — unzip the OOXML package, parse its XML parts, and reassemble either paragraph runs (DOCX) or a row-and-column grid (XLSX).
Markdown branch — parse the syntax into a structured tree, then walk it to emit text with heading levels and code blocks kept distinct from prose.
Handoff — every branch ends at the same place: raw, unclean, unchunked text, passed forward to Concept 05.

09
MATHEMATICS

Reconstructing reading order from glyph coordinates

A PDF's content stream reports text chunks in whatever order the file's writer emitted them — not necessarily top-to-bottom. Each chunk c has a position (x, y) in PDF's coordinate system, where y increases upward from the page's bottom edge. Reading order is recovered by sorting on y descending first, then x ascending within chunks that share a line:

key(c) = (−y_c, x_c) reading_order = sort ascending by key(c)

Sorting by −y first means a chunk higher on the page (larger y) always sorts before one lower down; sorting by x second only matters for chunks that share a line (the same y, or within a small tolerance of it in a real implementation, since two chunks are rarely at the exact same pixel height). This is a genuinely small piece of geometry — nothing beyond a two-key sort — but it's the entire mechanism separating a PDF library's "extract text" from a naive byte read.

10
WORKED EXAMPLE

Un-shuffling one policy sentence by hand

Suppose a PDF's content stream emits three text chunks for one policy sentence, in this stored (non-reading) order:

Emitted orderTextxykey(c) = (−y, x)
1st"Call support if unsure."1050(−50, 10)
2nd"45 days from purchase."14090(−90, 140)
3rd"Refund window is"1090(−90, 10)

Sorting ascending by key(c): (−90, 10) comes first, then (−90, 140), then (−50, 10) — because −90 is smaller than −50, and between the two tied at −90, x = 10 is smaller than x = 140. That reorders the three chunks to "Refund window is" → "45 days from purchase." → "Call support if unsure.", which reads correctly as "Refund window is 45 days from purchase. Call support if unsure." — the emitted order was scrambled across two visual lines; the sort rule alone puts it back together.

11
CONCRETE USE

Four cases: two clean fits, a boundary case, a mistake

CLEAN FIT

A born-digital policy PDF

Text layer present, glyph positions well-formed — a standard PDF text-extraction library recovers the sentence reliably.

CLEAN FIT

A README.md in a code repository

A Markdown parser separates headings, code fences, and prose correctly, keeping code blocks verbatim rather than treating them as ordinary text.

BOUNDARY CASE

A PDF with a multi-column layout

Two side-by-side columns can have overlapping y-ranges; a simple (−y, x) sort can interleave column text incorrectly unless the library also detects column boundaries — a real limitation of the simplified rule in Section 09, not a flaw to hide.

MISTAKE TO AVOID

Treating an .xlsx sheet as one long paragraph

Flattening every cell left-to-right, top-to-bottom loses which number belonged to which row — tabular data needs a row-aware tool, not a text-flow one.

12
CODE

Reading-order reconstruction, from scratch

This is the mechanism behind Section 09's rule, applied to Section 10's exact chunks — not a real PDF binary parser, but the same sorting logic a real one performs after it has already located each chunk's position.

PYTHON · SORTING PDF TEXT CHUNKS BACK INTO READING ORDER 
from dataclasses import dataclass

@dataclass
class TextChunk:
    text: str
    x: float
    y: float   # PDF coordinates: y increases upward from the page bottom

def reading_order_key(chunk: TextChunk):
    return (-chunk.y, chunk.x)   # higher on the page first, then left to right

chunks = [
    TextChunk("Call support if unsure.", x=10,  y=50),
    TextChunk("45 days from purchase.",  x=140, y=90),
    TextChunk("Refund window is",        x=10,  y=90),
]

ordered = sorted(chunks, key=reading_order_key)
sentence = " ".join(c.text for c in ordered)

assert sentence == "Refund window is 45 days from purchase. Call support if unsure."
assert ordered[0].text == "Refund window is"          # emitted 3rd, reads 1st

# Edge case: two chunks on the exact same line, same y -- x alone must decide.
tied = [TextChunk("world", x=50, y=0), TextChunk("hello", x=10, y=0)]
assert " ".join(c.text for c in sorted(tied, key=reading_order_key)) == "hello world"
13
ECOSYSTEM

The same five branches, in real libraries

PDF: pypdf and pdfplumber expose text extraction directly in Python; PDFMiner.six exposes the lower-level layout analysis both are often built on. HTML: BeautifulSoup and lxml parse markup into a DOM tree and let you select real content nodes by tag or CSS selector. DOCX: python-docx reads paragraphs and runs out of the OOXML package without you touching the zip or XML directly. XLSX: openpyxl reads cells sheet-by-sheet and row-by-row; pandas builds on libraries like it to load a sheet straight into a row-and-column table. Markdown: Python-Markdown, markdown-it, and mistune all parse Markdown's syntax into a tree before rendering or extracting text. Framework-level document loaders (LangChain, LlamaIndex — Modules 12 and 14) wrap most of these behind one common loader interface, trading some fine-grained control for a consistent call shape across formats.

16
DIAGNOSIS

Failure modes

EMPTY EXTRACTION

A PDF library returns no text at all

Usually means the page has no embedded text layer — a scanned image, not a parsing bug. That's a signal to route to Concept 04's OCR, not to retry the same library harder.

BOILERPLATE LEAK

HTML extraction still includes nav and ad text

The DOM parser ran, but the wrong nodes were selected — a targeting problem, not a parser failure; the fix is selecting the actual content node, not switching tools.

SILENT TRUNCATION

A .docx's headers, footers, or text boxes go missing

Many OOXML readers only walk the main document body by default — content living in headers, footers, or floating text boxes needs to be requested explicitly or it's silently dropped.

18
REALITY

Production implications

  • Parsing libraries are version-sensitive — a .docx saved by a newer or older version of Word, or a PDF generated by an unusual tool, can expose edge cases a library handled fine on other files; production pipelines need per-file error handling, not an assumption that one library covers every file of a given extension.
  • Extraction throughput varies enormously by format and file size — a thousand-page PDF or a workbook with dozens of sheets can dominate an ingestion job's total runtime if parsing isn't budgeted for separately from everything after it.
  • A parsing failure should be logged against the specific source file, not silently skipped — otherwise a gap in coverage looks identical to a gap that was never in the source inventory at all, undermining Concept 01's inventory guarantee.
19
RECALL

Knowledge check

Why can't a .docx file be read correctly by decoding its raw bytes as text?
Because .docx is a zip archive of XML parts (OOXML) — the raw bytes start with a zip header and compressed data, not characters, so decoding them as text returns binary noise rather than any of the document's words.
In key(c) = (−y_c, x_c), what does sorting by −y first accomplish?
It puts chunks higher on the page (larger y, since PDF's y-axis increases upward) before chunks lower on the page, recovering top-to-bottom reading order before x breaks ties within the same line.
Why isn't jumping straight to OCR the right response to a PDF returning no extracted text?
An empty extraction usually means there's no text layer at all — worth confirming first, since if a text layer does exist, a text-extraction library will recover it more accurately and cheaply than OCR would.

23
CAREER PRACTICE

Interview questions

Name the central parsing difficulty of PDF, HTML, and Excel in one sentence each.
PDF: text exists only as positioned glyphs with no guaranteed reading order. HTML: real text is present but interleaved with presentation and boilerplate markup. Excel: content is a two-dimensional grid, not prose, so no sentence exists until rows and columns are read together.
Why does treating .docx and .xlsx as plain text files fail, specifically?
Both formats are Office Open XML packages — zip archives containing XML parts — so the file's raw bytes begin with a zip header and compressed data, never with readable document text.
A teammate says "Markdown doesn't need a real parser, it's already basically plain text." What's the flaw?
Markdown's syntax markers (#, *, -, code fences) carry meaning that naive string operations can't reliably separate from ordinary text — a real parser is what correctly tells a heading from a sentence and preserves a code block's verbatim content.
Design question: a PDF has two side-by-side columns. Why can Section 09's simple (−y, x) sort rule fail here, and what would a more robust extractor need to add?
Two columns can have overlapping y-ranges, so sorting purely by (−y, x) can interleave text from both columns line by line instead of reading one full column before the other; a more robust extractor needs column-boundary detection (grouping chunks by x-range first) before applying the reading-order sort within each column.
