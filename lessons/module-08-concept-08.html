MODULE 08 · CONCEPT 08

Same encoder. Two roles.
A prefix is how it tells them apart.

Concept 03 already named the mechanism by title -- E5's "query: "/"passage: " prefixes and BGE's query-only instruction -- as the thing that lets one shared bi-encoder still distinguish a query from a document. It never built that out. This concept does: a bi-encoder runs the exact same weights on both sides with no cross-attention between the two runs, so "Where is my order?" encoded as a query and the identical string encoded as a document look IDENTICAL to the model unless the text itself carries a role marker. A toy, honestly-caveated mean-pooling example shows the identical 2-token prefix is exactly 6.0x more of a 5-token query's pooled vector than of a 40-token passage's -- pure arithmetic, verified two independent ways. Real evidence backs the real cost: the BGE/C-Pack paper's own ablation (arXiv:2309.07597) shows dropping the instruction costs Retrieval 1.37% and the C-MTEB average 0.88%, while Classification and Clustering are unaffected or even improve -- and E5's model card states plainly that skipping its prefix convention causes "performance degradation."

01 · CONCEPT FIRST

A label that tells a shared encoder which role the text is playing

THIS CONCEPT

Instructions/prefixes: literal text prepended before embedding ("query: ", "passage: ", or a query-only instruction) so one shared encoder can still tell a query apart from a document.

NOT THIS CONCEPT

Multilingual and domain embedding models (Concept 09); embedding-model selection (Concept 10) -- both named forward only.

First memory: one shared encoder can't tell "query" from "document" unless the text itself says so.
02 · WHY IT EXISTS

One shared encoder, run twice, with no cross-attention between the runs

Concept 03 already established the bi-encoder as one shared encoder run twice -- once over the query, once over the document -- with no cross-attention linking the two runs. From the encoder's point of view, "Where is my order?" run through the query side and "Where is my order?" run through the document side look IDENTICAL, token for token, unless something inside the text itself marks which role it's playing this time.

03 · CONCRETE EXAMPLE

E5's paired prefixes vs. BGE's query-only instruction

Two real, different, verified answers to the same architectural need. E5's model card FAQ: "Do I need to add the prefix 'query: ' and 'passage: ' to input texts? Yes, this is how the model is trained, otherwise you will see a performance degradation." Every input gets a role label, on both sides. BGE's model card instead says the instruction belongs on the query side only: "If you need to search the relevant passages to a query, we suggest to add the instruction to the query... In all cases, no instruction needs to be added to passages." Same underlying need, two different real conventions.

04 · TECHNICAL MECHANISM

The same prefix vector, weighted very differently by pooling

Per Concept 06's mean-pooling formula, a prefix's tokens are just more terms in the average. A 2-token prefix is 2/(2+5) = 28.57% of a 5-token query's total, but only 2/(2+40) = 4.76% of a 40-token passage's -- a ratio of exactly 6.0x, before even asking what direction the prefix vector points.

Wrong-side prefix vs. omitted prefix -- two different mistakes

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Any embedding model needs a prefix."

False -- Concepts 01-07's toy models, and many real symmetric models, are prefix-free by design.

"Adding a prefix always helps every task."

False -- the BGE ablation (Section 10) shows Classification improving by 0.38% and Clustering by 3.35% WITHOUT the instruction.

"E5 and BGE use the same prefix rule."

False -- E5 prefixes both sides differently; BGE only ever prefixes the query, never the passage.

Query-encoding and document-indexing are usually separate code paths

A refactor that touches one without the other can silently apply the wrong prefix on one side.

04
INTUITION

An interpreter who is told the role before they start

Imagine one interpreter who translates differently depending on whether they're told "this is a question" or "this is an answer" before they begin -- the same interpreter, the same skill, but a different starting instruction changes how they process what follows.

Analogy boundaryThe interpreter picture explains the ROLE-MARKING idea -- that telling the same processor which role a text is playing changes its output. It does not explain the actual mechanism (self-attention over the prefix's own tokens, Section 06) -- that's a real neural computation, not a human interpreter's judgment.

06
MECHANISM

The prefix's tokens join the sequence before pooling ever runs

Per Concept 02's pipeline, a prefix's own tokens enter tokenization and self-attention alongside every other token in the text -- meaning the prefix can influence how every OTHER token gets contextualized, not merely contribute one extra term to a later average. Only after that contextualization does Concept 06's pooling step run. This concept's worked example (Section 10) uses a simplified pooling-only toy to build intuition about token-count sensitivity, but the real mechanism behind why prefixes work at all is this self-attention step, not post-hoc averaging.

09
MATHEMATICS

Deriving the token-share ratio

Q_with = (k·u_prefix + N·Q_content) / (k+N)
Q_with − Q_content = (k/(k+N))·(u_prefix − Q_content)

With prefix length k=2 tokens: a 5-token query's prefix share is k/(k+N) = 2/7 = 28.5714%; a 40-token passage's share is 2/42 = 4.7619%. The ratio (2/7)/(2/42) = 42/7 = exactly 6.0 -- a clean arithmetic fact of mean pooling and token count alone, independent of what direction the prefix vector actually points.

10
WORKED EXAMPLE

Part 1: the toy mechanism. Part 2: the real, quantified evidence.

Part 1 -- mechanism (illustrative toy, honestly caveated). A query tokenizes to 5 content tokens, a passage to 40; the prefix string itself tokenizes to 2 tokens either way. Toy pooled vectors: Q_content=(0.70, 0.10); D1_content=(0.68, 0.14); u_q=(-0.20, 0.50) (the "query: " prefix's own pooled contribution); u_p=(0.45, -0.35) (the "passage: " prefix's own pooled contribution). Applying Concept 06's mean-pooling formula with the prefix counted as 2 extra tokens: Q_with_prefix = (2·u_q + 5·Q_content)/7 = (0.442857, 0.214286); D1_with_prefix = (2·u_p + 40·D1_content)/42 = (0.669048, 0.116667). Token share: 2/7 = 28.5714% for the query, 2/42 = 4.7619% for the passage -- a ratio of exactly 6.0x. Displacement (Euclidean distance between the with-prefix and content-only vectors): 0.281396 for the query, 0.025776 for the passage -- a ratio of 10.917 here, but that larger number is specific to this toy's choice of u_q and u_p, not a general law; the 6.0x token-share ratio is the universal arithmetic fact.

This mean-pooling toy is a simplified, untrained stand-in. The real mechanism (Section 06) is that a prefix's tokens enter self-attention alongside every other token BEFORE pooling, changing how everything else gets contextualized -- not merely contributing one more term to a post-hoc average. Part 1 only demonstrates the token-count-sensitivity intuition honestly; it does not reproduce what a real trained encoder does.

Part 2 -- real evidence (BGE/C-Pack, arXiv:2309.07597, Table 3). BGE-finetune (keeps the query-side instruction) scores, by C-MTEB task: Retrieval 71.53, STS 54.98, Pair Classification 78.94, Classification 68.32, Re-rank 65.11, Clustering 48.39, Average 63.96. BGE w.o. Instruct (instruction removed, everything else identical): Retrieval 70.55, STS 53.00, Pair Classification 76.77, Classification 68.58, Re-rank 64.91, Clustering 50.01, Average 63.40. Deltas (w.o.Instruct minus finetune): Retrieval -0.98 (-1.37%), STS -1.98 (-3.60%), Pair Classification -2.17 (-2.75%), Classification +0.26 (+0.38%), Re-rank -0.20 (-0.31%), Clustering +1.62 (+3.35%), Average -0.56 (-0.88%). Retrieval, STS and Pair Classification -- the tasks closest to "does this query match this passage" -- measurably suffer without the instruction; Classification and Clustering, which don't depend on query/passage role at all, are unaffected or even slightly better. E5's own model card FAQ states, without hedging: "Yes, this is how the model is trained, otherwise you will see a performance degradation."

Verification method: Part 1 was computed and cross-checked twice -- direct mean-pooling arithmetic, and the algebraic simplification Q_with − Q_content = (k/(k+N))·(u_prefix − Q_content) -- matching to 6 decimal places. Part 2's two table rows were extracted from the paper's raw HTML table cells, confirmed against the paper's own column headers, with all seven deltas and relative percentages independently recomputed as the exact subtraction of the two rows.

12
CODE

Extending Concept 06's pool_mean() to accept a prefix

PYTHON · NO LIBRARIES 
import math

def pool_mean_with_prefix(content_vec, content_tokens, prefix_vec=None, prefix_tokens=2):
    if prefix_vec is None:
        return content_vec
    cx, cy = content_vec
    px, py = prefix_vec
    total = prefix_tokens + content_tokens
    return ((prefix_tokens*px + content_tokens*cx) / total,
            (prefix_tokens*py + content_tokens*cy) / total)

def euclid(a, b):
    return math.sqrt((a[0]-b[0])**2 + (a[1]-b[1])**2)

Q_content, u_q = (0.70, 0.10), (-0.20, 0.50)
D1_content, u_p = (0.68, 0.14), (0.45, -0.35)

Q_with = pool_mean_with_prefix(Q_content, 5, u_q, 2)
D1_with = pool_mean_with_prefix(D1_content, 40, u_p, 2)
assert tuple(round(v, 6) for v in Q_with) == (0.442857, 0.214286)
assert tuple(round(v, 6) for v in D1_with) == (0.669048, 0.116667)

assert round(euclid(Q_with, Q_content), 6) == 0.281396
assert round(euclid(D1_with, D1_content), 6) == 0.025776

share_q, share_d = 2/(2+5), 2/(2+40)
assert round(share_q / share_d, 4) == 6.0

DIAGNOSIS

Failure modes

SYMPTOM

Queries and documents that should match score lower than expected -- or unrelated documents score suspiciously high

Both are consistent with a prefix regression, not necessarily a relevance-labeling bug.

DIAGNOSTIC

Check the query-encoding and document-encoding code paths

Confirm each applies the model's documented prefix correctly and on the correct side.

18
REALITY

Production implications

  • A query-encoding service and a document-encoding/indexing service are usually different code paths -- a prefix regression can be introduced silently during a library upgrade or a refactor.
  • It's easy to miss because embeddings still compute and still return SOME similarity score, just a degraded one, not an error.
  • Ties directly to Section 16's diagnostic: check both code paths whenever retrieval quality drifts without an obvious data change.

23
CAREER PRACTICE

Interview questions

Conceptual: why does a bi-encoder need a prefix at all if it's the same encoder on both sides?
With no cross-attention between the query run and the document run, nothing else in the architecture distinguishes the two roles -- the text itself has to carry that signal.
Mathematical: derive the token-share ratio for arbitrary N and prefix length k.
Share = k/(k+N). For two texts of length N1 and N2, the ratio of their shares is (k+N2)/(k+N1) -- for k=2, N1=5, N2=40, that's 42/7 = 6.0.
Coding: implement the prefix-aware pool_mean.
Section 12 gives the full implementation, with assertions reproducing the exact 2/7, 2/42 shares and the displacement numbers.
Debugging: a retrieval pipeline's scores degraded after a library upgrade. What do you check first?
Whether the query-encoding and document-encoding code paths still apply the model's documented prefix correctly and on the correct side -- a silent prefix regression still returns scores, just degraded ones.
System design: how would you unit-test that a production pipeline always applies the correct prefix on the correct side?
A test that feeds a known string through both the query-encoder and document-encoder functions and asserts the literal prefixed text (or a hash of it) matches the model's documented convention before tokenization ever runs -- catching a swapped code path independent of any embedding math.
