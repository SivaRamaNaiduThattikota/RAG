MODULE 03 · CONCEPT 02

Why we cannot simply ask
the LLM: external knowledge

Concept 01 named the fix: a retriever, wired to a generator. Before this course builds a single piece of that retriever, it owes you the argument for why the fix is necessary at all — not "nice to have," but architecturally required. Asking a plain LLM to supply external knowledge fails for three tied-together reasons: its weights are frozen the moment pretraining stops, so there's no write channel at inference time; those weights can only ever encode what was in the training corpus, so anything that was never there isn't in there at any density; and the forward pass itself has no read channel to any outside source while it runs. This is a can't, not a won't — the rest of this lesson is spent proving that distinction.

01 · CONCEPT FIRST

Three reasons, all architectural, all pointing the same way

Why can't we just ask the LLM for the external knowledge we need? Because three architectural facts hold at once, and each one alone would already be enough to block it. Its weights are frozen the instant pretraining stops — there's no channel at inference time that writes anything new into them. Those weights can only ever encode whatever density of a fact was present in the training corpus — so knowledge that was never in that corpus, private or otherwise, cannot be in there at any density, thin or thick. And the forward pass that turns a prompt into an answer has no read channel to any outside source while it runs — this is Module 02 Concept 09's "no verification step" pushed one level further: not just no fact-checking of an answer already drawn from memory, but no retrieval step of any kind, ever, at any point in that computation.

Say this precisely: it's a can't, not a won't. The model isn't being lazy, stubborn, or under-instructed. There is no lever inside a plain LLM's inference call that a better-worded prompt could pull to reach data it never had. The rest of this lesson exists to make that distinction stick.

First memory: frozen weights, a corpus-bounded encoding, and no read channel at inference — three architectural facts, one closed loop, and no prompt reaches outside it.
02 · WHY IT EXISTS

The fix that keeps almost working, and never does

Here's the failure pattern teams hit constantly: the model doesn't know something, so someone reaches for the system prompt. "Be accurate." "Double-check yourself before answering." "Only answer if you're sure, and cite a source." Each instruction sounds like it should help, and each one fails to reliably fix anything — because none of them address what's actually missing. This concept exists to explain, in depth, why that entire class of fix is structurally doomed, before Concept 03 catalogs the specific knowledge categories — cutoffs, private data, frequently-changing information — where this failure shows up hardest.

03 · CONCRETE EXAMPLE

Three prompts, three confident numbers, all unverifiable

Someone asks a plain LLM with no retriever wired in — Oracle RAG's internal home-office equipment reimbursement cap doesn't exist in any public document — the same underlying question three times, each time with a more elaborate prompt.

ATTEMPT 1 · "JUST ASK"

"What is our internal home-office equipment reimbursement cap?" Answer: a fluent, specific-sounding number — say, "$350 per employee." No source, no hedge, no way to check it.

ATTEMPT 2 · "DOUBLE-CHECK YOURSELF"

Same question, plus "please double-check yourself before answering." Answer: a similarly fluent number, possibly restated with more confidence, possibly a different guess entirely. Still no source, still unverifiable.

ATTEMPT 3 · "ONLY ANSWER IF CERTAIN, CITE A SOURCE"

Same question, plus "only answer if you're certain, and cite a source." Answer: a fluent number, now attached to an invented-sounding citation, or a hedge that still resolves to a specific guess. Either way, the number can still be wrong.

All three can be wrong, every time — not because the phrasing was weak, but because none of the three prompt variants added anything to what was sitting in the weights. They only changed which already-frozen patterns got emphasized during decoding.

04 · TECHNICAL MECHANISM

No write channel back in, no read channel out

FACT 1 · FROZEN PARAMETERS

Module 02 Concept 09 already named the weight groups — the embedding table, each block's attention and feed-forward weights, the output head. All of them are the fixed output of a training run that already finished. Nothing at inference time writes back into any of them. Whatever was absent from those weights when training stopped stays absent forever, no matter what gets typed into the prompt afterward.

FACT 2 · NO READ CHANNEL

The forward pass's only inputs are the prompt's tokens and those same frozen weights. There is no function call, no network request, no file read anywhere inside that computation. A private document that was never part of the training corpus literally cannot be consulted during a forward pass — not "is unlikely to be," cannot be, no matter what the prompt instructs it to do.

05 · ARCHITECTURE / FLOW

The closed inference loop

Prompt tokens→ Forward pass (frozen weights only)→ Logits→ Decode loop→ Output token, appended back into context→ loop continues

Trace every arrow in that loop. None of them ever leaves the box to touch a document, a database, or the internet — the output token gets appended back into the same context that's about to be fed through the same frozen weights again. It's a closed loop by construction, not by omission.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"If I just phrase the prompt better, it'll get the private or current fact right."

No — nothing in the prompt's text can supply data that was never in the training corpus. Phrasing changes emphasis, not access.

"Telling it to search its memory harder is like telling a person to try harder."

No — there is no memory to search beyond the frozen weights. "Trying harder" isn't a lever this architecture has; there's no effort dial to turn.

"A system prompt saying you have access to our database actually grants that access."

No — a system prompt is still just tokens read by the same frozen-weight forward pass. Declaring access in English doesn't wire anything.

08 · YOUR PROJECT MAPPING

Two ways Oracle RAG hits this exact wall

PRIVATE DATAInternal policy documents were never public

Oracle RAG's internal policy documents were never posted anywhere public, so they were never in any foundation model's training corpus. No prompt can retrieve what was never encoded in the first place.

POST-CUTOFF DATARecent policy revisions add a second, distinct problem

Even a document that eventually becomes public is still past any model's training cutoff the moment it postdates that cutoff. Same wall, different route to it.

WHAT THIS MEANSExactly the gap Module 03's retriever closes

09 · WHAT YOU SHOULD UNDERSTAND

Readiness check before moving on

Frozen parameters

Weights are fixed the moment training stops — no write channel exists at inference time, ever.

No read channel

The forward pass has no way to reach anything external — a structural absence, not a switched-off feature, and stronger than Concept 09's "no verification step."

Can't, not won't

This is an architectural limitation, not an effort problem or a prompting problem.

Two instances, one cause

Private/never-seen data and post-cutoff data are mechanically the same underlying cause: "this content was never part of the training corpus when the weights were fixed."

04
INTUITION

Handcuffed to the desk, no phone, no library card

Extend Concept 01's open-book-exam analogy one step further. This exam-taker is also handcuffed to the desk, with no phone and no library card. No matter how cleverly the instructions printed on the exam paper are worded — "think carefully," "double-check your work," "only answer if you're sure" — nothing physically lets them consult a source they haven't already memorized.

Analogy boundaryUnlike a handcuffed student, the model feels no frustration and has no awareness of the wall it's up against. This is a structural fact about a computation graph, not a motivational obstacle. Lewis et al.'s framing of parametric-only models makes the paper-level version of this same point: such models can't precisely access or update the knowledge they'd need.

09
MATHEMATICS

Zero terms in the training sum

Recall Concept 09's cross-entropy training framing, restated over the fixed pretraining corpus C:

θ* = argmin_θ Σ_{x∈C} loss(x; θ)

If a fact f — a private document, or an event postdating C's collection — satisfies f∉C, it contributes zero terms to that sum:

f ∉ C ⇒ f contributes 0 terms to Σ_{x∈C} loss(x; θ)

No gradient step ever pushed θ toward or away from f. Therefore P_θ(answer | q) for a query q about f is not systematically a function of f at all — whatever it outputs is incidental, not recall of f. This is Concept 01 Section 09's exact object, P(answer|query): this section derives why that object is structurally blind to any f∉C. Kasai et al.'s RealTime QA is the empirical confirmation — frozen-parameter accuracy degrades sharply past the training window, exactly as the zero-terms argument predicts.

10
WORKED EXAMPLE

Two cases, one zero-terms argument

PRIVATE CASE

Oracle RAG's internal "home-office equipment reimbursement cap" document D_priv was never posted publicly, so D_priv ∉ C for any general-purpose foundation model. The training sum has literally zero terms mentioning D_priv's contents — nothing pushed θ toward the real number, so the model produces some fluent number sourced from unrelated generic reimbursement-policy patterns instead.

CUTOFF CASE

A policy revision R issued last week postdates C's collection date, regardless of how public R eventually becomes. R ∉ C by the exact same zero-terms argument, for a completely different reason than the private case — R could become fully public tomorrow and would still have contributed zero training terms today.

Flag the mechanical difference from Concept 09 Section 10's sparse-but-present carryover-cap example: that fact was public and rare inside C, still contributing a few terms. These two cases are either never-public or not-yet-existing when C was collected — zero terms, not few. Same failed-lookup symptom on the surface, two distinct causes, neither of them "thin coverage."

12
CODE

Two signatures make the argument literal

PYTHON · FROM-SCRATCH PSEUDOCODE 
weights = {
    # a tiny stand-in for frozen theta -- a real model's weights are
    # billions of numbers; this dict only needs to demonstrate that
    # nothing in it was ever about Oracle RAG's actual reimbursement
    # policy, because that policy document was never public.
    "generic_reimbursement_pattern":
        "many companies cap home-office reimbursements somewhere "
        "between $200 and $500",
}

def plain_llm_answer(prompt, weights):
    # no corpus parameter exists here -- there is nothing this
    # function could search even if the prompt text asks it to.
    # the only things reachable are `prompt` itself and `weights`,
    # no matter what the prompt's words say to do instead.
    if "reimbursement" in prompt.lower():
        pattern = weights["generic_reimbursement_pattern"]
        return f"I'd estimate around $350 per employee. ({pattern})"
    return "I don't have enough information to answer that."

def rag_answer(prompt, weights, corpus):
    # the one new argument, `corpus`, is the entire fix -- a place
    # to look that isn't just the frozen weights above.
    hits = [doc for doc in corpus if "reimbursement" in doc.lower()]
    if hits:
        return f"According to the policy document: {hits[0]}"
    return plain_llm_answer(prompt, weights)

corpus = [
    "Home-office equipment reimbursement is capped at $750 per "
    "employee per fiscal year, per HR Policy 4.2.",
]

plain_prompt = "What's our internal reimbursement cap for home-office equipment?"
careful_prompt = (
    plain_prompt
    + " Please double-check yourself, and only answer if you're "
      "certain, citing a source."
)

print(plain_llm_answer(plain_prompt, weights))
print(plain_llm_answer(careful_prompt, weights))
print(rag_answer(plain_prompt, weights, corpus))

Changing only the prompt text passed into plain_llm_answer — never its arguments — never changes what data is reachable; both calls fall back to the same generic pattern in weights. The fix is an added argument and a wire, not cleverer phrasing.

13
ECOSYSTEM

Nobody fixes this with a better prompt template

No mainstream provider fixes this gap via prompting. "Tools," "function calling," "file search," and "web browsing" product features are exactly a wired-in read channel — a retriever, in Concept 01's vocabulary — bolted onto the closed loop this concept describes, not a smarter prompt template. Petroni et al.'s LAMA finding, that directly probing a language model's parameters as a knowledge base surfaces large, uneven gaps, is the empirical reason providers built retrieval and tool features instead of relying on prompt engineering. Kasai et al.'s RealTime QA is the empirical demonstration of frozen-parameter accuracy degrading past the training window. Modules 04 through 10, and 12 through 13, are where the actual wired fix gets built — not delivered here.

DIAGNOSIS

Three failure modes specific to prompting as the fix

INSTRUCTION INFLATION

Stacking instructions with zero effect

Ever more elaborate system-prompt language, with zero effect on what's actually reachable during the forward pass.

18
REALITY

Production implications, at introductory depth

  • Never rely on prompt instructions alone to bound private or time-sensitive claims — they cannot, by construction.
  • Audit any existing "answer accurately" or "always cite your sources" system-prompt language as a false sense of mitigation.
  • Treat a vendor's "we added web browsing / file search" announcement as literally "we wired in a retriever," not a prompting improvement.
  • Budget for an actual retrieval component wherever content is proprietary or changes faster than a retraining cycle can track — which Module 03 onward starts building.
19
RECALL

Knowledge check

Why does zero training-corpus terms for a fact mean zero gradient pressure on θ regarding it?
The training objective is a sum over terms in the corpus C. If a fact f is never in C, it never appears in that sum, so no gradient step is ever computed with respect to it — nothing pushes θ toward or away from f.
Restate the can't-versus-won't distinction in your own words.
"Won't" describes a present capability being misapplied, like hallucinating from real-but-lossy memory. "Can't" describes a capability that was never wired in at all — there is no read channel to reach external knowledge, no matter the instruction.
Why doesn't a system prompt claiming database access grant it?
A system prompt is still just tokens fed into the same frozen-weight forward pass. Granting access requires an actual function call or network read wired into the computation graph — a sentence describing access isn't that wire.
Why are post-cutoff and never-public content mechanically the identical argument, even though they feel different day-to-day?
Both satisfy f∉C — the fact was never part of the training corpus when θ was fixed — for different real-world reasons (one was never public, one didn't exist yet). The zero-terms argument doesn't care which reason applies.

FEEDBACK

Solution and teach-back

Open the worked solution
Fix 1 is (a): "double-check your facts" is text read inside the same closed loop — it reweights decoding, it adds no argument the forward pass can read from, so nothing about what's reachable changes. Fix 2 is (b): claiming SharePoint access in a system prompt is still just tokens; without an actual wired function call or network read, no capability exists behind the claim. Fix 3 is (c): fine-tuning genuinely changes θ, so it does add real capability, but at the explicit recurring cost of a full training run every single week the documents change. 22
PORTABLE MEMORY

Concept card

The argument

Frozen θ after training, plus f∉C, means zero gradient terms for f. No read channel in the forward pass means no prompt can supply f either. Both facts together: no prompt can supply a fact that was never in the training corpus, no matter how it's worded.

Selection rule

  • Public, dense fact → a plain LLM is fine, no retrieval needed
  • Private or post-cutoff fact → no prompt fixes it, only a wired retriever does
  • Memorable example: the handcuffed exam-taker with no phone and no library card
23
CAREER PRACTICE

Interview questions

Explain to a non-technical stakeholder why "just tell it to check its facts" won't fix wrong answers about internal-only documents.
The model can only answer from patterns it picked up during training, and it has no way to look anything up while it's answering. Telling it to "check its facts" doesn't give it anything new to check against — it's still working from the same fixed memory either way.
What's structurally different between hallucination and this concept's "no read channel" argument?
Hallucination (Concept 09) is a behavior of the decode loop — a loop that could in principle be handed evidence and still fail to use it well. The missing read channel is a structural absence that holds even before the loop runs at all; there's nothing to hand it in the first place.
Why does adding "you have file search" to a system prompt do nothing without an actual tool wired in?
The forward pass only ever reads prompt tokens and frozen weights. A sentence claiming a capability is still just tokens — it doesn't add a function call or network read to the computation graph, so nothing about what's reachable actually changes.
Contrast the cost and benefit of fine-tuning versus wiring in retrieval for a fact that changes weekly.
Fine-tuning weekly means a full training run every single week, and the fact is only current until the next change. Wiring in retrieval costs a retriever, an index, and a search step per query, but the underlying document can be updated at any time with no retraining at all — the forward pass just reads the current version next time.
