Concepts 01-06 of this module all searched a corpus by vector similarity alone. This concept is the first to combine that similarity search with a structured metadata constraint -- a tenant, a date cutoff, an access level. PROGRESSIVE BEGINNER CORE

Same query vector, one more constraint

Every mechanism through Concept 06 ranked a corpus by similarity to a query and stopped there. Real systems almost never stop there -- a search also has to respect who is allowed to see what, and when. This concept is about the three different ways to make a similarity search obey a metadata constraint, and what each way actually costs.

01 · CONCEPT FIRST

Metadata filtering: combining "most similar" with "actually eligible"

INSTINCT

Similarity search already returns the closest vectors -- surely that's the whole job.

REALITY (this concept)

Almost every real deployment also needs a structured constraint -- this tenant only, this date range only, this access level only. There are three genuinely different ways to combine that constraint with the similarity search itself, and they are not interchangeable in cost.

First memory: pre-filter, post-filter, or build the filter into the ANN search itself -- three different orderings of the same two ingredients, never free.
02 · WHY IT EXISTS

A geometrically close match can still be the wrong answer

Nothing in Concepts 01-06's own mechanisms knows anything about who owns a chunk or when it was written. A plain vector search over a shared index can return another tenant's ticket, or a document that expired last year, for the simple reason that it happens to sit close to the query vector. Metadata filtering exists to stop that -- narrowing eligibility to "documents this tenant is allowed to see," "documents not yet past their cutoff date," and so on, on top of whatever the similarity ranking says.

03 · CONCRETE EXAMPLE

A multi-tenant support search, and a 17-vs-5 headline number

Picture a support-ticket search shared by many tenants. A query arrives, and the system ranks all N=20 candidate chunks by similarity to it -- rank 1 is the closest match, rank 20 the farthest, exactly Concepts 01-06's own similarity-ranking convention. A metadata filter then restricts results to one tenant, "Acme." Only 6 of the 20 chunks actually belong to Acme (30% selectivity), and their positions in the similarity ranking are scattered, not clustered near the top: ranks {3, 7, 9, 14, 17, 20}. The system needs the top k=5 valid Acme results.

If the system runs the vector search first and discards non-Acme hits afterward (post-filtering), it has to scan down the ranked list looking for Acme hits: rank 3 (1st), rank 7 (2nd), rank 9 (3rd), rank 14 (4th), rank 17 (5th) -- the 5th Acme hit only appears at rank 17. To return 5 valid results, the system must fetch the top 17 candidates from the vector index, not the top 5, discarding 12 non-Acme candidates along the way. That's a 3.4x over-fetch (17 ÷ 5). If instead the system checks the tenant filter first (pre-filtering), it identifies the 6 Acme chunks directly, then ranks only those 6 by similarity -- touching 6 vectors total, never 17, to return the true top-5 Acme results.

Cross-check against the general heuristic used in practice, expected fetch depth ≈ k ÷ p: 5 ÷ 0.30 = 16.67, which rounds to 17 -- matching this toy corpus's actual scattered-case depth almost exactly. That heuristic is a good expected-case predictor, but it is not a guarantee: if the same 6 Acme chunks happened to occupy the 6 least-similar ranks instead (15-20), the 5th one is only reached at rank 19 (a 3.8x over-fetch) -- and if the filter is selective enough that fewer than k matches exist anywhere in the corpus (at 20% selectivity there are only 4 Acme chunks total), post-filtering cannot return 5 valid results no matter how deep it fetches. Pre-filtering has no such ceiling on cost -- it only has a ceiling on how many results actually exist.

04 · TECHNICAL MECHANISM

Three strategies, same two ingredients

Pre-filtering runs the metadata check first: the eligible set of candidates is determined before the vector search starts, and the vector search then only considers candidates on that allow-list. Post-filtering runs the vector search first, over-fetching candidates, then discards the ones that fail the metadata check -- cheap when the filter matches most of the corpus, expensive (and, per Weaviate's own documentation, unpredictable) when the filter is very restrictive, since "you cannot easily predict how many elements will be contained in the search," and a very restrictive filter risks the underlying vector search containing no match at all. Filtered (integrated) ANN search builds the metadata awareness directly into the index's own traversal -- Weaviate's ACORN and sweeping strategies pass an inverted-index allow-list of eligible ids straight into the HNSW graph traversal (the exact structure named in Concept 03, reused here unchanged), and Qdrant's filterable HNSW applies the filter to graph nodes during the greedy search itself, in one pass, rather than running a separate step before or after.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Post-filtering with top-k=5 always returns 5 results."

False -- if fewer than 5 matching chunks exist anywhere in the corpus, no fetch depth, however deep, can produce 5. At 20% selectivity in the toy corpus (only 4 Acme chunks total), k=5 is structurally impossible.

"Pre-filtering is always cheaper."

Mostly true in this concept's own example, but it isn't free -- it costs a separate metadata index, and if the eligible set itself is still huge, ranking within it can still be expensive.

"Filtering never changes recall."

False for naive post-filtering -- per Weaviate's own documented risk, a very restrictive filter can leave the underlying vector search with no match inside its fetch window at all, silently returning fewer results than requested.

04
INTUITION

Guest list first, or check IDs at the door

Pre-filtering is like checking the guest list before anyone walks up to the door -- only invited guests are even considered, so the doorman never wastes a moment on someone who was never getting in. Post-filtering is like letting everyone walk in first and checking IDs at the door as they arrive -- fast when almost everyone is on the list, slow and unpredictable when the venue is nearly empty of invitees, because the doorman has to keep letting people through until enough valid guests have shown up. Filtered/integrated ANN search is like a doorman who already knows the guest list and only walks toward invited guests in the crowd to begin with.

Analogy boundaryThis is a framing device, not a new measurement -- the actual costs below come from the verified 20-chunk worked example and its four-selectivity table, not from the analogy.

06
MECHANISM

Step by step, against the same toy corpus

Pre-filtering. The metadata index identifies the 6 Acme chunks directly -- a cheap lookup independent of vector similarity -- then the system computes similarity ranking only among those 6, touching 6 vectors total to return the true top-5 Acme results. Post-filtering. The system scans down the full similarity ranking from rank 1, checking each candidate's tenant as it goes, and stops once 5 Acme hits have been found -- which happens at rank 17 in this corpus's scattered arrangement, so 17 candidates are fetched and 12 discarded. Filtered/integrated ANN search. Weaviate's ACORN and sweeping strategies pass an inverted-index allow-list of eligible (Acme) ids straight into the HNSW graph traversal itself, so the graph descent only ever considers eligible neighbours in the first place; Qdrant's filterable HNSW applies the same idea inside the graph's own greedy search, and for categorical filters like a tenant id, pre-builds dedicated per-category subgraphs so the graph stays connected within one category without a separate allow-list pass.

09
MATHEMATICS

An expected-case heuristic and an exact worst case

Expected fetch depth ≈ k ÷ p (uniform-mixing assumption: matches are spread evenly through the ranking)
Exact worst-case fetch depth = N − (totalMatches − k) (assumption: the k matches needed sit at the least-similar end of the ranking)
Over-fetch factor = fetch depth ÷ k

The heuristic is an expected-case predictor, not a guarantee -- Section 10's own worked table shows it lands within a fraction of a rank of the toy corpus's actual scattered-case depth, while the worst-case formula gives the true ceiling when matches happen to sit at the bottom of the ranking instead.

The 20%/k=5 row is impossible outright -- only 4 Acme-equivalent chunks exist in the corpus at that selectivity, so no fetch depth can ever produce 5 valid results. 11
CONCRETE USE

A clean fit, a boundary case, and a mistake

CLEAN FIT

A low-selectivity tenant filter

When a filter matches only a small slice of the corpus, pre-filtering keeps the cost fixed at the size of that slice -- never inflated by how deep the matches happen to sit in the full similarity ranking.

BOUNDARY CASE

A filter matching nearly 100% of the corpus

Post-filtering's over-fetch cost approaches 1.0x -- effectively free, per the table's own 70% row -- because almost every fetched candidate already passes the filter.

MISTAKE TO AVOID

Assuming post-filtering's top-k=5 always returns 5 results without checking total matches

Exactly the 20%/k=5 impossible row -- a naive implementation can silently return fewer than k results instead of surfacing the shortage.

CODE

Reproducing the scan-depth table from scratch

JAVASCRIPT · FROM SCRATCH -- REPRODUCES THIS CONCEPT'S OWN SCAN-DEPTH TABLE EXACTLY 
// matchRanks: sorted ranks (1-indexed) where the metadata filter matches,
// out of a corpus of size N. Returns the same fetch/discard/over-fetch
// figures already verified in Section 10 -- nothing here is re-measured
// against a real system, only re-derived from a fixed, stated input.
function scanDepth(matchRanks, k) {
  if (matchRanks.length < k) {
    return { fetched: null, discarded: null, overFetch: null, impossible: true };
  }
  const fetched = matchRanks[k - 1]; // the k-th match, in rank order
  const discarded = fetched - k;
  const overFetch = fetched / k;
  return { fetched, discarded, overFetch, impossible: false };
}

const selectivity30 = [3, 7, 9, 14, 17, 20]; // 30% of N=20
const r1 = scanDepth(selectivity30, 3);
const r2 = scanDepth(selectivity30, 5);
console.assert(r1.fetched === 9 && r1.discarded === 6, "30%, k=3");
console.assert(r2.fetched === 17 && r2.discarded === 12, "30%, k=5");
console.assert(Math.round(r2.overFetch * 100) / 100 === 3.40, "30%, k=5 over-fetch");

const selectivity20 = [4, 8, 13, 18]; // 20% of N=20, only 4 total matches
console.assert(scanDepth(selectivity20, 5).impossible === true, "20%, k=5 impossible");

function worstCaseFetch(N, totalMatches, k) {
  return N - (totalMatches - k);
}
console.assert(worstCaseFetch(20, 6, 5) === 19, "30%, k=5 worst case");

ECOSYSTEM

Real production sources for all three strategies

Weaviate's own filtering documentation defines pre-filtering directly: "eligible candidates are determined before a vector search is started. The vector search then only considers candidates that are present on the allow list." It also states post-filtering's real risk in its own words: "you cannot easily predict how many elements will be contained in the search, as the filter is applied to an already reduced list of candidates... there is a chance that the original vector search does not contain any match at all." Weaviate's ACORN and sweeping strategies are its own named filtered/integrated ANN mechanisms, passing an eligible-id allow-list directly into HNSW traversal. Qdrant's "Filterable HNSW Without Recall Loss" names the same post-filtering baseline this concept uses -- "they only suggest to iterate over top search results and apply conditions consequently after the search" -- and documents Qdrant's own filtered-HNSW modification: applying filter criteria directly to graph nodes during greedy search, with dedicated per-category subgraphs for categorical filters and bucketed connections for numerical-range and geo filters. Pinecone's indexing overview confirms metadata fields are "automatically indexed for filtering" alongside a record's vector -- a third named vector database treating structured metadata indexing as mainstream, current practice.

DIAGNOSIS

Failure modes

OVER-FETCH EXHAUSTS THE BUDGET

A fixed top-k fetch window runs out before k matches are found

Exactly the 30%-worst-case scenario (matches at ranks 15-20) -- a system that only ever fetches, say, the top 15 candidates would find just 4 of the 6 Acme hits and silently under-return.

THE IMPOSSIBLE CASE

Fewer than k matches exist anywhere in the corpus

The 20%/k=5 row -- no fetch depth, however deep, produces a 5th match, because only 4 exist. This is a ceiling on the data, not on the strategy.

SILENT UNDER-RETURN

Naive post-filtering returns fewer than k results without warning

Without an explicit check against total matches, a caller expecting exactly k results may never notice it received fewer.

REALITY

Production implications

  • Weaviate's own filtering documentation describes falling back toward brute-force, flat search under very restrictive filters -- a direct operational consequence of pre-filtering's own "narrow the candidates, then search" design.
  • Qdrant's own filterable-HNSW article documents that its per-category subgraph approach grows the graph's edge count, bounded at roughly 2x per their own measurement -- a real, named memory cost of building strategy three.
  • Choosing a strategy is a real design decision made per filter, not once for a whole system -- a low-selectivity tenant filter and a near-total-match date filter can reasonably use different strategies in the same deployment.
  • Module 20, "Authorization-aware retrieval and access control" and "Tenant isolation, multi-tenancy and security trimming" (named forward), owns the security and compliance stakes of getting a tenant filter wrong -- this concept only covers how the filter combines with the search itself.

CAREER PRACTICE

Interview questions

Conceptual: why does post-filtering risk returning fewer than k results?
Because it fetches a fixed number of candidates from the unconstrained similarity ranking and discards the ones that fail the metadata check afterward -- if the fetch window isn't deep enough to contain k matching candidates, the discard step leaves fewer than k.
Mathematical: given selectivity 70% and k=5 on a corpus of N=20, compute the over-fetch factor.
Using this concept's own fixed 70% arrangement, the 5th match lands at rank 7, so fetched=7, discarded=2, over-fetch = 7 ÷ 5 = 1.40x -- matching the table's own 70%/k=5 row.
Coding: extend Section 12's script to a new selectivity level of 90% (18 of 20 matches) at k=5.
Build an 18-element sorted match-rank array consistent with 90% selectivity, call scanDepth(matchRanks, 5), and expect a fetched value very close to 5 -- the over-fetch factor should approach 1.0x as selectivity approaches 100%, per the table's own monotonic trend.
System design: a low-selectivity tenant filter and a near-total-match date filter both need to run in the same retrieval call. What does this concept say about strategy choice?
Strategy is chosen per filter, not once for the whole system -- the low-selectivity tenant filter is a strong candidate for pre-filtering or integrated ANN, while the near-total-match date filter can likely use post-filtering cheaply, since its over-fetch cost approaches 1.0x.
Debugging: a production system's post-filtered top-5 request sometimes returns only 2 results. Diagnose.
Check the total number of documents matching the metadata filter for that query. If fewer than 5 exist in the corpus at all, no fetch depth can produce 5 -- exactly the 20%/k=5 impossible row. If more than 5 exist but the fetch window is too shallow, the fix is either a deeper fetch window or switching that filter to pre-filtering or an integrated ANN strategy.
