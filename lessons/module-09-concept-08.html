MODULE 09 · CONCEPT 08

Mark it deleted.
Don't rebuild the whole index yet.

Concepts 01-07 all treated the corpus as fixed once indexed. Real corpora change -- documents get updated, deleted, replaced -- and every structure this module has built (HNSW's graph, IVF's inverted lists, PQ/SQ's compressed codes) has to cope with that or degrade. FAISS's own documentation lists deletion support for IndexFlat and IndexIVFFlat, with no entry anywhere for IndexHNSWFlat. The real, standard workaround production systems use is the tombstone: mark an entry deleted without immediately restructuring anything, then periodically compact. A 20-chunk toy index shows exactly why that trade-off works -- and why its cost depends on where a deletion lands, not how many there are.

PROGRESSIVE BEGINNER CORE

Mark, don't rebuild -- until compaction actually runs

Every structure through Concept 07 assumed the corpus stayed fixed after indexing. Real corpora don't. This concept is about what actually happens -- and what it actually costs -- when a document gets updated or deleted after it's already been indexed.

01 · CONCEPT FIRST

Update, delete, tombstone -- three precise words

UPDATE / DELETE

A document changed or was removed from the source corpus after it was already indexed.

TOMBSTONE (this concept)

The real workaround: mark the entry invalid without immediately restructuring the index. It stays physically present -- still a node in HNSW's graph, still an id in IVF's list -- but flagged so queries skip it.

First memory: per Weaviate's own documentation, both updates and deletes go through the same tombstone-then-async-cleanup path -- an update is a tombstone-old plus insert-new, not an in-place edit.
02 · WHY IT EXISTS

Concepts 01-07 silently assumed a static corpus

Every mechanism this module has built -- exact search, HNSW, IVF, PQ/SQ, metadata filtering -- was demonstrated on a corpus that never changed after indexing. Real corpora change constantly. Immediately restructuring a graph or a compressed index on every single delete would be expensive; tombstoning defers that cost to a later, batched compaction step instead.

03 · CONCRETE EXAMPLE

20 chunks, 5 deletes, and a cost that doesn't scale with count

A toy index of N=20 chunks (the same scale as Concept 07's own corpus). A query produces a full similarity ranking over all 20 physical entries; the system needs the top k=5 valid results. Five deletes land, one at a time, at fixed ranks: 2, 5, 11, 16, 19.

TickTombstonesFetchedSkippedOver-fetch
0 (fresh)0501.00x
1 (rank 2)1611.20x
2 (rank 5)2721.40x
3 (rank 11)3721.40x (unchanged)
4 (rank 16)4721.40x (unchanged)
5 (rank 19)5721.40x (unchanged)

Ticks 3-5 add three more deletes -- the corpus's own tombstone rate keeps climbing (15%, 20%, 25%) -- but the query's own cost stays frozen at 1.40x, because all three land past rank 7, the depth this particular query already needed. Cost is positional, not count-based. Compaction then physically purges all 5 tombstones and rebuilds the structure, returning to fetched=5, over-fetch=1.00x -- identical to tick 0.

04 · TECHNICAL MECHANISM

Three structures, three different deletion costs

HNSW's graph (Concept 03) makes naive deletion hard: removing a node risks disconnecting its neighbours' own shortest paths through the graph. FAISS's own "Special operations on indexes" wiki page lists remove_ids support for IndexFlat, IndexIVFFlat and IDMap -- IndexHNSWFlat is never named anywhere on that page. IVF's inverted lists (Concept 04) make deletion comparatively cheap: crossing an id off one list touches nothing else, though FAISS's own page notes a real precondition -- a plain-array direct map can't remove without shifting every index; only a hashtable direct map with an id-selector removes without a full scan. PQ/SQ's compressed codes (Concept 05) delete exactly like an uncompressed vector would -- compression only changes each vector's own byte cost, not how membership in a list or graph works.

06 · IMPORTANT DISTINCTIONS

Tombstone vs. compaction vs. Concept 07's post-filtering

TermThe real difference
Tombstone (this concept)Mark an entry invalid immediately; defer restructuring.
Compaction (this concept)The later, batched restructuring that physically purges tombstoned entries -- Weaviate's own async cleanup, Qdrant's own Vacuum Optimizer.
Post-filtering (Concept 07)Same scan-and-skip shape at query time, but discards results for failing a metadata check, not for being deleted -- a different reason, identical mechanism.
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"More tombstones always means more query cost."

False -- ticks 3-5 in Section 03's own table are the counterexample. Cost is positional (where a tombstone sits relative to a query's own fetch window), not count-based.

"An update is a cheap in-place edit."

False, per Weaviate's own documentation -- updates go through the same tombstone-old-plus-insert-new path as deletes, not an in-place mutation.

"Compaction is free."

False -- it is a real, scheduled rebuild cost. Module 19's own maintenance-cost concept covers quantifying it; this concept only names that the cost exists.

04
INTUITION

A closed subway station, and a crossed-out phone-book card

Deleting an HNSW node is like ripping out a subway station -- every neighbouring line's own cable has to be re-spliced, so instead operators post a "closed" sign and reroute trains, doing the real rewiring on a scheduled maintenance window (the tombstone-then-compaction pattern). Deleting an IVF entry is like crossing one card out of one drawer in a phone-book index -- nothing else in that drawer, or any other drawer, needs to move at all.

Analogy boundaryBoth analogies explain WHY the two costs differ, not the exact numbers -- those come from the verified worked example in Section 10, not from the analogy itself.

06
MECHANISM

Three structures, cited from real documentation

HNSW. FAISS's own "Special operations on indexes" wiki page names remove_ids as "Supported by IndexFlat, IndexIVFFlat, IDMap" -- IndexHNSWFlat never appears on the page. Weaviate's own vector-index docs state directly: "Cleanup is an async process that rebuilds the HNSW graph after deletes and updates. Prior to cleanup, objects are marked as deleted, but they are still connected to the HNSW graph. During cleanup, the edges are reassigned and the objects are deleted for good." IVF. FAISS's own page distinguishes sequential indexes (where removing one entry shifts every higher id down by one) from IndexIVF and IDMap2, which store ids explicitly -- removing one leaves every other id untouched, cheap by construction, though a plain-array direct map still can't remove without a full scan; only a hashtable direct map with an id-selector avoids that. PQ/SQ. Compression (Concept 05) changes each vector's own byte cost, not how list or graph membership works -- deleting a compressed code is mechanically identical to deleting an uncompressed one.

MATHEMATICS

The same shape as Concept 07's own formulas, reused

p_live = (N − tombstones) / N — the live fraction, directly analogous to Concept 07's own selectivity p
Expected fetch depth ≈ k / p_live — Concept 07's own k/p heuristic, cited, applied to live fraction instead of selectivity
Worst-case fetch depth = N − (liveCount − k) — identical formula shape to Concept 07's own worst-case formula

None of these three equations is new mathematics -- all reuse Concept 07's own already-cited shapes, substituting "live" for "matches a filter."

The plateau, explained. Ticks 3-5 add three more deletes, but every one lands at a rank past 7 -- the depth this query already needed at tick 2 -- so none of them change the answer. The corpus's own tombstone rate keeps climbing (15% → 20% → 25%), but this query's own cost is frozen. A different query, with a different similarity ranking, would feel those same three tombstones differently.

Worst case, cross-checked. If all 5 tombstones instead sat at ranks 1-5, the system must fetch 10 candidates to collect 5 live ones -- matching the closed-form worst-case formula N − (liveCount − k) = 20 − (15 − 5) = 10 exactly.

The real-system callback. This toy index's 25% tombstone rate (tick 5) sits just above Qdrant's own documented Vacuum Optimizer trigger, deleted_threshold: 0.2 -- in a real Qdrant segment at this deletion rate, compaction would already be scheduled.

CODE

The tick-by-tick trace, implemented directly

JAVASCRIPT · FROM SCRATCH -- REPRODUCES THIS CONCEPT'S OWN TICK-BY-TICK TABLE EXACTLY 
// tombstoneRanks: sorted ranks (1-indexed) marked deleted, out of a
// corpus of size N. Scans ranks in order, skipping tombstoned ones,
// until k live results are collected.
function scanPastTombstones(N, tombstoneRanks, k) {
  const tombstoned = new Set(tombstoneRanks);
  let collected = 0, skipped = 0, fetched = 0;
  for (let rank = 1; rank <= N; rank++) {
    fetched = rank;
    if (tombstoned.has(rank)) { skipped++; continue; }
    collected++;
    if (collected === k) break;
  }
  return { fetched, skipped, collected, impossible: collected < k };
}

const N = 20, k = 5;
console.assert(scanPastTombstones(N, [2], k).fetched === 6, "tick 1");
console.assert(scanPastTombstones(N, [2, 5], k).fetched === 7, "tick 2");
console.assert(scanPastTombstones(N, [2, 5, 11], k).fetched === 7, "tick 3 -- unchanged");
console.assert(scanPastTombstones(N, [2, 5, 11, 16, 19], k).fetched === 7, "tick 5 -- still unchanged");
console.assert(scanPastTombstones(N, [1, 2, 3, 4, 5], k).fetched === 10, "worst case");

function worstCaseFetch(N, liveCount, k) {
  return N - (liveCount - k);
}
console.assert(worstCaseFetch(20, 15, 5) === 10, "worst-case formula matches the scan");

ECOSYSTEM

Real production sources for tombstoning and compaction

FAISS's own "Special operations on indexes" wiki page is the primary source for this concept's own per-structure deletion costs -- its "Removing elements from an index" section names remove_ids as supported by IndexFlat, IndexIVFFlat and IDMap, with no mention anywhere of IndexHNSWFlat. Weaviate's own vector-index documentation gives the tombstone mechanism itself, verbatim, in its "Deletions" section: objects marked deleted stay wired into the HNSW graph until an async cleanup pass reassigns their edges -- covering both deletes and updates through the same path. Qdrant's own Vacuum Optimizer documentation states directly: "Qdrant does not delete entries immediately... it marks records as deleted and ignores them for future queries," and names the real trigger values deleted_threshold: 0.2 and vacuum_min_vector_number: 1000 -- the source of this concept's own 20%-vs-25% comparison.

DIAGNOSIS

Failure modes

SKIPPED SKIP STEP

A caller bypasses the tombstone-skip logic

Symptom: stale, deleted content still shows up in results, served directly from an entry that was marked invalid but never checked.

UNBOUNDED GROWTH

Compaction never runs

Symptom: tombstone rate climbs indefinitely, and every query's own over-fetch cost keeps rising along with it.

OVER-AGGRESSIVE COMPACTION

A rebuild runs too often or too broadly

Symptom: query throughput starves mid-rebuild -- Qdrant's own copy-on-write proxy-segment design exists specifically to mitigate this.

REALITY

Production implications

  • Staleness SLOs and compaction scheduling are a real operational decision, not a default -- Qdrant's own deleted_threshold (0.2) is a concrete, documented example of making that decision explicit.
  • Weaviate's own async cleanup design keeps search available throughout compaction; Qdrant's own segment-level copy-on-write keeps a segment readable mid-rebuild -- both real, named mitigations against the over-aggressive-compaction failure mode above.

CAREER PRACTICE

Interview questions

Conceptual: why is deleting an HNSW node harder than deleting an IVF entry?
Removing a graph node risks disconnecting its neighbours' own shortest paths through the structure, requiring re-splicing; removing an IVF entry just crosses an id off one inverted list, with nothing else to preserve.
Mathematical: at N=20, k=5, with 7 tombstones bunched at ranks 1-7, compute the fetch depth.
Live count = 13. Worst-case-style scan: fetched = 12 (ranks 1-7 skipped, ranks 8-12 collected as the 5 live results) -- over-fetch = 12÷5 = 2.40x.
Coding: extend scanPastTombstones to also return the live fraction p_live.
Add const pLive = (N - tombstoneRanks.length) / N to the function and include it in the returned object -- a direct application of Section 09's own p_live formula.
System design: how would you decide when to run compaction for a given index?
Track the tombstone rate per segment (Qdrant's own deleted_threshold pattern) and trigger a rebuild once it crosses a chosen bound, balancing query-cost creep against the real cost of the rebuild itself -- not a fixed schedule alone.
Debugging: a production search occasionally returns a document that was deleted hours ago. What do you check first?
Whether the retrieval path actually checks the tombstone flag before returning a candidate -- Weaviate's own design keeps a tombstoned object physically present until cleanup, so any code path that skips the flag check will surface it.
