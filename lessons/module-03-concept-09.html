MODULE 03 · CONCEPT 09

Naive, advanced and
modular RAG taxonomy.

Concepts 01 through 08 built one specific shape of RAG — retrieve the top-k most similar chunks, then generate — without ever naming that shape as a category. This concept turns inward and gives it a name: naive RAG. It then introduces two more sophisticated shapes as silhouettes only, not builds: advanced RAG adds steps before retrieval (like query rewriting) and after it (like re-ranking), still as one fixed sequence. Modular RAG goes further and treats each pipeline stage as a swappable, composable component rather than a fixed sequence at all. Modules 11 through 17, and Module 23 onward, build the two newer shapes for real — this concept only gives all three their names and the criteria that tell them apart.

01 · CONCEPT FIRST

Three shapes, one family

NAIVE RAG

The exact shape Concepts 01-08 built, now given a name: retrieve the top-k most similar chunks, then generate an answer from them. One fixed sequence — nothing before retrieval, nothing after it.

ADVANCED RAG

The same fixed sequence, with steps added around retrieval — a pre-retrieval step like query rewriting before it, a post-retrieval step like re-ranking after it. Named here only; Modules 15-17 build these steps for real.

MODULAR RAG

Treats retrieval, generation, and every other stage as a swappable, composable component rather than one fixed sequence at all. Named here only; Module 23 and later modules design it for real.

THE COMMON GROUND

All three still retrieve, then generate — Concept 01's two boxes, unbroken. The taxonomy names what changes around that core, not a departure from it.

First memory: naive, advanced, and modular RAG are three shapes of the same idea, not three competing techniques — Concept 08's fine-tuning/search/tool-use boundary lines are a completely different comparison and don't apply here.
02 · WHY IT EXISTS

A name for the shape you already built, before two more

Concepts 01 through 08 built and defended one working shape of RAG without ever calling it anything. That's fine for learning it once, but it breaks down the moment this course needs to compare that shape against something more sophisticated in Modules 11 through 23, or the moment you read a paper or a vendor's claims that use "naive," "advanced," and "modular" as load-bearing terms. Without the names, every comparison has to be re-explained from scratch. With them, "this system is still naive RAG" is a precise, checkable claim.

WITHOUT THE TAXONOMY

Every RAG system looks the same from a distance — "it retrieves, then generates" — with no vocabulary for how much more a more sophisticated pipeline is actually doing.

WITH THE TAXONOMY

Three names, each with a checkable criterion, let you place any RAG system precisely — including the one this course has been quietly building since Concept 06.

03 · CONCRETE EXAMPLE

The same Oracle assistant, three ways it could be shaped

Concept 06's Oracle policy assistant retrieves the top-k most relevant policy chunks for an employee's question and generates an answer from them — nothing more. That is naive RAG, exactly as built. Now imagine two upgrades, neither built yet: first, a step that rewrites a vague employee question ("what about travel?") into a specific one before retrieval even runs, plus a step that re-ranks the retrieved chunks for relevance before they reach generation — that upgraded shape is advanced RAG. Second, imagine the retrieval step itself could be swapped out per request — a policy retriever for HR questions, a different retriever for IT questions, routed dynamically — with re-ranking optionally skipped when there's only one candidate chunk. That reconfigurable shape is modular RAG.

AS BUILT

Retrieve top-k policy chunks, generate — Concept 06's assistant, exactly. Naive RAG.

HYPOTHETICAL UPGRADE 1

Add query rewriting before retrieval, re-ranking after it — still one fixed order. Advanced RAG.

HYPOTHETICAL UPGRADE 2

Swap which retriever runs per request, skip re-ranking when it isn't needed — no single fixed order. Modular RAG.

04 · TECHNICAL MECHANISM

What actually changes between the three shapes

NAIVE RAG

One fixed sequence, two stages

Retrieve, then generate. Nothing runs before retrieval; nothing runs between retrieval and generation.

ADVANCED RAG

Same fixed sequence, more stages

A pre-retrieval step, a post-retrieval step, or both — inserted into the same fixed order naive RAG already used.

MODULAR RAG

Not a fixed sequence at all

Stages become swappable, composable components — added, removed, reordered, or routed differently per request.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Naive RAG means bad or wrong RAG."

It's a name for a shape, not a judgment — Concept 06's pipeline is a complete, working system that happens to be naive RAG's exact definition.

"Advanced RAG always produces better answers than naive RAG."

Not guaranteed — added steps cost latency and complexity; whether they help is an evaluation question (Module 18), not something the label settles by itself.

"Modular means using every available module."

Modular means components can be swapped, added, or removed — not that a system must use as many of them as possible.

"Every system must climb naive → advanced → modular."

Not addressed here — whether a given system needs to move up this ladder at all depends on requirements this concept doesn't evaluate.

04
INTUITION

An assembly line, an assembly line with inspection stations, and a factory floor

A simple assembly line takes a part through the same fixed stations in the same fixed order, every time — that's naive RAG. Add two inspection stations — one before assembly to check the part is the right one, one after to check the result — and the line still runs in one fixed order, just with more stations — that's advanced RAG. Now imagine a factory floor where stations can be added, removed, or rerouted depending on what's being built that day, with no single fixed order at all — that's modular RAG.

Analogy boundaryA factory floor still has physical constraints an RAG pipeline doesn't share. The point of the analogy is the structural claim only — fixed order versus fixed order with additions versus no fixed order — not anything about factories, robotics, or scheduling.
05
PRECISION

Formal definitions

TermDefinitionBoundary
Naive RAGA RAG pipeline consisting of exactly retrieval (Concept 01, Concept 06) followed by generation, with no additional pre- or post-retrieval steps, in one fixed orderNot a partial or unfinished pipeline — a complete, named baseline shape
Advanced RAGNaive RAG's fixed sequence with at least one pre-retrieval step (e.g. query rewriting, query expansion) and/or post-retrieval step (e.g. re-ranking, filtering) insertedStill executes in one fixed order; which specific steps exist is a Module 15-17 question, not this concept's
Modular RAGA RAG architecture in which pipeline stages — retrieval, generation, and any others — are swappable, composable, and can be added, removed, reordered, or routed differently per requestDefined by structural composability, not by which or how many steps happen to be present at any one time

This three-way naming follows the taxonomy introduced by Gao, Xiong, Gao et al. (2023) in their RAG survey — Section 13 cites it directly.

06
MECHANISM

The same core, three different structures around it

Naive RAG — query → retrieval → generation. Concept 06's pipeline, unchanged, in one fixed order.
Advanced RAG, pre-retrieval only — query → [pre-retrieval step] → retrieval → generation. Still one fixed order, one stage added before retrieval.
Advanced RAG, post-retrieval only — query → retrieval → [post-retrieval step] → generation. Still one fixed order, one stage added after retrieval.
Advanced RAG, both — query → [pre-retrieval] → retrieval → [post-retrieval] → generation. Still one fixed order — the deciding fact is that an order still exists at all.
Modular RAG — the same stages, plus routing, become swappable components with no single required order — which stages run, and in what sequence, can change per request.

09
MATHEMATICS

A light configuration-count argument, not a new derivation

This concept stays at the naming level, but one count is worth making precise: how many distinct pipelines does each shape actually allow? Naive RAG allows exactly one: retrieve, then generate, always. Advanced RAG, with p possible pre-retrieval step types and q possible post-retrieval step types, each independently included or excluded but still executed in one fixed relative order, allows:

Distinct advanced-RAG configurations ≈ 2p × 2q

With p = 2 (say, query rewriting and query expansion) and q = 2 (say, re-ranking and filtering), that's 2² × 2² = 16 distinct fixed-order configurations — still just one order per selection. Modular RAG adds a further, harder-to-count dimension: which components run, and in what order, can be decided per request rather than fixed at design time, so the same architecture can realize many different configurations across different queries without being redesigned. Neither number is a rigorous complexity bound — it's an illustration of exactly why "modular" is the right word: composability multiplies the space of realizable pipelines, not just the count of optional steps.

11
CONCRETE USE

Four cards: a clean fit, a boundary case, a counterexample, and a mistake

CLEAN FIT

Concept 06's Oracle assistant, correctly labeled

A complete, working baseline that happens to be naive RAG's exact definition — not an unfinished system.

BOUNDARY CASE

A small deduplication step on retrieved chunks

Does removing duplicates before generation count as a "post-retrieval step"? By this concept's criterion, yes — any step inserted between retrieval and generation makes the fixed sequence advanced RAG's shape, regardless of how small the step is.

COUNTEREXAMPLE

A modular codebase that always runs steps in the same order

Modular code organization is not the same claim as a modular pipeline — if the running system never actually varies which steps execute or in what order, it is naive or advanced RAG by whichever steps it has, not modular RAG.

MISTAKE TO AVOID

Labeling by framework instead of by structure

Building a pipeline in LangGraph doesn't make it modular RAG, and a plain script doesn't make it naive RAG — the classification depends on the pipeline's own structure, not which tool built it.

CODE

The three-way classifier, from scratch

PYTHON · CLASSIFY A PIPELINE DESCRIPTION AS NAIVE, ADVANCED, OR MODULAR 
def classify_rag_shape(has_pre_retrieval, has_post_retrieval, is_composable):
    # Composability dominates the classification -- it is a structural
    # claim, independent of how many pre/post steps happen to exist.
    if is_composable:
        return "modular"
    if has_pre_retrieval or has_post_retrieval:
        return "advanced"
    return "naive"


# The six s10 rows, as boolean facts about each pipeline
pipelines = [
    dict(has_pre_retrieval=False, has_post_retrieval=False, is_composable=False),  # Concept 06's assistant
    dict(has_pre_retrieval=True,  has_post_retrieval=False, is_composable=False),  # + rewriting only
    dict(has_pre_retrieval=False, has_post_retrieval=True,  is_composable=False),  # + re-ranking only
    dict(has_pre_retrieval=True,  has_post_retrieval=True,  is_composable=False),  # + both, fixed order
    dict(has_pre_retrieval=False, has_post_retrieval=False, is_composable=True),   # swappable retrievers only
    dict(has_pre_retrieval=True,  has_post_retrieval=True,  is_composable=True),   # rewriting + re-ranking + swappable
]

for p in pipelines:
    print(classify_rag_shape(**p))
# naive
# advanced
# advanced
# advanced
# modular
# modular

assert classify_rag_shape(False, False, False) == "naive"
assert classify_rag_shape(True, False, False) == "advanced"
assert classify_rag_shape(False, False, True) == "modular"
13
ECOSYSTEM

Where this taxonomy comes from

Gao, Xiong, Gao, Jia, Pan, Bi, Dai, Sun, Wang & Wang (2023), a widely cited RAG survey, is the direct source of the naive/advanced/modular three-way split this concept teaches — it defines naive RAG as the basic retrieve-then-generate process, advanced RAG as adding pre-retrieval and post-retrieval optimizations, and modular RAG as a more flexible, composable framework. Gao, Xiong, Wang & Wang (2024), Modular RAG, develops the third shape in much more depth, reframing RAG systems as LEGO-like reconfigurable modules with defined routing and orchestration patterns — exactly what Module 23 and later modules build on, and exactly what this concept only names.

DIAGNOSIS

Failure modes — of using the taxonomy itself

MISLABELING

Calling a system "advanced" because it feels sophisticated

The label depends on Section 05's exact criteria — a pre- or post-retrieval step present — not on general complexity or polish.

MARKETING RETROFIT

Applying "modular" to justify a design choice after the fact

Modularity is a structural, checkable property of the running pipeline — Section 12's classifier either confirms it or it doesn't.

FORCED PROGRESSION

Assuming every system must eventually become modular

This concept names three shapes; it does not claim one is always the correct destination — that depends on requirements outside this concept's scope.

IGNORED COST

Treating modularity as free flexibility

Section 15's cost column is real — composability has to be built, routed, and tested, not just declared.

REALITY

Production implications, at introductory depth

  • Track which named shape a system actually is, so later evaluation (Module 18) and cost analysis (Module 19) compare against the correct baseline instead of an assumed one.
  • Treat naive → advanced → modular as an available path, not a mandatory one — Section 16's "forced progression" failure mode is a real risk to avoid.
  • The label is a communication tool for engineers and stakeholders, not a target metric to optimize toward on its own.

FEEDBACK

Solution and teach-back

Open one defensible reasoning pattern
There is exactly one pre-retrieval step (the rewriting), no post-retrieval step, and no swappable or composable components — the retriever and the order never vary. By Section 12's classifier, is_composable is false and has_pre_retrieval is true, so the pipeline is advanced RAG. The deciding fact is the presence of the pre-retrieval step alone; the absence of swapping rules out modular RAG regardless of anything else in the description.

Teach-back: explain, in your own words, why "no swapping happens" is enough by itself to rule out modular RAG, even before checking whether any pre- or post-retrieval steps exist.

CAREER PRACTICE

Interview questions

How would you explain the difference between advanced RAG and modular RAG to a teammate who conflates them?
Advanced RAG still runs in one fixed order every time, just with more steps in it; modular RAG's defining property is that which components run, and in what order, can change per request — a structural difference, not a difference in step count.
A stakeholder says a system is "modular" because it's built with LangGraph. How do you evaluate that claim?
Check whether the running pipeline actually varies which components execute or their order across requests — the framework used to build it doesn't determine the classification; the observed behavior of the pipeline does.
Design question: given a naive RAG baseline, what is the minimal change that would make it advanced RAG, and what would additionally be required to make it modular RAG?
Adding a single pre- or post-retrieval step (e.g. re-ranking) makes it advanced RAG. Reaching modular RAG additionally requires making stages swappable and routable — e.g. a router deciding per request which retriever or re-ranker, if any, actually runs.
