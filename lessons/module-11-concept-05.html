MODULE 11 · CONCEPT 05

Concepts 01-04 embedded a document.
This one embeds a question.

Every concept in this module so far has stayed on the offline path: hash, chunk, embed, and persist a document that already existed. This concept is the first to go online -- a user's question gets embedded through the same shared encoder, with a different prefix, and that single query vector is compared against every persisted vector from Concept 04 to produce a ranked candidate set, not a stored row.

PROGRESSIVE BEGINNER CORE

A question has to become a vector before it can be compared to anything

Concepts 01-04 answered "what happens to a document before a user ever asks anything." This concept answers the very next question: the instant a user types something, what happens to their question before the system can find anything relevant to it?

01 · CONCEPT FIRST

Same translator, different sentence

The chunk-embedding stage (Concept 03) and this concept both run text through the exact same all-MiniLM-L6-v2 model -- no separate "query model" exists. What changes is which sentence goes in (a user's question instead of a document passage) and a one-word label attached to it. What comes out the other end is a ranked list of candidates: chunks the search thinks are relevant, not an answer.

First memory: retrieval doesn't answer the question -- it finds candidates. Answering is a later stage's job.
02 · WHY IT EXISTS

Concept 04 persisted vectors that nobody has read back yet

Without this concept, Concept 04's committed rows just sit there -- durable, but never queried. This concept is the first to actually call the query(vector, k) half of Module 10 Concept 14's own adapter interface, closing the loop between "a document's vector is safely stored" and "a user's question can find it."

03 · CONCRETE EXAMPLE

"How long is the grace period?" against four stored chunks

A user asks a question about the doc_9f21 grace-period policy that Concepts 02-04 chunked, embedded, and persisted. That question gets embedded into the same vector space as chunk c007 (the grace-period chunk itself) and three unrelated chunks -- billing cycle, late fee, refund policy. Comparing the question's vector to all four produces a ranked order, computed and verified below: c007 first by a wide margin, the other three trailing far behind.

04 · TECHNICAL MECHANISM

Embed, then search -- two calls, not one

Step 1 -- embed the query. The question text goes through the shared encoder with a "query: " prefix (Module 08 Concept 08's convention, mirroring the "passage: " prefix Concept 02 attaches to documents). Step 2 -- search. That single vector is handed to query(vector, k) (Module 10 Concept 14), which runs a similarity comparison against every persisted vector from Concept 04 and returns the top k as a candidate set -- chunk ids and scores, not generated text.

05 · ARCHITECTURE / FLOW

Where this sits in the fixed skeleton

Concept 04 — persisted the document's vector→ THIS concept — embeds the question, searches, returns candidates→ Concept 06 — turns candidates into evidence
06 · IMPORTANT DISTINCTIONS

"Candidate" is not "answer," and "retrieval" is not "generation"

A candidate set is a ranked list of chunk ids and similarity scores -- nothing has been read for correctness yet, and nothing has been handed to a language model. Bi-encoder asymmetry (Module 08 Concept 03) is the reason this works at all: the query and the document were embedded by two separate calls to the same shared model, with no cross-attention between them, which is exactly what makes it possible to embed the query once and compare it against millions of pre-computed document vectors instead of re-running the model per pair.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Retrieval already answers the question."

False -- retrieval returns candidates ranked by similarity; nothing has verified any of them are actually correct or sufficient. That's Concept 06's job.

"The query gets embedded the same way as a document, prefix and all."

Not quite -- same model, same vector space, but a different prefix ("query: " vs. "passage: "), per Module 08 Concept 08's own convention.

Readiness check before moving on

Name the two-step online mechanism

Embed the query (same shared model, "query: " prefix), then call query(vector, k) against the persisted index.

Explain why one shared model can do both jobs

Bi-encoder asymmetry -- query and document are embedded independently, no cross-attention, so document vectors can be pre-computed once and reused for every future query.

Distinguish a candidate set from an answer

Ranked chunk ids and similarity scores -- correctness and sufficiency are checked later, not here.

Teach-back questions

  1. Why does a query get a different prefix than the documents it's being compared against, if both go through the same model?
  2. What specifically does query(vector, k) return -- and what does it not return?
  3. If chunk c007 scores 0.9405 and the next-best candidate scores 0.2261, what does that gap tell you about how confident the match is?

01
ORIENTATION

The first Module 11 concept to touch a live query

This is the fifth concept of Module 11 (5/11), and the first to leave the offline path entirely. Concepts 01-04 covered a document's own journey -- ingest, chunk, embed, persist -- and never once involved a user's actual question. This concept opens the online path: a question comes in, gets embedded, and gets compared against everything Concept 04 already made durable. Every mechanism cited here (bi-encoder asymmetry, the prefix convention, the adapter interface, ANN over-fetch math) comes from Modules 08-10 and is reused, not re-derived.

02
PRECISION

Query embedding, retrieval, and candidate search -- three separate words

TermDefinition
Query embeddingRunning the user's question text through the shared encoder with a "query: " prefix to produce one vector
RetrievalThe act of comparing that query vector against a persisted index to find similar vectors
Candidate searchThe specific call that returns the top-k ranked results -- ids and similarity scores, not text answers
03
DEPENDENCIES

What this concept reuses instead of re-deriving

Bi-encoder asymmetry (Module 08 Concept 03), the query/document prefix convention (Module 08 Concept 08), the ANN mechanisms and recall/latency trade-off table (Module 09 Concepts 01-06), the tenant-filter over-fetch fact (Module 09 Concept 07), and the store-agnostic adapter interface (Module 10 Concept 14) are all cited below at the exact numbers already established in those concepts -- none of them are recomputed here.

04
EVIDENCE + CONTROL

Bi-encoder asymmetry, cited

Module 08 Concept 03 establishes that a bi-encoder embeds the query and the document with two independent calls to the same shared model -- no cross-attention between them. That's the entire reason document vectors can be computed once at ingestion (Concept 02-03) and reused for every future query without re-running the model per pair; a cross-encoder could score a query-document pair more accurately but would have to re-run for every single candidate, which doesn't scale past a handful of documents.

05
ARCHITECTURE

Where the query vector goes to be compared

The query vector never gets written to Module 10 Concept 03's five-table schema -- it's a transient, single-use vector that exists only for the duration of one search call. What it's compared against are the already-persisted rows in the embeddings table (Concept 04's own subject), via the adapter's query(vector, k) method (Module 10 Concept 14).

06
MECHANISM

The concrete SQL this call runs, cited

SQL · ORACLE'S OWN COSINE-DISTANCE SEARCH (Module 10 Concept 05) 
SELECT chunk_id, VECTOR_DISTANCE(embedding, :query_vector, COSINE) AS dist
FROM embeddings
ORDER BY dist ASC
FETCH FIRST :k ROWS ONLY;
SQL · PGVECTOR EQUIVALENT (Module 10 Concept 11) 
SELECT chunk_id, embedding <=> %(query_vector)s AS dist
FROM embeddings
ORDER BY dist ASC
LIMIT %(k)s;
07
CODE

The adapter call, cited

Module 10 Concept 14's own adapter interface exposes this as one call: store.query(query_vector, k=5). Everything below the interface -- exact-brute-force (Module 09 Concept 01), HNSW (Concept 03), or IVF (Concept 04) -- is an implementation detail the caller doesn't need to know to use it correctly.

08
DISTINCTIONS

Prefix convention: "query: " is not "passage: "

Module 08 Concept 08 establishes the asymmetric prefix convention and its own worked ratio: a 5-token query carries a 6.0x smaller token share than a 40-token passage. The document side (Concept 02 of this module) attaches "passage: " at ingestion; this concept is the first in Module 11 to attach the query-side counterpart, "query: ", at retrieval time. Same encoder, same 384-dimensional output space, different label on the input string.

09
WORKED EXAMPLE

"How long is the grace period?" against four persisted chunks

Continuing this course's own doc_9f21 grace-period corpus: a user asks "query: how long is the grace period?". Four chunks are already persisted from Concepts 02-04 -- c007 (the grace-period chunk itself) plus three unrelated chunks from the same policy document: billing cycle, late fee, and refund policy. The real 384-dimensional all-MiniLM-L6-v2 vectors from Concept 03 are not re-typed here; instead this section uses a small 6-dimensional stand-in, one axis per topic, so the ranking arithmetic is fully hand-checkable while still preserving the same relative-similarity shape a real embedding would produce. This stand-in is flagged explicitly: it demonstrates the ranking mechanism, not the real model's actual output.

10
CODE

Cosine ranking, computed via node

NODE · COSINE SIMILARITY OVER TOY 6-DIM VECTORS 
function dot(a,b){return a.reduce((s,x,i)=>s+x*b[i],0)}
function norm(a){return Math.sqrt(dot(a,a))}
function cos(a,b){return dot(a,b)/(norm(a)*norm(b))}

const q = [1,0,0,0,0,0.2];               // "how long is the grace period?"
const candidates = {
  c007_grace: [0.9,0.1,0,0,0.3,0.1],
  c_billing:  [0.2,0.2,0.9,0,0.1,0.1],
  c_latefee:  [0.1,0.9,0.2,0,0.2,0.1],
  c_refund:   [0,0,0.1,0.9,0.2,0.1],
};

Object.entries(candidates)
  .map(([id, v]) => [id, cos(q, v)])
  .sort((a, b) => b[1] - a[1])
  .forEach(([id, s]) => console.log(id, s.toFixed(4)));

12
MATHEMATICS

Cosine similarity, restated as the equation actually run

cos(q, v) = (q · v) / (‖q‖ × ‖v‖)

This is the identical formula behind both VECTOR_DISTANCE(...,COSINE) (Oracle) and <=> (pgvector) cited in Section 06 -- those operators return a distance (1 − cosine similarity for normalized vectors), which is why the SQL in Section 06 sorts ascending while the table above sorts descending on similarity itself. Same underlying number, opposite sort direction depending on which side of the subtraction you're looking at.

13
EVIDENCE + CONTROL

What top_k actually controls

k is a hard cutoff on count, not on quality -- it returns exactly the top k scores regardless of how weak the lowest one is. At k=1 in the worked example, only c007 comes back. At k=4, refund policy (cosine 0.0210, barely related) comes back too, simply because there were only four candidates to rank in the first place. This is the same "count vs. quality" distinction the lab in Section 16 makes interactive.

14
CONCRETE USE

Over-fetch: when k alone stops being enough, cited

Module 09 Concept 07 establishes that a metadata filter applied after the similarity search (post-filtering) can silently discard true matches before they're ever returned -- on a 20-chunk corpus with 30% tenant selectivity, returning a real k=5 requires over-fetching to top-17, a 3.4x multiplier, not top-5. That fact is cited here exactly as originally computed, not re-derived: if this concept's own worked example added a tenant filter on top of the four candidates, the same "fetch more than k, then filter" logic would apply before Concept 06 ever sees the result.

MECHANICS

The lab's own data model

All four candidates and their fixed cosine scores (Section 11's own verified numbers) are held in one array, pre-sorted descending. Each top_k pick simply slices that same fixed array at a different length and re-renders the chip row -- no re-scoring happens on click, because the ranking itself doesn't change when k changes; only how much of it gets kept does.

18
MECHANICS

The lab's own JS logic

A single renderCandidates function toggles the active button, rebuilds the rank-chip-row with .sorted-in on kept chips (reusing the sortIn225 keyframe already established in Module 10 Concept 01's own sorting lab) and .excluded on discarded ones, then rewrites the callout text and class -- all driven from the same small facts object, no new CSS classes anywhere.

19
CONCRETE USE

What each pick teaches

TOP_K = 1

The tightest, safest cut

Only the strongest match returns -- best when the query is specific and a wrong candidate would be costly.

TOP_K = 2

A hedge against gaps

Keeps one real backup candidate in case the top match turns out to be insufficient at the evidence-selection stage.

TOP_K = 4

The full corpus, weak tail included

Demonstrates concretely that k alone doesn't guard against low-quality matches -- refund policy at 0.0210 still comes back.

CORRECTION

Misconceptions

Incorrect beliefCorrection
Retrieval returns the answer to the questionFalse -- it returns a ranked candidate set of chunk ids and scores; nothing has verified correctness yet.
The query needs its own separate embedding modelNot quite -- same shared bi-encoder as the document side, just a different prefix ("query: " vs. "passage: ").

22
CAREER PRACTICE

Interview questions

Conceptual: why can a single shared encoder embed both queries and documents without a separate query-specific model?
Bi-encoder asymmetry -- the query and document are embedded by two independent calls to the same model with no cross-attention between them, so the same encoder and vector space serve both sides; only the input prefix differs.
System design: a RAG system returns a candidate set with a huge score gap between rank 1 and rank 2 for some queries, and a tiny gap for others. What does that gap tell you, and what would you do differently in each case?
A large gap signals one confident, unambiguous match; a small gap signals multiple plausible candidates. The system could route small-gap queries to a stricter downstream evidence check or a re-ranking step, while large-gap queries can move forward with less scrutiny.
