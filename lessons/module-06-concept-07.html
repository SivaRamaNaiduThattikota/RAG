MODULE 06 · CONCEPT 07

Same document.
Different day, different words.

Concept 06 resolved copies of the same content that exist RIGHT NOW, side by side. This concept covers a different axis: one document's own content changing ACROSS TIME. A refund policy edited from a 30-day window to a 45-day window is still, in every meaningful sense, the same policy — but its content hash from Concept 06 says otherwise every single time. This concept gives it a stable doc_id that survives the edit, plus a version_number, content hash, and effective_at/superseded_at timestamp per revision, so a question like "what did this policy say on a given date" has a real answer.

01 · CONCEPT FIRST

A number that survives the edit, plus a timestamp for each revision

THIS CONCEPT

A stable doc_id assigned once and never reassigned, plus a version_number, content hash and effective_at/superseded_at timestamp attached to every revision of that same document.

NOT THIS CONCEPT

Concept 06's same-content-at-once dedup (R1/R2/R3 all coexisting right now) and Concept 08's full provenance/lineage/audit trail — both different problems, named only as neighbors here.

First memory: the doc_id is the thread that runs through every version of one document. The content hash is not that thread — it's expected to change on every single edit, or there would be nothing to version in the first place.
02 · WHY IT EXISTS

Without a stable ID, an edited document looks brand new every time

A policy gets edited. Its content hash from Concept 06 changes completely — that's the avalanche effect working exactly as designed. But if nothing links the old hash to the new one, the pipeline treats the edited document as a totally unrelated, brand-new record. Old and new evidence both sit in the index with no connection between them, retrieval can surface either one with no sense of which is current, and nothing can answer a question like "what did the refund policy say on the day this ticket was filed." This concept exists to give a document an identity that survives its own edits, so questions like that have a real answer.

03 · CONCRETE EXAMPLE

The refund policy Concept 03 already raised — now with a stable ID

Concept 03 already described this exact case: a refund policy that said "30 days," was superseded by a version that says "45 days," changed by "a commit message from fourteen months ago." This concept gives that same policy a persistent identity: doc_id = POLICY-REFUND-001, assigned once and never reassigned.

VERSION 1 · SUPERSEDED

"…within 30 days of purchase."

Effective 2024-11-02, superseded 2025-06-18 — a 228-day lifespan as the current version.

VERSION 2 · CURRENT

"…within 45 days of purchase."

Effective 2025-06-18, no superseded_at — 431 days current as of today, 2026-08-23.

Same doc_id both times. Two completely different content hashes. That's not a contradiction — it's the point.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"The hash is the identity."

False — the hash is guaranteed to change on every edit (Concept 06's avalanche effect), or there would be nothing left to version. The doc_id has to live outside the hash entirely.

"Delete superseded versions — only the latest one matters."

False whenever an audit or point-in-time question matters. Superseded versions get tombstoned, not deleted, echoing Concept 06's own handoff pattern.

"You need Concept 01's full authority ranking to find the current version."

False — within one document's own history, recency (or version_number) alone is enough. Concept 01's full type+recency ranking is for choosing across different SOURCES, not for picking a version within one document.

09 · WHAT YOU SHOULD UNDERSTAND

Readiness check before moving on

Identity is not the hash

doc_id stays byte-identical across every edit; the content hash is expected to change every single time.

Why the hash can't do the hash's job AND identity's job

Hashing is built for the avalanche effect — there is nothing partial or stable about it to hang a version history on.

Five fields are enough

doc_id, version_number, content_hash, effective_at/superseded_at and status are sufficient to answer "what was current on date X."

Recency alone decides within one document's own history

Concept 01's full auth(s) formula is for ranking across different sources, not for finding the current version of one document.

04
INTUITION

A passport number, renewed again and again

A passport number stays exactly the same across every renewal, even though the photo and the expiry date — the content — change every single time. Nobody argues a renewed passport belongs to a different person just because the photo changed; the number is what carries identity forward through every renewal. A document's doc_id plays exactly that role: it is the number that survives, while the content hash is the photo that is expected to change.

Analogy boundaryThe passport analogy explains why identity has to be kept separate from content in the first place. It doesn't explain how an "as of" query actually resolves which version was current on a given date — Section 09 gives that formally.

06
MECHANISM

Assign once, compare on every re-ingestion

Assignment lane — assign doc_id exactly once, at first ingestion. Every later re-ingestion of the same source reuses it; it is never regenerated.
Change-detection lane — on re-ingestion, recompute the content hash and compare it to the current version's hash for that same doc_id, using Concept 06's exact-hash check scoped to one document instead of the whole corpus.
No-op branch — hashes match: nothing has changed since the last ingestion, and no new version is created.
New-version branch — hashes differ: append version_number+1 with the new hash and effective_at = now, then set the prior version's superseded_at = now and status = SUPERSEDED.

09
MATHEMATICS

Why identity is invariant and the hash never is

Formalize a version history as an ordered sequence V = (v1, …, vn) that all share one doc_id. Define current(doc_id, t) as the vi such that effective_at(vi) ≤ t < superseded_at(vi) — or vn itself, if vn has no superseded_at set, meaning it is still current. doc_id is invariant across every i in that sequence: it holds exactly the same value for v1 through vn. content_hash(vi), by contrast, is guaranteed NOT to be invariant — if h(norm(vi)) equaled h(norm(vi+1)), there would have been nothing to version in the first place; the change-detection lane in Section 06 would have taken the no-op branch instead.

11
CONCRETE USE

Two clean fits, a boundary case, a mistake

CLEAN FIT

A compliance policy edited quarterly

Point-in-time audit questions — "what did this say on the day of the incident" — need exactly the effective_at/superseded_at metadata this concept assigns.

CLEAN FIT

A wiki page edited repeatedly under one page ID

The page's own ID is the doc_id; every edit becomes a new version without losing the page's continuity.

BOUNDARY CASE

A document moved or renamed with unchanged content

Same identity or a new one? Resolved by a source-system-native key (a stable database ID, a ticket number), never by file path or URL alone.

MISTAKE TO AVOID

Assigning a brand-new doc_id on every re-ingestion

Check the hash against the existing doc_id's current version first — an unchanged source should never mint a fresh identity for content that hasn't actually changed.

12
CODE

A version store and an as-of lookup, from scratch

PYTHON · NO LIBRARIES BEYOND HASHLIB 
import hashlib

store = {}  # doc_id -> list of version dicts, oldest first

def content_hash(text):
    return hashlib.sha256(text.encode("utf-8")).hexdigest()

def add_version(doc_id, text, now):
    h = content_hash(text)
    versions = store.setdefault(doc_id, [])
    if versions and versions[-1]["hash"] == h:
        return versions[-1]  # no-op: nothing actually changed
    if versions:
        versions[-1]["superseded_at"] = now
        versions[-1]["status"] = "SUPERSEDED"
    version = {
        "version_number": len(versions) + 1,
        "hash": h,
        "effective_at": now,
        "superseded_at": None,
        "status": "CURRENT",
    }
    versions.append(version)
    return version

def current_version_as_of(doc_id, t):
    for v in reversed(store[doc_id]):
        if v["effective_at"] <= t and (v["superseded_at"] is None or t < v["superseded_at"]):
            return v
    return None

v1 = add_version("POLICY-REFUND-001",
    "Refund requests must be submitted within 30 days of purchase.", "2024-11-02")
v2 = add_version("POLICY-REFUND-001",
    "Refund requests must be submitted within 45 days of purchase.", "2025-06-18")

assert v1["hash"] != v2["hash"]
assert current_version_as_of("POLICY-REFUND-001", "2025-01-01")["version_number"] == 1
assert current_version_as_of("POLICY-REFUND-001", "2026-08-23")["version_number"] == 2

ECOSYSTEM

The same mechanism, in real systems

Slowly Changing Dimension Type 2 in data warehousing is the direct real-world implementation of this concept's identity+versioning mechanism: a surrogate key (this concept's doc_id) stays fixed while effective-date and end-date columns track each revision, exactly like effective_at/superseded_at here. Git's commit history extends Concept 03's own mention of "a commit message from fourteen months ago" — every commit is a per-revision timestamp and message attached to a file that keeps one identity across every change. Cloud object-store versioning (keeping every past version of an object under one key) is a named, not-derived, industry parallel to the same underlying idea.

15
CONTRAST

Stable identity vs. pure content-addressable storage

ApproachStrengthWeakness
Identity + versioning (this concept)Supports as-of queries; "the same thing, changed" stays a meaningful statementExtra bookkeeping — a version store, timestamps, and a change-detection check on every re-ingestion
Pure content-addressable storageSimple — the hash IS the address, no version store needed at allNo persistent identity by design; an edit produces an unrelated new object with nothing linking it to the old one

Decision framework: use content-addressing when "the same thing, changed" genuinely isn't a concept you need — pure immutable blobs, cache entries. Use stable identity whenever "what changed" or "what was true then" matters, which is exactly this concept's case.

16
DIAGNOSIS

Failure modes

UNSCOPED DEDUP

Near-duplicates fed in as if they were new versions of an unrelated doc_id

Concept 06's dedup must run scoped per doc_id first — otherwise a near-duplicate of a completely different document gets mistaken for a new version.

CLOCK SKEW

As-of query results silently corrupted

If effective_at/superseded_at come from clocks that disagree, "what was current on date X" can return the wrong version, or none at all.

ORPHANED DOC_ID

No retirement marker when a source is deleted

A doc_id left with no explicit "retired" status looks like it's still tracking a live source, when the source is actually gone.

REALITY

Production implications

  • Retaining every superseded version has a real storage cost — it's a genuine trade-off against the value of point-in-time audit answers, not a free default.
  • The index should default to serving the current version for ordinary retrieval, while still supporting historical/as-of queries when they're explicitly asked for.
  • Freshness and how quickly a new version propagates ties directly to Module 19's freshness SLOs, named forward-only here.
19
RECALL

Knowledge check

Why can't a document's content hash also serve as its stable identity?
A cryptographic hash is designed to change completely on any content change (the avalanche effect) — if it were also the identity, every edit would mint a brand-new, unrelated document with no link to its own past.
Why does the 14-month gap between v2's effective date and today matter here?
It's an independent numeric check against Concept 03's own claim that the 45-day rule changed "a commit message from fourteen months ago" — the two concepts' numbers line up because they describe the same underlying policy history.
Why must Concept 06's dedup be scoped to one doc_id before this concept's versioning runs?
Otherwise a near-duplicate of a completely different document could be mistaken for a new version of an unrelated doc_id — dedup has to resolve "is this really the same document" before versioning asks "has this document's content changed."

23
CAREER PRACTICE

Interview questions

Why can't a content hash double as a document's stable identity?
A hash is designed so any content change produces a completely unrelated output (the avalanche effect) — using it as identity would mean every edit mints a brand-new, unlinked document, which defeats the entire purpose of tracking a version history.
How does a Type 2 Slowly Changing Dimension relate to this concept?
It's the direct data-warehousing implementation of the same idea: a surrogate key stays fixed across changes (this concept's doc_id) while effective-date and end-date columns track each revision, exactly like effective_at/superseded_at here.
Why does deduplication need to be scoped to one doc_id before versioning runs?
Otherwise a near-duplicate of an entirely different document could be misread as a "new version" of an unrelated doc_id — dedup has to confirm sameness of identity before versioning asks whether that same document's content has changed.
How would you design an as-of query for a document with several stored versions?
Store effective_at and superseded_at per version, then find the version vi where effective_at(vi) ≤ t < superseded_at(vi) for the requested timestamp t — or the latest version if it has no superseded_at set, meaning it's still current.
