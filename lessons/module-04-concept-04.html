MODULE 04 · CONCEPT 04

Euclidean and other
distance functions.

Concept 03 gave two vectors a similarity score built from the angle between them — cosine similarity, where a higher number means more alike. This concept gives the complementary family: distance functions, where a lower number means more alike. Euclidean distance is not a new formula — it is Concept 02's L2 norm (cited, not re-derived), computed for the first time on a difference vector instead of on a single vector's own coordinates. Manhattan distance does the same with the L1 norm, as a contrast. The concept closes on a fact neither prior concept could state alone: for vectors already normalized to length one, Euclidean distance and cosine similarity always rank nearest neighbors identically.

01 · CONCEPT FIRST

Euclidean and Manhattan distance — the family where lower means more alike

EUCLIDEAN DISTANCE

The straight-line gap between two vectors' endpoints. ‖A-C‖₂ = ‖(3,4)-(4,3)‖₂ = ‖(-1,1)‖₂ = √2 ≈ 1.41 — one number, from two vectors.

MANHATTAN DISTANCE

The grid-step gap instead — add up each component's absolute difference. ‖A-C‖₁ = |-1| + |1| = 2.

SAME FORMULA, NEW INPUT

Both are Concept 02's L2 and L1 norms — nothing new in the formula itself. What's new is the input: the norm of the difference vector A - C, not of A or C alone.

LOWER = CLOSER

Distance is the inverse-flavored idea from Concept 03's similarity: 0 means identical, and there is no upper bound — two vectors can be arbitrarily far apart.

USES CONCEPT 02'S NORM

Every distance computed here reuses Concept 02's exact norm formulas — only the input, a difference vector, is new.

NOT YET: PROBABILITY

Turning scores into likelihoods, or reasoning about uncertainty given evidence, is Concept 05's job — not today's.

First memory: Euclidean distance is Concept 02's L2 norm applied to the difference between two vectors; Manhattan distance is the L1 norm applied the same way. Lower always means closer — the opposite direction from Concept 03's cosine similarity.
02 · WHY IT EXISTS

Cosine similarity ignores something distance functions were built to measure

Concept 03 answered "which direction does this vector point in?" precisely, and deliberately threw away magnitude to do it. But a direction-only answer can miss real information: two vectors pointing in nearly the same direction can still sit very far apart in absolute terms, and a system that only ever asks "how aligned?" has no number for that. Euclidean distance answers a different, equally valid question: how far apart are these two vectors' endpoints, treating their full geometry — direction and magnitude together — as one combined gap?

WITHOUT A WAY TO MEASURE THE GAP

Ticket A and ticket B point in exactly the same direction (cosine similarity 1.0), but direction-only similarity has no number for the fact that B describes a much longer, more detailed ticket.

WITH EUCLIDEAN / MANHATTAN DISTANCE

The straight-line or grid-step gap between A and B is a real, measurable number — 5, in this case — that direction-only similarity can never report.

03 · CONCRETE EXAMPLE

Same three tickets, a completely different ranking

Reuse Concept 03's exact three tickets: A = (3, 4), B = (6, 8), C = (4, 3) — "refund" and "billing" mention counts. Concept 03 found cosine(A, B) = 1.0 and cosine(A, C) = 0.96, ranking B as more similar to A than C is. Distance asks the same three tickets a different question.

A · B EUCLIDEAN DISTANCE

‖A-B‖₂ = ‖(-3,-4)‖₂ = √(9+16) = √25 = 5.

A · C EUCLIDEAN DISTANCE

‖A-C‖₂ = ‖(-1,1)‖₂ = √(1+1) = √2 ≈ 1.41 — much closer than A and B, even though cosine similarity ranked B ahead.

A · B MANHATTAN DISTANCE

‖A-B‖₁ = |-3| + |-4| = 7.

A · C MANHATTAN DISTANCE

‖A-C‖₁ = |-1| + |1| = 2.

By direction alone (Concept 03), B was the better match. By actual distance, C is the closer one — nearly four times closer than B. Neither ranking is wrong; they answer different questions about the same three tickets.

04 · TECHNICAL MECHANISM

Subtract first, then reuse Concept 02's norm

EUCLIDEAN DISTANCE

L2 norm of a difference

‖v-w‖₂ = √((v₁-w₁)² + … + (vₙ-wₙ)²) — Concept 02's L2 norm, computed on the difference vector v-w.

MANHATTAN DISTANCE

L1 norm of the same difference

‖v-w‖₁ = |v₁-w₁| + … + |vₙ-wₙ| — Concept 02's L1 norm, same difference vector.

DIFFERENCE VECTOR FIRST

One extra step, before any norm

Both formulas need v-w computed first — subtract matching components before either norm is taken.

NO UPPER BOUND

Unlike cosine similarity's [-1, 1]

A distance can be 0 (identical vectors) or grow without limit — there is no ceiling, unlike Concept 03's bounded score.

05 · ARCHITECTURE / FLOW

A second, unrelated way to compare two vectors

Concept 02 — one vector's own norm↓Concept 03 — two vectors, compared by direction↓This concept — two vectors, compared by distance↓Concept 05 — probability, next

Concept 03 and this concept both take two vectors as input, but they produce fundamentally different kinds of number from the same inputs — one bounded and direction-only, the other unbounded and magnitude-sensitive. Later, when a vector index is built (Module 09-10, forward reference), one of these two families — or dot product — is chosen as the index's metric, fixed for the whole index.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Distance and similarity are just opposite versions of the same number."

Not quite — flipping a similarity score's sign or subtracting it from 1 does not generally produce a valid distance, and the reverse isn't generally true either. They're different formulas that often, not always, agree on ranking.

"Euclidean distance can be negative when two vectors point in different directions."

Never — it's a square root of a sum of squares, always ≥ 0. It equals zero only when the two vectors are identical.

"Manhattan distance is just a rough approximation of Euclidean distance."

It's an exact, well-defined distance in its own right — Concept 02's L1 norm applied to a difference — not an approximation of anything. It measures a genuinely different kind of path.

"If cosine similarity ranks B ahead of C, distance will rank them the same way."

Section b03 disproves this directly: cosine ranks B ahead, raw Euclidean distance ranks C ahead. They're only guaranteed to agree once both vectors are normalized.

04
INTUITION

Two ways to measure the gap between two addresses

Picture two street addresses on a city grid. A bird flying between them measures the straight-line gap — Euclidean distance. A pedestrian confined to the streets measures a different gap, walking only along the grid's blocks — Manhattan distance, Concept 02's exact taxicab-norm intuition, now applied to the gap between two addresses instead of to one address's distance from a single starting corner.

Analogy boundaryThe bird and the pedestrian only illustrate which path each formula corresponds to — neither vector is a real address, and nothing here claims one distance is "more correct" than the other.

06
MECHANISM

Tracing both computations on A = (3, 4) and C = (4, 3)

Subtract matching components — A - C = (3-4, 4-3) = (-1, 1).
Square each component (for Euclidean) — (-1)² = 1, and 1² = 1.
Sum the squares, then take the square root — 1 + 1 = 2, √2 ≈ 1.41. That's the Euclidean distance.
Take absolute values instead (for Manhattan) — |-1| = 1, and |1| = 1.
Sum the absolute values — 1 + 1 = 2. That's the Manhattan distance directly, no square root involved.

09
MATHEMATICS

The identity connecting distance and similarity

For vectors v, w ∈ ℝⁿ:

d₂(v,w) = ‖v-w‖₂ = √(Σᵢ(vᵢ-wᵢ)²) d₁(v,w) = ‖v-w‖₁ = Σᵢ|vᵢ-wᵢ| ‖v-w‖₂² = ‖v‖₂² + ‖w‖₂² - 2(v·w) if ‖v‖₂ = ‖w‖₂ = 1: ‖v-w‖₂² = 2 - 2cos θ

The first two lines are direct definitions — Concept 02's norms, computed on v-w. The third line expands the squared distance using nothing but the definition of a dot product of a vector with itself, (v-w)·(v-w) — new algebra this concept owns, even though every symbol in it was defined earlier. The fourth line is the payoff: once both vectors are normalized to length one (Concept 02's exact operation), squared Euclidean distance becomes a strictly decreasing function of cosine similarity (Concept 03's exact quantity) — a larger cosine similarity always means a smaller distance, with no exceptions. That single fact is why, and only why, Euclidean-distance ranking and cosine-similarity ranking always agree once every vector shares the same norm.

11
CONCRETE USE

Four cards: a clean fit, a boundary case, a counterexample, and a mistake

CLEAN FIT

A=(3,4) versus C=(4,3), raw or normalized

Cosine similarity (0.96) and Euclidean distance (1.41 raw, 0.283 normalized) rank this pair the same way relative to A and B either way — direction and distance already agree here without normalizing.

BOUNDARY CASE

v = w exactly

Both distances equal exactly 0 — the only case where either distance is 0, regardless of dimension or magnitude (Section 05).

COUNTEREXAMPLE

A versus B, before normalizing

Cosine similarity ranks B ahead of C (1.00 versus 0.96); raw Euclidean distance ranks C ahead of B (1.41 versus 5.00) — the two rankings disagree until both vectors are normalized.

MISTAKE TO AVOID

"Distance zero and cosine-similarity zero mean the same thing"

They don't — distance 0 means the two vectors are identical; cosine similarity 0 means they're at a right angle, nowhere near identical. Zero has no shared meaning across these two families.

CODE

Euclidean distance, Manhattan distance, and the ranking flip, from scratch

PYTHON · NO LIBRARIES, REUSING CONCEPT 02'S NORMALIZE 
def euclidean_distance(v, w):
    # Section 09 -- Concept 02's L2 norm, computed on the difference vector
    return sum((vi - wi) ** 2 for vi, wi in zip(v, w)) ** 0.5

def manhattan_distance(v, w):
    # Section 09 -- Concept 02's L1 norm, same difference vector
    return sum(abs(vi - wi) for vi, wi in zip(v, w))

def normalize(v):
    # Concept 02, Section 09 -- cited directly, not re-derived
    n = sum(x * x for x in v) ** 0.5
    if n == 0:
        raise ValueError("cannot normalize the zero vector")
    return [x / n for x in v]


A, B, C = [3, 4], [6, 8], [4, 3]

print(euclidean_distance(A, C))                 # 1.4142135623730951
print(euclidean_distance(A, B))                 # 5.0
print(manhattan_distance(A, C))                 # 2
print(manhattan_distance(A, B))                 # 7

A_n, B_n, C_n = normalize(A), normalize(B), normalize(C)
print(round(euclidean_distance(A_n, B_n), 3))   # 0.0
print(round(euclidean_distance(A_n, C_n), 3))   # 0.283

# raw vectors: C is the closer one to A
assert euclidean_distance(A, C) < euclidean_distance(A, B)
# normalized vectors: B is now the closer one -- the ranking flipped
assert euclidean_distance(A_n, B_n) < euclidean_distance(A_n, C_n)
assert abs(euclidean_distance(A_n, B_n) - 0.0) < 1e-9

ECOSYSTEM

Where production code exposes the same two ideas

NumPy computes Euclidean distance directly as numpy.linalg.norm(v - w), or Manhattan distance as numpy.abs(v - w).sum() — both are just Concept 02's norm functions handed a difference array instead of a single vector. SciPy's scipy.spatial.distance.euclidean and .cityblock name the same two functions explicitly. Production vector databases — Pinecone, Qdrant, Milvus, and Oracle AI Database's VECTOR_DISTANCE — all expose a metric parameter at index-build time, typically EUCLIDEAN (L2), COSINE, or DOT (inner product), and that choice is made once for the whole index, not per query.

16
DIAGNOSIS

Failure modes — of computing and using distance

RANKING MISMATCH ON RAW VECTORS

Ranking by raw Euclidean distance when embeddings aren't normalized

Section 11's counterexample: raw distance and cosine similarity can rank the same two candidates in opposite order — a real bug if the system assumes they always agree.

METRIC MISMATCH AT QUERY TIME

Querying a Euclidean-built index as if it were cosine, or vice versa

Section 13's production point: the metric is fixed at index-build time; querying with the wrong assumption silently returns a differently-ranked, not obviously broken, result set.

SQUARED-DISTANCE SHORTCUT MISUSE

Comparing a squared distance to a non-squared threshold

Many systems skip the square root for speed since it doesn't change the ranking — but comparing that squared value against a threshold meant for the un-squared number silently changes which candidates pass.

DISTANCE-ZERO CONFUSED WITH SIMILARITY-ZERO

Treating a distance near 0 the same way as a cosine similarity near 0

Section 11's mistake to avoid: distance 0 is the best possible match; cosine similarity 0 is an unrelated direction. Reading one scale using the other's meaning inverts the interpretation.

17
CORRECTION

Misconceptions

Incorrect beliefCorrection
Distance and similarity are opposite versions of the same underlying numberThey are different formulas that only reliably rank things the same way once every vector is normalized (Section 09) — before that, Section 11 shows them disagreeing outright.
Manhattan distance is a rougher approximation of Euclidean distanceIt's an exact, independently valid distance (Concept 02's L1 norm on a difference vector), not an approximation of the L2 version — the two only coincide when a difference vector has at most one non-zero component.
If two vectors have distance 0, they must also have cosine similarity 0The opposite is true: distance 0 means the vectors are identical, which forces cosine similarity to its maximum of 1, not to 0.
18
REALITY

Production implications, at introductory depth

  • If a vector index is built for Euclidean distance, embeddings need comparable norms for scores to be meaningful across the whole index — the same normalization discipline Concept 02 raised for norms and Concept 03 raised for dot product, applying a third time here.
  • Section 16's squared-distance shortcut is routine in practice: since ranking order is unaffected by the square root, many nearest-neighbor libraries default to comparing squared Euclidean distance and skip the sqrt call entirely for speed.
  • Section 09's derivation is why switching an index from Euclidean to cosine, or the reverse, is not just a preference: on already-normalized embeddings the two produce identical rankings, but on un-normalized ones they can disagree exactly as Section 11 shows.
19
RECALL

Knowledge check

State the Euclidean distance and Manhattan distance formulas for two vectors v and w.
Euclidean: d₂(v,w) = ‖v-w‖₂ = √(Σ(vᵢ-wᵢ)²). Manhattan: d₁(v,w) = ‖v-w‖₁ = Σ|vᵢ-wᵢ|.
Why does normalizing two vectors before computing Euclidean distance make its ranking match cosine similarity's ranking?
For unit vectors, ‖v-w‖₂² = 2 - 2cos θ (Section 09). Since this is a strictly decreasing function of cosine similarity, the vector with the highest cosine similarity to a query always has the smallest normalized Euclidean distance to it, and vice versa — the two rankings cannot disagree once both are computed on unit vectors.
A raw Euclidean-distance ranking and a raw cosine-similarity ranking disagree on the same two candidates. Which one is "wrong"?
Neither. They measure different things — actual combined gap versus direction alone — and are only guaranteed to agree once every vector is normalized (Section 09). Disagreement on raw, un-normalized vectors is expected, not a bug in either formula.

A=(3,4) and B=(6,8): perfect cosine similarity (1.0), yet a raw Euclidean distance of 5 — the farthest pair in this concept's worked example, until both are normalized, when the distance drops to exactly 0.

CAREER PRACTICE

Interview questions

Why might a system that ranks candidates by raw Euclidean distance return different top results than the same system ranking by cosine similarity?
Raw Euclidean distance is sensitive to both direction and magnitude, while cosine similarity ignores magnitude entirely. A candidate that is directionally aligned but has very different magnitude from the query can end up geometrically far away even though it's a strong directional match — Section 11's A/B/C example shows this concretely.
Derive, at a high level, why Euclidean distance and cosine similarity always agree on ranking once every vector is normalized to the same length.
Expanding ‖v-w‖₂² as ‖v‖₂² + ‖w‖₂² - 2(v·w) and substituting ‖v‖₂ = ‖w‖₂ = 1 gives ‖v-w‖₂² = 2 - 2cos θ. Because this is a strictly decreasing function of cosine similarity, minimizing squared Euclidean distance and maximizing cosine similarity are the same optimization once every vector is a unit vector.
Design question: a team wants to switch a vector index from cosine similarity to Euclidean distance to save a normalization step at query time. What would you check first?
Whether the embeddings already stored in the index are normalized to unit length. If they are, Section 09's identity guarantees the two metrics produce identical rankings, so the switch is safe and removes the division step. If they are not, the switch will silently change which candidates rank highest (Section 11), so normalizing every stored embedding first — not just skipping the metric — would be the actual prerequisite.
