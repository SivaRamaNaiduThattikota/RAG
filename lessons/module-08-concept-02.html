MODULE 08 · CONCEPT 02

Concept 01 named the object.
Here's how it actually gets made.

Concept 01 defined an embedding and explicitly deferred both HOW it's produced and HOW it's trained. This concept opens the first deferral: the real forward-pass pipeline an already-trained embedding model runs at inference time. Tokenize, look up a per-token embedding, run a bidirectional transformer encoder's real self-attention over every token against every other token, pool the results into one fixed-size vector. On "The order shipped late," the payoff is concrete: "the," a function word with the weakest signal of its own, moves the FARTHEST under contextualization -- while "shipped," the sentence's dominant content word, moves the LEAST, because it attends 72.67% to itself. And cosine similarity between "shipped" and "late" rises from 0.8159 to 0.9755 -- geometric proof the encoder pulls the two words describing the same event closer together, something no per-word-in-isolation embedding could ever do.

01 · CONCEPT FIRST

Four stages: tokenize, embed, contextualize, pool

THIS CONCEPT

The deterministic forward-pass pipeline an already-trained embedding model runs at inference time: tokenize → look up token embeddings → contextualize via a transformer encoder → pool → one vector.

NOT THIS CONCEPT

How those parameters got learned (Concept 04); which pooling strategy to use (Concept 06); whether queries and documents get embedded differently (Concept 03).

First memory: contextualization uses a separate, content-dependent weight for every token pair -- not one fixed global blend.
02 · WHY IT EXISTS

Concept 01 deferred this on purpose

Concept 01 named the object (v=f(x), θ learned) but explicitly declined to open the mechanism producing v: "this concept does not derive that training procedure... here only the OUTCOME and the CONTRAST matter." This concept opens exactly that deferral -- and closes RAG Module 07 Concept 08's own explicit simplification: its toy contextualize(t)=base(t)+0.5·doc_mean was a stylized stand-in for the real mechanism, now shown for the first time with actual per-token-pair weights.

03 · CONCRETE EXAMPLE

"The order shipped late" -- a function word moves farther than the content word

Four tokens, four illustrative 2D base vectors. Under real contextualization, "shipped" (the sentence's dominant content word) moves LEAST (Euclidean distance 0.2634) because it attends 72.67% to itself. "the" (a function word with the weakest signal of its own) moves FARTHEST (1.4748), spreading its attention almost evenly across all four tokens.

06 · IMPORTANT DISTINCTIONS

Token vs. text, real vs. toy, bidirectional vs. causal

PairingThe real difference
Token embedding vs. text embeddingOne vector per token, pre-context, vs. one vector for the whole input, post-pooling
Real per-token-pair softmax weights vs. Concept 08's toy contextualize()Same word "contextualize," genuinely different mechanism -- learned, content-specific weights vs. one fixed hand-picked blend
Bidirectional encoder attention vs. causal/decoder attentionSame formula, different mask -- a text-embedding encoder typically sees the whole input at once
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Token embeddings are already the final vector."

False -- they're pre-context and one-per-token, not one-per-input.

"Contextualization means every word gets the same fixed blend with the rest of the sentence."

False -- that was Concept 08's own explicitly-labeled simplification. Real weights are content-specific, per token pair.

"Since this uses self-attention it must be the same causal mechanism Module 02 walked through."

False -- real text-embedding encoders are typically bidirectional, with no causal mask.

MATHEMATICS

Attention(Q,K,V) = softmax(QK^T/√d_k)V, with Q=K=V= the token's own base embedding (a real encoder projects each through separate learned W_Q/W_K/W_V matrices first -- simplified away here to expose the aggregation mechanism)

CODE

Attention and mean pooling, from scratch

PYTHON · REUSES MODULE 02 CONCEPT 04'S OWN FORMULA 
import math

def tokenize(text):
    """Whitespace tokenizer -- explicitly simpler than real BPE (Module 02
    Concept 02's job); kept simple to isolate contextualization."""
    return text.lower().rstrip(".").split()

EMBED = {"the": (0.10, 0.10), "order": (2.00, 0.40),
         "shipped": (1.80, 1.90), "late": (0.30, 2.10)}

def dot(u, v):
    return u[0] * v[0] + u[1] * v[1]

def softmax(xs):
    m = max(xs)
    exps = [math.exp(x - m) for x in xs]
    s = sum(exps)
    return [e / s for e in exps]

def attention_contextualize(tokens, embed, d_k=2):
    scale = math.sqrt(d_k)
    out = {}
    for ti in tokens:
        scores = [dot(embed[ti], embed[tj]) / scale for tj in tokens]
        weights = softmax(scores)
        cx = sum(w * embed[tj][0] for w, tj in zip(weights, tokens))
        cy = sum(w * embed[tj][1] for w, tj in zip(weights, tokens))
        out[ti] = (cx, cy)
    return out

def pool_mean(vectors):
    n = len(vectors)
    return (sum(v[0] for v in vectors) / n, sum(v[1] for v in vectors) / n)

tokens = tokenize("The order shipped late.")
contextualized = attention_contextualize(tokens, EMBED)
assert round(contextualized["shipped"][0], 4) == 1.6010
assert round(contextualized["shipped"][1], 4) == 1.7274
pooled = pool_mean(list(contextualized.values()))
assert round(pooled[0], 4) == 1.3842
assert round(pooled[1], 4) == 1.5025

REALITY

Production implications

  • The tokenizer and encoder must be the exact same trained artifact pair -- a mismatched tokenizer produces token IDs the encoder was never trained on, silently.
  • Encoder max-sequence-length truncates long chunks before pooling ever runs, reinforcing why Module 07's chunking discipline exists.
  • Batching multiple texts through one encoder call improves throughput (named only).
19
RECALL

Knowledge check

Why does "the" move farther than "shipped" under contextualization?
"The" has no dominant neighbor to lock onto, so its attention spreads nearly evenly across all four tokens, pulling its contextualized position noticeably away from its base position. "Shipped" attends 72.67% to itself, so its contextualized position stays close to where it started.
Why is a text-embedding encoder typically bidirectional rather than causal?
A text embedding is meant to summarize a whole, already-complete input -- there's no reason to hide later tokens from earlier ones the way a causal/decoder model must during generation.
Why isn't a token embedding, by itself, already a usable text embedding?
It's pre-context (produced before contextualization) and one-per-token -- a retrieval system needs one fixed-size vector per chunk or query, which requires pooling across all the contextualized token vectors first.

CAREER PRACTICE

Interview questions

Conceptual: why isn't a token embedding yet a text embedding?
A token embedding is produced before contextualization and exists one-per-token; a text embedding is one fixed-size vector for the whole input, produced only after pooling across all the contextualized token vectors.
Mathematical: state the Attention(Q,K,V) formula and what the Q=K=V simplification means here.
Attention(Q,K,V) = softmax(QK^T/√d_k)V. Q=K=V=the token's own base embedding is a stated simplification -- a real encoder first projects each token through separate learned W_Q/W_K/W_V matrices before running the same formula.
Coding: implement attention_contextualize() and pool_mean().
attention_contextualize computes scaled dot-product scores, softmaxes them per token, and takes the weighted sum of all base vectors; pool_mean averages the resulting contextualized vectors -- Section 12 gives the full from-scratch implementation with matching asserts.
Debugging: a "semantic search" demo returns near-identical scores for very different sentences. What's the first thing to check?
Whether pooling is actually running at all, or whether raw token embeddings are being compared directly -- comparing the wrong-shaped, pre-context vectors can produce collapsed, near-identical similarity scores regardless of actual meaning.
System design: how would you verify a vendor's embedding endpoint is actually bidirectional and not silently truncating long inputs?
Feed it a long input exceeding a suspected max-sequence-length and check whether content near the end still influences the resulting vector; feed it a sentence where later words disambiguate earlier ones and confirm the earlier words' contribution actually shifts -- a causal-only or truncating implementation would fail one of these checks.
