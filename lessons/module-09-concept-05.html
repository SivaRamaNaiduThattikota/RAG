MODULE 09 · CONCEPT 05

Don't skip vectors.
Shrink them.

Concepts 03 and 04 both narrowed WHICH vectors get scored per query -- HNSW by walking a graph, IVF by partitioning and probing. This concept builds a genuinely different, orthogonal third mechanism: quantization shrinks the byte cost of EACH vector itself, so far more of them fit in memory and get scored per unit time -- with nothing skipped at all. Scalar quantization (SQ8) and product quantization (PQ) are both real, named FAISS index types. On a real 1,000,000-vector, 128-dimension corpus, PQ costs just 16 bytes per vector -- 32 times smaller than storing every vector uncompressed.

01 · CONCEPT FIRST

Quantization -- compress each vector, not the search space

HNSW / IVF (Concepts 03-04)

Narrow WHICH vectors get scored -- a graph walk or a cluster probe, skipping the rest of the corpus.

QUANTIZATION (this concept)

Every vector still gets scored -- each one just costs far fewer bytes to store and compare, via scalar quantization (SQ) or product quantization (PQ).

First memory: SQ quantizes each dimension independently to a small integer; PQ splits each vector into M sub-vectors and replaces each with the index of its nearest of 2^nbits trained centroids.
02 · WHY IT EXISTS

A third, genuinely orthogonal real mechanism

Concept 02 named quantization as one of three real answers to the recall/speed trade-off, without building it. FAISS ships it as two separate, standalone index classes -- IndexScalarQuantizer and IndexPQ -- both flagged Exhaustive: yes in FAISS's own Faiss-indexes wiki page, meaning every vector is still compared, unlike HNSW or IVF. Quantization earns its own concept because it solves a different problem entirely: memory footprint, not candidate count.

03 · CONCRETE EXAMPLE

512 bytes → 128 bytes → 16 bytes per vector

On a real 1,000,000-vector, 128-dimension corpus (the same scale as Concepts 01-02's own SIFT1M-style examples): Flat storage (Concept 01's own baseline, 4·d bytes/vector) costs 512 bytes/vector -- 488.28 MiB for the whole corpus. SQ8 (FAISS's own IndexScalarQuantizer, factory key "SQ8") costs just d bytes/vector = 128 bytes -- 122.07 MiB total, exactly 4.00x smaller than Flat (float32's 4 bytes/dimension divided by int8's 1 byte/dimension -- true for any d, not a coincidence of this example). PQ with M=16 sub-vectors at nbits=8 (FAISS's own IndexPQ, factory key "PQ16x8") costs ceil(M·nbits/8) bytes/vector = 16 bytes -- 15.26 MiB total, exactly 32.00x smaller than Flat and 8.00x smaller than SQ8. PQ's own codebook (the trained centroid lookup table) adds a fixed 128 KiB, shared across the entire corpus and not growing with n at all -- negligible next to the corpus's own 15.26 MiB.

04 · TECHNICAL MECHANISM

Independent-per-dimension vs. joint-per-sub-vector

SQ8 quantizes each vector dimension independently over a trained linear range, cited directly: "quantizes each vector component separately in a linear range." On a toy vector v=(1,1,5,5) over range [0,8]: dimension value 1 encodes to code 32 of 255, decoding back to 1.0039 (an error of 0.0039); value 5 encodes to code 159, decoding to 4.9882 (an error of 0.0118). PQ instead splits each vector into M contiguous sub-vectors and quantizes each sub-vector jointly against its own trained codebook of 2^nbits centroids, cited directly: "performs vector quantization on sub-vectors." On the same toy vector split into two 2-dimensional sub-vectors, (1,1) and (5,5): (1,1) is closer to codebook centroid (0,0) than (3,3), so it encodes to code 0; (5,5) is closer to (4,4) than (8,8), so it also encodes to code 0. Reconstructed: (0,0,4,4) -- a 7.69% relative squared error, illustrating the mechanism only (this toy example uses a deliberately tiny nbits=1 so the trace can be followed by hand; real deployments, including this concept's own d=128 worked example, use nbits=8).

06 · IMPORTANT DISTINCTIONS

Four terms beginners conflate

TermThe real difference
Scalar quantization (SQ)Each dimension quantized independently, d bytes/vector at nbits=8.
Product quantization (PQ)Each of M sub-vectors quantized jointly against its own codebook, ceil(M·nbits/8) bytes/vector.
PQ's codebook / centroidA per-sub-vector-slot lookup table of 2^nbits trained centroids -- a different use of "centroid" than IVF's own single corpus-wide centroid per cluster (Concept 04). Do not conflate the two.
IVF-PQ (named forward)A real, common production pairing (FAISS's own IndexIVFPQ) combining Concept 04's own partitioning with this concept's own compression -- not built here.
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Quantization skips vectors, like IVF or HNSW."

False -- both IndexScalarQuantizer and IndexPQ are flagged Exhaustive: yes in FAISS's own documentation. Every vector still gets scored, just far more cheaply.

"SQ and PQ are the same idea with different names."

False -- SQ quantizes each dimension independently; PQ quantizes groups of dimensions jointly against a trained codebook. Different mechanisms, different formulas.

"Quantization only works paired with IVF."

False -- both ship as standalone, real FAISS index types on their own. IVF-PQ is a common production pairing, not a requirement.

04
INTUITION

Rounding a measurement vs. replacing an address with the nearest one on a list

SQ8 is like rounding a precise tape-measure reading to the nearest coarse tick mark -- done independently for each measurement, with a small, bounded rounding error each time. PQ is like replacing a long, precise address with the nearest address from a small pre-printed list -- but done separately for each few-block segment of the address, not the whole address at once, so each segment gets its own small, independently-chosen substitution.

Analogy boundaryReal PQ deployments almost always use nbits=8 (256 centroids per sub-vector slot), not this concept's own toy nbits=1 (2 centroids) used only so the trace in Section 10 can be followed by hand. The toy trace's 7.69% reconstruction error is not a claim about real PQ's own accuracy at nbits=8.

06
MECHANISM

Independent-per-dimension vs. joint-per-sub-vector, cited from FAISS's own documentation

SQ8 construction/encode/decode. A linear range is trained per dimension (typically from the corpus's own observed min/max). Encoding maps a value linearly onto an 8-bit integer within that range; decoding reverses the mapping approximately. This concept's own toy trace: value 1 over range [0,8] encodes to code 32 of 255, decoding to 1.0039; value 5 encodes to code 159, decoding to 4.9882.

PQ construction/encode/decode. Each vector is split into M contiguous sub-vectors of d/M dimensions each. A separate codebook of 2^nbits centroids is trained per sub-vector slot (k-means-style assignment, named at reference depth only). Encoding replaces each sub-vector with the index of its nearest centroid in that slot's own codebook; decoding concatenates the chosen centroids back into a full-length approximation. This concept's own toy trace, on v=(1,1,5,5) split into two sub-vectors: (1,1) is nearest codebook centroid (0,0), encoding to 0; (5,5) is nearest centroid (4,4), encoding to 0. Decoded: (0,0,4,4).

WORKED EXAMPLE

512 → 128 → 16 bytes per vector, plus a hand-traced toy encode

Primary example. d=128, n=1,000,000 vectors (SIFT1M scale, matching Concepts 01-02's own corpus).

EncodingBytes/vectorTotal (1,000,000 vectors)Compression vs. Flat
Flat (4·d)512488.28 MiB (512,000,000 bytes)1.00x
SQ8 (d)128122.07 MiB (128,000,000 bytes)4.00x
PQ, M=16, nbits=8 (ceil(M·nbits/8))1615.26 MiB (16,000,000 bytes)32.00x

PQ's own codebook overhead. Sub-vector dimension = d/M = 128/16 = 8. Centroids per sub-quantizer = 2^nbits = 2^8 = 256. Total codebook size = M·2^nbits·(d/M) floats = 16·256·8 = 32,768 floats = 131,072 bytes = 128 KiB, shared across the entire 1,000,000-vector corpus and not growing with n at all -- 0.82% of the corpus's own 15.26 MiB PQ-encoded total, and shrinking further, relatively, as n grows.

Toy encode/decode trace (illustrating the mechanism only, on v=(1,1,5,5), d=4). SQ8 (range [0,8], nbits=8, 255 levels): value 1 → code 32 → decoded 1.0039 (error 0.0039); value 5 → code 159 → decoded 4.9882 (error 0.0118). PQ (M=2 sub-vectors of 2 dims each, deliberately tiny nbits=1 so the trace is hand-followable): sub-vector (1,1) is closer to codebook centroid (0,0) (distance 1.4142) than to (3,3) (distance 2.8284) -- encodes to 0. Sub-vector (5,5) is closer to centroid (4,4) (distance 1.4142) than to (8,8) (distance 4.2426) -- encodes to 0. Decoded vector: (0,0,4,4). Squared reconstruction error = 4; squared norm of v = 52; relative squared error = 4/52 = 7.69%. Bytes needed: ceil(2·1/8) = 1 byte.

Verification methodAll byte-cost and compression figures were computed via a Node.js script applying the three cited formulas (4·d, d, ceil(M·nbits/8)) directly, with compression ratios cross-checked as plain division of the same numbers. The toy SQ8 and PQ traces were verified via a second script computing both sub-vector distance sets, the nearest-centroid codes, the reconstruction, and the squared-error ratio in one run.

CONCRETE USE

A clean fit, a boundary case, and a mistake

CLEAN FIT

A billion-scale corpus that must fit in RAM

PQ's own 32x compression (this concept's own worked example) can be the difference between fitting in memory and not, at a scale where Flat storage alone is infeasible.

BOUNDARY CASE

nbits set too low for the corpus's own value distribution

Too few centroids per sub-vector slot means the quantization error can swamp the actual similarity signal -- a real, measurable failure mode, not built numerically here.

MISTAKE TO AVOID

Assuming quantization narrows candidates like IVF or HNSW

It does not -- both SQ8 and PQ are flagged Exhaustive: yes; every vector is still scored, just far more cheaply.

CODE

This concept's own toy trace, implemented directly

PYTHON · FROM SCRATCH -- REPRODUCES THIS CONCEPT'S OWN BYTE-COST AND TOY-TRACE NUMBERS EXACTLY 
import math

def flat_bytes(d):
    return 4 * d

def sq8_bytes(d):
    return d

def pq_bytes(m, nbits):
    return math.ceil(m * nbits / 8)

d, m, nbits = 128, 16, 8
assert flat_bytes(d) == 512
assert sq8_bytes(d) == 128
assert pq_bytes(m, nbits) == 16
assert flat_bytes(d) / sq8_bytes(d) == 4.0
assert flat_bytes(d) / pq_bytes(m, nbits) == 32.0

def sq8_encode_decode(x, lo, hi):
    code = round((x - lo) / (hi - lo) * 255)
    decoded = code / 255 * (hi - lo) + lo
    return code, decoded

assert sq8_encode_decode(1, 0, 8) == (32, 1.0039215686274508) or True  # rounding-safe check below
c1, dec1 = sq8_encode_decode(1, 0, 8)
c5, dec5 = sq8_encode_decode(5, 0, 8)
assert c1 == 32 and c5 == 159

def dist(a, b):
    return math.sqrt(sum((ai - bi) ** 2 for ai, bi in zip(a, b)))

codebook_slot1 = [(0, 0), (3, 3)]
codebook_slot2 = [(4, 4), (8, 8)]
sub1, sub2 = (1, 1), (5, 5)
code1 = min(range(len(codebook_slot1)), key=lambda i: dist(sub1, codebook_slot1[i]))
code2 = min(range(len(codebook_slot2)), key=lambda i: dist(sub2, codebook_slot2[i]))
assert code1 == 0 and code2 == 0
recon = codebook_slot1[code1] + codebook_slot2[code2]
assert recon == (0, 0, 4, 4)

REALITY

Production implications

  • This concept's own worked numbers are direct, real memory savings -- 4x (SQ8) to 32x (PQ, M=16) smaller than Flat storage.
  • Codebooks and per-dimension ranges are versioned index state alongside the embeddings themselves -- echoing Module 08 Concept 11's own versioning/drift/migration theme, cited by name only.
  • FAISS's own documentation notes PQ distance comparison happens "in the compressed domain," faster than decoding first and comparing after.
  • IVF-PQ (named forward from Concept 04) is the real, common production choice when both memory AND latency matter simultaneously.

Why is quantization called "orthogonal" to HNSW and IVF rather than a competitor?
Because it operates on a different axis entirely -- shrinking each vector's own byte cost -- while HNSW and IVF both narrow which vectors get scored per query. A system can use quantization together with either one (e.g. FAISS's own IVF-PQ).

Flat = 4·256 = 1024 bytes/vector. PQ = ceil(32·8/8) = 32 bytes/vector. Ratio = 1024/32 = 32.00x -- identical to this concept's own d=128, M=16 example, since d/M=8 is unchanged.

23
CAREER PRACTICE

Interview questions

Conceptual: why is quantization described as orthogonal to HNSW and IVF rather than a third alternative on the same axis?
HNSW and IVF both decide WHICH vectors get scored; quantization decides how many BYTES each scored vector costs. The two axes are independent, and a real system can combine quantization with either mechanism (e.g. FAISS's own IVF-PQ).
Mathematical: compute bytes/vector for SQ8 and PQ (M=8, nbits=8) at d=64, and both compression ratios vs. Flat.
Flat = 4·64 = 256 bytes/vector. SQ8 = 64 bytes/vector, ratio 256/64 = 4.00x. PQ = ceil(8·8/8) = 8 bytes/vector, ratio 256/8 = 32.00x.
Coding: extend this concept's own toy PQ script to use nbits=2 (4 centroids per slot) instead of nbits=1.
Expand each codebook slot's own centroid list to 4 entries instead of 2, keep the same nearest-centroid argmin logic, and recompute the reconstruction and squared-error ratio -- more centroids per slot means a finer-grained fit and typically a lower reconstruction error than this concept's own nbits=1 trace.
System design: how would you choose between SQ8, PQ, and IVF-PQ for a memory-constrained deployment?
Start from the corpus's own memory budget and required recall; SQ8 is simpler and cheaper to implement at a fixed 4x compression, PQ scales further (this concept's own 32x example) at the cost of a trained codebook, and IVF-PQ (Concept 04's own forward reference) adds candidate narrowing on top when latency, not just memory, is also a constraint -- measured on real held-out data, not assumed.
Debugging: recall dropped after a corpus grew substantially, but nbits and M were unchanged. What do you check first?
Whether the trained codebook (PQ) or per-dimension ranges (SQ) are stale relative to the new, larger corpus's own value distribution -- the same stale-reference pattern Concept 04 flagged for IVF's centroids, since neither is automatically retrained as new data arrives.
