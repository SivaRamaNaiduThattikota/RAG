MODULE 11 · CONCEPT 11

Ten mechanisms, proven separately.
One script, chained end to end, nothing hand-typed.

Concepts 01 through 10 each isolated one stage of RAG and proved it worked on its own terms. PROGRESSIVE BEGINNER CORE

Every concept before this one tested itself. This concept tests the seams between them.

Ten separate worked examples is not the same claim as "the pipeline works." This concept is the one script in Module 11 where a stage's input is the real, computed output of the stage before it -- not a hand-picked stand-in -- and it reports what happens when that's true, findings included.

01 · CONCEPT FIRST

Proven separately is not proven connected

Concept 03's chunker split its own test text correctly. Concept 06's selector deduped its own test candidates correctly. Concept 08's decoder cited its own test evidence correctly. None of that proves what happens when Concept 06's selector has to rank chunks Concept 03's chunker actually produced, from a store Concept 04's own persistence logic actually wrote and reloaded, embedded by a function none of the earlier concepts needed. This concept is the one script that runs the whole chain for real: ingest six documents, chunk them, embed the chunks, write them to disk and read them back, embed a real query, retrieve against the reloaded store, select and dedup the top-k, assemble the prompt, generate an answer, check its citation, then do it again for two follow-up turns -- one run, real numbers throughout.

First memory: ten passing worked examples don't guarantee the assembled system behaves the way you'd expect -- some things only surface once every stage actually feeds the next one.
02 · WHY IT EXISTS

Every earlier concept got a clean hand-off from its neighbor

Concept 05's retrieval ran against Concept 04's exact illustrative vectors. Concept 07's prompt assembly ran against Concept 06's exact hand-built evidence set. Real pipelines don't get exact, pre-agreed inputs from the stage before them -- they get whatever that stage actually produced. This concept is where retrieval reads chunks that were genuinely written to disk and reloaded (Concept 04's own "computed is not the same as saved" point, checked here rather than stated), where selection ranks a real cosine score instead of a hand-picked one, and where generation cites a chunk that was actually assembled into the prompt, not merely retrieved into a candidate list.

03 · CONCRETE EXAMPLE

Six documents, one new embedding, and a rank order that doesn't line up the way you'd guess

Six small documents go in: the same standard-return, shipping, order-status, and cancellation text Concepts 06/07/08/10 already established, plus two new ones built for this concept -- a genuine paraphrase of the order-status text, and a longer grace-period document long enough to actually split into two chunks under the char-stride chunker. Turn 1 asks "What is the return window after the grace period?" -- its own phrasing, not a replay of Concepts 06/07/10's exact query string. The top-ranked chunk is doc_grace_c2 at cosine 0.4951 -- the second half of the grace-period document, which contains no number at all. The chunk that actually says "14 days," doc_grace_c1, ranks third at 0.4931. At this run's k=4, both still make it into the assembled evidence, so the answer comes out right regardless -- but the ranking itself is a real, computed surprise, not the tidy order a hand-built example would have shown.

04 · TECHNICAL MECHANISM

Reuse ten shapes, add exactly one new mechanic

Every stage below reuses an earlier concept's own logic by shape, not by invention: the chunker is Concept 03's stride splitter; top-k selection is Concept 06's cutoff-then-k-then-dedup snippet; prompt assembly is Concept 07's own assemble() and its [SOURCE n] tag; citation checking is Concept 08's "a tag is not proof" rule; conversation history is Concept 10's rewrite-then-retrieve pattern. The one necessary new piece: this module has never had a trained embedding model to run, and a true end-to-end script has no illustrative cosine score to fall back on -- it has to retrieve against something real. The embedding here is a deterministic hashed bag-of-words vector, disclosed plainly as a stand-in, not a trained model.

06 · IMPORTANT DISTINCTIONS

"Framework-free" isn't "reinvented," and "in the ranked list" isn't "in the prompt"

Framework-free means no LangChain-style abstraction hides the wiring between stages -- it does not mean the mechanics themselves are new. Nine of this script's ten stage-mechanics are the exact shape Concepts 01-10 already established; only the embedding function is genuinely new, and it's flagged as such rather than sanded into looking routine. Separately: a chunk being retrieved into the ranked candidate list is not the same claim as a chunk reaching the assembled prompt. At k=2, doc_grace_c1 -- the chunk with the actual "14 days" fact -- ranks third at 0.4931, safely above the 0.35 cutoff, and still never reaches the prompt, because only the top two survive selection.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"A paraphrase should score almost 1.0 against the original."

Not under a hashed bag-of-words stand-in. doc_cC_dup_c1, a genuine hand-written paraphrase of doc_cC_c1's order-status fact, scores cosine 0.8098 against it -- comfortably under a naive 0.90 duplicate cutoff, which had to be lowered to 0.75 before the dedup path actually fired in this run.

"If the right chunk is in the corpus, it reaches the prompt."

Not automatically -- at k=2, doc_grace_c1 is retrieved into the ranked list (rank 3 of 7, well above cutoff) but dropped before assembly. Only at k=3 or higher does it survive into this run's evidence set.

CODE

The one new mechanic: a deterministic hashed bag-of-words embedding

JAVASCRIPT · EMBEDDING FUNCTION (node-run, see Section 09) 
function weightOf(token) {
  if (STOP_WORDS.has(token)) return 0.05;
  const w = 0.06 + Math.min(token.length, 10) * 0.02;
  return Math.min(w, 0.28);
}

function hashToken(token) {
  let h = 0;
  for (let i = 0; i < token.length; i++) h = (h * 31 + token.charCodeAt(i)) >>> 0;
  return h % EMBED_DIM; // EMBED_DIM = 64
}

function embed(text) {
  const vec = new Array(EMBED_DIM).fill(0);
  tokenize(text).forEach((t) => { vec[hashToken(t)] += weightOf(t); });
  return vec;
}

This is not a trained model -- this module has never had one available to run. It is the simplest thing that turns cosine similarity below into a real, script-computed number instead of another hand-picked one. Every score in Sections 07-08 came out of this exact function; none were typed from memory. Chunking, selection, and prompt assembly are omitted here since they are Concept 03/06/07's own code, reused unmodified -- see those pages for the full listings.

CAREER PRACTICE

Interview questions

Systems: why would two component-level tests both pass, yet the assembled pipeline still misbehave?
Because each component test typically feeds the component a hand-picked, well-formed input rather than the real output of the previous stage -- a chunker can split correctly and a selector can dedup correctly, and still interact badly once the selector has to rank chunks the chunker actually produced from a store that was actually written and reloaded.
Conceptual: what's the difference between a chunk being "retrieved" and a chunk "reaching the prompt"?
Retrieved means it appears in the ranked candidate list, typically after clearing a similarity cutoff; reaching the prompt means it survived top-k selection and deduplication and was actually written into the assembled context string generation sees. At k=2 in this run, the fact-bearing chunk clears the cutoff but does not survive selection -- it is retrieved but never reaches the prompt.
Architecture: what's the one component this raw implementation had to build that a framework would give for free, and why did it matter here?
A real embedding function -- this module never had a trained model to call, so a deterministic hashed bag-of-words embedding was built as a disclosed stand-in. It mattered because it made every retrieval score in this concept a real, script-computed number rather than another hand-picked illustrative one, at the cost of known weaknesses like scoring genuine paraphrases well below what a trained model would.

CROSS-REFERENCE

"Computed is not the same as saved," checked instead of stated

Module 11 Concept 04 established the principle that a vector computed in memory is not the same thing as a vector actually persisted and retrievable later. This concept is the first place in the module that principle gets checked rather than asserted: all 7 chunk records are written to a real file on disk, reloaded into a fresh variable, and compared field-by-field against the in-memory originals before retrieval is allowed to run against them. The round trip passes here (OK), but the check itself -- not just the write -- is what this concept adds; a script that wrote and never reloaded would have no way to know whether the persisted copy was actually usable.

21
CROSS-REFERENCE

"In the corpus" is not "in the prompt," now with real numbers

Module 11 Concept 07 Section 13 made this point illustratively: a relevant chunk can exist in the corpus and even rank inside the candidate pool, yet still never reach the assembled prompt if selection cuts it before then. This concept confirms it empirically. Re-running Section 08's selection at k=2, k=3, and k=4 on the identical Turn 1 ranking: at k=2, the evidence set is [doc_grace_c2, doc_cC_dup_c1] and the fact-bearing chunk is absent; at k=3 and k=4, it's [doc_grace_c2, doc_cC_dup_c1, doc_grace_c1] and the fact-bearing chunk is present. The chunk's own retrieval rank never changes (3rd of 7, cosine 0.4931, well above the 0.35 cutoff) -- only the selection width does. "In the ranked candidates" and "in the prompt" are different claims, and only the second one is what generation can honestly cite from.

22
CROSS-REFERENCE

Checking the checker, not just trusting it

Module 11 Concept 08 Section 20 and Concept 09's read-back check both establish that a citation tag has to be verified against the actual cited text, not trusted on sight. This concept adds one more layer: it verifies that the verification code itself actually catches a bad citation, rather than assuming a function that returned ok=true once is trustworthy in general. After Turn 1's real citation check passes, the same claim ("14 days") is deliberately reattributed to the wrong chunk (doc_grace_c2 instead of doc_grace_c1) and re-checked: the checker returns ok=false, correctly flagging the mismatch. A citation checker that always returns true would have passed Turn 1's real check too -- this negative test is what rules that out.

CROSS-REFERENCE
