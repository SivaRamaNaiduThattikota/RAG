01 · CONCEPT FIRST

Two pipelines, not one

OFFLINE INDEXING

Documents → parsing → chunking → embedding → storing vectors in an index. Runs once, or periodically, before any user has asked a single question.

ONLINE QUERY

A user's query → retrieval against the already-built index → context assembly → generation. Runs fresh, every single request.

First memory: offline indexing happens before any query exists; online query happens because one just arrived — two different pipelines, two different triggers.
02 · WHY IT EXISTS

Concept 01's promise, finally paid

Concept 01 said retrieval "searches the corpus" and left it there — true, but it hides that the corpus had to become searchable somehow, at some earlier point in time. This concept supplies that missing earlier point: offline indexing makes the corpus searchable, once. Online query does the searching, every time a question arrives — never the reverse.

WITHOUT THE SPLIT

"Retrieval searches the corpus" — usable, but silent about how the corpus got ready to be searched at all.

WITH THE SPLIT

Offline indexing builds the index. Online query reads it. Different inputs, different triggers, and usually a completely different frequency.

03 · CONCRETE EXAMPLE

A policy PDF, before and after anyone asks about it

Before any employee ever asks a question, an ingestion job takes Oracle's travel-policy PDF, parses it into text, splits that text into chunks, turns each chunk into an embedding, and stores the resulting vectors in an index. Nobody asked anything yet — this happens on a schedule, or whenever documents change. Only later, when an employee actually types "what's the pre-approval rule for international travel?", does the online query pipeline wake up: it searches the index offline indexing already built, assembles the relevant chunks into context, and generation writes the answer.

OFFLINE, EARLIER

Parse → chunk → embed → store — done once, before the question existed, with no query in sight.

ONLINE, JUST NOW

Retrieve → assemble context → generate — done fresh, because this specific question just arrived.

04 · TECHNICAL MECHANISM

Naming the stages — silhouettes only

OFFLINE · STAGE 1

Parsing

Turn a raw document into usable text. How parsing handles tables, layout, or scanned pages is Module 06's job.

OFFLINE · STAGE 2

Chunking

Split that text into smaller retrievable units. Why chunking exists and every strategy for doing it is Module 07's job — this concept only names it as a stage.

OFFLINE · STAGE 3

Embedding

Turn each chunk into a vector capturing its meaning. What an embedding is, and the mathematics behind it, is Module 08's job.

OFFLINE · STAGE 4

Storing in a vector index

Persist those vectors somewhere searchable. How a vector index actually works — HNSW, IVF, exact search — is Module 09 and Module 10's job.

Three more stages exist on the online side, covered in the next step: retrieval, context assembly, and generation. Every "how" behind these seven words is deliberately out of reach until its owning module — this concept's only job is the order, and the boundary between "before any query" and "because a query arrived."

06 · IMPORTANT DISTINCTIONS

What each pipeline is not

ThisIs notBecause
Offline indexingSomething that happens per queryIt runs once, or on its own schedule, entirely independent of any specific question ever being asked
Online queryIndexing or re-indexingIt only reads an index that already exists — it never parses, chunks, embeds, or stores anything new
The vector indexNon-parametric memory itselfThe index is one concrete storage form non-parametric memory takes — Concept 05's term, now given its first internal structure
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Indexing happens at query time, live."

No — that would force every single question to pay the full parse-chunk-embed-store cost. Indexing is precomputed, before the query exists.

"A newly uploaded document is instantly searchable."

No — it's invisible to the online query pipeline until offline indexing actually processes it. Uploading is not indexing.

"Offline and online are the same pipeline, just run twice."

No — different inputs (documents vs. a query), different triggers (a schedule or event vs. a request), and usually a completely different frequency.

09 · WHAT YOU SHOULD UNDERSTAND

Readiness check before moving on

Offline indexing's stages

Documents → parsing → chunking → embedding → storing vectors in an index — done once, before any query exists.

Online query's stages

Query → retrieval against the index → context assembly → generation — done fresh, every request.

Why the split exists

Indexing can't wait for a query — too slow per request. Querying can't happen before the index exists — nothing to search yet.

The consequence of the split

A document not yet indexed is invisible to every online query, no matter how good retrieval is.

04
INTUITION

A library's catalog, and a visitor's question

A librarian catalogs new books continuously, in the background — assigning them a place on the shelf and an entry in the card catalog — whether or not anyone happens to be browsing that day. A visitor who walks in and asks a question gets an answer by searching whatever the catalog already contains, right now. Cataloging is offline indexing; the visitor's question is the online query. If a book arrived ten minutes ago and hasn't been cataloged yet, the visitor's question about it comes up empty — not because the librarian searched badly, but because cataloging hasn't caught up.

Analogy boundaryA library's catalog updates in a steady trickle, one book at a time. A real offline indexing pipeline more often runs in batches — nightly, hourly, or triggered by a change — so the "ten minutes ago" gap in the analogy is frequently hours or days in a real system. Module 19 covers the actual scheduling trade-offs; this concept only supplies the two-pipeline shape.

06
MECHANISM

Seven moments, two pipelines, one shared index

T0 — Documents exist in the source system. The index is empty. No query has happened yet.
T1 — Offline indexing runs: parses, chunks, embeds, and stores vectors for the current document set. The index now holds every chunk that existed at T0.
T2 — An employee asks a question. Online query runs: retrieves from the T1 index, assembles context, generates an answer. The index itself is untouched.
T3 — A different employee asks a different question. Online query runs again, against the exact same T1 index — no re-indexing happened between T2 and T3.
T4 — A new policy document is uploaded. The index does not change yet — offline indexing has not run again.
T5 — A third employee asks about that brand-new policy. Online query runs, searches the still-T1 index, and finds nothing about it — a timing gap, not a retrieval failure.
T6 — Offline indexing runs again on its next scheduled pass. The new document is now parsed, chunked, embedded, and stored. From this point on, online queries about it succeed.

09
MATHEMATICS

Why splitting the cost in two is not just tidy — it's cheaper

Let C_index be the total cost of running offline indexing once over the document set, and C_query be the cost of one online query. If Q queries get served before the index needs rebuilding, the total cost of serving them is:

Total cost = C_index + Q × C_query
Average cost per query = C_index / Q + C_query

As Q grows, C_index / Q — the amortized share of indexing cost each query actually pays — shrinks toward zero. Indexing's cost gets paid once and spread across every query that follows; running it fresh inside every single query instead would mean every query pays the full C_index on top of C_query — the arithmetic behind why the two pipelines are split at all, not just a design preference.

10
WORKED EXAMPLE

500 documents, 10,000 questions

Indexing 500 policy documents takes roughly 2 seconds each to parse, chunk, embed, and store — C_index ≈ 1,000 seconds, paid once. Each online query — retrieval, context assembly, generation — costs roughly 0.3 seconds: C_query = 0.3.

ScenarioTotal cost for 10,000 queriesAverage cost per query
Split pipelines (indexing once, query many times)1,000 + 10,000 × 0.3 = 4,000 seconds0.4 seconds
Hypothetical: re-index inside every query10,000 × (1,000 + 0.3) = 10,003,000 seconds1,000.3 seconds

The split isn't a minor optimization — re-indexing per query would be roughly 2,500 times slower on average in this example, for the identical set of documents and questions.

11
CONCRETE USE

Four cards: a clean fit, a boundary case, a counterexample, and a mistake

CLEAN FIT

A stable policy corpus, indexed nightly

Thousands of queries per day against a document set that changes rarely — the amortization argument wins decisively.

BOUNDARY CASE

A corpus that changes every few minutes

Offline indexing has to run far more often, shrinking the amortization benefit — but the two pipelines stay conceptually separate regardless of how tight the schedule gets.

COUNTEREXAMPLE

A live lookup against a database or API, per query

No index is built in advance at all — Module 21's structured-data RAG covers this pattern; naming it only as a boundary here, not exploring it.

MISTAKE TO AVOID

Assuming both pipelines must run on the same server

They're separate pipelines by responsibility, not by deployment — Module 19 covers how they're actually deployed, often on entirely different infrastructure.

12
CODE

Two functions, one shared index

PYTHON · OFFLINE INDEXING VS. ONLINE QUERY, SILHOUETTE ONLY 
# Offline: runs once (or on a schedule), before any query exists.
# Every internal step is a stub -- HOW parsing, chunking, embedding,
# and storage actually work is Modules 06-10's job, not this one.
def build_index(documents):
    index = []
    for doc in documents:
        text = parse(doc)               # Module 06
        chunks = chunk(text)             # Module 07
        for piece in chunks:
            vector = embed(piece)        # Module 08
            index.append({"chunk": piece, "vector": vector, "source": doc["id"]})
    return index                         # Module 09/10 owns the real storage structure


# Online: runs once per user request, reading an index that must
# already exist. It never calls build_index -- that would defeat
# the entire point of separating the two pipelines.
def answer_query(query, index):
    if not index:
        return "No documents indexed yet -- nothing to retrieve."
    hits = retrieve(query, index)                # Module 09/16
    context = assemble_context(hits)             # Module 17
    return generate(query, context)               # Module 02's mechanism, cited


# The shape that matters: build_index runs ONCE, up front.
# answer_query runs MANY times, against whatever build_index
# already produced -- including zero times, if no query ever arrives.
corpus_index = build_index(policy_documents)
answer_1 = answer_query("What's the pre-approval rule?", corpus_index)
answer_2 = answer_query("How many vacation days carry over?", corpus_index)

Notice what's missing on purpose: parse, chunk, embed, retrieve, assemble_context, and generate are named but not implemented. Their internals are exactly the stages Modules 06 through 10 and 17 build out for real — this code exposes only the order and the one-build/many-read shape.

13
ECOSYSTEM

Where the split shows up in the literature

Chen, Fisch, Weston and Bordes (2017), DrQA, is an early, clean instance of exactly this shape: a document retriever builds a TF-IDF index over Wikipedia once, and a separate reader model answers each question against whatever the index already contains. Karpukhin et al. (2020), Dense Passage Retrieval, modernizes the same split with dense embeddings — the passage encoder runs offline to build the index, and only the much smaller question encoder runs at query time. Johnson, Douze and Jégou (2017), FAISS, is the systems-level counterpart: a library purpose-built for storing and searching the large vector indexes offline indexing produces, at a scale no per-query computation could match.

16
DIAGNOSIS

Failure modes

STALE INDEX

Documents changed, but reindexing hasn't run

Online queries answer confidently against an index that no longer matches reality — Section 06's T4-T5 moments made concrete.

QUERY-TIME INDEXING ATTEMPT

Trying to embed and search live, with no prebuilt index

Every query now pays the full indexing cost Section 09 showed gets amortized away — devastatingly slow at any real scale.

INDEX-QUERY MISMATCH

The index and the query assume different embedding models

Retrieval returns nonsense because the two sides of the pipeline were never speaking the same vector space — Module 08's embedding-model-selection concept, forward-referenced, not solved here.

17
CORRECTION

Misconceptions

Incorrect beliefCorrection
Retrieval finding nothing means retrieval is brokenUsually means offline indexing hasn't processed that document yet — a timing gap, not a retrieval defect.
The two pipelines must run at the same cadenceThey're independent by design — indexing can run hourly while queries arrive continuously, or the reverse.
An online query can trigger its own reindexingNot by default — reindexing is offline's responsibility, triggered by schedules or document changes, not by the act of asking a question.
18
REALITY

Production implications, at introductory depth

  • Offline indexing needs its own trigger — a cron schedule, a document-change event, or both — separate from anything a user does.
  • A stale index is a measurable risk, not a hypothetical one — tracking last-indexed time per document is how staleness gets caught before a user does.
  • The two pipelines have very different latency budgets: online query latency is user-facing and must stay tight; offline indexing latency mostly isn't, and can trade time for thoroughness.

FEEDBACK

Solution and teach-back

Open one defensible reasoning pattern
A catalog changing every few minutes needs offline indexing on a similarly tight cadence — every few minutes, or event-driven on each new item, rather than nightly. Chosen too infrequently, newly added items stay invisible to every online query for the entire gap between indexing runs, exactly like Section 06's T4-T5 moments: not a retrieval failure, but a schedule mismatched to how fast the corpus actually changes.

Teach-back: explain, in your own words, why making the schedule tighter always costs something, even though it also always shrinks the freshness gap.

CAREER PRACTICE

Interview questions

Explain the offline/online split to a non-technical stakeholder.
Think of it like a library: cataloging new books happens in the background, on its own schedule. A visitor's question gets answered by searching whatever's already cataloged, right then. The two never swap jobs.
Why does amortizing indexing cost across many queries matter more as query volume grows?
Average cost per query is C_index/Q + C_query — as Q grows, the indexing share shrinks toward zero, while re-indexing per query would keep paying the full C_index on every single request regardless of volume.
Coding: what would you add to build_index and answer_query to make the "index must exist before it's useful" rule observable, not just implied?
A guard in answer_query that checks whether the index is empty and returns an explicit "nothing indexed yet" result, plus a last-indexed timestamp stored alongside the index so staleness is measurable rather than assumed.
Debugging: a user reports a document they uploaded an hour ago doesn't show up in any answer. Where do you look first?
Whether offline indexing has run since the upload — check the last-indexed timestamp against the upload timestamp before suspecting retrieval logic at all.
System design: sketch the two pipelines and name one component each would need in a real deployment.
Offline: a scheduler or event trigger plus a parsing/chunking/embedding job that writes to a vector store. Online: an API endpoint that runs retrieval against that same vector store, assembles context, and calls a generation model — deployed and scaled independently of the offline job.
