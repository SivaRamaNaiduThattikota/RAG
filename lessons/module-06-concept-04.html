MODULE 06 · CONCEPT 04

A page can look full
and still have nothing to read.

Concept 02 parsed five file formats that all shared one thing: an embedded text layer already sitting inside the file, waiting to be read out. A scanned page has no such layer — it's a grid of pixels, and nothing inside the file says which pixels are letters. This concept covers two separate problems that both live inside Concept 02's own file formats: optical character recognition (OCR), for pages with no text layer at all, and layout analysis, for pages that do have text but arrange it across columns, tables and figures whose position — not the order bytes happen to sit in the file — is what actually determines correct reading order.

01 · CONCEPT FIRST

Two different reasons a document's text isn't just sitting there

OCR + LAYOUT ANALYSIS (THIS CONCEPT)

Recovering text that was never stored as text at all (OCR, for a scanned or photographed page), and determining the correct reading order and structure of text that does exist but is arranged across columns, tables and figures (layout analysis).

NOT THIS CONCEPT (CONCEPT 02)

Reading a file format's own embedded text layer directly, in the single reading order the file's internal structure already implies — no recognition and no reading-order decision required.

First memory: a scanned page has no text to read, only pixels to recognize — and even a page that does have text can still end up in the wrong reading order if a plain top-to-bottom byte scan ignores its columns.
02 · WHY IT EXISTS

Two assumptions Concept 02's five parsers quietly relied on

Concept 02 assumed every PDF, HTML page or Word document already had a text layer sitting inside it, extractable in one straightforward pass. That assumption breaks in two distinct ways many real documents hit. First: a huge amount of real-world knowledge exists only as scanned paper — old contracts, signed forms, photographed receipts, faxed complaints — where a file format's parser finds no text layer to extract, because none was ever created. Second, even a fully digital, born-native PDF report can lay its text out across multiple columns, sidebars, tables and captioned figures, where the file's raw internal text-stream order and the page's actual visual reading order are two different things. Both problems have to be solved before a document is truly usable text, and neither one is what Concept 02's five parsers were built to do.

03 · CONCRETE EXAMPLE

One receipt misread by two characters — and one page misread by ignoring its columns

OCR

A scanned order confirmation reads "ORDER 4471" to a human eye. The OCR engine returns "0RDER 447l" — mistaking a capital O for a zero and a digit 1 for a lowercase L. Two characters wrong out of ten is enough to break an exact-match lookup, even though a human would read it correctly at a glance.

LAYOUT

A two-column quarterly report opens "Complaint volume rose 12%…" at the top of its left column and "Mortgage servicing complaints held steady…" at the top of its right column. Reading strictly left-to-right, top-to-bottom across the full page width interleaves one sentence from each column before either paragraph finishes — the raw text order is nonsense even though both columns are typed correctly.

Neither failure is a parsing bug in Concept 02's sense — the characters, once recognized, and the columns, once laid out, are both real. The problem is deciding what those pixels or that position actually mean before treating the result as reliable text.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"OCR output is basically as reliable as typed text."

Even strong OCR engines routinely confuse visually similar characters (O/0, 1/l/I, rn/m). A downstream exact-match lookup or citation can silently break on a difference a human reader wouldn't even notice.

"Reading a page top-to-bottom, left-to-right always gives the right order."

That rule only holds for a single-column layout. A multi-column page read that way interleaves unrelated sentences from different columns before either one finishes.

"A table can just be flattened into one line of text."

Flattening a table's cells into a single text run destroys which value belongs to which row and column — the same fact ("the fee is $35") can end up attached to the wrong row entirely.

"If a PDF has any embedded text, none of its pages need OCR."

Mixed documents are common: a born-digital cover page next to a scanned signature page in the same PDF. The embedded-text check has to run per page, not once for the whole file.

09 · WHAT YOU SHOULD UNDERSTAND

Readiness check before moving on

OCR and layout analysis solve different problems

OCR recovers missing text from pixels; layout analysis orders and structures text that already exists.

OCR output can look right and still be wrong

Visually similar characters get swapped in ways a quick glance won't catch — exactly Section 03's ORDER 4471 example.

Reading order is a layout decision, not a byte-order default

A multi-column page's correct order has to be determined from block position, not assumed from raw text-stream order.

Tables need structure preserved, not just characters

Flattening a table into one line loses which value belongs to which row and column — Concept 05's cleaning happens after this, not instead of it.

04
INTUITION

A photograph, a newspaper, and a spreadsheet mistaken for a sentence

A scanned page is a photograph of writing, not writing — nothing inside the file says "this group of pixels is the letter O"; a trained recognition model has to guess, and it guesses wrong often enough to matter. A multi-column page is more like a newspaper than a letter: a letter's sentences run in one unbroken line, but a newspaper page's columns are separate stories that happen to share a page, and reading across them at the same height mixes two unrelated stories into nonsense. A table is a spreadsheet, not a sentence — reading it as one flat line of prose throws away exactly the row/column relationship that gave its numbers meaning in the first place.

Analogy boundaryOCR and layout analysis are not the same failure with two names. A perfectly recognized character can still land in the wrong reading position, and a perfectly ordered layout can still contain a misrecognized character. Section 16 treats them as two independent failure modes for exactly this reason.

06
MECHANISM

Four lanes, one shared handoff

Check for a text layer, per page — if one exists, skip OCR and go straight to layout analysis; if none exists, run OCR first. This check runs per page, not once for the whole file (Section 07's beginner mistake).
OCR lane — binarize the image, segment it into lines/words/characters, classify each segment against a trained recognition model, then apply language-model post-correction.
Layout lane — detect a bounding box per content block, classify each block's type (heading, paragraph, table, figure, caption), then order the blocks by reading convention rather than raw position in the file.
Table lane — within a block classified as a table, detect row and column boundaries directly, preserving cell-to-position mapping instead of flattening to one line.
Handoff — every lane still ends at the same place: a raw, unclean, unchunked, but now correctly-recognized, correctly-ordered and structure-preserved record, passed forward to Concept 05.

09
MATHEMATICS

Character error rate from an edit distance

Given a reference string of length N and a hypothesis string produced by OCR, let S be the number of substituted characters, D the number of characters present in the reference but missing from the hypothesis (deletions), and I the number of characters present in the hypothesis but absent from the reference (insertions), all counted by the minimum-cost alignment between the two strings — the Levenshtein edit distance. Character error rate is:

CER = (S + D + I) / N

A CER of 0 means a perfect transcription; a CER above 0.5 generally means the hypothesis is unusable without correction. Word error rate (WER) applies the same formula to whole words instead of characters, and is generally higher than CER for the same transcription, since a single wrong character is enough to mark an entire word wrong under WER.

WORKED EXAMPLE

Two characters wrong, computed by hand

Reference: "ORDER 4471" (N = 10 characters, including the space). OCR hypothesis: "0RDER 447l". Aligning character by character:

No characters are missing (D = 0) and none are extra (I = 0) — the hypothesis is the same length as the reference, and every position lines up one-to-one. S = 2 (positions 1 and 10). CER = (2 + 0 + 0) / 10 = 0.20, or 20%. Two characters out of ten is enough to break an exact-match lookup for order number "4471" entirely, even though a human reader would recognize both substitutions instantly from context.

CONCRETE USE

Four cases: two clean fits, a boundary case, a mistake

CLEAN FIT

A high-resolution, single-column scan of a typed memo

Character shapes are unambiguous and there is only one column to read — OCR confidence is high and no reading-order decision is even needed.

CLEAN FIT

A born-digital, single-column PDF report

Concept 02's plain text-layer read already produces the correct order; this concept has nothing extra to do.

BOUNDARY CASE

A scanned form with a printed table of checkboxes

OCR alone recognizes each character correctly, but without table-aware layout analysis, checkbox rows and their labels can get associated with the wrong column entirely.

MISTAKE TO AVOID

Feeding a multi-column PDF through Concept 02's parser and trusting its raw text-stream order

Some PDF libraries emit text in the order objects were written into the file, which frequently has no relationship at all to the page's visual column layout.

12
CODE

Character error rate, from scratch

This is the mechanism behind Section 09's formula, applied to Section 10's exact "ORDER 4471" example — a standard Levenshtein edit-distance computation, decomposed into the S/D/I counts CER actually needs, both numbers independently confirmed before use.

PYTHON · EDIT DISTANCE AND CHARACTER ERROR RATE 
def edit_distance(ref, hyp):
    n, m = len(ref), len(hyp)
    dp = [[0] * (m + 1) for _ in range(n + 1)]
    for i in range(n + 1):
        dp[i][0] = i
    for j in range(m + 1):
        dp[0][j] = j
    for i in range(1, n + 1):
        for j in range(1, m + 1):
            if ref[i - 1] == hyp[j - 1]:
                dp[i][j] = dp[i - 1][j - 1]
            else:
                dp[i][j] = 1 + min(
                    dp[i - 1][j],      # deletion
                    dp[i][j - 1],      # insertion
                    dp[i - 1][j - 1],  # substitution
                )
    return dp[n][m]

def cer(ref, hyp):
    return edit_distance(ref, hyp) / len(ref)

reference = "ORDER 4471"
hypothesis = "0RDER 447l"

assert edit_distance(reference, hypothesis) == 2   # O->0 and 1->l, two substitutions
assert cer(reference, hypothesis) == 0.2            # 2 / 10

# Edge case: dropping the leading character entirely is a pure deletion,
# not a substitution -- a different failure shape with a lower CER here.
dropped = "RDER 4471"
assert edit_distance(reference, dropped) == 1
assert cer(reference, dropped) == 0.1
13
ECOSYSTEM

The same four lanes, in real tools

OCR: Tesseract is the standard open-source engine; cloud OCR APIs (AWS Textract, Google Document AI, Azure AI Document Intelligence) trade a per-page cost for higher accuracy on harder scans and built-in layout detection. Layout analysis: PDF-native libraries (PyMuPDF, pdfplumber) extract each block's bounding box directly from a born-digital PDF's own coordinate data; learned layout models (e.g. LayoutLM-family models) classify block types and predict reading order on scanned or mixed pages where no reliable coordinate data exists. Table extraction: Camelot and pdfplumber target born-digital PDF tables directly; PubTables-1M is a large benchmark dataset purpose-built for training and evaluating table detection and structure-recognition models on real, messy documents. Framework-level connectors (LangChain, LlamaIndex — Modules 12 and 14) wrap several of these behind one common loader interface, the same file-format-versus-mechanism trade Concept 02 and Concept 03 both named already.

DIAGNOSIS

Failure modes

CHARACTER SUBSTITUTION

OCR swaps a visually similar character with no error signal

Section 10 showed it directly: O becomes 0, 1 becomes l, and nothing about the output looks obviously wrong without comparing against ground truth.

READING-ORDER SCRAMBLE

A multi-column page gets read in raster order

Section 04's newspaper analogy: two unrelated columns interleave sentence-by-sentence, producing text that is typographically correct and semantically nonsense.

TABLE FLATTENING

A table's rows and columns collapse into one line

The cell-to-position mapping Section 06's table lane is built to preserve is lost, and a retrieved number can no longer be tied back to the row or column it actually belonged to.

CORRECTION

Misconceptions

Incorrect beliefCorrection
OCR either works or it doesn't — there's no partial creditFalse — Section 09's CER is a continuous measurement, and Section 10's worked example shows a mostly-correct transcription that still fails an exact-match lookup.
A page's visual layout and its file's text-stream order are the same thingFalse — Section 11's mistake-to-avoid: some PDF libraries emit text in write order, not reading order, and the two frequently disagree on multi-column pages.
Once a table's characters are extracted correctly, the extraction is doneFalse — Section 16's table-flattening failure: correct characters in the wrong row/column relationship are still a broken extraction.
18
REALITY

Production implications

  • OCR confidence scores are worth keeping, not discarding — a per-character or per-word confidence score from the OCR engine lets downstream steps flag low-confidence spans for review rather than trusting every character equally.
  • Skew, resolution and lighting are real preprocessing concerns — deskewing, denoising and contrast correction before OCR measurably reduce CER, and are usually cheaper than accepting a higher error rate and fixing it downstream.
  • Layout models trained on one document style don't automatically generalize — a layout model tuned on financial reports can misclassify blocks on a completely different document style (legal contracts, medical forms), so accuracy has to be checked per document type in production, not assumed from a vendor's benchmark.
19
RECALL

Knowledge check

Why does CER = (S + D + I) / N use the reference string's length, N, as the denominator rather than the hypothesis string's length?
Because CER measures how much of the true content was recovered correctly. Using the reference length keeps the denominator fixed regardless of whether the hypothesis is longer, shorter, or the same length — a hypothesis that drops characters entirely (increasing D) still gets penalized relative to what should have been there.
What does a naive raster scan get wrong on a two-column page that a layout-aware read gets right?
A raster scan reads strictly left-to-right, top-to-bottom across the full page width, which interleaves sentences from both columns row by row. A layout-aware read finishes one column top-to-bottom before starting the next, preserving each column as one coherent block of text.
Why is flattening a table into one line of text considered a failure even if every character is recognized correctly?
Because a table's meaning depends on which value sits in which row and column. Flattening discards that row/column relationship, so a correctly recognized number can no longer be tied back to what it actually measured.

FEEDBACK

Solution and teach-back

Open the worked solution
Reference "INV-2208" (N = 8 characters). Hypothesis "INV-22O8": positions 1-6 (I, N, V, -, 2, 2) match; position 7 is a substitution (0 → O); position 8 (8) matches. S = 1, D = 0, I = 0. CER = (1 + 0 + 0) / 8 = 0.125, or 12.5%. Layout-analysis failure with 0% CER: every character on a two-column page could be recognized with perfect accuracy, and the page would still be unusable if the blocks are read in the wrong order — a raster scan interleaving two columns produces a 0%-CER transcription that is nonetheless semantically scrambled, exactly Section 16's reading-order-scramble failure.

PORTABLE MEMORY

Concept card

OCR + layout analysis

  • OCR: recognizes text from pixels when no text layer exists — measured by character error rate
  • Layout analysis: detects blocks, classifies their type, and orders them by reading convention, not file order
  • Tables: preserve row/column structure as structure, never flatten to one line

23
CAREER PRACTICE

Interview questions

How would you measure whether an OCR pipeline is good enough to trust for a retrieval corpus?
Compute character error rate (and word error rate) against a hand-verified reference sample, not just a visual spot check. Track it per document type and per scan-quality bucket, since a single average can hide a subset of documents with unusably high error rates.
A two-column PDF's extracted text reads correctly for a few sentences, then suddenly jumps to an unrelated topic. What's the likely cause, and how would you fix it?
Likely a raster-order extraction reading across both columns row by row instead of finishing one column before starting the next. The fix is a layout-analysis step that detects each column as its own block and orders blocks column-first, not a re-run of the OCR or text-extraction step itself.
Why can't you rely on "every character was extracted correctly" as your only quality bar for a scanned table?
Because correct characters can still be attached to the wrong row or column if the table's structure wasn't preserved during extraction. A quality bar needs to check cell-to-position correctness, not just character-level accuracy.
Design question: you're ingesting a mixed batch of PDFs where some pages are born-digital and others are scanned. How do you handle both without wasting OCR calls on pages that don't need it?
Check each page individually for an existing, extractable text layer before deciding whether to route it through OCR. Pages with a usable text layer skip OCR entirely and go straight to layout analysis if needed; only pages with no text layer at all get the more expensive OCR step.
