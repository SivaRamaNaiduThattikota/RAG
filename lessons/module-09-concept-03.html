MODULE 09 · CONCEPT 03

One graph, many layers.
Search descends, greedily.

Concept 02 named the trade-off -- skip most of the corpus, accept a bounded chance of missing the truth -- without saying how any real index actually chooses what to skip. This concept builds the first real answer end to end: Hierarchical Navigable Small World (HNSW) graphs. A multi-layer structure where search starts at a sparse top layer and greedily follows the closest neighbour at each step, dropping a layer whenever no closer neighbour remains, until the bottom layer's own local minimum is the answer. A hand-traced six-point toy graph makes the mechanic concrete; FAISS's own published benchmark then shows the algorithm's own internal recall/speed dial.

01 · CONCEPT FIRST

HNSW -- a hierarchy of proximity graphs, searched top-down and greedily

ABSTRACT (Concept 02)

Some structure narrows the candidates. Mechanism unnamed.

HNSW (this concept)

A multi-layer graph. Each node connects to a handful of nearby nodes. Search starts at a sparse top layer, greedily follows the closest neighbour, and drops a layer whenever no closer neighbour remains -- until the bottom layer's own local minimum is the answer.

First memory: HNSW searches by starting sparse and high, then greedily descending toward dense and close -- following the closest neighbour at every step, one layer at a time.
02 · WHY IT EXISTS

Concept 02 named the trade-off; this is the first real "how"

Concept 02 established that every ANN index narrows the candidate set somehow, and put a real number on the resulting recall/speed trade. It deliberately left "somehow" unexplained. HNSW, from Malkov and Yashunin's 2016 paper (arXiv:1603.09320), is the first of this module's three named mechanisms (HNSW, IVF, quantization) to get its own concept, because it is one of the most widely deployed real ANN algorithms in production vector databases today.

03 · CONCRETE EXAMPLE

Six points, two layers, one greedy trace: A → D → C

Six toy 2-D points stand in for embeddings: A=(0,0), B=(3,1), C=(5,1), D=(7,2), E=(9,3), F=(10,4). The dense bottom layer (Layer 0) connects every point to its immediate neighbours in a chain: A–B–C–D–E–F. The sparse top layer (Layer 1) keeps only two of the six points, A and D, joined by one edge. Query Q=(5.2, 1.1). Search always starts at the graph's single fixed entry point, A, in the top layer. Distance from Q: A=5.3151, D=2.0125. D is closer, so the search moves to D. D's only Layer 1 neighbour is A, already worse -- no improvement, so Layer 1 terminates at D and the search descends into Layer 0. At D in Layer 0, D's chain-neighbours are C (0.2236 from Q) and E (4.2485 from Q); C is closer, so the search moves to C. C's chain-neighbours are B (2.2023) and D (2.0125), both farther than C's own 0.2236 -- no improvement, so the bottom layer's own local minimum is reached and the search returns C.

04 · TECHNICAL MECHANISM

Three named parameters, none re-derived at length here

HNSW's own paper (Malkov and Yashunin, arXiv:1603.09320) names two construction-time parameters and one search-time parameter. M caps how many graph edges each node keeps per layer (this toy graph uses at most 2, far below any real deployment). ef_construction controls how thorough the search is while the graph is being built -- a higher value builds a better-connected, slower-to-build graph. ef_search controls how many candidates the search keeps active at query time -- this toy trace's greedy walk is the special case ef_search=1 (always move to the single closest neighbour); Section 10's own second worked example shows what happens when ef_search is raised well above 1 on a real corpus.

06 · IMPORTANT DISTINCTIONS

Four terms beginners conflate

TermThe real difference
LayerOne full proximity graph over a subset of the corpus. Layer 0 always holds every point; higher layers hold exponentially fewer.
NodeOne stored vector, present in Layer 0 and possibly in some higher layers too (this toy graph: only A and D reach Layer 1).
EdgeA stored connection between two nodes in the same layer, capped in count by M. Not a computed distance -- a precomputed link the search walks along.
Entry pointThe one fixed node every search starts from, always in the topmost layer. This toy graph's entry point is A.
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"The search checks every node in a layer before moving on."

False -- it only ever compares the current node's own edges, moving as soon as a closer neighbour is found. That's what makes it fast: no layer is ever scanned in full.

"More layers always means a better index."

False -- layer count follows from M and the corpus size via the paper's own exponentially-decaying assignment rule; it is not a free dial to crank up.

"Greedy descent always finds the true nearest neighbour."

False -- this toy trace happened to land on the true answer, confirmed by brute-force check, but Concept 02's own recall<100% framing still applies to HNSW in general; a differently-shaped graph can dead-end at the wrong local minimum.

04
INTUITION

A city map with a highway system above the local streets

Layer 0 is the local street grid -- every address is reachable, but only via short hops between neighbours. Layer 1 (and any higher layers, in a larger real graph) is a sparse highway system connecting only a few hub addresses, letting a search cover large distances in a couple of hops before dropping down onto local streets for the final, precise approach. HNSW's search always enters via the highway system and only descends to local streets once no faster highway hop remains.

Analogy boundaryReal HNSW graphs typically use 2-5 layers with far higher per-node connectivity (M is commonly 12-48) than this toy graph's single extra layer and degree-2 chain. The layer-count and connectivity shown here are deliberately minimal, chosen so the trace in Section 10 can be followed by hand.

06
MECHANISM

Construction and search, both from the real paper

Construction (cited, not re-derived at proof-level depth). Each new point is inserted starting from the top layer down. The paper's own layer-assignment rule draws the point's maximum layer from an exponentially decaying random distribution, so most points land only in Layer 0, and progressively fewer reach each higher layer -- exactly why this toy graph's Layer 1 keeps only 2 of its 6 points. At each layer the point is inserted, it connects to up to M of its nearest already-inserted neighbours, found via a search using ef_construction as the candidate-list size.

Search (the mechanic this concept's own toy trace demonstrates). Starting at the fixed entry point in the topmost layer, the search greedily moves to whichever neighbour is closest to the query, among the current node's own graph edges only -- never scanning the whole layer. When no neighbour improves on the current node, that layer's local minimum has been reached and the search descends one layer, carrying the current node as the new layer's starting point. This repeats until Layer 0's own local minimum is reached, which becomes the returned answer (or, with ef_search > 1, the top candidates from a small maintained candidate list -- Section 10's own second worked example shows this dial in action).

WORKED EXAMPLE

A hand-traced toy graph, then a real tunable dial

The toy graph. Six 2-D points: A=(0,0), B=(3,1), C=(5,1), D=(7,2), E=(9,3), F=(10,4). Layer 0 (dense, all six): chain edges A–B, B–C, C–D, D–E, E–F. Layer 1 (sparse, two nodes): A–D. Query Q=(5.2, 1.1), entry point A.

PointCoordinatesDistance to Q
A(0, 0)5.3151
B(3, 1)2.2023
C(5, 1)0.2236
D(7, 2)2.0125
E(9, 3)4.2485
F(10, 4)5.6080

The trace. Layer 1, at entry point A (5.3151 from Q): A's only Layer 1 neighbour is D (2.0125 from Q), closer -- move to D. At D, D's only Layer 1 neighbour is A, already worse -- no improvement, Layer 1 terminates at D, descend to Layer 0. Layer 0, at D (2.0125 from Q): D's chain-neighbours are C (0.2236) and E (4.2485); C is closer -- move to C. At C (0.2236 from Q): C's chain-neighbours are B (2.2023) and D (2.0125), both farther -- no improvement, Layer 0's own local minimum is reached. The search returns C. A brute-force sort of all six distances confirms C (0.2236) is genuinely the smallest -- the true nearest neighbour among all six points, not merely the graph's local minimum. This trace happened to find the true answer; Concept 02's own recall < 100% framing still holds for HNSW in general, since a differently-shaped graph or a less fortunate entry point can dead-end at the wrong local minimum instead.

ef_search as a tunable dial (FAISS's own published SIFT1M benchmark, bench_hnsw.py, same corpus as Concept 02's own table). This toy trace used the equivalent of ef_search=1 -- always move to the single best neighbour. Real deployments tune ef_search upward to check more candidates per step. FAISS's own published numbers: at ef_search=16, 0.011 ms per query at 87.40% recall@1; at ef_search=256 (16x larger), 0.104 ms per query (a 9.45x latency increase) at 99.20% recall@1 (an 11.80-point recall gain). One single HNSW index, one internal parameter, a real recall/speed dial -- distinct from Concept 02's own cross-index dial (choosing between different named indexes entirely).

Verification methodThe six toy distances were computed with two independently-structured Node.js scripts -- one using a shared dist() helper function, one with fully inline manual arithmetic for each point -- and both produced identical results to the same precision. A third script brute-force-sorted all six distances to confirm C is the true global minimum, not merely a local one. The ef_search ratios (9.45x latency, 11.80 recall points) were each computed two ways (direct division/subtraction, and via intermediate rounding) with matching results.
11
CONCRETE USE

A clean fit, a boundary case, and a mistake

CLEAN FIT

A million-scale corpus needing sub-millisecond queries

HNSW's O(log n) search scales far better than Concept 01's own linear exact search once the corpus is large.

BOUNDARY CASE

A corpus small enough to fit in one layer

If every point lands in Layer 0 only (no higher layers formed), the search degenerates to a single-layer greedy walk with no descent step at all.

MISTAKE TO AVOID

Treating greedy descent as guaranteed-correct

This concept's own toy trace found the true answer, but that is not a guarantee -- HNSW's own recall is measured, not assumed, exactly as Concept 02 established.

CODE

The toy graph's own greedy search, implemented directly

PYTHON · FROM SCRATCH -- REPRODUCES THIS CONCEPT'S OWN SIX-POINT TRACE EXACTLY 
import math

points = {
    "A": (0, 0), "B": (3, 1), "C": (5, 1),
    "D": (7, 2), "E": (9, 3), "F": (10, 4),
}
layer1_edges = {"A": ["D"], "D": ["A"]}
layer0_edges = {
    "A": ["B"], "B": ["A", "C"], "C": ["B", "D"],
    "D": ["C", "E"], "E": ["D", "F"], "F": ["E"],
}

def dist(p, q):
    return math.sqrt((p[0] - q[0]) ** 2 + (p[1] - q[1]) ** 2)

def greedy_descend(entry, edges, query):
    current = entry
    while True:
        current_d = dist(points[current], query)
        neighbours = edges.get(current, [])
        better = min(neighbours, key=lambda n: dist(points[n], query), default=None)
        if better is None or dist(points[better], query) >= current_d:
            return current  # local minimum -- no improving neighbour
        current = better

query = (5.2, 1.1)
top_of_layer1 = greedy_descend("A", layer1_edges, query)   # -> "D"
answer = greedy_descend(top_of_layer1, layer0_edges, query)  # -> "C"

true_best = min(points, key=lambda k: dist(points[k], query))
assert answer == true_best == "C"

DIAGNOSIS

Failure modes

UNDER-CONNECTED GRAPH

M set too low for the corpus

Symptom: greedy descent dead-ends at the wrong local minimum more often than expected, since too few edges exist to route around a bad early move.

STATIC ef_search

Never tuning ef_search per workload

Symptom: an index left at a default ef_search either wastes latency budget (too high) or leaves recall on the table (too low) -- Section 10's own table shows both directions are real, measured costs.

17
CORRECTION

Misconceptions

Incorrect beliefCorrection
Greedy descent always finds the true nearest neighbourFalse -- it finds a local minimum along the path taken; Section 10's own trace happened to match the true global minimum, confirmed separately by brute force.
More layers automatically means better recallFalse -- layer count follows from the paper's own random assignment rule tied to M and corpus size, not a free-standing quality knob.
ef_search only affects speed, not correctnessFalse -- Section 10's own FAISS numbers show ef_search moving both latency and recall@1 together, in the same direction.
18
REALITY

Production implications

  • ef_search is usually the first dial tuned in production -- raise it until recall clears the product's own bar, watching the latency cost the whole way, per Section 10's own table.
  • M and ef_construction are set once at build time and are far more expensive to change than ef_search, since changing them means rebuilding the graph.
  • HNSW's own graph must fit in memory for fast traversal -- a real operational constraint that Concept 06 (recall-latency-memory trade-offs) generalizes across all three named ANN families.
  • Concept 04's own IVF is the real alternative when memory, not latency, is the binding constraint.

RECALL

Knowledge check

Describe HNSW's search rule from memory.
Start at the fixed entry point in the sparse top layer; greedily move to the closest neighbour among the current node's own graph edges; descend a layer when no neighbour improves; stop when Layer 0's own local minimum is reached.
Why does this concept's own toy trace terminate at C rather than continuing to B?
Because C's own chain-neighbours, B (2.2023) and D (2.0125), are both farther from the query than C itself (0.2236) -- no improving move remains, so C is the layer's local minimum and the search stops.
What does raising ef_search from 16 to 256 cost and buy, per Section 10's own FAISS numbers?
Costs a 9.45x latency increase (0.011 ms to 0.104 ms per query); buys an 11.80-point recall@1 gain (87.40% to 99.20%) -- all inside one single HNSW index, no rebuild required.

FEEDBACK

Solution and teach-back

Open the worked solution
Distances to (5,0): P=5, Q=3, R=1, S=1, T=3. At Q (distance 3), Q's chain-neighbours are P (5) and R (1) -- R is closer, move to R. At R (distance 1), R's chain-neighbours are Q (3) and S (1) -- S ties R's own distance, not strictly closer, so no improving move exists and the search terminates at R. A brute-force check shows R and S are exactly tied at distance 1, both true nearest neighbours -- the search returns one valid answer, R, without needing to break the tie.

Teach-back: why does a tie between two equally close neighbours not force the search to keep moving?

CAREER PRACTICE

Interview questions

Conceptual: why does HNSW start searching at the top layer instead of Layer 0?
The top layer is sparse, so a single hop there can cover a large distance across the embedding space; descending only once no closer neighbour remains means the expensive, fine-grained Layer 0 search starts already close to the answer.
Mathematical: given ef_search=16 at 0.011 ms/87.40% recall and ef_search=256 at 0.104 ms/99.20% recall, compute the latency ratio and recall-point gain.
Latency ratio = 0.104 ÷ 0.011 ≈ 9.45x. Recall gain = 99.20% − 87.40% = 11.80 points.
Coding: extend this concept's own greedy_descend function to also return the full path visited.
Accumulate each `current` node into a list before reassigning it inside the while loop, and return that list alongside the final answer -- for this concept's own toy graph, the Layer 0 path would be ["D", "C"].
System design: a production HNSW index's recall dropped after a corpus grew 10x. What do you check first?
Whether M and ef_construction, both set for the old corpus size, are still adequate -- the paper's own layer-assignment rule ties layer structure to corpus size, so a much larger corpus with unchanged construction parameters can produce a thinner, worse-connected graph than a fresh build would.
Debugging: two runs of the same HNSW index on the same query return different top-1 results. Why might that happen even with no index changes?
Concurrent inserts can change edges mid-query in a live index, or ef_search > 1 combined with tied or near-tied distances can make the maintained candidate list's exact contents depend on floating-point comparison order -- Section 21's own tie between R and S shows the same effect at toy scale.
