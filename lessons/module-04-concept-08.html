MODULE 04 · CONCEPT 08

Ranking functions
and optimization objectives.

Concept 06 built a distribution from raw scores; Concept 07 measured how well that distribution agrees with the truth. Neither one, on its own, said what a retrieval system actually does with either idea. This concept closes that gap with two separate objects. A ranking function sorts candidates by score — the thing a retrieval system runs at inference, needing nothing but the raw scores Concepts 03-04 already built. A contrastive optimization objective is Concept 07's cross-entropy, framed as one positive candidate against several negatives — the thing a training loop actually minimizes to make the raw scores themselves better.

01 · CONCEPT FIRST

A ranking function sorts; an optimization objective trains

RANKING FUNCTION

Given raw scores, sort the candidates from largest to smallest. Needs nothing but the scores themselves — no distribution, no truth, no training. Runs at inference, every query, every time.

OPTIMIZATION OBJECTIVE

A number a training loop tries to shrink. This concept's version — the contrastive loss — is Concept 07's cross-entropy, computed with one candidate marked "positive" (actually relevant) and the rest marked "negative."

First memory: ranking answers "which one wins, right now?"; the optimization objective answers "how do I change the scores so the right one wins more decisively next time?"
02 · WHY IT EXISTS

Concepts 06-07 never said when either piece actually runs

Concept 06 proved softmax never changes which score is largest. Concept 07 showed cross-entropy punishes a confidently wrong distribution. Neither concept connected those facts to an actual system: does a retrieval system need to compute a full distribution just to return its top-k results? And what, concretely, is a model being trained against? This concept answers both.

WITHOUT THIS CONCEPT

It's tempting to assume softmax has to run every time a query is answered, since it "produces the real probabilities."

WITH THIS CONCEPT

Concept 06 already proved ranking is invariant to temperature — so a live system can skip softmax entirely at inference and just sort the raw scores (b03).

03 · CONCRETE EXAMPLE

The same three scores, doing two different jobs

Reusing Concepts 06-07's exact scores, z = [2.0, 1.0, 0.1], with doc 1 marked as the query's actual positive (relevant) passage and docs 2-3 as negatives.

RANKING (INFERENCE)

Sort z directly: doc 1 > doc 2 > doc 3. No softmax computed at all — Concept 06 Section 09 guarantees this is the same order softmax would give, at any temperature.

LOSS (TRAINING)

Cross-entropy against doc 1 as the positive, cited directly from Concept 07: −ln(0.659) ≈ 0.4170 nats.

WHAT CHANGED

Nothing new was computed — the ranking reused raw scores, the loss reused Concept 07's exact formula and exact number.

WHAT'S ACTUALLY NEW

The framing: "positive vs. negatives" instead of "candidates vs. true label" — the same object, a name retrieval training literature uses (Section 05).

04 · TECHNICAL MECHANISM

What training actually does: push the positive's raw score up

Doc 1's raw scoreSoftmax (doc 1 share)Contrastive loss
2.0 (start)0.6590.4170 nats
3.00.8400.1743 nats
4.00.9350.0677 nats
5.00.9750.0254 nats

Docs 2-3's scores never move in this table — only doc 1's does. As it rises, its softmax share climbs toward 1 and the loss falls toward 0. This is, mechanically, what a training step does: nudge the raw scores (via the embedding model's weights, Module 09, forward reference) so the positive's share grows and the loss shrinks — the exact numbers above were computed with Concept 06's own softmax formula, not a new one.

05 · ARCHITECTURE / FLOW

Where ranking and the loss each sit

Concept 06 — distribution↓Concept 07 — cross-entropy↓Concept 08 — ranking at inference, contrastive loss at training↓Module 09 — the actual training loop

Ranking and the loss never run at the same moment in a real system's life. Ranking runs constantly, in production, on every query, using only raw scores. The loss runs only during training, on batches of queries with known positives, and never touches a live user's request at all.

06 · IMPORTANT DISTINCTIONS

Ranking function, loss function, and where negatives come from

TermWhat it actually isCommon confusion
Ranking functionSorts candidates by raw score — an inference-time operation, no training involvedAssumed to require a softmax pass; Concept 06 Section 09 already proved raw scores alone give the identical order
Contrastive lossConcept 07's cross-entropy, with one positive and one or more negatives — a training-time numberTreated as a different formula from cross-entropy; it is the identical formula, just applied to a positive/negatives framing (Section 09)

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"A live retrieval system computes softmax to rank its results."

It doesn't need to — Concept 06 Section 09 already proved raw scores sort identically to any softmax output, for any temperature.

"Contrastive loss is a completely different idea from cross-entropy."

It's the identical formula (Section 09) — "contrastive" describes the positive-vs-negatives framing, not a different piece of math.

"More negatives per query always makes training strictly better."

More negatives make the softmax's denominator larger and the task harder, which usually helps up to a point — but this concept only names the trade-off; tuning it is out of scope here.

"The ranking function is what gets trained."

The ranking function itself has no parameters — training adjusts the embedding model producing the raw scores, and the ranking function is simply re-run on whatever scores that model happens to output.

08 · YOUR PROJECT MAPPING

Ranking and training, in the Oracle RAG project

AT INFERENCESort raw similarity scores, no softmax

Retrieving the top-k chunks for a live query only ever needs Concepts 03-04's raw scores, sorted directly — the fastest possible path, and provably correct per Concept 06 Section 09.

04
INTUITION

A leaderboard, and the coach who studies it afterward

A ranking function is the leaderboard itself — whoever scored highest today is listed first, full stop, no further analysis needed. The contrastive loss is the coach reviewing that leaderboard afterward, specifically asking: "the athlete who should have won — how far below first place did they actually land, and by how much do we need to raise their performance before they'd win outright?" The leaderboard gets read constantly, every event. The coach's review happens on its own schedule, entirely separately, and never changes what today's leaderboard said.

Analogy boundaryThe coach analogy captures "reviewed separately, on its own schedule," not the exact arithmetic — the loss's exact value comes from Concept 07's formula, not from any subjective coaching judgment.

09
MATHEMATICS

The contrastive loss is exactly Concept 07's cross-entropy

Write the InfoNCE-style contrastive loss out in full, for a query q, its positive d⁺, and negatives D⁻:

L(q, d⁺, D⁻) = −log( exp(sim(q,d⁺)/τ) / Σ_{d ∈ {d⁺}∪D⁻} exp(sim(q,d)/τ) )

The fraction inside the log is exactly Concept 06's softmax_τ, applied to the similarity scores of {d⁺}∪D⁻, evaluated at the positive's own index. So the whole expression is:

L(q, d⁺, D⁻) = −log( softmax_τ(sim scores)[d⁺] ) = H(P, Q), P one-hot at d⁺, Q = softmax_τ(sim scores)

— which is precisely Concept 07's definition of cross-entropy against a one-hot truth. Nothing about temperature, the exponential, or the normalizing sum is new; only the names "positive" and "negatives" are.

11
CONCRETE USE

Four cards: a clean fit, a boundary case, a production use, and a mistake

CLEAN FIT

Ranking a live query's top-k without softmax

Sorting raw similarity scores directly returns the identical order softmax would, at any temperature — Concept 06 Section 09, applied.

BOUNDARY CASE

A single negative (one positive, one negative)

With only one negative, the loss reduces to a two-outcome cross-entropy — the same formula, the smallest possible contrastive setup.

PRODUCTION USE

In-batch negatives at scale

A training batch of 100 queries gives every query 99 free negatives — other queries' positives — with no extra retrieval or mining step (Section 18).

MISTAKE TO AVOID

Computing softmax at serving time "to be safe"

It changes nothing about the returned ranking (Concept 06 Section 09) and only adds unnecessary computation to every live query.

12
CODE

Ranking and the contrastive loss, from scratch

PYTHON · NO LIBRARIES 
import math

def rank(scores):
    # A ranking function needs only the raw scores -- no softmax at all.
    return sorted(range(len(scores)), key=lambda i: -scores[i])

def softmax(scores, T=1.0):
    m = max(scores)
    exps = [math.exp((s - m) / T) for s in scores]
    total = sum(exps)
    return [e / total for e in exps]

def contrastive_loss(scores, positive_idx, T=1.0):
    # Concept 07's cross-entropy, against a one-hot truth at positive_idx.
    probs = softmax(scores, T)
    return -math.log(probs[positive_idx])

z = [2.0, 1.0, 0.1]

print(rank(z))                                   # [0, 1, 2] -- doc 1 first
assert rank(z) == rank(softmax(z, 1.0))            # ranking is invariant, Concept 06 Section 09
assert rank(z) == rank(softmax(z, 0.3))            # still true at a different temperature

loss = contrastive_loss(z, positive_idx=0)
print(round(loss, 4))                             # 0.4170
assert abs(loss - 0.4170) < 1e-3

loss_after_training = contrastive_loss([5.0, 1.0, 0.1], positive_idx=0)
assert loss_after_training < loss                 # raising the positive's score shrinks the loss

ECOSYSTEM

Where production code exposes the same mechanism

The sentence-transformers library's MultipleNegativesRankingLoss implements exactly this concept's loss, treating every other example in a training batch as a free negative for the current one — the in-batch negatives strategy named in Section 18. PyTorch's torch.nn.functional.cross_entropy (Concept 07, Section 13) can be called directly on a batch of similarity scores treated as logits, with the positive's index as the target — no separate "contrastive loss" implementation is actually required, since it is the same function under a different name.

16
DIAGNOSIS

Failure modes

UNNECESSARY INFERENCE-TIME SOFTMAX

Computing a full distribution just to rank

Wastes compute on every live query for a result Concept 06 Section 09 already guarantees is unchanged.

TOO FEW NEGATIVES

A softmax denominator with almost no competition

If only one weak negative is present, the loss can shrink to near 0 without the model actually learning to discriminate hard cases.

FALSE NEGATIVES IN-BATCH

Another query's positive accidentally being relevant to this query too

In-batch negatives assume other queries' positives are irrelevant here — when that assumption breaks, the loss punishes the model for a correct answer.

TEMPERATURE MISMATCH

Using a training-time τ that doesn't match deployment assumptions

Since ranking is temperature-invariant (Concept 06) but the loss is not, an unexamined τ can still shape training dynamics even though it never affects served rankings.

18
REALITY

Production implications

  • Never compute softmax purely to serve a ranking — Concept 06 Section 09's invariance makes it pure overhead at inference time.
  • Prefer in-batch negatives as the default training strategy for dense retrievers — it scales with batch size for free, and is the approach behind widely used dense-passage-retrieval training recipes (Section 24).
  • Watch for false negatives when using in-batch negatives at scale — as batch size grows, the chance that some other query's positive is also secretly relevant to the current query rises, and needs periodic auditing rather than being assumed away permanently.
19
RECALL

Knowledge check

Why doesn't a production retrieval system need to compute softmax to return a ranked list?
Concept 06 Section 09 proves softmax never changes the order of its inputs for any T > 0 — sorting the raw scores directly always gives the identical ranking.
Is the contrastive loss a different formula from cross-entropy?
No — Section 09 shows it is exactly Concept 07's cross-entropy formula, with the true distribution one-hot at the positive candidate and the predicted distribution given by Concept 06's softmax over similarity scores.
What are in-batch negatives, and why are they the standard choice?
Other queries' positive documents, already present in the same training batch, reused as the current query's negatives — free, requiring no extra retrieval or mining step (Section 13, Section 18).

FEEDBACK

Solution and teach-back

Open the worked solution
Ranking directly from z = [1.5, 1.5, 0.5, -1.0]: the positive (index 0) is tied for first with the second candidate (index 1), both ahead of index 2, ahead of index 3 — order [0 or 1 tied, then 2, then 3]. Softmax at T=1: exponentials ≈ [4.4817, 4.4817, 1.6487, 0.3679], summing to ≈10.9800, giving probs ≈ [0.4083, 0.4083, 0.1502, 0.0335]. Contrastive loss against the positive: −ln(0.4083) ≈ 0.8956 nats. Raising temperature to T=3 would NOT change the ranking — Concept 06 Section 09 guarantees the order is preserved for any T > 0; only the sharpness of the softmax shares (and therefore the loss) would change, not which candidates lead.

Teach-back: explain, in your own words, why the positive being exactly tied with another candidate here produces a meaningfully higher loss (0.8956 nats) than Concept 07's clear-lead example (0.4170 nats), even though neither case has the positive ranked last.

23
CAREER PRACTICE

Interview questions

Explain why a contrastive loss and a plain classification cross-entropy loss are, mathematically, the same thing.
Both are H(P,Q) = −ln(q_correct) for a one-hot true distribution P and a predicted softmax distribution Q — the only difference is that a classification problem has a fixed set of classes, while a retrieval query's "classes" are its positive and negative candidates, which vary per query (Section 09).
Why can a production retrieval system skip computing softmax entirely?
Because ranking only needs the order of the scores, and softmax_T never changes that order for any T > 0 (Concept 06 Section 09) — sorting the raw scores directly is both correct and cheaper.
What is an in-batch negative, and what production risk does relying on them introduce as batch size grows?
Another query's positive document, reused as a free negative for the current query. As batch size grows, the chance that one of those "negatives" is secretly also relevant to the current query rises, silently penalizing the model for a correct answer (Section 16, Section 18).
Design question: you need to train a new embedding model to distinguish two very similar negative candidates from the true positive. What lever from this concept would you reach for first, and why?
Increase the number and difficulty of negatives (harder negatives specifically, not just more of them) so the softmax's denominator forces a sharper distinction — the loss only pushes the model to separate the positive from whichever negatives are actually present in it (Section 16's "too few negatives" failure mode, in reverse).
