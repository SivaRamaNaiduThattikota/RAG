MODULE 10 · CONCEPT 02

Three jobs the database owns.
Three it never touches.

Concept 01 answered which category of system this course lives inside -- a vector database, not a store or a search engine. That leaves an open question: what does a database sitting inside a RAG pipeline actually *do*, moment to moment? This concept answers it with a fixed list of three owned responsibilities -- persistence, transactional consistency, query execution -- and three explicit exclusions -- chunking, embedding, generation -- with a citation behind every claim on both sides of that boundary.

01 · CONCEPT FIRST

After "which category," the next question is "which jobs"

Concept 01 established that this course runs inside a vector database, not a bare store or a search engine. That tells you the kind of system you're dealing with -- it doesn't yet tell you what that system actually does when a chunk arrives or a query comes in. This concept answers that directly with three owned jobs and three explicit non-jobs.

First memory: "vector database" is a category. "Persistence, transactional consistency, query execution" are the three specific jobs that category commits to owning. This concept is about the second list, not the first.
02 · WHY IT EXISTS

A quick anchor back to Concept 01, not a re-teach

Concept 01's own boundary: a vector database is a full DBMS that owns its own indexing, compression, filtering, tombstones and replication as first-class features, with Oracle AI Database as this module's own exemplar. That's the category. This concept doesn't re-argue it -- it takes that category as given and asks the more specific question a beginner runs into next: once you're inside that category, what is the database itself actually responsible for on every single request?

03 · CONCRETE EXAMPLE

Three owned jobs, named plainly

1 · PERSISTENCE

When a chunk arrives, the database stores its text reference, its embedding vector, and its metadata (like tenant_id) together, as one unit -- not three separate systems you keep in sync by hand.

2 · TRANSACTIONAL CONSISTENCY

A write either fully lands or it doesn't land at all. An update or delete never leaves the index in a half-changed state.

3 · QUERY EXECUTION

At search time, the database runs the vector search and applies any metadata filter (like "only this tenant's chunks") as a single operation, not two steps you glue together yourself.

Second memory: these three are a fixed, closed list for this concept -- not a starter set. Everything else a database happens to do (backups, monitoring, user management) is real, but it's outside what this concept is naming.
04 · TECHNICAL MECHANISM

Owned job 1: persistence -- one unit, not three systems

A chunk has three parts: its text reference, its embedding vector, and its metadata. If those three lived in three different systems, keeping them lined up would be your job, by hand, forever -- and a filtered query could silently return a chunk whose vector and metadata had drifted out of sync. Because persistence is an owned database job, the database itself guarantees that a chunk's three parts arrive, live, and get returned together, as one row-like unit.

05 · ARCHITECTURE / FLOW

Owned job 2: transactional consistency -- lands fully, or not at all

Write arrives at the database→ Either the whole write commits, or none of it does→ Index never sits half-updated

This is the same idea Module 09 Concept 08 already built for updates and deletes -- mark the old entry as gone first (a tombstone), then clean it up later, so nothing is ever caught mid-change. That mechanism isn't re-explained here; it's simply named as the thing that makes "transactional consistency" one of the database's own owned jobs, not something the app has to guarantee itself.

06 · IMPORTANT DISTINCTIONS

Owned job 3 vs. what the database does not own

JobWho owns it
Query execution -- vector search + metadata filter as one operationThe database. It picks from Module 09 Concept 07's own named strategies (pre-filtering, post-filtering, filtered/integrated ANN) internally.
Splitting a document into chunksModule 07 -- finished long before the database ever sees anything.
Turning text into a vectorModule 08 -- also finished before the database sees anything; it only ever receives an already-computed vector.
Generating an answer from the retrieved chunksPhase 3, starting Module 11 -- happens strictly after the database hands its results back. The LLM never talks to the database directly.
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"The database must be doing the chunking, since it stores chunks."

False -- by the time a chunk reaches the database, Module 07's chunking work is already finished. The database only ever sees the finished result.

"The database calls the LLM to generate the answer."

False -- the database hands back matching chunks and stops. Building a prompt and calling an LLM is a separate stage (Phase 3), and the LLM never queries the database directly.

09 · READINESS CHECK

One insert, one query, traced across the boundary

Take one chunk on its round trip. Insert: the chunk is already made (Module 07) and its vector is already computed (Module 08) -- both before the boundary; the database then persists and commits the row as one atomic unit -- at the boundary; the app logs the returned chunk_id -- after the boundary. Query: the query text is already embedded (Module 08) -- before; the database runs the ANN search and the tenant filter together and returns five matching chunks -- at; those five chunks get handed to a separate generation stage -- after, and the LLM never queries the database itself.

03
PREVIEW

Three owned responsibilities, the spine of this whole concept

OWNED · 1

Persistence

A chunk's identity, embedding vector and metadata are stored together, as one durable unit.

OWNED · 2

Transactional consistency

A write fully commits or fully rolls back; updates/deletes never leave the index half-changed.

OWNED · 3

Query execution

Vector search and metadata filter run as one operation, not two steps the app glues together.

Every section from here to Section 16 maps back to exactly one of these three. Sections 13-15 then name the three things this list deliberately excludes.

04
DEFINITION

Owned responsibility 1: persistence

Persistence, here, means the database stores a chunk's identity, its embedding vector, and its metadata together, as one durable unit -- not as three separate systems the application has to keep aligned by hand. This is what turns "a place where vectors happen to be saved" into "a database" in the sense Concept 01 already defined.

05
WHY IT MATTERS

Why "together" is the whole point

If a vector and its metadata could live in two different systems and drift out of sync, a filtered query could silently return a stale or mismatched result -- a chunk whose metadata says one tenant while its vector was actually written for another. Persistence being an owned database job means the database itself guarantees that alignment; the application never has to reconcile the two on its own.

06
DEFINITION

Owned responsibility 2: transactional consistency

python-oracledb's own transaction-management documentation states it directly: "A database transaction is a grouping of SQL statements that make a logical data change... By default, python-oracledb does not commit this transaction to the database. You can explicitly commit or roll it back using the methods Connection.commit() and Connection.rollback()." A write, in other words, either fully commits or fully rolls back -- there is no partially-landed state the application has to detect and clean up itself.

07
MECHANISM

The mechanism this guarantee rides on for updates and deletes

Module 09 Concept 08 already verified the mechanism directly: Weaviate's own vector-index documentation states that on delete, "objects are marked as deleted, but they are still connected to the HNSW graph" until an asynchronous cleanup process reassigns edges; Qdrant's own Vacuum Optimizer waits for a deleted_threshold of 0.2 before physically compacting removed entries. Neither of those mechanisms is re-derived here -- they're cited directly as the reason transactional consistency for updates and deletes doesn't require an in-place rewrite to stay atomic.

08
SYNTHESIS

One owned job, two different underlying machines

An insert commits atomically, in the classic sense Section 06 describes. An update or delete gets the same atomicity guarantee through a different route -- mark-then-compact rather than an in-place rewrite. Both are instances of the same owned responsibility: at no point does a caller ever observe a half-written or half-deleted state. That's why "transactional consistency" is listed as a single job, even though inserts and deletes lean on different machinery underneath.

09
DEFINITION

Owned responsibility 3: query execution

At query time, the database runs the vector similarity search and applies any metadata filter (like restricting to one tenant's own chunks) as a single operation -- not as two separate steps the application has to run and then glue together itself.

10
MECHANISM

Which strategy runs underneath is the database's own choice

Module 09 Concept 07 already named three strategies a database can choose from to execute that combined operation: pre-filtering, post-filtering, and filtered/integrated ANN (Weaviate's own ACORN and sweeping approaches, Qdrant's filterable HNSW). That concept's own verified numbers are reused directly here, unchanged: on a 20-chunk, 30%-selectivity corpus, retrieving k=5 under post-filtering requires over-fetching to the top-17 candidates -- not just the top-5 -- to survive discarding the 12 that get filtered out, a 3.4x over-fetch (17 ÷ 5 = 3.40). Which of the three strategies actually runs is an internal decision the database makes; the application only ever calls one filtered search.

11
SOURCE

Grounding query execution in the database's own documented design

Weaviate's own filtering documentation is the primary source behind Sections 09-10: the pre-filtering/post-filtering/integrated-ANN distinction is Weaviate's own documented design choice, not an abstraction this course invented. That's what grounds "query execution" as a real, verifiable database responsibility rather than a convenient simplification.

13
EXCLUSION 1

Not owned: splitting documents into chunks

Module 07, "Chunking & document representation" (complete, 10/10), owns splitting source documents into chunks. That work is strictly out of scope for the database layer -- named here only as a forward reference, with zero re-teaching of any chunking mechanism. By the time a chunk reaches the database, this stage has already finished.

14
EXCLUSION 2

Not owned: turning text into a vector

Module 08 (complete, 11/11) owns turning chunk text and query text into vectors. LangChain's own embeddings documentation states it directly: "Embedding models transform raw text ... into a fixed-length vector of numbers that captures its semantic meaning ... texts with similar ideas are placed close together in the vector space." The database never runs this step itself -- it only ever receives an already-computed vector, whether that vector belongs to a chunk being inserted or a query being searched.

15
EXCLUSION 3

Not owned: generating an answer

Phase 3 (Module 11 onward, not yet built) owns building a prompt from retrieved chunks and calling a language model. LangChain's own models documentation states it directly: "Models are the reasoning engine of agents. They drive the agent's decision-making process..." The LLM never queries the database directly -- it only ever receives whatever the database has already returned, after the database's own job is finished.

TRACE A, CONTINUED

Six months later: the same boundary handles an edit

A later edit to that same chunk is delete_chunk immediately followed by write_chunk, at the identical boundary. Atomicity here is delivered by Module 09 Concept 08's own verified mark-then-compact mechanism, cited directly and not re-derived: Weaviate keeps a tombstoned object wired into its HNSW graph until an asynchronous cleanup process reassigns its edges; Qdrant's own Vacuum Optimizer waits for its deleted_threshold=0.2 before physically compacting. This is what "transactional consistency of an update" concretely looks like -- not a single in-place rewrite, but a delete-then-write pair that the database's own tombstone lifecycle keeps atomic from the caller's point of view.
