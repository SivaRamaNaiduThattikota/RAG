01 · CONCEPT FIRST

What Oracle actually does with both signals

This concept answers a specific question: what does Oracle actually do when a chunk table needs both keyword and semantic retrieval at once? Oracle's real answer is a single, unified CREATE HYBRID VECTOR INDEX plus one DBMS_HYBRID_VECTOR.SEARCH call -- not a hand-rolled UNION of CONTAINS and VECTOR_DISTANCE written by hand in application code.

First memory: keyword search catches exact terms and misses paraphrases; vector search catches paraphrases and can't privilege an exact match. Hybrid fusion is Oracle scoring both, inside the database, and merging them into one number per row.
02 · WHY IT EXISTS

Neither signal alone is enough

Keyword search (Oracle Text's CONTAINS/SCORE) catches exact-term matches and misses paraphrases. Vector search (Concept 05's VECTOR_DISTANCE) catches paraphrases but has no way to privilege a row that happens to share the query's exact wording. Production retrieval needs both signals combined into one ranked list, not a forced choice between them -- which is exactly what a hybrid index is for.

03 · CONCRETE EXAMPLE

Acme's six matches, two ways of finding them

Module 10's own running Acme dataset has exactly six relevant chunks. Of those six, only four contain literal query-term overlap that Oracle Text's CONTAINS/SCORE() would actually match -- the other two are paraphrases with zero lexical overlap, so Oracle Text alone misses them. Vector search alone always surfaces all six (locked in from Concepts 05 and 06) but has no exact-match confidence signal. Hybrid fusion is the only mode that both recovers all six and ranks the double-hit chunks -- the ones matched by both signals -- highest.

04 · TECHNICAL MECHANISM

The minimal real syntax

Per Oracle's own documentation as of this writing, the minimal form is CREATE HYBRID VECTOR INDEX my_hybrid_idx ON doc_table(text_column) PARAMETERS('MODEL my_embed_model'); -- one statement, naming the text column and the embedding model, that builds both Oracle Text structures and vector-search structures together inside a single domain index.

05 · ARCHITECTURE / FLOW

Two scores, one fusion step

Query text→ Lexical score (CONTAINS-style)→ Fused via RSF / RRF / WRRF→ Semantic score (vector distance, normalized 0-100)

Query text feeds two scoring paths at once inside the same index: a keyword path producing a CONTAINS-style lexical score, and a vector path producing a cosine-based similarity that Oracle normalizes onto a 0-100 "semantic score" scale before it's comparable to the lexical side. One named fusion formula -- RSF, RRF, or WRRF -- merges both into the final ranked result.

06 · IMPORTANT DISTINCTIONS

Legacy Oracle Text vs. the modern unified index

PathThe real difference
Legacy: standalone CONTEXT index + CONTAINS/SCORE()Still real, still documented, still useful for pure-keyword cases -- but produces one lexical score only, with nothing to fuse against.
Modern: CREATE HYBRID VECTOR INDEX + DBMS_HYBRID_VECTOR.SEARCHOne domain index storing both text-search and vector-search structures together, fusing both scores internally via RSF/RRF/WRRF.
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Hybrid retrieval means writing two SQL queries yourself and UNIONing the results."

False. Oracle's real mechanism is one index (CREATE HYBRID VECTOR INDEX) plus one query function (DBMS_HYBRID_VECTOR.SEARCH) that fuses both signals inside the database engine.

"Vector distance and a CONTAINS score can just be added together."

False. They're on different scales -- Oracle normalizes the vector side into a comparable 0-100 semantic score before fusing it with the lexical score using RSF, RRF, or WRRF.

04
INTUITION

Not a choice between two search engines -- a merge

Hybrid retrieval isn't picking a winner between keyword search and vector search. It's letting Oracle score a row both ways at once -- once for exact-term overlap, once for semantic closeness -- and merging both scores into a single number per row before ranking anything. Neither score wins outright; the fusion formula decides how much weight each one carries.

06
MECHANISM

One JSON call, fused inside the engine

DBMS_HYBRID_VECTOR.SEARCH executes the fused ranking inside the database engine via one JSON-parameterized call and a search_fusion mode -- not a UNION written in application code. The package also exposes GET_SQL (returns the equivalent SQL text Oracle would run) and SEARCHPIPELINE, per Oracle's own package overview. The lexical side runs Oracle Text's CONTAINS-style scoring; the vector side runs a cosine-based similarity that Oracle normalizes onto its 0-100 semantic-score scale; one named formula (RSF, RRF, or WRRF) merges both into the row's final fused score.

09
MATHEMATICS

The RSF formula, reproduced before it's trusted

Per result: RS = score × weight, for each side (text and vector). RSF = (sum of RS across both sides) ÷ (sum of 100 × weight across both sides) × 100.

This formula is derived from Oracle's own published worked Table 8-3 -- Oracle does not state it as a bare equation on the page, but three example rows with known vector/text scores, weights, and fused outputs are published. Before applying this formula to any new numbers, it was independently reproduced against Oracle's own three published rows and matched to 2 decimals (454/75.67, 345/57.5, 245/40.83) -- a correctness check, not a re-derivation from first principles.

Two undocumented internals, flagged plainlyThe exact distance-to-semantic-score (0-100) normalization formula Oracle uses internally is not published on any reachable page -- only the directional statement (100 best, 0 worst) is confirmed. Separately, Oracle Text's real internal SCORE() weighting (Salton/inverse-frequency-based) is documented only qualitatively -- rare terms score higher, and Oracle publishes a table of occurrences-needed-to-score-100 by corpus size, but the literal formula itself is not published. Both stand-ins used in Section 10's worked example are flagged there as original, transparent substitutes, not reproductions of Oracle's actual internal algorithms.

WORKED EXAMPLE

A lexical tie that hybrid fusion breaks

This continues Concept 03's own doc_9f21 / ver_9f21_2 (CURRENT version) directly, completing Concept 03's own deliberately truncated chunk text and adding four sibling chunks from the same version:

  • chk_9f21_2_01 (idx 1): "Vendor accounts are provisioned by IT with least-privilege access scoped to one system per contract."
  • chk_9f21_2_02 (idx 2): "Employee password resets use a separate self-service flow described in the internal IT handbook." -- wrong entity (employee, not vendor)
  • chk_9f21_2_03 (idx 3): "To reset a vendor account, an admin must open the vendor portal, select Reset Credentials, and issue the vendor a new temporary password." -- completes Concept 03's own truncated seed text
  • chk_9f21_2_04 (idx 4): "Vendor security policy defines third-party access requirements for internal systems."
  • chk_9f21_2_05 (idx 5): "Vendor accounts must be revoked within 24 hours of contract termination during offboarding."

Query: "reset vendor account password" (stemmed terms: reset, vendor, account, password). The teaching point: chk_02 (employee reset -- wrong entity) ties lexically with chk_01 and chk_05 (correct entity, vendor) -- lexical scoring alone cannot break that tie or demote the topically wrong chunk. Vector similarity can and does.

SQL · LEGACY ORACLE TEXT PATH 
CREATE INDEX chunks_ctx_idx ON chunks(chunk_text) INDEXTYPE IS CTXSYS.CONTEXT;

SELECT c.chunk_id, SCORE(1)
FROM chunks c
WHERE CONTAINS(c.chunk_text, 'vendor account reset', 1) > 0
ORDER BY SCORE(1) DESC;
SQL · MODERN UNIFIED PATH (per Oracle's own documentation as of this writing) 
CREATE HYBRID VECTOR INDEX my_hybrid_idx ON doc_table(text_column)
  PARAMETERS('MODEL my_embed_model');

select json_serialize(DBMS_HYBRID_VECTOR.SEARCH(json('{
  "hybrid_index_name":"my_hybrid_idx",
  "search_scorer":"rsf",
  "search_fusion":"UNION",
  "vector":{"search_text":"reset vendor account password","search_mode":"CHUNK","aggregator":"MAX","score_weight":1,"rank_penalty":5},
  "text":{"contains":"reset AND vendor AND account","score_weight":10,"rank_penalty":1},
  "return":{"values":["rowid","score","vector_score","text_score"],"topN":5}
}')) RETURNING CLOB pretty);

Scoring rule, verbatim from Oracle's docs and the key teaching point: vector similarity produces a VECTOR_DISTANCE-based score; Oracle Text produces a CONTAINS/keyword score; these are on different scales, so Oracle normalizes the vector side into a semantic score on a 100(best)-0(worst) scale before fusing with RSF, RRF, or WRRF.

Independent verification method, stated plainly: a node script first reproduced Oracle's own published RSF Table 8-3 exactly using the formula from Section 09 -- all three outputs matched Oracle's own published numbers to 2 decimals, proving the RSF implementation faithful before trusting it on new numbers. That proven-correct formula was then applied to this concept's own 5-chunk example using (a) a lexical side -- a transparent, hand-checkable term/stem-matching counter (distinct terms matched × 10 + total occurrences × 5, normalized to 0-100 against the max), explicitly not a claim to reproduce Oracle's real Salton-based SCORE(), just a teachable, verifiable stand-in that feeds the real RSF formula -- and (b) a vector side -- real cosine-similarity math on small hand-authored 5-dimensional toy topic embeddings (topics: vendor / reset-credential / employee / security-policy / offboarding), converted to Oracle's VECTOR_DISTANCE(...,COSINE) convention (distance = 1 - similarity), then to a 0-100 "vector_score" via similarity × 100.

11
CONCRETE USE

Three fusion modes, three JSON shapes

TEXT_ONLY

Equivalent to legacy CONTAINS

search_fusion:"TEXT_ONLY" runs only the lexical side -- the same result a standalone CONTAINS/SCORE() query would give, but through the unified API.

VECTOR_ONLY

Pure semantic search

search_fusion:"VECTOR_ONLY" runs only the vector side -- equivalent in spirit to Concept 05's own VECTOR_DISTANCE query, through the unified API.

RERANK

One side re-orders the other's candidates

search_fusion:"RERANK" -- one signal supplies the candidate set, the other re-orders it, distinct from a straight UNION/INTERSECT merge.

REPETITION

Trade-offs, restated

  • Lexical-only misses paraphrases (2 of Acme's 6) but is cheap and exact-match-confident.
  • Vector-only never misses recall but can't privilege exact matches -- no way to boost a row just because it shares the query's exact wording.
  • Hybrid costs one extra scoring pass but is the only mode that both recovers all 6 and ranks exact+semantic double-hits highest.

DIAGNOSIS

Failure modes

UNNORMALIZED SUM

Vector distance and CONTAINS score added directly

Cause: treating VECTOR_DISTANCE and SCORE() as already comparable numbers. Fix: let Oracle's own RSF/RRF/WRRF fusion normalize the vector side to its 0-100 semantic score first -- don't hand-sum the raw values.

ASSUMED MODEL COMPATIBILITY

CREATE HYBRID VECTOR INDEX built assuming any embedding model plugs in

Cause: Oracle scopes the PARAMETERS clause to in-database ONNX models or REST-hosted providers, not directly Module 08's all-MiniLM-L6-v2 model unless imported as ONNX. Fix: confirm the embedding model backing the hybrid index is a supported ONNX/REST type before assuming direct compatibility.

FEEDBACK

Solution and teach-back

Open the worked solution
Using RS = score × weight and RSF = (sum of RS) ÷ (sum of 100 × weight) × 100 with text weight 3 and vector weight 1 (sum of weights × 100 = 400): chk_03 -- RS = 100×3 + 99×1 = 399, RSF = 399/400×100 = 99.75. chk_01 -- RS = 40×3 + 68×1 = 188, RSF = 47.00. chk_05 -- RS = 40×3 + 58×1 = 178, RSF = 44.50. chk_02 -- RS = 40×3 + 50×1 = 170, RSF = 42.50. chk_04 -- RS = 20×3 + 56×1 = 116, RSF = 29.00. Fused order: chk_03 > chk_01 > chk_05 > chk_02 > chk_04 -- checked against the same RSF formula used in Sections 09 and 10, and consistent with the pattern already shown there: heavier text weighting keeps the wrong-entity chk_02 closer to the middle of the pack than the 1:1 or 5:1 weightings did, but chk_03's lexical dominance still keeps it first.

Conceptual: how does Oracle fuse keyword and vector search internally, and why can't you just add the two scores?
Via DBMS_HYBRID_VECTOR.SEARCH's fusion step -- CONTAINS-style lexical scoring and cosine-based vector scoring run on different scales, so Oracle normalizes the vector side into a comparable 0-100 semantic score before merging both with a named formula (RSF, RRF, or WRRF). Adding the raw, unnormalized values directly would be meaningless.
Conceptual: name Oracle's three hybrid fusion scorers and what each optimizes for.
RSF (Weighted-Sum Fusion) blends normalized scores directly by weight; RRF (Reciprocal-Rank Fusion) blends by each side's rank position rather than raw score; WRRF (Weighted Reciprocal-Rank Fusion) adds explicit per-side weights on top of RRF's rank-based blending.
Coding: write the minimal real CREATE HYBRID VECTOR INDEX statement.
CREATE HYBRID VECTOR INDEX my_hybrid_idx ON doc_table(text_column) PARAMETERS('MODEL my_embed_model');
System design: why decide search_fusion and search_scorer explicitly before shipping a retrieval endpoint?
Because accepting Oracle's defaults silently means the fusion behavior your users experience was never a deliberate choice -- and the embedding model backing the index must also be confirmed as a supported ONNX/REST type before assuming an existing model (like Module 08's all-MiniLM-L6-v2) plugs in directly.
