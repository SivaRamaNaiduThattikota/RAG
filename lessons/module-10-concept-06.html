01 · CONCEPT FIRST

The cliffhanger, named again

Concept 05 built the VECTOR column and VECTOR_DISTANCE. But does having a fast column mean fast search? Not automatically. Concept 05 deliberately left open what happens to VECTOR_DISTANCE's default metric once a vector index exists on the column -- this concept is that answer.

First memory: exact search checks every row; a vector index lets Oracle skip most rows and estimate the closest ones instead -- but only when you ask it correctly.
02 · WHY IT EXISTS

Exact vs. approximate, in plain language

Exact search checks every row and computes a real distance for each one -- the same brute-force framing Module 09 Concept 01 already established. A vector index lets Oracle skip most rows and just estimate the closest ones, which is faster but not guaranteed to be 100% correct. Whether that estimate ever happens depends on one rule this concept exists to teach.

03 · CONCRETE EXAMPLE

Oracle's two real index types

Oracle names exactly two real index categories: In-Memory Neighbor Graph, for which HNSW is the only supported type, and Neighbor Partition, for which IVF is the only supported type. Both mechanisms -- how HNSW's graph and IVF's clusters actually work -- were already covered in Module 09 Concepts 03 and 04 and are not repeated here.

04 · TECHNICAL MECHANISM

The minimal real syntax

Per Oracle's own documentation as of this writing, the simplest form is CREATE VECTOR INDEX embeddings_hnsw_idx ON embeddings (embedding) ORGANIZATION INMEMORY NEIGHBOR GRAPH DISTANCE COSINE WITH TARGET ACCURACY 95; -- naming the column, the organization keyword, the distance metric, and a target accuracy percentage.

05 · ARCHITECTURE / FLOW

The one rule that matters

No index — every query is exact→ CREATE VECTOR INDEX ... DISTANCE COSINE→ Same metric in the query — approximate, index used→ Different metric in the query — exact fallback, index silently skipped

The index only gets used if your query's distance metric matches the metric the index was built with. Same metric = fast + approximate. Different metric = Oracle quietly falls back to exact -- no error.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Once a vector index exists, every query against that column becomes approximate."

False. Per Oracle's own documentation, if the query uses a different distance function than the one the index was built with, an exact match is triggered because the index cannot be used in that case.

"This is the same trap as Concept 05's <-> operator."

Different trap. Concept 05's trap was about which operator string maps to which metric. This concept's trap is about an index-metric mismatch silently reverting an approximate query to an exact one, with no error at all.

04
INTUITION

A shortcut that only works if you take the right exit

Building a vector index is like building a highway shortcut between two neighborhoods. If you get on it, you get there fast, but only approximately close to your real destination. If you take the wrong exit -- a different metric than the one the shortcut was built for -- there is no crash and no error sign. The road simply routes you back onto the slow surface streets, checking every intersection along the way, and you'd never know unless you noticed how long the trip took.

06
MECHANISM

An index changes execution, not meaning

A vector index in Oracle AI Vector Search is an optional, metric-bound structure that changes HOW a distance query executes, not what VECTOR_DISTANCE itself returns for any given pair of vectors. Per Oracle's own guidance on using vector indexes, the minimal required clauses are the column to index and an organization keyword; DISTANCE and TARGET ACCURACY have their own documented defaults but this course writes them explicitly, matching Concept 05's own explicit-COSINE convention.

10
WORKED EXAMPLE

The index only fires when the metric matches

Concept 05 asked plainly what happens to VECTOR_DISTANCE's default metric once a vector index exists on the column. This four-step progression answers it, using this course's own embeddings table (VECTOR(384, FLOAT32), Concepts 03 and 05), not Oracle's own literal "galaxies" example table.

SQL · STEP 1 -- NO INDEX, EXACT BASELINE 
SELECT c.chunk_id, c.text
FROM chunks c
JOIN documents d ON c.doc_id = d.doc_id
JOIN embeddings e ON e.chunk_id = c.chunk_id
ORDER BY VECTOR_DISTANCE(e.embedding, :query_embedding, COSINE)
FETCH FIRST 5 ROWS ONLY;

No index exists on embeddings.embedding yet, so every surviving row's distance is computed -- the same brute-force framing Module 09 Concept 01 already established.

SQL · STEP 2 -- CREATE THE VECTOR INDEX (per Oracle's own documentation as of this writing) 
CREATE VECTOR INDEX embeddings_hnsw_idx ON embeddings (embedding)
  ORGANIZATION INMEMORY NEIGHBOR GRAPH
  DISTANCE COSINE
  WITH TARGET ACCURACY 95;

-- The IVF equivalent, named for completeness only, not built out further:
CREATE VECTOR INDEX embeddings_ivf_idx ON embeddings (embedding)
  ORGANIZATION NEIGHBOR PARTITIONS
  DISTANCE COSINE
  WITH TARGET ACCURACY 95;

Oracle names exactly two real ANN index categories: In-Memory Neighbor Graph, for which HNSW is the only supported type, and Neighbor Partition, for which IVF is the only supported type -- cited to Module 09 Concepts 03 and 04 for the underlying mechanisms, not re-derived here. QUANTIZATION, OFFLOAD_CREDENTIAL_NAME, ONLINE rebuilds, and GLOBAL-vs-LOCAL partitioning also exist as real clauses/options, mentioned here for completeness only, never load-bearing in this concept.

SQL · STEP 3 -- SAME QUERY, SAME METRIC (COSINE = COSINE) 
SELECT c.chunk_id, c.text
FROM chunks c
JOIN documents d ON c.doc_id = d.doc_id
JOIN embeddings e ON e.chunk_id = c.chunk_id
ORDER BY VECTOR_DISTANCE(e.embedding, :query_embedding, COSINE)
FETCH FIRST 5 ROWS ONLY;

Identical query text to Step 1. The index now exists and its build metric (COSINE) matches the query's own metric (COSINE), so Oracle uses it: fewer rows touched, approximate search, recall below 100% and governed by TARGET ACCURACY 95 -- cited to Module 09 Concept 02's own SIFT1M numbers and Module 09 Concept 06's own consolidated trade-off table, not re-measured here.

SQL · STEP 4 -- SAME QUERY SHAPE, DIFFERENT METRIC (EUCLIDEAN AGAINST A COSINE-BUILT INDEX) 
SELECT c.chunk_id, c.text
FROM chunks c
JOIN documents d ON c.doc_id = d.doc_id
JOIN embeddings e ON e.chunk_id = c.chunk_id
ORDER BY VECTOR_DISTANCE(e.embedding, :query_embedding, EUCLIDEAN)
FETCH FIRST 5 ROWS ONLY;
Concept 05's own cliffhanger, resolvedPer Oracle's own documentation: "If you use a different distance function than the one used to create the index, an exact match is triggered because you cannot use the index in this case." The embeddings_hnsw_idx index built in Step 2 was built with DISTANCE COSINE. Step 4's query asks for EUCLIDEAN instead -- so Oracle silently falls back to an exact, full scan, with no error and no warning in the query result itself. This is a different trap from Concept 05's own <-> operator trap: that one was about which operator string maps to which metric. This one is about an index-metric MISMATCH silently reverting an approximate query to an exact one.
No indexIndex + same metricIndex + different metric
Rows touched: all rowsRows touched: a small subsetRows touched: all rows
Search type: exactSearch type: approximateSearch type: exact (silent fallback)
Recall: 100% by definitionRecall: <100%, governed by TARGET ACCURACY 95Recall: 100% by definition -- same as no index

The cliffhanger is resolved: creating a vector index changes the execution path Oracle takes, not what VECTOR_DISTANCE's default metric returns. The default stays COSINE regardless of index state -- what changes is whether the query's own metric happens to match the index the optimizer could otherwise use.

16
DIAGNOSIS

Failure modes

SILENT EXACT FALLBACK

Query is slower than expected, no error raised

Cause: the query's distance metric does not match the metric the vector index was built with. Fix: match the query's metric to the index's DISTANCE clause, or build a second index for the second metric.

UNEXPECTED RECALL DROP

Results look plausible but occasionally miss a true nearest neighbor

Cause: approximate search under TARGET ACCURACY < 100 is working as designed. Fix: raise TARGET ACCURACY if recall matters more than latency, per Module 09 Concept 06's own trade-off table.
