01 · CONCEPT FIRST

"Managed and specialist stores" names four separate real products, not one category

Concept 01 already drew the store/database/search-engine boundary in the abstract, naming Qdrant as one boundary case. This concept goes further: Pinecone, Qdrant, Weaviate, and Milvus are four separately built, separately maintained, separately versioned real systems, each with its own client library and its own real API surface. None of the four APIs below is a dialect of a shared standard the way Oracle's SQL and pgvector's SQL both are (Concept 11) -- there is no common vector-store SQL.

First memory: the operation is identical -- write one chunk, then find it again filtered to one tenant. The syntax, and even the tenant mechanism itself, is different in all four.
02 · WHY IT EXISTS

Most real RAG systems never touch SQL at all

Concepts 05-10 built one full real path through Oracle SQL. Concept 11 translated that path into pgvector, another SQL dialect. A large share of real production RAG systems skip SQL entirely and call a managed vector-store API instead. This concept names four of the most commonly used ones and shows, concretely, that "call the API" hides four genuinely different real API shapes underneath.

03 · CONCRETE EXAMPLE

The same chunk, written four different real ways

This course's own chunk: chunk_id="c007", tenant_id="acme" (Concept 04), a 384-dimension all-MiniLM-L6-v2 embedding (Concept 03). Per each vendor's own real, live-verified syntax: Pinecone's index.upsert(vectors=[{"id":"c007","values":embedding}], namespace="acme"); Qdrant's client.upsert(collection_name="rag_atlas_chunks", points=[PointStruct(id="c007", vector=embedding, payload={"tenant_id":"acme"})]); Weaviate's acme_chunks.data.insert({"chunk_id":"c007"}, vector=embedding); Milvus's client.insert(collection_name="rag_atlas_chunks", data=[{"id":"c007","vector":embedding,"tenant_id":"acme"}]). Four real calls, four different shapes, one identical chunk.

04 · TECHNICAL MECHANISM

Four different real answers to "how do you isolate one tenant?"

Concept 04 already cited two of these: Pinecone's own multitenancy guide recommends a namespace argument -- physical isolation, not a filter clause. Qdrant's own multitenancy documentation treats tenant_id as a mandatory, indexed payload field checked with a pre-filter. This concept verifies two more, live: Weaviate's own client source defines a native tenant object (multi_tenancy_config at collection creation, with_tenant("acme") at query time) -- a structural mechanism, not a filter or a namespace argument. Milvus's own quickstart documents a plain boolean filter-expression string, filter="tenant_id == 'acme'", evaluated inside one shared collection.

06 · IMPORTANT DISTINCTIONS

What each vendor's own real API actually calls "isolate by tenant"

VendorReal tenant-isolation mechanism
PineconeA namespace argument on both upsert and query -- physical isolation, cited in Concept 04, verified again here.
QdrantA mandatory, indexed payload field checked with a FieldCondition/MatchValue pre-filter -- cited in Concept 04, verified again here.
WeaviateA native tenant object -- multi_tenancy_config at creation, with_tenant(...) at query time -- verified live this session from the client's own source.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"A metadata filter is how every vendor does multi-tenancy."

Only two of the four (Qdrant, Milvus) use a filter for it. Pinecone uses a namespace argument, not a filter clause at all; Weaviate uses a dedicated tenant object, not a filter either.

"If I know one vendor's filter syntax, I can guess the others'."

Pinecone's own filter DSL is a nested operator dict ({"tenant_id":{"$eq":"acme"}}); Qdrant's is typed Python objects (FieldCondition/MatchValue); Milvus's is a plain boolean-expression string ("tenant_id == 'acme'"). None of the three share syntax with either of the others.

04
INTUITION

Four separate real products, not four flavors of one thing

Oracle's SQL and pgvector's SQL both descend from the same standard -- that's why Concept 11 found real overlap (the three shorthand operators). Pinecone, Qdrant, Weaviate, and Milvus descend from no shared standard at all. Each is a separately founded company or open-source project, with its own client library, its own object model (records, points, objects, entities), and its own real API surface. Calling all four "vector stores" is accurate at the category level Concept 01 already defined, and completely unhelpful at the code level -- which is the level this concept works at.

ORACLE / PGVECTOR (Concept 11)

Two dialects of the same root language, SQL. Real syntactic overlap exists and was found.

PINECONE / QDRANT / WEAVIATE / MILVUS (this concept)

Four separate client libraries, four separate object models. No shared root language to find overlap in.

Scope noteThis concept does not claim one of the four vendors is "better" at anything. It claims only that their real APIs, verified live this session, are not interchangeable -- a narrower, checkable claim.

MECHANISM

Four SDKs, four real object models, verified live this session

Per Pinecone's own Python SDK README, fetched live this session: a serverless index is created with pc.indexes.create(name=..., dimension=..., metric="cosine", spec=ServerlessSpec(...)), then written to with index.upsert(vectors=[...], namespace=...) and read with index.query(vector=..., top_k=..., namespace=...). MATHEMATICS

The one shared number: 384

This concept introduces no new math. The one number every one of the four real code blocks in Section 12 shares is Concept 03's own embedding width, 384 (all-MiniLM-L6-v2) -- passed as dimension=384 to Pinecone's and Milvus's own index/collection creation calls, as size=384 inside Qdrant's own VectorParams, and implicitly, as the length of the real embedding list, to Weaviate's own vector= argument, which carries no separate dimension parameter at collection-creation time in the self-provided-vector mode used here.

CONCRETE USE

Three real API differences, side by side

WRITE SHAPE

Dict-list vs. typed object vs. separate call vs. flat dict

Pinecone's vectors=[{"id":...,"values":...}]; Qdrant's points=[PointStruct(id=..., vector=..., payload=...)]; Weaviate's data.insert(properties, vector=...); Milvus's data=[{"id":...,"vector":...,"tenant_id":...}].

FILTER DSL

Nested dict vs. typed objects vs. fluent chain vs. boolean string

Pinecone's {"tenant_id":{"$eq":"acme"}}; Qdrant's FieldCondition(key=...,match=MatchValue(value=...)); Weaviate's Filter.by_property("tenant_id").equal("acme"); Milvus's "tenant_id == 'acme'" string.

TENANT MECHANISM

The axis where nothing agrees

Pinecone: a namespace argument. Qdrant: a payload pre-filter. Weaviate: a native tenant object. Milvus: a filter-expression string (with database-level and partition-key-level alternatives named, not coded, in its own docs).

pc = Pinecone(api_key="...")
pc.indexes.create(
    name="rag-atlas-chunks",
    dimension=384,
    metric="cosine",
    spec=ServerlessSpec(cloud="aws", region="us-east-1"),

index.upsert(

    namespace="acme",
)

results = index.query(
    vector=query_embedding,
    top_k=5,
    namespace="acme",
    include_metadata=True,

PYTHON · QDRANT (real client syntax, live-verified this session) 
from qdrant_client import QdrantClient, models

client = QdrantClient(url="http://localhost:6333")
client.create_collection(
    collection_name="rag_atlas_chunks",
    vectors_config=models.VectorParams(size=384, distance=models.Distance.COSINE),
)

client.upsert(
    collection_name="rag_atlas_chunks",
    points=[
        models.PointStruct(id="c007", vector=embedding, payload={"tenant_id": "acme"})
    ],
)

hits = client.query_points(
    collection_name="rag_atlas_chunks",
    query=query_embedding,
    query_filter=models.Filter(
        must=[models.FieldCondition(key="tenant_id", match=models.MatchValue(value="acme"))]
    ),
    limit=5,
)
PYTHON · WEAVIATE (real client syntax, live-verified this session) 
from weaviate.classes.config import Configure, Property, DataType
from weaviate.classes.query import MetadataQuery

client.collections.create(
    "RagAtlasChunk",
    vector_config=Configure.Vectors.self_provided(),
    properties=[Property(name="chunk_id", data_type=DataType.TEXT)],
    multi_tenancy_config=Configure.multi_tenancy(enabled=True),
)
chunks = client.collections.use("RagAtlasChunk")
acme_chunks = chunks.with_tenant("acme")

acme_chunks.data.insert({"chunk_id": "c007"}, vector=embedding)

response = acme_chunks.query.near_vector(
    near_vector=query_embedding,
    limit=5,
    return_metadata=MetadataQuery(distance=True),
)
PYTHON · MILVUS (real MilvusClient syntax, live-verified this session) 
from pymilvus import MilvusClient

client = MilvusClient(uri="./rag_atlas.db")
client.create_collection(collection_name="rag_atlas_chunks", dimension=384)

client.insert(
    collection_name="rag_atlas_chunks",
    data=[{"id": "c007", "vector": embedding, "tenant_id": "acme"}],
)

res = client.search(
    collection_name="rag_atlas_chunks",
    data=[query_embedding],
    filter="tenant_id == 'acme'",
    limit=5,

TRADE-OFFS

What each vendor's own model costs, what it buys

VendorCostWhat it buys
PineconeManaged-only, usage-based billing; namespace isolation means no cross-namespace query in one callNo infrastructure to run; namespace argument is a single, simple isolation primitive
QdrantSelf-hosted or managed; a payload pre-filter must be indexed and included in every query by the callerOpen-source, runs locally (":memory:" or on disk) or in the cloud; typed filter objects with IDE support
WeaviateSelf-hosted or managed; multi-tenancy must be enabled at collection-creation time, not added laterA first-class tenant object, not a caller-remembered filter; per-tenant load/release for hot/cold data
MilvusSelf-hosted, embedded (Lite), or managed (Zilliz); the simple boolean filter has no built-in tenant object at the API level shown hereOpen-source; billion-scale design; database-level and partition-key-level structural isolation available as named alternatives
16
DIAGNOSIS

Failure modes

ASSUMED FILTER PORTABILITY

A team copies Pinecone's $eq filter dict into a Qdrant call

Cause: assuming a metadata filter is a metadata filter everywhere. Fix: Qdrant needs typed FieldCondition/MatchValue objects, not a dict with a $eq key -- that key means nothing to Qdrant's own client.

FORGOTTEN TENANT SETUP

A write succeeds on Weaviate but the tenant filter at query time returns nothing

Cause: multi_tenancy_config=Configure.multi_tenancy(enabled=True) was never set at collection-creation time, or with_tenant("acme") was omitted at write time. Fix: multi-tenancy is a structural collection property in Weaviate, not a per-call filter that can be bolted on afterward.

CAREER PRACTICE

Interview questions

Conceptual: why doesn't Oracle-versus-pgvector's real syntactic overlap (Concept 11) extend to Pinecone, Qdrant, Weaviate, or Milvus?
Because Oracle and pgvector are both real SQL implementations descending from a shared relational standard, which is why their shorthand distance operators matched character-for-character. Pinecone, Qdrant, Weaviate, and Milvus are four separately designed client libraries with no shared standard underneath them -- there is no common root language for their APIs to overlap in.
Conceptual: which of the four vendors isolates tenants without using a filter predicate at all, and what does each use instead?
Pinecone (a namespace argument on upsert/query) and Weaviate (a native tenant object created at collection-creation time and selected with with_tenant(...) at query time). Qdrant and Milvus both use an actual filter predicate -- a payload FieldCondition/MatchValue in Qdrant, a boolean filter-expression string in Milvus.
Coding: write the minimal real Qdrant filter for tenant_id equal to "acme".
models.Filter(must=[models.FieldCondition(key="tenant_id", match=models.MatchValue(value="acme"))]) -- passed as the query_filter argument to client.query_points(...).
System design: your team is choosing between Weaviate's native tenant object and Milvus's boolean filter string for a new multi-tenant RAG system. What's the real trade-off, based only on what this concept established?
Weaviate's tenant object is structural -- it must be created explicitly per tenant before any write, and it's enforced by the collection itself, which forecloses the caller ever forgetting the predicate. Milvus's filter string is enforced entirely by the caller remembering to pass it on every query -- more flexible (no setup step per tenant) but with no structural guarantee against a caller who omits the filter, the same forgotten-predicate risk Concept 04 already named for a plain SQL WHERE clause. This concept does not establish which trade-off is better for any specific workload -- only that they are different real risks.
