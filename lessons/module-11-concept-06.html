Choosing which candidates the prompt actually sees.

PROGRESSIVE BEGINNER CORE

The list is ranked. Now someone has to decide where it ends.

Concept 05 returns candidates sorted by score. Nothing about that ranking says how many of them belong in the prompt, or whether two near-identical chunks should both make the cut. This concept is that decision.

01 · CONCEPT FIRST

A sorted list of applicants, versus the ones you actually hire

Ranking candidates by score is like sorting a stack of resumes by fit -- useful, but it doesn't tell you how many to hire, or what to do when two resumes are basically the same person applying twice. Top-k evidence selection is that second, separate decision: given a ranked candidate list, which ones actually become the evidence the model gets to read.

First memory: ranking answers "in what order," selection answers "how many, and which ones survive the cut."
02 · WHY IT EXISTS

Concept 05's list is deliberately too long

Module 09 Concept 07 already established that a tenant-filtered ANN search has to over-fetch -- at 30% tenant selectivity, getting a true k=5 back requires searching roughly top-17. Concept 05 returns that over-fetched pool. Without this concept, all 17 (or however many pass the tenant filter) would go straight into the prompt -- wasting budget and diluting the model's attention with candidates nobody actually wanted included.

03 · CONCRETE EXAMPLE

Nine candidates, one grace-period chunk, one duplicate

Take nine tenant-filtered candidates for the query "what's the return window after the grace period," including chunk c007's child (cosine 0.8944, the exact sentence -- Module 07 Concept 06) and its parent (cosine 0.6761, the restored context -- Module 07 Concept 07), plus a near-duplicate pair, cC and cD, both describing order-status definitions almost verbatim. A 0.75 score cutoff and k=5 selection, verified below, keeps c007's child, drops cD as redundant, and backfills the next real candidate in its place.

04 · TECHNICAL MECHANISM

Three filters, applied in order

Score cutoff -- discard anything below a minimum similarity, regardless of rank. k selection -- from what remains, take the top k by score. Redundancy check -- if two survivors are near-duplicates, keep the higher-scored one and backfill the next candidate below the raw top-k line, so the final set still has k distinct pieces of evidence.

06 · IMPORTANT DISTINCTIONS

"Top-k retrieval" and "top-k evidence selection" are not the same k

Module 09 Concept 07's "top-17" was a search-time over-fetch count, chosen to survive a tenant filter -- it is not the number of chunks that end up in the prompt. This concept's k is the second, smaller, deliberate number: how many of the already-filtered candidates actually become evidence. Conflating the two hides the fact that the search-time k is inflated on purpose.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Whatever the ANN search returns is what goes in the prompt."

False -- the search result is the over-fetched candidate pool (Module 09 Concept 07); evidence selection is the separate step that trims it down.

"Higher k in retrieval means more evidence in the prompt."

Not necessarily -- retrieval's k accounts for filter loss; evidence selection's k is a fresh, usually smaller, decision made after the filter has already run.

02
PRECISION

Ranked, filtered, and selected -- three separate claims

TermDefinition
RankedOrdered by similarity score -- says nothing about how many are usable
FilteredRestricted to candidates that pass a hard constraint (e.g. tenant_id) -- says nothing about score quality
SelectedThe final, bounded evidence set that reaches the prompt -- the output of this concept
03
DEPENDENCIES

The over-fetch this concept inherits, cited

Module 09 Concept 07 established that post-filtering an ANN search at 30% tenant selectivity requires fetching roughly top-17 candidates to actually return a true k=5 after the tenant filter removes 70% of what came back -- a 3.4x over-fetch, worse (3.8x) in the stated worst case. That candidate list -- already over-fetched, already tenant-filtered -- is exactly what Concept 05 hands to this concept. This concept's own k is a second, independent, usually smaller number.

05
MECHANISM

The three filters, named precisely

Score cutoff removes candidates below a minimum similarity regardless of rank. k selection takes the top k of whatever remains. Redundancy dedup checks the survivors for near-duplicates and, if found, drops the lower-scored copy and backfills the next candidate below the raw top-k line -- keeping the final evidence set at exactly k distinct pieces.

06
MECHANISM

Why a score cutoff exists at all

A ranked list has no natural stopping point of its own -- rank 6 and rank 60 both "exist" in the sorted order. A score cutoff enforces a quality floor independent of rank, so that if only 2 candidates are actually relevant, only 2 get selected, even if k asks for 5.

07
MECHANISM

Why k selection is still needed on top of a cutoff

A cutoff alone can leave far more candidates than a prompt should carry -- a permissive threshold on a large corpus could pass dozens. k selection is the second, independent bound: never send more than k pieces of evidence, no matter how many clear the cutoff.

08
IMPORTANT DISTINCTIONS

Redundancy dedup and backfill

Two near-duplicate chunks (e.g. two passages both stating the same order-status definitions) both scoring highly is not the same as two independent pieces of evidence -- it's one fact taking up two evidence slots. Dropping the lower-scored duplicate and backfilling the next real candidate below the raw top-k line keeps the evidence set both non-redundant and at full size.

10
CODE

The selection function, verified via node

JAVASCRIPT · SELECTION LOGIC (also the lab's own code) 
const sorted = candidates.slice().sort((a, b) => b.score - a.score);
const passCutoff = sorted.filter(c => c.score >= cutoff);
const topk = passCutoff.slice(0, k);
const evidence = topk.filter(c => !c.dupOf);
const pool = passCutoff.filter(c => !evidence.includes(c) && !c.dupOf);
while (evidence.length < k && pool.length) evidence.push(pool.shift());
11
MECHANISM

Why the order is cutoff, then k, then dedup

Applying the cutoff first means k never has to "waste" a slot on a candidate that shouldn't be evidence at all. Applying dedup last, after k, means the redundancy check only has to look at the small set that actually made the cut -- not the whole candidate pool -- which is exactly what the code in Section 10 does.

22
CAREER PRACTICE

Interview questions

Conceptual: why isn't a fixed score cutoff enough on its own, without also bounding by k?
A permissive cutoff on a large or noisy corpus can pass far more candidates than a prompt should reasonably carry -- k enforces a hard ceiling independent of how many clear the quality bar.
System design: your evidence set keeps returning near-duplicate chunks from the same source document. What's the fix?
Add an explicit redundancy check (e.g. a similarity threshold between selected candidates, or dedup by source paragraph) before finalizing the evidence set, with a backfill step so the set doesn't shrink below the target k.
