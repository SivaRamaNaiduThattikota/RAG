MODULE 11 · CONCEPT 07

An evidence set isn't a prompt yet.
Assembling the string the model actually reads.

Concept 06 hands off a final evidence set: five chunks, chosen, deduped, and budget-checked. Nothing about that set is text the model can read yet -- it's still a list of separate objects. This concept is the step that turns it into one string: system instructions, the evidence chunks in some order with clear boundaries between them, and the user's query, all concatenated and checked against what's left of the context window after the model's own answer needs room to be generated.

PROGRESSIVE BEGINNER CORE

The evidence is picked. Now someone has to write the letter.

Concept 06 returns a short list of chunks that survived a cutoff, a k, and a dedup check. None of that list is readable by the model on its own -- it's five separate pieces of text sitting in five separate variables. This concept is the step that glues them, in some order, with instructions and the user's question, into the single string that actually gets sent.

01 · CONCEPT FIRST

A stack of source printouts, versus the letter you actually mail

Choosing which five printouts to cite is Concept 06's job. Turning them into one coherent letter -- with an opening line, the citations in some order, and the question you're actually answering -- is a separate act of writing. Context injection and prompt construction are that second act: given a fixed evidence set, produce the one string the model reads.

First memory: selection answers "which five," assembly answers "in what shape, with what glue, and does the result even fit."
02 · WHY IT EXISTS

Five chunks are five variables, not one input

Module 11 Concept 06 leaves you holding a JavaScript array of chunk objects. An LLM API call takes a string (or a small number of message strings) -- not an array. Without this concept, there is no defined way to turn "here are five relevant chunks" into "here is the text the model will condition its answer on." Someone has to decide the order, the separators, and where the instructions and the question go.

03 · CONCRETE EXAMPLE

The same five chunks, now one 954-token string

Take Concept 06's exact evidence set -- cA, c007's child, cB, cC, cE, 880 tokens total -- and wrap it: a 35-token system instruction, five chunks each preceded by a [SOURCE n] boundary tag, and a 9-token query. Node-verified below: the assembled string costs 954 tokens against a 3,584-token prompt budget, leaving 2,630 tokens of headroom.

04 · TECHNICAL MECHANISM

Three parts, glued in a fixed shape

System instructions -- fixed text telling the model how to use what follows (e.g. "answer only from the evidence below"). Ordered, boundary-marked evidence -- the selected chunks, concatenated with a visible separator between each so the model can tell where one source ends and the next begins. The query -- the user's actual question, placed last so it reads as "given all that, answer this."

06 · IMPORTANT DISTINCTIONS

"In the prompt" and "in the corpus" are different claims

A fact can be true and sitting in the corpus somewhere and still never make it into the assembled string -- if it wasn't selected, or if it got truncated to fit the budget. Module 03 Concept 04 already drew this line for grounding and provenance: what the model can cite is only what is actually in the prompt it read, not everything that exists in the index. This concept is exactly where that boundary gets drawn in code.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"If the evidence set fits Concept 06's token budget, the final prompt fits too."

Not automatically -- the system instructions, boundary tags, and query all add tokens on top of the evidence total; those have to be counted too, against the model's real context window minus a generation reserve.

"Order doesn't matter -- the model reads the whole prompt anyway."

Position still matters for how much attention a given chunk gets; Module 02 Concepts 07/10 already documented that models don't weight all positions in a long prompt equally (the "lost in the middle" effect).

01
ORIENTATION

Turning a fixed evidence set into a prompt string

This is the seventh concept of Module 11 (7/11). Concept 06, "Top-k evidence selection," produces a final evidence set -- score-cutoff-filtered, k-bounded, deduped, and already under its own token budget. This concept is the very next step, and only that step: writing the system instructions, ordering and boundary-marking the evidence, appending the query, and checking the resulting string against the model's real prompt budget. It does not re-derive candidate ranking, filtering, or evidence selection -- all three are cited as already-settled background. In Module 11 Concept 01's six-stage naming (ingest → chunk → embed → store → retrieve → generate), this concept is the seam between stage 5 (retrieve, which Concept 06 finished) and stage 6 (generate, which Concept 08 begins).

03
DEPENDENCIES

The evidence set this concept inherits, cited

Module 11 Concept 06's node-verified worked example produced a final evidence set of five chunks -- cA (150 tokens), c007's child (180 tokens), cB (200 tokens), cC (190 tokens), and cE (160 tokens) -- totalling 880 tokens, ordered by descending similarity score. This concept takes that exact list, in that exact order, as its starting input; it does not re-run the cutoff, k, or dedup logic.

04
DEPENDENCIES

The context-window facts this concept inherits, cited

Module 02 Concept 07 established that models do not attend to every position in a long prompt equally -- evidence buried in the middle of a long context is recalled less reliably than evidence near the start or end (the "lost in the middle" effect). Module 02 Concept 10 and Module 03 Concept 07 established that context windows have a hard token ceiling, and that filling them is not free -- attention cost scales worse than linearly with length. Both facts are reused here as the reason ordering and budget-checking matter, not re-derived.

05
MECHANISM

The three parts, named precisely

System instructions are fixed text, written once per application, telling the model its role and constraints (e.g. answer only from evidence, cite sources). Ordered, boundary-marked evidence is Concept 06's chunk list, concatenated in a chosen order with an explicit tag before each chunk so the model can tell where one source ends and the next begins. The query is the user's live question, appended last so the assembled string reads as instructions, then evidence, then "now answer this."

06
MECHANISM

Why system instructions are fixed, not per-query

The instruction text ("answer only using the evidence below; say you don't know if it isn't there; cite the source id for any claim") is the same for every request this application makes -- it is not derived from the retrieved chunks or the user's question. Fixing it once means every call gets the same grounding contract, and its token cost (35 tokens in the worked example below) is a known constant, not a variable to recompute per request.

07
MECHANISM

Why boundary tags exist at all

Concatenating five chunks with nothing between them leaves the model no way to tell where cA ends and c007's child begins -- and no way to cite "source 2" instead of "somewhere in that wall of text." A boundary tag like [SOURCE n] before each chunk costs a small, fixed number of extra tokens (6 in the worked example below) and buys back exactly that: a citable, separable structure.

08
IMPORTANT DISTINCTIONS

Ordering is a real decision, not a formality

Concept 06's list already arrives sorted by descending score -- keeping that order puts the single highest-scoring chunk first, not buried. Reordering it so a high-value chunk lands in the middle of a five-chunk block reintroduces exactly the lost-in-the-middle risk Module 02 Concept 07 documented, even though the evidence set itself hasn't changed at all. The lab in Section 16 makes this concrete by moving c007's child between the front and the middle of the same five chunks.

09
WORKED EXAMPLE

The same five chunks, now being assembled

Continuing Concept 06's worked example: the query is "What is the return window after the grace period?" and the evidence set is the same five chunks, 880 tokens. This concept adds fixed system instructions and the query text on top, and wraps each chunk in a boundary tag. Every token count below comes from a node script counted by word-count proxy on the actual instruction and query strings -- flagged clearly as an approximation, not a real tokenizer run.

Flag: the 880-token evidence total and the two grace-period cosine scores are the only previously-verified external facts here. The system-instruction and query token counts are computed in this lesson's own node script (word-count proxy, not a real BPE tokenizer) and are flagged as an approximation; the 6-token boundary-tag cost, the 4,096-token context window, and the 512-token generation reserve are illustrative constants chosen for this worked example.
10
CODE

The assembly function, verified via node

JAVASCRIPT · PROMPT ASSEMBLY (also the lab's own code) 
function assemble(system, evidence, query) {
  const blocks = evidence.map((c, i) => `[SOURCE ${i + 1}: ${c.id}]\n${c.text}`);
  const prompt = [system, ...blocks, `Question: ${query}`].join("\n\n");
  return prompt;
}
// token accounting mirrors the string above, chunk by chunk:

11
MECHANISM

Why instructions come first and the query comes last

Placing system instructions first means the model reads its constraints before it reads any evidence, rather than retroactively reinterpreting evidence it already read. Placing the query last means the final thing the model reads before generating is the exact question it needs to answer -- both are ordering conventions carried over unchanged from ordinary prompt-engineering practice, not something specific to RAG.

13
EVIDENCE + CONTROL

Grounding vs. corpus, restated at the assembly seam

Module 03 Concept 04 established that a model's answer is grounded only in what it actually read, not in everything true that exists somewhere in the corpus. This concept is where that line becomes literal: if c007's parent form (the 420-token, 0.6761-scoring version with fuller context) never made it into Concept 06's evidence set, it is not in this assembled string either -- no matter how true or well-indexed it is. "In the corpus" and "in the prompt" are different sets, and this is the exact step that fixes which chunks cross from one to the other.

14
MATHEMATICS

The prompt-budget check, node-confirmed

prompt_budget = context_window − generation_reserve = 4096 − 512 = 3584 tokens
headroom = prompt_budget − assembled_total = 3584 − 954 = 2630 tokens

Against an illustrative 4,096-token context window with a 512-token reserve set aside for the model's own generated answer, the 954-token assembled prompt leaves 2,630 tokens of headroom -- confirmed by the same node script cited in Section 12.

Important distinction: Concept 06's 880-token figure was checked against its own 1,200-token evidence budget and passed. That check says nothing about the assembled string's 954-token total against the model's real 3,584-token prompt budget -- they are two different sums against two different ceilings. A pipeline that only checks the evidence budget and skips this one can still overflow the model's actual context window once instructions, boundaries, and the query are added.

17
MECHANICS

The lab's own data model

The lab holds the same five chunks as Section 12 (fixed token counts, fixed 35-token system instructions, fixed 9-token query, fixed 6-token boundary overhead per chunk) plus a fixed 4,096-token context window. The only two things a user changes are the generation reserve and which of two fixed orderings is applied to the five chunks -- every render call re-runs the Section 10 assembly and Section 12 accounting against those two inputs, nothing is precomputed.

18
MECHANICS

The lab's own JS logic

On every control change, one render function computes prompt_budget = 4096 − reserve, applies the selected ordering to the five chunks, and, if the assembled 954-token total exceeds that budget, truncates chunks from the end of the current order (lowest-priority position first) until the total fits or no chunks remain. It then repaints the boundary-strip (each surviving chunk a .boundary-chunk, alternating .shade-a/.shade-b, with c007's child marked distinctly and flagged if it lands in the middle position), a budget-bar segment sized to the surviving total over the prompt budget, and a callout naming whichever state applies: comfortable headroom, truncation in progress, or the buried-middle risk.

22
CAREER PRACTICE

Interview questions

Conceptual: why check the assembled prompt's token count separately from the evidence set's token count?
System instructions, boundary tags between chunks, and the user's query all add tokens on top of the evidence total -- a pipeline that only checks the evidence budget can still overflow the model's real context window once those are added.
System design: your evidence set is unchanged between two requests, but the model's answer quality drops. What assembly-side change could explain that without touching retrieval at all?
A change in chunk ordering (or a shrinking generation reserve forcing truncation) can move a critical chunk into a lower-recall position, or drop it entirely, even though the exact same chunks were selected as evidence.
